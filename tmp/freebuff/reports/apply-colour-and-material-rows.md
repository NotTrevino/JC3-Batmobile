## 2. The paint rows, with their replacement values

### T-MA3 — base colour: gain withdrawn (the white-violet car)

| step | value | class |
|---|---|---|
| authored base (`Batmobile_V3_WheelArchs_NEW_MIC` #767) | `[0.025787, 0.025787, 0.03, 1]` linear | decoded (`COLOUR_PARAMS.md` §2) |
| BmAK's own adjustment `Diffuse_Adjust` | `[2.2, 2.0, 2.0, 1]` | decoded (§2) |
| product = the shipped look | `[0.0566, 0.0516, 0.06]` linear = sRGB 0.265/0.254/0.272 | derived |
| what the build wrote | `[0.4784, 0.4588, 0.4941]` sRGB = `0.1946/0.1779/0.2086` linear (bytes `0x7a/0x75/0x7e`) | decoded from `factors.json` |
| error | **3.44×** BmAK, in linear light | derived |
| **replacement** | **`0x43/0x41/0x45`** = 0.0566/0.0516/0.0600 linear | derived |

The cause is named, not guessed: GRB-6's gain 3.4476 was derived by matching a **vanilla tint luma**
(0.1837) to a **flat albedo luma** (0.0533) — two different quantities — and it was then applied on
top of a colour that already carried BmAK's `Diffuse_Adjust`. Gain 1.0 reproduces the authored
effective colour exactly. The row's old third number (byte `0x83/0x7d/0x86`) matched neither the
pre-gain nor the delivered value and is gone.

### T-MA4 — gloss: 0.45 → 0.600, and the "cap" is retracted

| quantity | value | class |
|---|---|---|
| authored gloss | **0.600** (`VALUES.json` `paint.authored_gloss`) | decoded |
| "vanilla caps paint gloss at 0.4" | **false**: the donor palette ships **8 of 10 tints at 0.45** (`Working/Palette/serpente_palette.xml`) | decoded (measured) |
| delivered | 0.450 in 16 paint blocks + 10 palette tints = 0.75 × authored | decoded |
| **replacement** | **0.600** in the blocks *and* the palette, declared **R3** (33 % above the highest value the fleet is seen to use) | derived |

`m_SpecularGloss` is `cb2[0]`, a float4 — one gloss per material channel — so the value is written
per channel, not once. The satin reading that justifies 0.6 is in `colour-bmak-wet-look.md` §3:
roughness 0.4 against reflectivity 0.2 per channel, `Material3_Roughness` 0.02 behind it (clear
lacquer), `clear_coat` 1.0, `EdgeMask_Roughness` 0.03 on the wear.

### T-MA2 — the body albedo does not exist in the grab

`NEW_Batmobile_V2_BODY_D` 4096×2048 is **not** in
`Working/Appearance/grab/Playable_Batmobile_SF/Texture2D/` (that directory holds `Body_Decals_D`,
`Body_N` and the chapter mask). The delivered `s0` is therefore one constant shared by 16 blocks, and
"identity (DDS, sRGB)" described a file that was never grabbed. The row now says so, proposes the
T-MA3 colour as the interim value, and names the real build action: a body-albedo grab, 1024² first
(2048² BC1 = 2 MB against 694 KB of headroom).

### T-MA5 — glass: the unported pair is derivable

BmAK `Glass_Opacity` 1.2, `Glass_Reflectivity` **0.8**, `Glass_Roughness` **1.1**,
`glass_smudges` 0.2 (decoded, `MATERIALS.md:1062`); measured mask means `Glass_S` R **0.565**,
G **0.074**.

```
SpecFresnel = 0.565 × 0.8  = 0.452   -> Window cb1 @4
SpecGloss   = 1 − 0.074 × 1.1 = 0.919 -> Window cb1 @0
```

Row value: `SpecGloss` **0.92**, `SpecFresnel` **0.45**. The row also records the binding defect the
build hides: the canopy normal is written to block table position 1 while `window.fb.txt` samples
`NormalMap` at **`s2`** (`app-per-pixel-reflectivity.md` §7 T5a) — same finding, two reports.
Per-pixel via `s3` stays UNKNOWN (test T5b).

### T-MA6 — three counts, not 28

24 distinct TGAs bound → 21 Batmobile `.ddsc` shipped → 9 slots a solid colour → 32 `s2`/`s3` slots on
`a00_dummy_black_mpm`. "28 shipped" counts the whole `.ee` texture set (21 + 7 others). The missing
asset is the master's `WheelArch_MicroMasks` default, which is why every separation mask is neutral.

### T-MA7 — the palette contradicts the blocks

Measured: 10 tints, `specular_gloss` **0.45 × 8 / 0.0 × 2**, `metallic` 1 × 8 / 0 × 2,
`clear_coat` 1 × 10. Keeping the donor menu is fine as a system, but as delivered one click replaces
the lore colour. Row value: keep the 10-tint menu, set every tint's colour to
`0x43/0x41/0x45` and every `specular_gloss` to `0.600`.

### T-MA1 — block totals corrected (carrier unchanged)

Re-decoded from `Working/Appearance/build/*.rbm`: body LOD1-5 = 17 blocks each (16 `CarPaintMM` +
1 `Window`), wheel LOD1-5 = 5 each × 4 wheels → **185 `CarPaintMM` + 25 `Window` = 210**, not
200 + 35 over "35 meshes" (the tree has 25 meshes). The mechanism (one slot → one block) is exact; only
the totals were 25 high.

## 5. Limits and what is still open

1. **Ramp rows are open.** `app-colour-ramp-textures.md` and `ramp-names-quick-search.md` do not
   exist; the 3 D10 components keep their drop and their reason. Nothing was invented to fill them.
2. **`F0_d = 0.04` is an assumption, not a decoded constant.** Every D2 error in §3 scales linearly
   with it. The report says so; so does the rule note.
3. **D3's channel order is UNKNOWN.** The banding plan declares one order and makes it a one-variable
   test (T3); the plan does not bake on the strength of H1 or H2.
4. **D4's bake is not implemented.** `appearance_pipeline.py` converts textures as they are; the
   lobe fold is POL-2-style work that does not exist yet, so those 14 rows stay `excluded` in
   `progress.json` until it runs — the plan records the carrier, not a delivered value.
5. **Historical audits that pin the ledger's sha256 will now report drift** — `t_row_evidence2.py`,
   `t_row_evidence3.py`, `t_au_retest.py`, `t_vnf_six.py` compare `T_ROWS.jsonl` against a sha they
   recorded earlier. They were already stale from the T-WP/T-S row work; this pass moves the sha
   again. They are audit snapshots, not gates, and were left untouched: repairing them means
   re-recording the pinned hash, which would erase the evidence that the ledger changed.
6. **No build, no install, no game process.** Every value above is a file read or arithmetic on file
   reads; `factors.json` and the RBMs were not rewritten.
