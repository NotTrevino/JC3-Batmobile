## 4. Oracles actually used

1. Constraint cinfos: pointer **bijection** onto the constraint objects + measured 24-byte
   spacing + 0x7FFFFFFF constant over 40 files.
2. Constraint atoms: an orthonormal 3x4 test (unit rows, orthogonal, det = +1) rather than a
   fixed offset; pivots are the translation 16 bytes later; limits read at measured offsets.
3. Mass float: same offset in every object and every file, strictly positive in 40/40 files,
   discrete authored values.
4. Body entries: 24-word domain census over 2936 entries — a field is called a pointer only
   when the packfile's own fixup table says so.
5. Ids and compounds: cross-checked against the grab's parts table and the reverse pointer map.

## 5. UNKNOWNs and why

1. **The constraints' axes.** Both atom transforms are decoded, but nothing in the object names
   which rotation column is the free axis, and the atoms store the same pivot, so an axis
   cannot be read off or proved. Next source: `hkpLimitedHingeConstraintData` atom layout from
   the Havok 2014 headers, or a round-trip test against a constraint whose limit angles are
   known from the entity file.
2. **Each constraint's partner body.** Each cinfo carries exactly one body id and the field at
   +0x0C is 0x7FFFFFFF in 100% of the fleet; no second id is stored there. The chassis
   (body 0) hypothesis is *not* proven and is not written as fact.
3. **The 24 packed bytes at mass-properties +0x10..+0x27** (centre of mass / inertia): values
   carry sub-1e-6 residue with a trailing exponent-like byte; no project decoder reads packed
   floats. Next test: 3-byte mantissa + exponent decode required to land inside the owning
   hull's bbox.
4. **mass ↔ hull** (the card's "mass properties consistent with hull volumes" oracle): the
   mass block belongs to a `hkRefCountedProperties` node, and neither the node nor the
   instance entry carrying it stores the shape, so 0 of 56 blocks resolve to a hull. Reported
   as not-run, not as passed.
5. **Most 96-byte body-entry words.** Their domains are measured (section C5) but no name is
   decoded; in particular the 4 words G2-30 left open are narrowed, not closed.
6. **The mass unit (kg).** The field is positive and authored; "kg" remains a hypothesis since
   the totals include non-vehicle files (max 221,619) and no per-vehicle mass budget is
   documented in the project.
7. **Fleet depth is 40 raw files, not 232.** The 232 `hkx/out` files hold summaries only; the
   remaining ~191 raw `.physicsc` files are not on disk. Stated, not worked around.
