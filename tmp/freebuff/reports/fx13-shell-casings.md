**Bone:** there is no bone name. The attachment is parented to the weapon entity, whose own `world` matrix is the mount; that is why the effect carries no `world` of its own - it inherits the weapon's frame. This is the mechanism the Batmobile chain gun needs: put `ShellEjection` under the chain-gun weapon entity's `SEffects` and it follows the gun, including turret/elevation motion.

**Trigger:** `Usage` is literally the string `Fire`. The same usage the muzzle flash's own attachment family uses; the casing object therefore fires on the weapon's fire event, not on a timer.

## 9. UNKNOWNs

1. **The cone's local axis.** The `.effc` stores the two angles as unnamed floats and the attachment has no `world` rotation, so which axis the casings open around is not in the files read. Would be settled by Q-3 (fire one burst, watch the ejection side) or by decoding the emitter's rotation modifier type (`Modifiers[1]/[3].TypeHash` 3793416313, not resolved to a name here).
2. **The per-shot particle count.** No count member; `MaxParticles` is a live cap, not a burst size. Rate and count are code-side. Would be found in the native effect runtime, not in the `.effc`.
3. **The infantry/turret/DLC `SAttachedEffect` members.** Only the container->`.effc` link is decoded for them (their `.ee` bytes are not in the grab). The attachment object is proven for the two mounted guns read from the install; for the rest, the same class/usage pattern is an inference from those two, not a decode.
4. **The 4 `ShellEjection` objects the B-08 audit found in `bm-008`.** The v0300 donor graph has none (this sweep's 14-container list), so their provenance is UNKNOWN - they cannot have come from the donor's own graph. The build must place the attachment deliberately (gap 2), not rely on inheritance.
5. **The shipped casing `.effc`'s runtime look.** Test ban: no game was launched, so the sizes/angles/gravity are decoded values, not an observed ejection.
