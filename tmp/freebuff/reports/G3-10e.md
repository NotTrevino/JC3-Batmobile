# G3-10e — the real joint limits of the 11 Serpente constraints, tied to atoms

**STATUS: done.**

G3-10b's "limits" column was a value-band filter, not a decode. This pass walks each
`hkpConstraintData` object as a list of `hkpConstraintAtom`s (a 16-bit type code at every atom start),
finds the atoms that hold angular limits, and reads their min/max at named byte offsets. Every value
below is either **decoded** (byte offset + an oracle that fails if the reading is wrong) or **UNKNOWN**
with the blocker named. The fleet proof is 419 `hkpLimitedHingeConstraintData` and 71
`hkpRagdollConstraintData` objects over 51 `.physicsc` files under `E:/Modding/_gamedata/JC3grab`.

Headline: the hinge's limits are at **+0x0FC (min)** and **+0x100 (max)** in radians, inside atom
type **14** at **+0x0F8**; the ragdoll's three limit atoms are types **15** at **+0x130** and
**16** at **+0x150** and **+0x170**, each with the pair at atom+8 / atom+12. All of G3-10b's 66
"limits" that were not transform bytes were replaced by these.

## What was decoded

### 1. The atom list

A `hkpConstraintAtom` starts with a 16-bit type code. At each offset below that code is **identical in
every object of the class** (419/419 hinges, 71/71 ragdolls) while the payload after it varies per car.
That constancy is the oracle: payload bytes are not constant across 419 different cars.

| class | atom start | type code | extent |
|---|---:|---:|---:|
| hinge | +0x020 | 2 | 144 B |
| hinge | +0x0B0 | 23 | 16 B |
| hinge | +0x0C0 | 18 | 40 B |
| hinge | +0x0E8 | 17 | 16 B |
| **hinge** | **+0x0F8** | **14** | **16 B — the angular limit atom** |
| hinge | +0x108 | 12 | 16 B |
| hinge | +0x118 | 5 | to the object end |
| ragdoll | +0x020 | 2 | 144 B |
| ragdoll | +0x0B0 | 23 | 16 B |
| ragdoll | +0x0C0 | 19 | 96 B |
| ragdoll | +0x120 | 17 | 16 B |
| **ragdoll** | **+0x130** | **15** | **32 B — limit atom 1** |
| **ragdoll** | **+0x150** | **16** | **32 B — limit atom 2** |
| **ragdoll** | **+0x170** | **16** | **32 B — limit atom 3** |
| ragdoll | +0x190 | 5 | to the object end |

Extents are uniform: every hinge is 304 B, every ragdoll 416 B, so `extent = next atom start − this
start` is well defined and the last atom runs to the end.

Atom 0 (type 2) holds the frames: three 16-B rows `(x, y, z, 0)` then the translation. Hinges have A
at +0x30 and B at +0x70; ragdolls add C at +0x0D0, which sits **inside atom 2** (type 19), not in
atom 0. Oracle: rows orthonormal and det +1 in **419/419** hinges (A and B) and **71/71** ragdolls
(A, B, C). The 4th float of each row is 0 in 410/419 hinges and 71/71 ragdolls (C); the **9** hinges
where it is not hold a scalar between −0.92 and 0.94 in row 1 (e.g. `atv.physicsc 0x94B20 w=-0.918929`,
`modernmoped.physicsc 0x32510 w=0.866025`). The rotation still decodes there, so it is a separate
field in that slot, not a damaged row — its meaning is UNKNOWN.

### 2. The hinge's angular limit — type 14 at +0x0F8

| field | offset | donor (left door, 0x4DA80) |
|---|---:|---|
| atom type | +0x0F8 | 14 |
| atom flags | +0x0FA | 1 |
| **min angle** | **+0x0FC** | **0 deg** (0.0 rad) |
| **max angle** | **+0x100** | **80 deg** (1.396263 rad) |
| constant, not a limit | +0x104 | 1.0 in 419/419 |

Oracles over the fleet:

| property | result |
|---|---|
| min <= max | **419/419** |
| both on a 0.5-deg grid | 405/419 |
| both within ±π | **419/419** |
| min = 0 (a joint closed at zero) | 227 |
| distinct (min, max) pairs | **64** |
| +0x104 | 1.0 in 419/419 |

The pairs that ship include `(-180, 180)`, `(-179, 179)`, `(-90, 0)`, `(-75.621, 0)`, `(-75, 75)`,
`(-50, 50)`, `(-45, 0)`, `(-35, 0)`, `(0, 30)`, `(0, 80)`, `(0, 90)`. The 14 values off the 0.5° grid
are things like −75.621°, i.e. authored angles converted back and forth — the same reason the grid
oracle is set at ≥95 %, not 100 %.

`-75.621` is also the check that matters: it is not a transform byte and not a pivot component, and it
only makes sense as an angle. A pivot or rotation byte would not (a) be identical in role across 419
objects, (b) be ordered min ≤ max in every one, and (c) sit on a fine degree grid with ±180 extremes.

### 3. The ragdoll's three limit atoms

Each has the same shape: type code at the atom start, **min at atom+8**, **max at atom+12**, a constant
0.8 at atom+16.

| atom start | type | min offset | max offset | min ≤ max | distinct pairs |
|---:|---:|---:|---:|---:|---:|
| +0x130 | 15 | +0x138 | +0x13C | 71/71 | 15 |
| +0x150 | 16 | +0x158 | +0x15C | 71/71 | 17 |
| +0x170 | 16 | +0x178 | +0x17C | 71/71 | 7 |

In the donor: `0x4DF40` = atoms 1–3 of (−0.3°, 0.3°), (sentinel, 3.195°), (−30°, 30°); `0x4E210` =
(−2°, 5°), (sentinel, 5°), (−2°, 2°). The **min at +0x158 is exactly
−100.0 rad in every ragdoll in the fleet**; `derived`: that is a "no lower limit" sentinel, not a pose
(a −100 rad cone angle would be meaningless, and it is bit-identical across 71 objects).

**UNKNOWN:** which of the three is the cone, the plane and the twist limit. The three atoms have the
same 32-B shape and nothing in the bytes orders them; a Havok 2014.1 header or a posed ragdoll would
settle it. I did not invent the mapping.

### 5. What G3-10b's 66 values were (re-derived from its own offsets)

| where the value sits | count |
|---|---:|
| inside a frame's rotation rows (+0x30..+0x5F, +0x70..+0x9F) | 10 |
| inside a frame's translation (+0x60..+0x6B, +0xA0..+0xAB) = the pivot re-listed | 24 |
| **in transform bytes total** | **34** |
| elsewhere in the object | 32 |
| total reported | 66 |

Both of the review's figures are re-derived. They **overlap**: the 24 pivot values are a subset of the
34, because G3-10b's 40-float window started at +0x90 and so swallowed frame B's translation. So 34 of
the 66 were never a limit — the review's arithmetic (34 + 24 = 58 of 66) double-counts its own 24.
That does not change its verdict: the column was not decoded, and this pass replaces it.

## UNKNOWNs (each with the blocker)

1. **The atom type names.** limits / motor / ball-socket / friction — the Havok 2014.1
   `hkpConstraintAtom` enum is not in this project (no header, no source), so only the numeric code is
   reported. Where it would be found: a 2014.1 Havok header (`hkpConstraintAtom.h`) or a public decoder
   that maps the type codes.
2. **Which ragdoll axis each of the three limit atoms is** (cone / plane / twist). The three atoms are
   shape-identical and nothing in the bytes orders them. Where: the same header, or posing the ragdoll.
3. **The non-limit atoms' fields** (+0x0B0 type 23, +0x0C0 type 18/19, +0x0E8 type 17, +0x108 type 12,
   +0x118/+0x190 type 5). Their bytes are constant per class but no oracle pins a name.
4. **The hinge's limited axis.** The hinge has one angular pair; which column of frame A/B is that
   axis is not named by any byte here.
5. **The 9 hinges' non-zero 4th slot** (a scalar in row 1 of frame A, −0.92…0.94). Decoded as present
   and excluded from the rotation; its meaning is UNKNOWN.
6. **Whether the ragdoll's −100 rad is a sentinel** — labelled `derived`, not `decoded`: it is exactly
   the same float in 71 objects and far outside any plausible cone angle, but no header says
   "unlimited".
