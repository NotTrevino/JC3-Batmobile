# G3-07b1 — resolving the six `.pdata` chunks and walking their callers to a global

`STATUS:` **done**.

`review-G3-07a.md` is accepted as the starting point: the 27 offsets hold, and the six "functions"
are `.pdata` chunks, four of them fragments. This card fixes the two things that report left open —
the chunk→function resolution and the real upward chain — and then walks callers until a
RIP-relative load of a global appears.

**Result in one paragraph.** All six anchors resolve to **five** whole functions (the
`part_node_update` and `raycast_body_read` anchors are the same 943-byte function). Every
anchor's upward walk reaches a RIP-relative load of a writable `.data` global within 1–4 hops,
but **none of those globals is a pointer**: the nearest one on the `part_node_update` path is the
`__security_cookie` at `0x142e15310` (depth 0, inside the function itself), then packed float
tables (`0x142d41d78…0x142d41d84`, `0x142d4b218`), then `0x142edc120` / `0x142dad020`, whose
at-rest contents are two packed 32-bit fields, not a VA. So the literal brief's loop terminates,
but it terminates on constants. The **best evidence-backed candidate for "the fixed address that
leads to a spawned vehicle" is `0x142ed7458`**: a `.data` slot that code *stores a live pointer
into* (`0x1401183f0`, `0x140162032`) and then uses as the part container — `[slot] → +0x120`
array base, `+0x128` index array, `+0x130` count — the exact triple decoded from
`0x14024b660`. That identity is **derived, not decoded**, and no walk from the six anchors reaches
it, so the answer is reported as a candidate with its UNKNOWNs stated, not as a proof.

## 2. What the tool does, and how each number can be reverted

1. For each of the six anchors it looks up the `.pdata` chunk, then merges neighbouring chunks
   while the earlier chunk ends exactly where the later starts **and** its last non-padding
   instruction is neither `ret` nor `jmp` (fallthrough). Reverting: delete the tool and the two
   generated files; nothing else reads them.
2. It decodes **every one of the 188,670 `.pdata` chunks from its own start** and records every
   `call rel32` and `jmp rel32` — 349,755 call sites, 109,264 jump sites. No byte scan for `E8`
   is used (that is what produced the false chain in G3-07a).
3. It walks parents breadth-first (call edges and tail-jump edges), reporting per hop the edge
   kind, the site's address, bytes and disassembly, and the caller as a whole merged function.
4. It stops at the first RIP-relative **load** whose target is in `.data` and is not the cookie,
   and classifies the target's at-rest contents.

`--check` rebuilds the document from the bytes, compares `.md` and `.json` byte for byte and
re-runs 8 oracles; a wrong size, address, edge or section makes it fail.

## 5. The part container (decoded) — the structure the walk actually reaches

`0x14024b660` is the loop that feeds the part-node update, byte for byte:

```
0x14024b688  8b 83 30 01 00 00     mov eax, dword ptr [rbx + 0x130]   <- count
0x14024b693  48 8b ab 28 01 00 00  mov rbp, qword ptr [rbx + 0x128]   <- index array
0x14024b69f  48 8b b3 20 01 00 00  mov rsi, qword ptr [rbx + 0x120]   <- array base
0x14024b6c0  8b 4c bd 00           mov ecx, dword ptr [rbp + rdi*4]   <- index
0x14024b6c6  48 69 c9 90 01 00 00  imul rcx, rcx, 0x190              <- stride 0x190
0x14024b6cd  48 03 ce              add rcx, rsi
0x14024b6d0  e8 0b 67 fb ff        call 0x140201de0                   <- the part-node update
```

So a part node is `container[+0x120] + index[+0x128][i] * 0x190`, with `container[+0x130]` the
count (**decoded**; this is new relative to G3-07a, which never named the container fields).

## 6. The candidate fixed address (derived, with its UNKNOWNs stated)

Searching the whole image for a `.data` slot that is **loaded** and then used with the container's
fields turned up 33 slots; of those, one is used with all three (`+0x120`, `+0x128`, `+0x130`):
**`0x142ed7458`**.

```
reader  0x1400ed76c  4c 8b 1d e5 9c de 02  mov r11, qword ptr [rip + 0x2de9ce5]  -> 0x142ed7458
        0x1400ed773  49 89 bb 30 01 00 00  mov qword ptr [r11 + 0x130], rdi
        0x1400ed77a  48 8b 05 d7 9c de 02  mov rax, qword ptr [rip + 0x2de9cd7]  -> 0x142ed7458
        0x1400ed781  48 89 98 28 01 00 00  mov qword ptr [rax + 0x128], rbx
writer  0x1401183f0  48 89 0d 61 f0 db 02  mov qword ptr [rip + 0x2dbf061], rcx -> 0x142ed7458
writer  0x140162032  48 89 0d 1f 54 d7 02  mov qword ptr [rip + 0x2d7541f], rcx -> 0x142ed7458
```

Both writers store a pointer that came back from a call (`0x140118170`) or from `rbx`, and both are
followed by `mov rax, qword ptr [rcx]` / `call qword ptr [rax + 8]` — a vtable call on the object
they just cached. The slot is **not** loader-relocated and its at-rest bytes
(`0x000b3db6002abdf48`) are two packed 32-bit values, so it only ever holds a pointer because code
writes one at run time (**decoded**: the stores and the absence of a `.reloc` entry;
**derived**: therefore it is a runtime-filled pointer slot).

Why this is only a candidate, not the answer:

1. **No walk from the six anchors reaches it.** The parents at depth 3+ are entered by indirect
   dispatch, so there is no static edge to follow: `0x1402ae460` ends
   `0x1402ae484 41 ff 93 20 01 00 00 call qword ptr [r11 + 0x120]` with `r11 = [rbx]` — a vtable
   slot, not a data field; and `0x140240980` (the third caller of the part-node update) has
   **0 call sites and 0 eight-byte pointer xrefs** anywhere in `.rdata`/`.data`.
2. **Identity with the part array is not proved.** `0x142ed7458`'s users write `+0x128`/`+0x130`
   but none of them performs `imul ..., 0x190` near the load, so the element stride that would tie
   it to §5 is missing from the static evidence. A neighbouring slot, `0x142e2b6f0`, is clearly a
   *different* container (`+0x130` begin / `+0x138` end, `sar rcx, 4` → 16-byte elements at
   `0x1400edba2`), which shows how easily these triples mislead.
3. Its writers `0x1401183f0` / `0x140162032` were not themselves walked upward (out of scope for
   this card: the brief stops at the first global load), so which subsystem owns the slot is
   **UNKNOWN**.

| `O1-image` | wrong PE (base, section count, 188,670 chunks, size) |
| `O2-crash-still-there` | `0x14151410f` no longer decodes to `movss xmm0, [rax+0x14]` |

review's claims, so a wrong chunk/region size fails rather than passing silently.

## 9. UNKNOWNs

1. **Whether `0x142ed7458` is the vehicle/part root.** Decoded: it is a `.data` slot written with
   a pointer (`0x1401183f0`, `0x140162032`) and used with `+0x120`/`+0x128`/`+0x130`. Not decoded:
   any `imul ..., 0x190` on the value loaded from it, i.e. the stride that would prove it is the
   array of §5. Would be found by walking `0x1401183f0`'s and `0x1401617e0`'s callers upward (out
   of this card's scope) or by reading the writer's callee `0x140118170`.
2. **Why the walk stops on the `part_node_update` side.** The last hops are entered only by
   indirect dispatch — `0x1402ae484 call qword ptr [r11 + 0x120]` with `r11 = [rbx]` (a vtable
   slot), and `0x140240980` has no call site and no eight-byte pointer to it anywhere in
   `.rdata`/`.data`. Where it would be found: a vtable-construction site that stores
   `0x140240980` into a class's slot table at run time, which the file image does not contain
   (the slot is written by an initialiser, not by static data).
3. **What `.rdata`-bounded values like `0x1425051d8` mean.** `0x142dad020` holds
   `(52.079925537109375, 1)`; the tool labels such values `packed-fields`, but whether the pair is
   `(float, int)` or something else is a reading, not a decode.
4. **Whether the `.data` "float table" hits are real globals or just rodata that was placed in
   `.data`.** `0x142d41d78…0x142d41d84` and `0x142d4b218` hold `0x3fc90fdb`-style radian
   constants; they are writable-section addresses, so they satisfy the brief's stopping rule, but
   nothing in the walk reads them as state.
