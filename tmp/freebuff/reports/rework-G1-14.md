## The one-line diagnosis

`--check` compared `json.dumps(old) == json.dumps(doc)` and printed the anchors; it never read the
note. `DAMAGE_RULES.md` was hand-written prose beside a generated JSON, so the two could disagree
forever — and did, in five places, one of them the missile damage number that G2-28/T-11/T-14 copy.
Fixing individual numbers would have left that hole open, so the note is now rendered by the
script and diffed byte for byte. `--check` also now fails when any anchor is `False` (before, an
anchor that had always been `False` would have "PASS"ed, as the review noted).

### 4. Three literal lists are not in the JSON — CONFIRMED (and the tool was the cause)

Reproduced with the tool's own covered-set (`masked_by_offset` = the offset of the candidate window
that swallowed the literal):

```
[4] old scan's mask, per literal (tool's own covered set)
   TakeRadiusDamageFromWeapon                     literal 0.5 @112 masked_by_offset=111
   TakeRadiusDamageFromWeapon                     literal 0.0 @119 masked_by_offset=None
   TakeRadiusDamageFromWeapon                     literal 0.0 @134 masked_by_offset=133
   TakeRadiusDamageFromWeapon                     literal 0.5 @174 masked_by_offset=173
   DrainWeaponGeneratorForDamage                  literal 0.0 @148 masked_by_offset=146
   DrainWeaponGeneratorForDamage                  literal 0.5 @218 masked_by_offset=217
   DrainWeaponGeneratorForDamage                  literal 0.5 @236 masked_by_offset=235
   DrainWeaponGeneratorForDamage                  literal 0.0 @251 masked_by_offset=250
   LoadHealth                                     literal 0.0 @302 masked_by_offset=301
```

The review blamed "an ad-hoc byte scan" in the prose; the deeper cause was in the tool. Its skip
mask marked every byte inside *any* 5-byte window that began on a byte looking like a reference —
and because a reference index like `a3 28 00 00` ends in zero bytes, a phantom window started one
byte before the real `0x1E` literal (`00 a3 28 00 00 | 1e 00 00 00 3f`) and masked it. Four `0.5`s
and one `0.0` therefore existed in the body and not in the artifact.

**Fix.** Both byte scans are replaced by one left-to-right walk (`walk()`): a candidate is accepted
only at or after the end of the last accepted token, so the leftmost reading wins and the literal
after a reference survives. The walk also resolves import references (`Core.Health`,
`Core.TakeRadiusDamageFromWeapon`) which the old trace dropped. Every literal list in the note is
now `functions.*.constants`, rendered: e.g. §3.2 reads
"**`0.0`, `0.1`, `0.5`, `1.0`, `1500.0`**" and §4 reads "**8** found, distinct `0.0`, `0.05`,
`0.5`, `1.0`". The method is stated as a candidate scan, not an expression tree (§7).

### 6. The regen negation is broader than the artifact — CONFIRMED

The artifact was `regeneration.bm_sdk_symbols` (a global `Counter` with no owners) plus the flat
name table:

```
[6] regen symbols and owners
   sdk counter (old artifact): {'DebugRestoreAmmo': ['RInventoryGadget'], 'EMPRepairable': ['RVehicleBatmobileBase'], 'GetMaxHealth': ['RVehicle', 'RVehicleBatmobileBase']}
   name-table *Regen* names: ['bRegenerateChildren']
   owners: {'bRegenerateChildren': [['RCrowdSpawnPointMaster', 'BoolProperty']]}
   vehicle-family classes 70 | family members 25 | matching Regen 0
```

(The first line shows the *new* record — symbol → owning classes; the old artifact was a bare
`Counter` with no owners. `bRegenerateChildren` was in the old name list and no class owned it.)

**Fix.** `regeneration` now records an owner for every symbol: each BmSDK file contributes its class
name, each BmGame export contributes its outer object and export class, and every class matching

members: **25** exist and **0** match `Regen`. The note renders exactly that, names
`bRegenerateChildren`'s owner, and prints the SDK symbol→class table.

### 7. Trace noise without a caveat; `read_by` by raw containment — CONFIRMED

Both halves reproduce:

```
[7] trace noise and containment-vs-token readers
   refs 34 | accepted tokens 69 | unaligned candidates 8
   sample: [(110, 'RemovePropSkeletal.PawnDied'), (111, 'GFxMovieHudMenu.SetupResolution'), (132, 'RemovePropSkeletal.PawnDied'), (133, 'GFxMovieHudMenu.SetupResolution'), (172, 'RemovePropSkeletal.PawnDied'), (173, 'GFxMovieHudMenu.SetupResolution'), (203, 'RCharacterDefine.SkinType'), (224, 'RemovePropSkeletal.PawnDied')]

   WeaponGeneratorPower                           containment 25 | token 25 | containment_only 0
   ArmouredMode                                   containment 41 | token 30 | containment_only 11
```

The new walk marks all five `PawnDied`/`SetupResolution` hits as **unaligned** candidates (offsets

**Fix.** `refs` contain accepted tokens only; `field_references` counts a reader only when the
field's export index appears as a token, and stores `containment_only` beside it (11 false readers
for `ArmouredMode`). §7 states the difference and the unaligned count (71 across the 14 traced
functions). `WeaponGeneratorPower` (25) and `HealthRecoverRate` (1) are unchanged by the stricter

## Limits of this rework (stated, not hidden)

- The walk is token-aligned, **not** a decompiler: an accepted token can follow a byte the size
  table does not cover, so an aligned name is a candidate call. §7 says this in the note, and no
  count in it rests on an unaligned candidate.
- Literals are byte-aligned candidates of `EX_IntConst`/`EX_FloatConst`; the note does not claim to
  know which operand the compiler built them for.
- `HealthRecoverRate[difficulty]` and `GetDamageMod`'s scaling remain **UNKNOWN** (native/CDO), as
  before — unchanged residuals for G1-22 / G2-28.
