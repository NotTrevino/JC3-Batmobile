## Issues

1. **`--check` is not read-only: it rewrites the `.npy` outputs and then "validates" them.**
   `Tools/scripts/grab_bones.py` `collect()` (line 558) unconditionally calls
   `BONE_ROOT.mkdir(...)` (639) and `np.save(...)` (648, 655) for the 180 bone files and
   `_split.npy`; `main()` calls `collect()` for both `--write` and `--check` (line 1175).
   `check_files()` (line 1063) then compares the freshly written arrays to the JSON that was made
   in the same run. Evidence: after re-running the card's check, the files' mtimes moved to
   `2026-10-29 02:28:45 / 02:28:46` (my run), not their Oct 24 creation dates.
   Why it matters: (a) `--check` mutates outputs on a command the MODLOG presents as verification;
   (b) a tampered `E:\Modding\_BmAKgrab\bones\*.npy` is silently overwritten before it is looked
   at, so the check can never fail on tampered face lists; (c) even without the rewrite,
   `check_files()` only checks dtype `(N,4)`, face-index bounds, slot bounds, `kind ∈ {0,1}`, no
   duplicate rows and the owned/split row *counts* — never that the face indices are the right
   ones. This makes the MODLOG sentence "validating all 180 `.npy` files" (MODLOG line ~8089)
   stronger than what the command proves. The `.md`/`.json` records are still byte-compared, and
   rerunning `--write`/`--check` makes the `.npy` correct at the end, so no number in the doc is
   wrong.

2. **Typed count literals in the generated doc (R11 nit).** `BONES.md` line 961 says
   "`...\bones\<bone>.npy`; 180 files" and line 993 says "PSK pivots vs glTF inverse bind (180
   joints)" — both are string literals inside `render_md()` (`Tools/scripts/grab_bones.py`), not
   `c["face_files"]` / `ch["gltf"]["joints"]`. They are correct today (180 files on disk, glTF
   `joints: 180`), but they are hand-typed and would silently disagree with the tables if the bone
   count ever changed. Everything else in the tables is filled from the record.

3. **`checks.slot_totals_match_cooked` is a typed `True`.** `Tools/scripts/grab_bones.py` line 708
   stores `"slot_totals_match_cooked": True` and `BONES.md` line 988 prints it. The underlying
   comparison does happen — `collect()` raises `BoneError` on any per-LOD/per-slot mismatch — so
   the value is true, but it is an asserted constant in the record rather than a computed boolean
   (unlike `owned_plus_split_equals_total`, which is computed).

4. **One interpretation presented as established: the 3.751 mm wheel-bone/hub gap.**
   `BONES.md` line 36 states "The wheel-bone/hub offset in §8 is the skeleton's own lateral pivot
   offset from the tyre geometry, not transform drift". The measurement is honest, but the cause
   is inferred, and the four corners do not behave alike: bone-pivot minus `stations.json` hub is
   f_l −3.16, −2.02, +0.07 mm and f_r +2.56, −2.08, −0.14 mm (|d| 3.751 / 3.297 mm) but only
   r_l −0.24, −0.01, +0.21 mm and r_r +0.40, −0.05, −0.19 mm (|d| 0.317 / 0.450 mm). Front and
   rear differ by a factor of ~10, which fits either a bone-placement offset or a
   tyre-centre-definition effect; the doc gives no evidence separating them. Reword as a measured
   difference (which §8 already is), or report the per-corner deltas and the cause as UNKNOWN.
   This is a wording issue, not a wrong number.

5. **Minor provenance label.** `BONES.md` §1/§4 column header says "MESHES.md", while the script
   compares against `MESHES.json` (`expected_meshes()`), the machine record behind that file. The
   two agree (299,837 / 144,857 / 21,720; slot sums match), so the values are right; the label
   just names the wrong artefact.

No issue found for: the card's `Do` steps (bone table, per-bone faces per slot, pivots through the
one transform, split flags are all delivered); the `.npy` row format documented in §7; LOD1/LOD2
material mapping (validated by per-section face counts, explicitly not by material names); or
