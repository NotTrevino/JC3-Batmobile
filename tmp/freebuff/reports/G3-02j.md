## 1. Result

**The `SetRBLinearVelocity` argument is the literal `(0, 0, 0)` cm/s, with
`bAddToCurrent = false`, and it is applied to `EjectFromVehicle.Car.Mesh` - the
Batmobile's mesh component, not the pawn Batman rides.**

So the card's premise does not survive its own bytes: this call is a **stop**,
not a launch. It zeroes the car's rigid-body velocity at eject time. The only
call in the body that can move the pawn is `TriggerSpecialMove`
(`+1103`: `Self`, `EjectFromVehicle.Loc`, one unnamed 1-byte token) - an
animation special move, so the launch is authored as a move, not as a velocity
number.

Raw argument bytes at `+513`:

```
1c 04 f7 ff ff  23 00 00 00 00 00 00 00 00 00 00 00 00 28 16
callee          vec: 13 bytes = (0,0,0)                       false end
```

Byte accounting: 13 + 1 = 14 argument bytes, terminator at `+532`, i.e. 15 bytes
from the callee to `0x16` inclusive, with no residue - a wrong width could not
hide in that block.

Receiver, re-serialised byte-exactly from the decoded tree:

```
Context(object = Context(object = LocalVariable "EjectFromVehicle.Car",
                         skip=9, prop="Core.Mesh", flag=0,
                         func=InstanceVariable "Core.Mesh")
        skip=24, prop=null, flag=0)
  -> Core.SetRBLinearVelocity((0,0,0), false)
```

The call is the first statement of the guarded block of the `if` at `+478`
(operand `0x034f`), whose condition is the bool variable
`EjectFromVehicle.FFInRange`.

## 3. ToggleBattleMode: 5269 vs 61474

```
+129  if ( BatmobilePawn.TryToChangeMode(5269).ReturnValue ) {
+156      bWaitingToDebounceRun       = true
+164      bWaitingToDebounceAimGadget = true
+172      jump
      }
+175  BatmobilePawn.TryToChangeMode(61474)   // callee at +188
+199  return                                  // 0x04
```

- Both calls are `RVehicleBatmobileBase.TryToChangeMode`; literals read from the
  bytes are exactly `5269` and `61474` (4-byte literal under token `0x2B`).
- The `if` condition re-serialises byte-exactly and its Context property is
  `TryToChangeMode.ReturnValue` (a BoolProperty), so **the branch is chosen by
  that call's own result**: `5269` is attempted inside the conditional block,
  and `61474` runs on the path the block jumps over, i.e. when
  `TryToChangeMode(5269)` returns false.
- The then-block tiles the whole gap `+156..+175` with no byte unexplained
  (two `LetBool` statements + one `Jump`).

## 4. Jump tokens

`0x07` / `0x06` are the only jump-shaped tokens, and they are used as
`0x07 <expr> <block>` / `0x06` guards. Their **u16 operand is not an in-body
byte offset in this build**: for every candidate base the target leaves the body
for some token, in both bodies.

| body | tokens | base = operand_end | base = token | base = operand_start |
|---|---|---|---|---|
| ToggleBattleMode | 5 | 2/5 inside | 2/5 | 2/5 |
| EjectFromVehicle | 20 | 10/20 inside | 10/20 | 10/20 |

Therefore the *absolute* jump target is **UNKNOWN** (tried u16 relative to
token / operand start / operand end, and the u32 read; none closes). Branch
membership above is derived from block structure and symbol resolution, not from
offset arithmetic, and the card says so. The token *sites* and operands are
enumerated in the card (all 5 and all 20, tabulated), so a later pass with the
right encoding can finish the job without re-decoding.

## 5. UNKNOWNs, stated as such

1. The absolute target of `0x06`/`0x07` operands (see section 4).
2. The numeric parameters of the eject launch: class defaults contain the
   special-move *references* `Eject.Eject_Up_To_Glide`,
   `Eject.Eject_Fwd_To_Glide`, `Eject.Abseil_Eject_Up_To_Glide`,
   `Eject.Abseil_Eject_To_Glide` (`RSpecialMoveConfigConfigurable`) but **zero**
   velocity keys and zero entries carrying the mode ids. Those numbers live in
   the special-move asset, which is not in this package.
3. Token `0x4A` (a 1-byte token used as an argument of
   `CantEjectFromBatmobile` and of `TriggerSpecialMove`) has no proven meaning;
   it is reported verbatim, never guessed.
