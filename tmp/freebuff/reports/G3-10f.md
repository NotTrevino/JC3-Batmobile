## 1. The raycast ids — one space, proved twice

Donor `sportsmuscle.physicsc`: 430 objects, **62 body entries**, 42 parts.

| question | answer | evidence |
|---|---|---|

| does the selected entry belong to that part? | **yes, donor** | the entry's `CPfxPartIndexProperty` value equals the part's index for **42/42** |

| what are the ids below 42? | ordinary part bodies | 24 ray ids, every one a `hknpConvexPolytopeShape` or a `hknpStaticCompoundShape` |
| ids no part names | 20 | `0,1,2,4,5,7,8,12,16,18,19,20,26,34,35,39,40,41` (world bodies of the same parts) + `60,61` (dynamic compounds) |

The per-part map (42 rows) is in `PHYSICS_ROLES5.md` §2 — e.g. part 0 `sportsmuscle_body` → ray 42 → extern mesh, part 26 `wheel_f_l` → ray 22 → polytope at the wheel corner with world body `-1`.

## 2. The static compounds — what they include

| compound | body | part | instances | child class | children in body table | child part index | worst AABB overflow |
|---|---:|---|---:|---|---:|---|---:|
| `0x8f20` | 16 | `front_bumper` (22) | 7 | `hknpConvexPolytopeShape` | 0 | `None` | −0.0100 m (inside) |
| `0xc570` | 26 | `rear_bumper` (6) | 7 | `hknpConvexPolytopeShape` | 0 | `None` | **+0.0202 m** (one child outside) |

* Each compound is the shape of **exactly one** body entry, and that body's part index is the bumper part.
* The children are 7 convex hulls each, **none** of which is a body entry — they are reachable only through the compound's instance array (`hknpStaticCompoundShape+0x60`), and none carries a `CPfxPartIndexProperty`.
* Instance transforms are decoded (basis, translation, scale all 1.0); the stored compound AABB is *not* the exact union — one rear-bumper child sticks out 2.0 cm, measured, not assumed.
* Both donor compounds are additionally instantiated as children of another compound (the two dynamic compounds), so "is a body's shape" and "is a child" are not mutually exclusive.

## What `--check` enforces (each can fail)

* donor: all 42 ray ids select the entry whose part index is that part; the extern-block ray set equals the extern body-id set; every ray below the block is a hull or a compound; each compound has exactly one body and one parent; compound children are not body entries and carry no part index;
* fleet: 6309/6309 ray ids inside their table and selecting a shape; 6265/6265 world body ids inside the table; 1480/1480 compounds are a body or a child; 6093/6093 children resolve to objects; every entry has exactly one system; static class counts pair; externs never outnumber polytopes;

## UNKNOWNs

1. **Which numbering the game's raycast query uses.** The `CPfxPartIndexProperty` value and the parts-module index disagree for part of the fleet (5466/6696 agree; the property is a permutation in only 50/121 files), so both numberings are well formed. Where it would be found: the engine's raycast consumer, or a per-part geometric oracle (hull AABB vs the part's mesh bounds) — not attempted here.
2. **Which engine system reads the `ray` field.** Decoded from `_vehicle_parts.vmodc`; its reader is not in any decoded file. Next source: the executable's parts-module reader.
3. **Whether a compound's child shapes are addressable by any id.** They are not body entries and carry no part property; nothing in the file names them except the compound's instance array. Whether the engine addresses an instance by index is UNKNOWN.
4. **The stored compound AABB** is not the exact union of its children (rear-bumper child 2.0 cm outside). Why the authored box differs is not decoded.
5. **Fleet body tables for the 112 entries whose raw `.physicsc` is absent from `hkx/all`** — their `out/` decodes are `summary` only, so the id mapping cannot run on them; the class-count invariants do cover all 233.
