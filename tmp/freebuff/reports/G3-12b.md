## Criterion 1 - the 4 NAMED-ONLY `.pfxc` decoded

Command:

```
uv run --with numpy --with pillow --with pefile --with capstone python Tools/scripts/decode_depth2.py --write
```

Output (verbatim):

```
wrote DECODE_DEPTH2.json and DECODE_DEPTH2.md (116 .ddsc: 71 FULL / 45 PARTIAL; 4 .pfxc: 4 PARTIAL; 8/8 checks)
```

Exit status 0 (`WRITE_EXIT=0`).

What is decoded (`decoded` = bytes at the stated offset; `derived` = arithmetic on them):

- `PFX\0` at 0, then three u32 = `1, 1, 3` and zeros to 0x14 — **identical on 4/4** (fleet
  invariant), wrapper field meanings **UNKNOWN**.
- the Havok packfile starts at **0x44 in all 4 files**, *located by its own* `0x57E0E057`
  magic (scan of the first 0x200 bytes), not by assuming the offset.
- `jc3hkx.Packfile` parses it: version string `hk_2014.1.0-r1`, sections
  `__classnames__`, `__types__`, `__data__`, **1920 bytes**, data section ending at 1988.
- **7 objects per file, 7 classes**, typed from the packfile's own virtual fixup table:
  `hkRootLevelContainer`, `hkxScene`, `hknpPhysicsSceneData`, `hknpPhysicsSystemData`,
  `hknpConvexPolytopeShape`, `hkRefCountedProperties`, `hknpShapeMassProperties`.
  That is the shape a debris collision file is expected to have end-to-end (scene -> system ->
  one convex hull + its part index + mass properties), and it is *read*, not inferred.
- after the packfile: **512 bytes in every file, 4 different md5s**
  (`43f5234e`, `3957a03d`, `dbd6c225`, `41b16092`) — same length, different bytes, so per-file
  data. **Not decoded**; this is why the grade is PARTIAL, not FULL.

MODLOG §2017's negative result is explained by this: it searched the `.pfxc` for a *baked mesh*
(contiguous float32 verts, int16 buffers, verbatim vertex matches) and found none. The mesh is
not baked as a vertex buffer — the file holds a Havok packfile whose `hknpConvexPolytopeShape`
object is the hull (the same class G3-12 grades FULL with block accounting elsewhere).

## Criterion 2 - the 116 `.ddsc` containers proved

Same command as above; `--check` re-derives the record:

```
uv run --with numpy --with pillow --with pefile --with capstone python Tools/scripts/decode_depth2.py --check
```

Output (verbatim):

```
OK: 116 .ddsc (71 FULL / 45 PARTIAL), 4 .pfxc (4 PARTIAL), 8/8 checks, md+summary byte-identical=True
```

Exit status 0 (`CHECK_EXIT=0`).

The container, decoded by offset on 116/116:

| offset | field | evidence |
|---|---|---|
| 0x00 | magic `AVTX` | 116/116 |
| 0x04 | version = 1 | 116/116 |
| 0x07 | resource dimension, stored − 1 (= 2) | 116/116 |
| 0x08 | texel format id: 77 (66 files), 71 (46), 87 (3), 83 (1) | mip chains close from it |
| 0x0C / 0x0E / 0x10 | width, height, depth (=1) | chain accounting |
| 0x14 / 0x15 | mip count of the full chain / stored in this file | stored levels = last N of the chain |
| 0x20 / 0x24 | header size = 128 / payload size | `128 + payload == file length` on 116/116 |
| 0x28 | constant 16 | 116/116; meaning UNKNOWN |
| 0x2C..0x80 | tail table | zero on 71 files, non-zero on 45 (UNKNOWN) |

The oracle is a **tiling**: mip `L` costs `max(1, w>>L) x max(1, h>>L)` texels in 4x4 blocks
with each dimension clamped to one block; the block size is not assumed but solved per file
from {8, 16, 32, 64} — only the value whose chain sum equals `size_body` is kept, and the
survivors form a function `77 -> 16 B`, `71 -> 8 B`, `87 -> 64 B`, `83 -> 16 B` (fleet
invariant, not a lookup). The ranges are laid from 128 in level order and the last ends at
EOF: **1013 mips, zero residue, on all 116 files.** A wrong block size or start level leaves a
gap or an overrun; neither occurs.

Result: **71 FULL** (container + every mip range + zero tail), **45 PARTIAL** (mip ranges
proven, but the 84-byte header tail holds a table that is not decoded).

## UNKNOWNs and why

- **The `.ddsc` header tail 0x2C..0x80 on 45 files.** A fixed-size table whose u32 pattern
  repeats (`0x10`, `0x10000`, `0x1000010`, `0x20000`, `0x80000`) and whose values track the
  mip set, but no field mapping fitted it: I read the tail as u32 and u16 at every byte offset
  and matched against the computed mip sizes and offsets — no match. Tried: block-size,
  size, offset, width/height readings. Where it would be: the 84 bytes at 0x2C..0x80 of those
  45 files. The mip ranges do not depend on it (they close by accounting), so the grade is
  PARTIAL for exactly those 45 and FULL for the other 71.
- **The u32 constant at 0x28 (= 16 on all 116).** Value decoded, meaning UNKNOWN: it is not the
  block size (format 71 blocks are 8 bytes) and not a floor on mip size (its 1x1 mips are 8
  bytes), so the two meanings one would expect are both excluded by the bytes.
- **The byte at 0x06 (5 or 9).** Constant within a format, no meaning established.
- **The `.pfxc` 512-byte trailing blob.** Same length on 4/4, 4 distinct md5s, so per-file
  data rather than padding; it begins with `0x3f800000` (1.0f) and ends with a table of 16-bit
  pairs. Whether it is shape data, a second allocation or a reference list is UNKNOWN. Tried:
  reading it as the hull's vertex block (the `hknpConvexPolytopeShape` is inline in the
  packfile, so this blob is separate), and as a 4-float/16-bit table — neither closed.
- **Whether a `.pfxc` is honoured for debris collision in the shipped game.** This task decodes
  the files; it does not test them (the reset forbids running the game).

## Limitations

- The block size per format is *derived* (the value that closes the accounting), not read from
  a published table; `77 -> 16` and `71 -> 8` agree with a BC3/BC1-shaped reading, `87 -> 64`
  with 4 bytes per texel, but no DDS/BC name is claimed anywhere in the output.
- No texel is decoded: nothing here proves what a block's bytes *mean*, only which bytes belong
  to which mip. The card's optional "decode mip 0" was replaced by the stronger per-file
  tiling oracle, and the record says so.
- The `.pfxc` object *contents* are typed and counted, not field-decoded; the hull's vertices
  are not extracted (that is `jc3hkx`'s per-class work, already graded for
  `hknpConvexPolytopeShape` in DECODE_DEPTH.md).
