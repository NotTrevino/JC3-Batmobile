### The "JC3 has no system" test

The close-out rule is that no row may end there. `t23_closeout_inventory.py` scans every listed
row's `why` and cells for the banned phrasings ("no JC3 system", "JC3 has no system", "no JC3
expression", "accept the limit") and fails if any of them appears on a row that names no card:

```
PASS: 199 rows, by disposition blocked 11, edit 16, epe 26, keep 29, next 109, out 1,
      superseded 7 | 20 carded, 22 closed, 0 unassigned, 0 banned final answers
```

- rows with **no** resolving card: **0** (target zero) — the tool fails the build if one appears
  (`UNASSIGNED` in `CARD_OF`, or a card id that `GRAB_BACKLOG.md`/`Research/specs` does not
  declare).
- **lore-compromised rows remaining: 0** (target zero). Definition used here, and the only one that
  makes the number meaningful: a row is lore-compromised when JC3's system cannot express the BmAK
  behaviour *and no card is named*. Rows with an open card are scheduled work, not compromises —
  they are the 20 above.

## 4. Phase-B batch sheet, regenerated

`python Tools/scripts/t23_closeout.py --write` regenerates `Working/Translation/BUILD_BATCHES.md`
and `build_batches.json` from the ledger, the §8 cards and the payload files. Two changes this
close-out made to the sheet:

1. **Every step now lists every edit it consumes.** New section *"Every phase-B step and the edits
   it consumes"*: one row per §8 step with the edit files it applies, the row count of each and the
   summed value count, or the declared reason it applies none. Coverage: 19 artefacts (17 payloads
   + 2 records) over 24 steps; the four steps that apply nothing (B-01 scaffold, B-14 release
   candidate) and the eight cards whose module does not exist yet are each listed with their
   reason instead of silently missing.
2. **B-17…B-20 are declared no-payload steps.** The sheet had already grown past the payload table
   (B-21…B-26 were declared), but B-17 (effect writer), B-18 (EMP disable), B-19 (drone hacker) and
   B-20 (sonar) were not, so `t23_closeout.py --check` failed on them. They are build gates whose
   module does not exist yet; each is now declared with the ledger row it will close
   (`T-FX1`/`T-FX2` for B-17, `T-WP15` for B-18, the T-11 blocked set for B-19, the pulse/reveal rows
   for B-20). No payload was invented for them: the honest state is "gate not built", and the
   declaration says so.

The step table now reads, for example, `B-24 | T-ST2, T-ST3, T-ST4, T-ST6, T-K3, T-K4, T-DR1,
T-E2, T-E5, T-B1, T-B4, T-A3, T-G4 | t1_handling.json (15) | 15 | applies the payload` — the
handling card added by the dimensions/steering/engine-aero keep-audit brief.

Also fixed while there: the gate's own summary string hard-coded `/10` for the decision count and
now prints `decisions 11/11 answered`, matching the check that was already testing `len == 11`
after D-11 was added.
