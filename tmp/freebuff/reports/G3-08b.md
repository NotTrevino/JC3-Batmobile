# G3-08b - eject mechanic mapping, static only

**STATUS: done.** The BmAK eject is decoded step by step (input -> guard -> seat -> car state ->
Batman's motion -> car afterwards) and each step is mapped onto JC3. The headline result is
that **the press/hold pair the operator describes is in JC3's files as "two actions on one
control", but not as press vs hold**: no file on this machine carries a hold threshold, and the
two JC3 binding tables **disagree about which control carries the pair** - the shipped
`keymap_gamepad.bin` puts `STUNT_JUMP` + `OPEN_PARACHUTE` on **d-pad down** and binds **no face
button at all**, while the player's export (and the menu) put them on **A**. The only
vehicle-context condition JC3's data contains is the donor exit's parent-speed gate: below 5 the
driver exit is `S_EXIT_VEHICLE`, from 5 up it is `S_EXIT_VEHICLE_PARA`. The launch half has no
JC3 carrier (0 launch members), and BmAK's own launch is an animation special move, not a
velocity - the `SetRBLinearVelocity` argument is `(0,0,0)` on the car's mesh, i.e. a stop.

## Answers to the brief

1. **BmAK input side was not redone.** `DefaultInput.ini:267` is re-read only as a byte check
   for the oracle (`Name="XboxTypeS_A"` carries `EjectFromVehicle`, and it is the only line that
   does). `CONTROLS.md` line 50/107 statements are quoted, not re-derived.
2. **Which JC3 action does hold-A trigger?** `OPEN_PARACHUTE` is on the same control as
   `STUNT_JUMP` in both JC3 tables; JC3's own controls menu labels press A = *jump to roof* and
   hold A = *open parachute*. The **hold duration is UNKNOWN** - it is in no file here.
3. **Press vs hold file evidence.** Exists as: one control carrying both actions (both tables),
   the menu label split, and the character state names (`S_EXIT_VEHICLE_PARA`,
   `S_EXIT_DRIVER_TO_HOOD_VEHICLE`). Does **not** exist as: a threshold, a duration, a
   press/hold flag, or a state/context table - `keymap_*.bin` bindings are one `(input, action)`
   pair of two `stringZ` properties; the export's 249 rows have exactly `{action, key}`.
4. **Vehicle context and launch velocity.** The context is the exit graph's
   `CInteractionGraphParentVelocityCondition` gate (5..999 for the parachute exit, 0..5 for the
   plain one). There is **no** launch velocity: 0 launch/impulse/force members in the donor's 26
   exits, and 0 member-style eject/parachute/bail/catapult names in the 232 vehicle module dumps.
5. **What the engine does.** The exit's `state` string is the contract
   (`exit.driver.moving.parachute` -> `S_EXIT_VEHICLE_PARA`); Rico's `rico_base.afsmb` carries
   that state (2 hits) and `ACT_EXIT_VEHICLE` (1), while the engine's `ACT_EJECT_FROM_VEHICLE`
   appears **0** times (plaintext and Jenkins-hex), and `rico_base.asb` carries
   `PPparachute_vehicle_eject` and `rico_vehi_car_low_driver_to_parachute.ban`. So the driver
   leaves the vehicle through a parachute **state**; no data drives an "eject action".
6. **Priority mapping (operator rule).** BmAK A (eject, double press) > JC3 A
   (`STUNT_JUMP`/`OPEN_PARACHUTE`); BmAK LB (exit, operator-stated live) > JC3 `EXIT_VEHICLE` on
   Y; JC3 keeps Start (pause) and Back (commlink) - and JC3's `ENTER_VEHICLE` on Y stays JC3's
   for entering. Conflicts recorded in the table: LB (JC3 fire secondary), A (jump-to-roof +
   parachute), B (`USE_VEHICLE_MOD`), X (`HANDBRAKE` - same idea), RB (primary fire), LT
   (reverse), LS press (horn).

## UNKNOWNs

1. **JC3 hold threshold.** Tried: both keymap bins (base + patch, 131/145 and 94/104 bindings),
   the player's export (249 rows), `settings/parachuteparams.bin` (344 B, 7 `parachute` hits -
   asset paths only), `text/master.stringlookup` (3,567 B, 0 hits, not an RTPC), the donor
   `.epe`, `rico_base.asb`/`.afsmb`, 232 entity dumps. No hold/duration/tap field exists. Would
   be in native input code or an input table outside the index.
2. **Which binding layer is live.** Shipped bin says d-pad down, export says A, the menu says A.
   All three are on the machine. Would need a runtime observation (the TEST BAN forbids it).
3. **Which action a vehicle consumes.** `keymap` appears in 0/232 module dumps; the
   action -> exit link is native.
4. **BmAK's double-press window / first-press behaviour.** A `LastEjectFromBatmobileTime`
   timestamp is written (`+1273..+1291`); the body's only float constants are
   `[1.0, 600.0, 0.0, 1.0, 1.0]`, none a sub-second window. Only one reference to that field is
   decoded, so no reader exists to inspect.
5. **Battle-mode moving block and boost fallback.** `BoostingOut` (6 refs), `CurrentEjectType`
   (`+343`) are present, but 385/1297 bytes are unattributed jump tokens; write-vs-read and the
   branch are not decoded.
6. **`CantEjectFromBatmobile`'s condition** (first call, `+3`, two unnamed 1-byte tokens):
   `CONTROLS_NATIVE.md` records 0 natives for `EjectFromVehicle`, and the callee body was not
   disassembled here.
7. **The car's post-eject rotation** (right in pursuit, straight in battle). Operator-stated;
   no decoded vector on either side.
