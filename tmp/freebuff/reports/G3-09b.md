# G3-09b — JC3 paint tint selection in the executable

**STATUS: partial.**

Found and proved: where the paint/tint knowledge lives in `JustCause3.exe` — the ADF schema
table carrying the palette field names, and the three functions that reference the
`CarPaintMM` material — and, by measurement, that the tint write is **not** name-addressed
(so the G3-09 open item cannot be closed by a name search of the executable).

Not found: the instruction(s) that fill the CarPaintMM dynamic float4s with a tint, and any
code-referenced exposure/tonemap constant. Both stay UNKNOWN with the next source named.

### C5 — the CarPaintMM plumbing (card item 2)

`CarPaintMM` occurs once, at VA `0x142332188`; it is referenced by **three** functions
(decoded: `lea r8, [rip+…]` resolving to that string, verified against `.pdata`):

| function | bytes | CarPaintMM ref at | names it resolves | notes |
|---|---|---|---|---|
| `0x1401056A0-0x14010586A` | 458 | `0x140105767` | 15 incl. `CarPaintMMShadow*`, `CarPaintMMPreZVelocity*`, `CarOutline*` | format string `CarLight%s`; callees `0x14111A1A0`, `0x14196B6F0`, `0x14196B780`, `0x141EBB180` |
| `0x140106800-0x140106AFD` | 765 | `0x140106962` | 25 incl. `CarPaintMM_RSM`, `CarPaintMM_Skinned_RSM`, `CarPaintRSM` | format string `CarPaintMM%s%s%s` at `0x142332268`; callees `0x14196B6F0`, `0x14196B780`, `0x141EBB180` |
| `0x140153430-0x1401538E3` | 1203 | `0x140153484` | 1 (`CarPaintMM`) | `mov qword ptr [rdi+0x10], rcx` with rcx = `CarPaintMM`; copies 15 16-byte `.rdata` constants; 32 16-byte stores |

The constants that function copies are at `0x1423310E0`–`0x1423311B0` and `0x142331360`, and
**all 15 are `(0, 0, 0, 0)`**. So that path initialises/clears a parameter block; on this
evidence it is *not* the tint writer (a call storing only zeros cannot put a paint colour
into a float4). This is recorded as such, not as the tint path.

- **UNKNOWN**: §4.

## 4. UNKNOWNs and why

1. **Which instruction writes the CarPaintMM dynamic float4s** (and which of the four is
   `TintColorR/G/B`). The names are absent, so it must be found by offset: identify the
   dynamic-param struct in the reflection system and the loop that fills it. The shader body
   is not on disk.
2. **Whether the parameter-block builder is the tint path at all.** Its 15 constants are all
   zero, so no; the actual writer is still unknown.
3. **The palette → material binding.** The image carries the palette schema and the material
   plumbing, but the code linking them is not identified (`Palette`/`tints` have 0 code
   references).
4. **Exposure/tonemap values.** No code-referenced constant; the strings are dead data for
   this purpose. A runtime capture remains the way to obtain them.
5. **Scan scope.** Rip-relative `lea/mov` references in `.text`, verified against `.pdata`
   (188,670 functions). An indirect reference — a name pointer stored in a table and loaded
   through it — is missed unless the table entry itself is referenced. "0 references" means
   "no direct reference", which is exactly what is claimed.
