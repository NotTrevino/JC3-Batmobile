## What was actually established (each with its oracle)

1. **Full byte accounting of all three `.rbm`.** Every file is header + three
   (`u32 type_hash`, payload, `u32 0x89ABCDEF`) blocks, and the parsed pieces add up to *exactly*
   the file size:

   | file | size | header | block 0 | block 1 | block 2 |
   |---|---|---|---|---|---|
   | lod1 | 45,912 | 53 | CarPaintMM 13,051 B | GeneralMkIII 7,126 B | CarPaintMM 25,658 B |
   | lod2 | 21,842 | 53 | CarPaintMM 8,587 B | GeneralMkIII 2,592 B | CarPaintMM 10,586 B |
   | lod3 | 14,590 | 53 | CarPaintMM 5,455 B | GeneralMkIII 1,214 B | CarPaintMM 7,844 B |

   Oracle: `sum == size` and each `CarPaintMM` block decoded by the project's verified
   `rbm_geom.decode_carpaintmm` to its exact end offset. This also corrects the framing of the old
   PARTIAL status: the unknown block sits in the *middle*, so `rbm_geom.decode()` stopped there and
   never reached a block it can in fact decode.
2. **The `GeneralMkIII` tail is decoded exactly** in all three files: `u32 count` + `count` u16
   indices (672 / 99 / 12), max index 175 / 54 / 11, ending precisely on the block checksum.
3. **A new decoded fact about the `GeneralMkIII` head:** its numeric run is **not 4-byte aligned**.
   A scan of the eight possible byte shifts gives 6-of-8 plausible parameter words at shift 1 (and
   the same run again at shift 5) and 0-of-8 at every other shift; read there the values are
   2000.0, 1.0, 0.0, 1.0, 1.0, `u32 1`, 1.571032, 0.480466, 1.438991, which implies a
   sub-4-byte field at +0x10 that shifts everything after it.
4. **The `.rbm` position reading is ruled out on the bytes:** a stride-12 float3 scan of the whole
   `GeneralMkIII` payload finds 0 points inside the AABB the file's own header carries, so the
   block is not "the same vertex layout as `CarPaintMM`".
5. **The `.epe` is closed.** 109,526 B in and 109,526 B out; 2,293 bytes differ, all of them in two
   named classes: 2,189 bytes of `0x50` padding that the writer emits as `0x00` (750 runs), and 104
   bytes inside 75 float32 fields whose relative change is 6.3e-8…4.3e-7 (97 of the 104 identical at
   seven significant digits), i.e. decimal-text round-trip noise from `ConvertProperty`, not a
   layout difference. **0 unexplained bytes**, so the earlier PARTIAL is now FULL.

## UNKNOWNs, and why they stay

1. **`GeneralMkIII` (0x2cec5ad5) vertex/attribute layout**, exact ranges 0x333c..0x49ce (5,778 B),
   0x21cc..0x2b22 (2,390 B), 0x1590..0x1a32 (1,186 B). Tried and rejected: a stride solver over
   `prefix + (count, stride)` for prefix 0..96 step 4 and strides 2..64 anchored on the block
   checksum — it closes once in lod2 (prefix 36, stride 8, 319 entries) and nowhere else, so it is a
   coincidence; `header + verts*stride` arithmetic fits 1, 4 and 6 different ways in the three files
   respectively, so no split can be picked without a second oracle; and the AABB test above kills
   the naive reading. The answer is in a serializer for that block type (Gibbed's JC3 RBM writer
   does not implement it; no published layout in the project).
2. **Meaning of the `GeneralMkIII` head fields** — the values are read and reproducible, but no
   oracle in the project names any of them, so only the bytes are claimed.
3. **Whether the `.epe` round trip is acceptable to the engine** (75 fields' low bits move). Not a
   byte question; only loading the file in the game could answer it, and this task never runs the
   game.
