## The decision from the consuming code

* **The stride is 20 bytes, not 16.** The builder `0x140153430` builds arrays and hands each to
  `0x141952f00` with a count (`mov r8d, 5|6|1|2`). That callee does `lea r8, [rdx + 0xc]`, reads
  fields at +0, +4, +8, +0xc, +0x10, and advances with `add r8, 0x14` (`0x141952fb9`). So the
  "15 16-byte constants" are **slices** of 20-byte records: 5 records = 100 B = 6×16 + 4, exactly
  the stores the disassembly shows.
* **Every field is read as an integer.** 7 `movsxd` sites, and **zero** scalar float loads
  (`movss`/`movsd`) at any of the 15 addresses across the whole image (40 reference sites, all
  `movdqa` ×39 / `movaps` ×1 — vector copies, which are type-agnostic until read).
* **Field 3 is an enum.** `movsxd rax, dword ptr [r8]` then `cmp eax, 0xe` then
  `mov rax, [rbx + rax*8 + 0x2dceff0]`: a 15-entry table, and entry 14 is `VOID` — the "no
  semantic" sentinel the compare tests for. The table's 15 entries are the D3D vertex semantics
  `POSITION, BLENDWEIGHT, BLENDINDICES, NORMAL, PSIZE, TEXCOORD, TANGENT, BINORMAL, TESSFACTOR,
  POSITIONT, COLOR, FOG, DEPTH, SAMPLE, VOID`. The records here use `POSITION` (0) and `TEXCOORD` (5).
* **Field 0 is a stream index** (0…2): it indexes a 4-slot per-stream offset accumulator
  (`mov dword ptr [rsp + r9*4 + 0x30]`), and the dword tables at `0x1425f664c` / `0x1425f66fc`
  hold the per-format sizes/alignment.
* **Not bit counts**: no field is masked, shifted or tested bitwise; the only bit-level test in the
  callee is `cmp eax, 0xe`, an equality against a table bound.

So: **indices / enum values**. As floats the same words would be denormals — not 0…1 colours and
not usable numbers — so the float reading is refuted twice over (no float consumer, and the values
could not be colours even if there were one).

## The corrected conclusion (replaces G3-09b §2 and its UNKNOWN 2 wording)

G3-09b: *"0 of them are non-zero, so as written that path initialises or clears a parameter block …
a call that stores only zeros cannot be what puts a paint colour into a float4."*

Replaced by: the builder seeds six arrays of **vertex-element records** (5 / 6 / 6 / 1 / 2 / 2
records, 22 in all) with integer indices, and each array goes to the layout builder `0x141952f00`,
which resolves every record's semantic through the `POSITION…VOID` table and accumulates
per-stream offsets. The values are non-zero and are not colours; the call cannot be the tint
writer because it **declares vertex semantics**, not because it stores zeros. Which instruction (if
any) writes the CarPaintMM tint float4s remains **UNKNOWN**, as G3-09b said.

Positive control inside the same function: it *does* use real float constants — `movabs r11,
0x3f8000003f800000` (1.0f, 1.0f) at `0x1401537d8` and `movss` zeros at `0x140153862` for a
different array — so the 15 index tuples are a different kind of data in the same code, not a
mis-read float array.
