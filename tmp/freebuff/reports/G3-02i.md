## 1. Method (what is decoded, and how it is checked)

Export resolution is by **name + `outer_index`**, not by path string: `object_path` builds a path
from the outer's *short* name, so state children print as `DrivingMode.<name>`, not
`RPlayerController.DrivingMode.<name>`. Function layout: script is `data[22:-16]`; trailer is
`data[-12]` pre-name word, `data[-8]` name index, `data[-4]` name number.

Calls are the `EX_VirtualFunction` (`0x1B`, FName operand) and `EX_FinalFunction` (`0x1C`, object
operand) tokens the repo walk accepts. Arguments are parsed forward from the operand to the
matching `EX_EndFunctionParms` (`0x16`), nesting sub-calls. Tokens fall in three classes:

| class | handling |
|---|---|
| named with a fixed operand width (repo table + `W5`/`W1`/`BARE`) | decoded at that width |
| carries a nested expression (`0x19 EX_Context`, `0x18 EX_Skip`, `EX_Let*`, jumps) | **exact gap** — it has no fixed width at all |
| not named by the repo table | smallest width in `{0,1,2,3,4,8,9,12,13}` that lets the list reach a `0x16`; row marked `*`, candidates recorded; no candidate → **exact gap** |

That third rule is what turned `0x4a`, `0x2b`, `0x24` and `0x2d` from gaps into decoded operands:
`0x2d` is bare (width 0), `0x24` is a 1-byte literal, `0x2b` carries a 4-byte value (the mode name
index), `0x4a` is bare. Width 0 is shown as `<0x4a>`; it may be a separator rather than a value,
so it is never counted as evidence of a weapon or mode.

## 6. UNKNOWNs

- **Control flow.** No jumps/branches are resolved: `EjectFromVehicle` still has 385 of 1297 bytes
  unexplained, `IsBatmobileFireButtonHeld` 188 of 574. So "the body contains `DriverLeave(true)`"
  is decoded; "this is the path an eject takes on a given frame" is not. Would be in: a full UE3
  expression/statement decoder with jump targets.
- **Virtual dispatch.** `DriverLeave`, `BattleModeFireButtonPressed`, `ButtonPressed`,
  `TriggerBoost`, `TriggerSpecialMove`, `ReadyToFire`/`IsFiring` are `0x1B` names. The candidate
  lists in the note are exports that share the name, not proof of the receiver. Would be in: the
  engine's vtable/state resolution, or a decoded `EX_Context` giving the receiver object.
- **`EX_Context` windows.** 6 argument lists stop inside one (offsets listed in the note:
  `EjectFromVehicle`@241/@281, `IsBatmobileFireButtonHeld`@44, …). Those tokens are
  `object-expression + skip offset + expression`, so no fixed width applies; the tokens after the
  gap are not attributed to an argument.
- **Unnamed tokens.** `0x4a`, `0x2b`, `0x2d`, `0xd8`, `0x23`, `0x24` are not in the repo's token
  table. Widths for the first four are decided by the terminator search and marked `*`; `0xd8`
  and one `0x2b` occurrence (at `EjectFromVehicle` 1243) had no candidate width at all and stay
  gaps. Would be in: a complete `EExprToken` enum for this build (version 863).
- **What the weapon indices mean.** `1`/`2`/`3` are decoded as integers; which weapon class each
  selects (and the objects behind `*PrimaryWeapon`/`SecondaryWeapon`) is not resolved here.
- **Binding → body choice.** `DefaultInput.ini` names commands; whether a command executes the
  state body or the `RPlayerController` sibling is engine dispatch, not stored in the package
  (the siblings are 1-byte stubs, which points at the state body but does not prove it).
