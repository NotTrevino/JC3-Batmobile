# B-10e - vehicle-vs-vehicle collision: the body and the box

## 1. Answers

### Q1 - is 3.495 x 2.271 x 7.025 m a mesh bbox in different axes, or another quantity?

**Both: it is a mesh bbox, and it is in different axes.** Recomputed from the pskx itself, the
`PNTS0000` chunk (201,338 vertices at byte 32 of `Batmobile_V2.pskx`) gives

```
min [-345.118, -174.706, -0.223]  max [357.442, 174.824, 233.962] cm
span [702.560, 349.530, 234.185] cm      (x length, y width, z height)
```

which is byte-identical to the render bounds `COLLISION_FRAME.md` recorded (O1). The B-10 figure
`[349.5, 227.1, 702.5]` is that bbox re-ordered to (width, height, length): width matches pskx y
to 0.030 cm, length matches pskx x to 0.060 cm. **Its height does not match**: 227.1 vs 234.185 cm
(-7.085 cm), so the height comes from the post-split parts set (B-02), and B-10's hull was built
7.1 cm short at the top. It is a *different quantity in kind* from the chassis box too: a render
mesh AABB vs an `RB_BodySetup` drivable box.

**Which axis maps to 6.903 m:** DIM-1's **z** (7.025 m) -> bone **x** (690.305 cm), residue
12.195 cm. Of the six bijections only `(2, 0, 1)` lands inside the 30 cm band; the runner-up is
147.436 cm out (O3). Width -> bone y (349.5 vs 374.536 cm, 25.036 cm), height -> bone z
(227.1 vs 207.5 cm, 19.6 cm).

### Q2 - can the chassis box rotation be derived?

**It does not need deriving: it is decoded, and it is the identity.** Reading each box element's
TM (element +0x14, 16 floats, rows = floats `4i+1..4i+3`) straight from `BmGame.upk` export 169750:

| bone | box | TM rows | translation cm | extents cm | det |
|---|---:|---|---|---|---:|
| `Batmobile_Chassis` | 0 | `[[1,0,0],[0,1,0],[0,0,1]]` | `[9.0, 0.0, 106.75]` | `[690.305, 374.536, 207.5]` | 1.0 |
| `Batmobile_Chassis` | 1 | `[[1,0,0],[0,1,0],[0,0,1]]` | `[0.0, 0.0, 79.0]` | `[679.585, 345.688, 103.5]` | 1.0 |
| `Batmobile_Rig_Weapons_Trans` | 0 | 4.000 deg about y | `[-30.5, 0.0, 93.25]` | `[166.177, 189.365, 39.8]` | 1.000000054 |

max |R - I| for the chassis boxes is exactly 0.0 (O4), all three TMs are orthonormal with det +1
(O5), and the only rotated box is the weapons pod at 4.000 deg about y (O6). So the "box TM
rotation not decoded" item in G3-01b was a **reading gap**: `boxes_tagged` took the 12 bytes
before the extents tag as the centre (they are the TM's translation) and never interpreted the
3x3, which sits 0x14 bytes into the element.

The requested oracle (a rotation is accepted only if it reproduces the convex hulls' bounding
boxes) was run over **371 candidates** - identity, the 4 deg weapons rotation, 90/180/270 about
each axis, and a 0.5 deg yaw sweep - and **accepted none**, on both hull sets:

| hull set | union span (cm) | accepted | best candidate | best residual |
|---|---|---:|---|---:|
| pursuit (13 elements) | 670.946 x 318.312 x 224.086 | 0 | identity, 19.359 / 56.224 / -16.585 | 56.224 cm |
| battle (43 elements) | 695.412 x 492.922 x 294.503 | 0 | identity | 118.386 cm |

That rejection is the correct result and is reported as a contradiction, not bent: the chassis box
is a *different collider* (PhysicsAsset `FKBoxElem`) from the StaticMesh convex hulls
(`RB_BodySetup` 169748/169749), so no rotation can be validated against them. The identity stands
as a byte reading, and B-10d's move to reshape the world hull to the chassis box mixes the two
systems.

### Q3 - which JC3 bodies do other vehicles collide with?

**The per-part bodies.** The donor's 62-entry body table maps 38 entries to parts (entry +0x0C
equals the entry index; `0x7FFFFFFF` for the other 24 - `PHYSICS_ROLES3.md` line 41), and the parts
module names those ids per part (`world_collision_body_id`, `raycast_body_id`):

| body | what | evidence |
|---|---|---|
| 0 | root part's world body | `world_collision_body_id` 0; shape `hknpConvexPolytopeShape` |
| 1..41 minus 22/23/36/37 | 38 part bodies | +0x0C part id = entry index |
| 22, 23, 36, 37 | four wheels (polytopes) | wheels' parts have world body -1, these as raycast body |
| 42 | part 0's raycast extern mesh | `part_index_of` = 0, `hknpExternMeshShape` |

Fleet census (233 entities, 11,643 parts): root part on body 0 in 203/233; 30 vehicles use another
id (armoredtruck 57, articulatedtruck 38, atv 51), so body ids are per-entity indices. 761 parts
carry world body -1.

**Collision layers: UNKNOWN.** No decoded word carries one: +0x50..+0x5C are zero in all 2,936
fleet body entries, +0x08 is the constant `0x7FFFFFFF` flag.

**Which hull must be replaced:** body 0 **and every part body still in the file**. The built
`Working/Collision2/batmobile.physicsc` still has all 62 body entries; B-10/B-10c/B-10d rewrote only
body 0's shape. The other 61 are untouched donor (Serpente) shapes, and the file offers no
vehicle-only body to substitute. A body-0-only rewrite cannot claim to have fixed vehicle-vs-vehicle
contact.
