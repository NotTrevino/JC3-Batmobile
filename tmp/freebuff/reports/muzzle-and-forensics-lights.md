## T-L10 - `ChainGunMuzzle`

**BmAK:** `SpotLightComponent` on bone `Batmobile_Rig_Weapons_Machine_Gun_01` (`|sportsmuscle_LOD1|body|Batmobile_Rig_Weapons_Machine_Gun_01|Batmobile_Rig_Weapons_Machine_Gun_01_LIG`), LightColor [255, 255, 255, 0] (class default: `Default__LightComponent` (Engine.upk)), Brightness 1 (class default: `Default__LightComponent` (Engine.upk)), Radius 4096 (component), InnerCone - / OuterCone 50, Falloff 1, CastShadows False, CastDynamicShadows False. No behaviour, no material: the lamp is a mesh-light that only the weapon's fire animation would switch, and the switch is not in the packages.

**Closest JC3:** a `VehicleDynamicLights` row, not a weapon system. The fleet's only lamps on a gun part are 6 rows on `bavariumtank_turret` (range 10, angle 10, white, behaviour `None`), so a row hung on `sportsmuscle_body` at the gun bone is idiom, not precedent. Members to fill:

**The flash itself** is not a light in JC3: `SAttachedEffect` (5,342 objects in the 232 graphs) carries `Effect` + `Usage`; `Usage` = `Fire` (`hash_jenkins` 4131019937). The muzzle-flash effects exist and are vehicle-mounted already: 31 `.effc` paths, the best carrier is `effects/jc_weapons/muzzle_flash/rico_50cal_muzzleflash.effc` with 21 vehicle carriers (root `EffectRTSystem`). None of them contains a light or flare node (0 light-ish member paths in the whole decoded `.effc` vocabulary), so the flash is sprites and particles only.

**Gap for the build:**

- JC3 has **no light member on a weapon tune**: 34 tune blocks in 25 WEAPONS.jsonl records, 444 distinct member paths, 0 light-ish members (measured).
- No `.effc` carries a light node: 25,025 decoded `.effc` rows, 0 member paths matching light/glow/lumin/flash (measured FX_VOCAB).
- A lamp cannot be pulsed by the shot: the only time-varying members are `blinking` (664 rows carry 1) whose period no decoded file states (UNKNOWN), and the behaviour names, which have no forensics or weapon mode.
- The BmAK cone (Radius 4096, OuterConeAngle 50) has no unit bridge to `range`/`angle` (G2-33 §8): the build picks fleet values and records the choice.
- The visible flash has to come from the effect side: `SAttachedEffect` with `Usage` = `Fire` (5,342 objects / hash 4131019937), pointing at e.g. effects/jc_weapons/muzzle_flash/rico_50cal_muzzleflash.effc (21 vehicle carriers).

## T-L21 - `BattleModeSpotLight` (forensics)

**BmAK:** `RHelicopterSpotLightComponent` on `Batmobile_Rig_Weapons_Drone_Decoder`. LightColor [195, 255, 244, 0] (component), Brightness 0, Radius 0, InnerCone - / OuterCone 0 - the numbers are **zeros**: the base and MK2 rigs ship a placeholder, the Joker rig ships 5/15 with dynamic shadows. What the lamp emits is driven at runtime by `RVehicle.bForensicsLightActive` (0x0884) through `LightsMaterial` / `LightsMaterialInst` / `LightsBrightness`.

**Closest JC3:** the same module row with a cone: `light_type` 1, `angle` 50 (the largest shipped, 74 rows; graph presets reach 60.0 and carry `spot_inner_angle` [0.0, 10.0, 30.0]); `range` 50 (66 rows); `diffuse` from the BmAK colour / 255; no alpha, no aim, no helicopter mode.

| lights[i].cast_shadows | 0 | BmAK CastShadows False |
| lights[i].multiplier | 1 | BmAK Brightness 0.0 (the component is a placeholder) |

**Gap for the build:**

- The rig is a **state, not a lamp**: `RVehicle.bForensicsLightActive` is a bool at 0x0884 (offset 2180); JC3 lights have no enable member and no forensics behaviour (vocabulary: HeadLight, LeftSignal, None, Reverse, RightSignal, SirenLightOffOnFast, SirenLightOn, SirenLightOnOffFast, TailLight).
- `RHelicopterSpotLightComponent` has no JC3 class: it declares only `AbsoluteRotation` (0x0334) on top of SpotLightComponent, and none of the aim/helicopter behaviour survives as data - the build keeps the lamp fixed to the bone transform.
- Inner cone exists only on the graph side (`SVehicleLight.spot_inner_angle`), never on the module row that binds the part: the build must author both sides with the same numbers.
- Colour alpha is not representable (`diffuse` is R/G/B only), and the BmAK red [255,0,0,255] / cyan [195,255,244,0] carry an alpha JC3 drops.
- The emissive mesh side is a `CarLight` block per mesh (11,367 blocks in 220 vehicles): 'UNKNOWN - the material/emissive parameter bytes are not decoded (MODLOG §102d), so a CarLight block can be copied byte-exact but not authored from numbers' - so the build copies a donor block instead of authoring one.
- No time base: `blinking` is a flag only (664 rows set it, no period anywhere) and the forensics pulse/sweep in BmAK is C++ / Blueprint, not data in the packages.

## What the build stage composes

STAGES.md forbids "JC3 has no system". The closest carriers above are three composable pieces, all already in the fleet:

1. **A light row per lamp** in `VehicleDynamicLights` (25 members, part `sportsmuscle_body`, anchor at the BmAK bone, `preset_id` 0) - the recipe `LIGHT_SYSTEM.md` §7a already proves on the wheel arch, with the numbers in this report instead of the donor's.

2. **A muzzle flash on the effect side** for T-L10: `SAttachedEffect` `Effect` = one of the 32 muzzle-flash `.effc`, `Usage` = `Fire`, parented to the mounted weapon entity (T-FX13 decoded the same carrier for casings).

3. **The emissive lamp meshes** through the donor's `CarLight` blocks (11,367 in 220 vehicles) - copy, because the parameter bytes are UNKNOWN.

Left for the assembler: the forensics *state* (pulse/sweep) and a per-shot light pulse have no data carrier in JC3; they are the two gaps a build must close by composition (a second light row driven by a behaviour, or an authored `.effc` variant), and the row must say which it chose.
