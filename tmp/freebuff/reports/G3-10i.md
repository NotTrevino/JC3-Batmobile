# G3-10i - what the runtime does with a constraint whose second body is absent

STATUS: done - the runtime substitutes **none** of the three candidates.  In `JustCause3.exe`
the loop that turns the 24-byte `hknpConstraintCinfo` records into world constraints validates
both body ids against the sentinel `0x7fffffff`, the body-array capacity and the body's own
live-flag, and every failing branch jumps to the loop increment: the record is **dropped**
before `hknpWorld::addConstraint` is reached.  There is no substitution of the world's fixed
body, no system root body, and no chassis body injected for an invalid id; the only way a
second body reaches a constraint is the caller assembling a cinfo from two live ids, which
game code does (example decoded below).

## The answer in one block

```
0x141569f96  movsxd rax, dword ptr [r8 + 0xc]     ; bodyB of the record
0x141569f9a  cmp eax, 0x7fffffff                  ; is it the invalid marker?
0x141569f9f  je 0x141569fc1                       ; yes -> the loop increment, no add
...
0x141569fbc  call 0x1414e7200                     ; only reached with two valid bodies
```

`0x7fffffff` therefore means "no second body" to this consumer, and the consumer's response
is to skip the record - not to attach it to the world, a root body or the chassis.  The
chassis case exists only where game code builds the cinfo itself (`0x140280530` fetches two
live body ids and stores them at cinfo `+0x08` / `+0x0c` before calling the same add).

## UNKNOWNs

- **Who dispatches the cinfo loop.** The walker has 0 direct `call`/`jmp` targets in `.text`
  and its address occurs in no qword slot; the single non-`.pdata` slot is `0x142c16158`, an
  `(RVA, int)` pair `(0x141569d00, -1)` inside a `.rdata` table whose owner was not identified
  (tried: whole-`.text` call/jmp scan, qword and RVA slot search across all sections, `.pdata`
  cross-check, the following `(RVA, int)` table entries).  Where it would be found: the
  packfile/resource loader that instantiates `hknpPhysicsSystemData` objects.
- **Whether the guard is the only consumer in practice.** The "494 rejected / 0 survive"
  figure is derived from the stored ids plus the assumption that the data object carries the
  file's ids unchanged.  No rewrite was found (`0x141569d00` copies the record; `0x141557a30`
  copies the ids verbatim), but a loader-side rewrite performed elsewhere in the image was not
  proven absent for every possible path.
- **Whether the 494 sentinel records are inert by design.** Whether the fleet files are
  templates whose joints are rebuilt by game code (as at `0x140280530`) or constraints the game
  never adds through this path is not decidable statically without a live-world check, which
  this task's rules forbid.
