# Review — G3-11 (Ledger reconciliation)

Independent review. I did not write the card. Read-only: no existing Research/, Tools/ or Working/ file was
modified; no game launched or attached to; nothing built or committed. No earlier review of G3-11 existed.

Subject: `Working/Translation/LEDGER_AUDIT.md` (50,824 B) + `.json` (168,243 B), generated by
`Tools/scripts/ledger_audit.py` (re-read in full, 590 lines), against `Working/Translation/T_ROWS.jsonl` (198 rows)
and `Builds/bm-RC1/` (receipt + 691-file aaf).

Labels: **decoded** = re-read by me from the raw source (built bytes, receipt JSON, file hashes); **derived** =
computed here with the rule stated; **UNKNOWN** = not established, with what blocked it.

## VERDICT: needs rework

The machinery is honest and reproducible — `--check` passes, every count I re-derived matches, the hashes match,
five spot-checked values are exactly right, and the tier system (value / string / member / none) is a real
improvement over a single "done". Two of its own caveats (now-vs-proposed, string-proves-carry) are correctly
stated.

But the central number, **TRANSLATED 85**, is not supported for 35 of those 85 rows by the definition the script
itself writes ("the row's value … is present in a **built** file"):

- **34 of 85** TRANSLATED rows cite a file whose `owner_card` in `Builds/bm-RC1/receipt.json` (`aaf.list`) is
  `base (bm-005 lineage)` or another earlier-build lineage — i.e. the file is an inherited copy that this build
  did not edit.
- **1 row (`T-DM1`)** cites `lave_health_medium.vmodc`, whose own `owner_card` is literally
  **`B-18 (vanilla bytes)`** — the receipt lists it under `b18.reverted_to_vanilla`. Its `max_health = 700` is
  the vanilla value, reported as TRANSLATED.

That is the failure mode RESET_FINDINGS §5.3 names ("files were verified against files"), reproduced inside the
audit that was meant to catch it. The fix is a provenance dimension, not a re-run: `receipt.aaf.list[].owner_card`
is already on disk and classifies every cited file.

Secondary but real: the recorded member path for array/vector members does not exist (41 value rows); `blocked`
rows are reported as TRANSLATED and described as "built ahead"; and the card's own report carries a member count
(`21,804`) that the artifact and the bytes contradict (`21,680`).

## Issues (file, value, why)

### I1 — TRANSLATED counts inherited/vanilla values as translated (`LEDGER_AUDIT.md` "Verdicts"; `LEDGER_AUDIT.json` rows)

Decoded, from `Builds/bm-RC1/receipt.json` → `aaf.list[].owner_card` (a per-file provenance the card never reads):

```
owner_card families over the 691 aaf entries: base 656 (613 "base (bm-005 lineage)" + 43 "base (bm-005 lineage)+B-18"),
                                              B-15 11, B-18 10 ("B-18 (vanilla bytes)"), B-15+B-18 5, others 9
evidence file provenance, by verdict:
   TRANSLATED   file built by a card                          51
   TRANSLATED   file inherited (base / earlier build)         34
   GUESSED      file inherited (base / earlier build)          7
```

Examples, all decoded: `modules/default/batmobile/…_land_steering.vmodc` = `base (bm-005 lineage)+B-18` — the six
TRANSLATED steering value rows (T-ST1…T-ST4, T-ST6, T-ST7) cite a donor module this build did not edit;
`lave_health_medium.vmodc` = `B-18 (vanilla bytes)` and is listed in `b18.reverted_to_vanilla` — T-DM1's
`max_health = 700` is the vanilla number. Against `LOG`/RESET this is precisely "a copied value is not a
translation". Fix: add the `owner_card` to each row's evidence and split the verdict (e.g. TRANSLATED vs
CARRIED/INHERITED), or restrict TRANSLATED to rows whose file has a card owner in this build.

### I2 — `blocked` rows are reported as built, and the md asserts it as fact

`LEDGER_AUDIT.md`, "Findings → Built ahead of the ledger (24)": T-ST7 (`blocked`) and T-WLD11 (`blocked`) appear
there, and both are TRANSLATED. For T-ST7 the found value is `t_to_full_steer_s = 0.8`, the *donor's* current
value (also cited by T-ST2), so nothing shows a build wrote it. For T-WLD11 the row's own `why` says the three
stunt areas are "0.10–0.60 m off the Batmobile shell" and that re-fitting needs a deform-point list — i.e. the row
claims it was **not** done — yet a hit on the string `front_area` makes the verdict TRANSLATED and the md lists it
under "built ahead". The heading states as fact something the evidence cannot separate: value present ≠ value
written (no before/after exists in the audit).

### I3 — the recorded member path is fabricated for arrays and vector members (`LEDGER_AUDIT.json` `evidence`)

Decoded: the ADF has `base_wheel_hardpoint_positions[0].position[0..2]` (four hardpoints, three floats each). The
card prints `base_wheel_hardpoint_positions.position = 0.7046999931335449`. `norm_segs()` strips `[...]` and the
value is a vector component, so `position` (a 3-float vector) and the hardpoint index are both gone from the
printed member. No such member exists, and the printed path cannot be re-read without guessing which hardpoint
and which component. This affects every value row over an array-of-vector member (41 value-tier rows print such
paths). Fix: record the exact member string from `jc3adf.walk` (with `[i]` and component index) next to the
normalised one. My own first spot-check failed on this path before I dumped the members — that is the reader
experience the card's evidence produces.

### I4 — `--check` is weaker than the md claims

`LEDGER_AUDIT.md` header: "`--check` re-derives this from the same inputs and fails on any drift." The code
(`ledger_audit.py:check`) compares only (a) the *verdict* per id against a fresh `build()`, and (b) that each row
line `| id | doc | dispo | verdict | tier |` is present in the md. It does not compare `evidence`, `notes`,
`member_hits`/`string_hits`, `counts`, `tiers`, `by_doc` or the md as a whole — so a changed evidence string, a
changed tier, or a rewritten Findings section passes. `len(stored["rows"]) != 198` is also hard-coded, so a
legitimately grown ledger fails the check. Fix: compare `fresh == stored` for the whole document (the script
already builds it) and drop the literal 198 in favour of "equals the ledger row count".

### I5 — the string tier rests on a container the card itself calls unreadable, and it does not discriminate

`rtpcdump` parses the `.epe` as 467 nodes / 7,322 properties, and the note says names are unresolved — yet 44 rows
are TRANSLATED because an 8+-character token occurs somewhere in those bytes (the same "name table, not usage"
objection the script raises against ADF files, `ledger_audit.py:string_index` docstring). The reuse count makes it
concrete (decoded from the JSON): **6 rows cite the single occurrence at `0x1B44` `sportsmuscle_body`**
(T-L10, T-L21, T-L22, T-L23, T-L28, T-L30); 3 rows cite `0x4F28 Front_Secondary_Head`; 3 cite
`0x3638`; 3 cite `0x41F8`; 2 cite `0x35CC`; 2 cite `0x50AC`. One occurrence cannot be evidence for six different
claims about which light/part was built. Fix: require the token to be at a node/property boundary (a real `rtpcdump`
node walk) and mark repeated single-offset citations as one shared evidence, not six.

### I6 — `G3-11.md` states 21,804 member rows; the artifact and the bytes say 21,680

`tmp/freebuff/reports/G3-11.md`: "50 ADF files decoded with `jc3adf` (21,804 member rows)". Decoded: my own
`jc3adf.walk` over the same 50 files = **21,680**, which is what `LEDGER_AUDIT.json`
(`inputs.build.adf_rows`) and `LEDGER_AUDIT.md` both print. Difference 124. The note is right; the report's number
is wrong and unlabelled. (Everything else in the report's counts checks out: 691 entries, 633 scanned, 17 receipt
steps, 9 output files, 61 parts.)

### I7 — `member` tier can rest on a generic hint that matches hundreds of members

`T-P2`'s evidence: "member present, no row number matches: …:part_damage_types.type.string = 'Default'
(**+614 more member(s)**)"; `T-LG1`: "+449 more". A `path_matches` overlap (a suffix of one side equal to a prefix
of the other) lets a one-segment hint match almost a whole module, so "member present" says nothing about the row.
The count is honest (it is printed), but the tier name reads as a positive finding. Fix: cap hits per hint and say
"hint too generic (N members)" when the match count exceeds a threshold.

  How: decode that file with `jc3hkx` and match `parts[].world_collision_body_id` / body counts against T-P3,
  T-CO2, T-CO3.
- **UNKNOWN 5 (`now` vs `proposed`) is resolvable per row through `owner_card`.** Not one global ambiguity: the
  receipt records for every aaf file whether it is base lineage, a vanilla revert (`B-18 (vanilla bytes)`), or a
  card's output. For the 34 inherited TRANSLATED rows the answer is "the value is the donor's"; for card-owned
  files the value at least passed through the build. Still UNKNOWN: which *cell* of a comma-shifted row the number
  came from (that part of the card's caveat stands).
- **UNKNOWN 1 (`.epe` name hashes) — narrowed, not closed.** The build ships
  `…/v0300_car_kensington_sportsmuscle_debug.stringlookup` (2,210 B) and `profile/online.stringlookup`, but the
  debug one contains **0** occurrences of `Front_Left_Point` or `sportsmuscle_body` (decoded), so it does not map
  the `.epe` ids. Whether `profile/online.stringlookup` does was not tested — that is the next place to look.
- **UNKNOWN 2 (effect refs in `.ee`)** stays: the card tested 8 Jenkins variants per path with 0 hits. Since the
  audit already scans non-ADF bytes, the one untested carrier is the `.ee` string table via
  `profile/online.stringlookup`; without it the negative stands.
