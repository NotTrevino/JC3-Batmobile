The dominant format is the **`.ddsc` AVTX container**: 116 of the 121 PARTIAL files (95.9%) and

with **116/116 files closing byte-for-byte to EOF**.

One thing must be said up front, because it changes what this card is: two earlier passes had
already been over this family.  `decode_depth2.py` (G3-12b) fitted the AVTX header and left 45
files on an unread 84-byte tail; `decode_depth6.py` (G3-12d) then decoded that tail as the
omitted-mip table and closed 116/116 `.ddsc` plus 4/4 `.pfxc`.  G3-12's own census, which this
card ranks, still carries the older 116 PARTIAL grades.  So this pass is an **independent
re-derivation and cross-check**, not a first decode: it re-enumerates the 116 files from the
archive rather than from G3-12's list, re-derives the layout, adds a negation test that the
earlier passes did not have, and confirms their per-file results (0 mismatches).  Nothing was
taken on trust from either pass; the one place this pass adds a *new* fact is the format map
(format 87 is 64 bytes per 4x4 block, 4 B/texel, which neither earlier pass reported).

### The decoded AVTX layout (116/116 files)

| offset | size | field | evidence |
|---|---:|---|---|
| 0x00 | 4 | magic `AVTX` | 116/116 |
| 0x04 | 2 | version = 1 | 116/116 |
| 0x06 | 1 | unknown (0, 5, 6, 8, 9) | values decoded, meaning UNKNOWN |
| 0x07 | 1 | resource dimension, stored - 1 = 2 | 116/116 |
| 0x08 | 4 | texel format id (77 x66, 71 x46, 87 x3, 83 x1) | block size solved per file |
| 0x0C | 2 | width (texels, level 0) | the chain closes from it |
| 0x0E | 2 | height (texels, level 0) | same |
| 0x10 | 2 | depth = 1 | 116/116 |
| 0x12 | 2 | flags (0, 1, 8, 9) | values decoded, meaning UNKNOWN |
| 0x14 | 1 | mip count, full chain | table length = this - the next field |
| 0x15 | 1 | mip count stored here | stored chain tiles to EOF |
| 0x16 | 2 | zero | 116/116 |
| 0x18 | 4 | zero | 116/116 |
| 0x1C | 4 | zero | 116/116 |
| 0x20 | 4 | header size = 128 | and 128 + payload == file length |
| 0x24 | 4 | payload size | stored chain sums to it exactly |
| 0x28 | 4 | constant 16 | 116/116, meaning UNKNOWN |
| 0x2C | 84 | omitted-mip table, 7 slots of 12 | 78 records over 45 files |

Storage identity that closes every file:

    full chain (levels 0..mip_count_full-1) == payload + sum(omitted-record sizes)
    104,034,368 B == 73,625,664 B + 30,408,704 B      (116/116)

Block size per format, solved per file from {8, 16, 32, 64} and required to be a function of
the format id: **71 -> 8 B** (0.50 B/texel), **77 -> 16 B** (1.00), **83 -> 16 B** (1.00),
**87 -> 64 B** (4.00).  Format 87's three files store exactly `width*height*4` bytes at level 0
(256x256x4 = 262,144 = payload; 256x16x4 = 16,384), consistent with an uncompressed 4-channel
format — but no project decoder or export proves the channel layout, so its *identity* stays
UNKNOWN.  The id -> codec names in the artifact (71 = colour BC1, 77 = glass BC3, 83 = normal
BC5) are cited from `Tools/scripts/tex2ddsc.py:5-7,20-22` as project precedent, not claimed as
byte evidence.

## What the oracles actually pin

The card asked for "byte accounting to the end of each file, or a round trip"; this pass does
both, and adds the negative test that makes them mean something:

- **O1** the 116 files are re-enumerated from the archive's own SARC directory and compared with
  G3-12's graded list: identical sets, so the ranking and the decode cover the same files.
- **O2/O3** every file closes as `128 + payload == length`, and exactly **one** of {8, 16, 32, 64}
  bytes per 4x4 block reproduces the payload — 116/116 single-candidate.  A wrong width, height
  or mip count has no candidate that closes.
- **O4** the surviving block size is a function of the format id across the fleet (4 formats, 4
  single-valued entries), which is what makes the per-file fit a format map rather than 116
  coincidences.
- **O5/O7** the 1,013 stored mips tile `[128, len)` with zero residue, and the omitted records
  reconcile the stored payload to the full chain with zero residue (104,034,368 B).
- **O6** the 84-byte tail is decoded, not skipped: 78 records, every one with tag 0x01000010,
  `offset` equal to the prefix sum of the level prices and `size` equal to that level's block
  price, with the remainder of the tail zero on all 116.
- **O8** round trip: rebuilding the 128-byte header from the decoded fields (including the
  table) and appending the payload reproduces the file byte for byte, 116/116.
- **O9** negation: moving width or height by 4 texels, or either mip count by 1, breaks the
  identity on **all 116** files (0 blind spots).  This is the check the earlier passes lacked:
  a field that could slide by one value and still close would not be pinned.  At ±1 texel the
  change is absorbed by 4x4 block rounding on all 116 (the `-1` direction only: 511 and 512
  texels both cost 128 blocks) — reported, not relied on, and the reason O9 perturbs by 4.
- **O10** cross-check against G3-12d's artifact: block size, both mip counts and the FULL grade
  agree on every file (0 mismatches) — an independent second derivation of the same layout.
- **O11/O12** the 121 PARTIAL split 116/3/1/1 by extension and the 4 NAMED-ONLY are all listed.

## UNKNOWNs

1. **Texel contents.** The block *layout* is decoded (offsets, sizes, tiling, per-format block
   size); no decoder turns a block into pixels, and no reference image exists in the project to
   validate one.  This pass deliberately stops at byte accounting.  Would be found by writing a
   BC1/BC3/BC5 decoder and comparing against an export from `ConvertTexture.exe`.
2. **Format 87's codec identity.** Its block size (64 B per 4x4 block = 4 B/texel) is decoded and
   its three files store exactly `w*h*4` bytes, but no project reader or export proves the
   channel order/encoding.  Would be found by exporting one of `t_spherical_ramp`,
   `t_flare_headlight_ramp` or `erosion_smallcurve_soft` through the engine's own converter.
3. **Header fields of unknown meaning:** `0x06` (values 0, 5, 6, 8, 9), flags `0x12` (0, 1, 8, 9)
   and the constant 16 at `0x28`.  The values are decoded on every file; their meaning is not
   carried by any oracle here.  Would be found in the engine's texture resource layout, which is
   not in the project.
4. **Why a level is omitted.** 45 files omit 1-4 levels and 78 records price them exactly, but
   why the cooker dropped those levels (streaming size, editor setting) is not in the bytes.
5. **G3-12's grades are stale for `.ddsc`.** Its census still says 116 PARTIAL because it was
   written before G3-12b/G3-12d.  This pass reports the current grade (116 FULL here, agreeing
   with G3-12d) rather than editing `DECODE_DEPTH.json`, which is another task's file.
