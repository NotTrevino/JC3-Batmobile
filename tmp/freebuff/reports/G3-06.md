## 4. The `BmScript` defaults in `Startup.upk`

97 property objects under `BmScript.RVehicleBatmobile`, 37 component objects under
`BmScript.Default__RVehicleBatmobile`, both read with the `PartialPackage` reader G3-05 built
for these packages.

### 4a. The 97 property objects: the values are **not** in them (three measurements)

1. **Payload size is a function of the property's class** (derived): 12 scalar properties
   (`FloatProperty` 6, `BoolProperty` 5, `IntProperty` 1) all have payload size **30**; 29
   pointer/array properties (`ObjectProperty` 25, `ArrayProperty` 3, `ComponentProperty` 1) all
   have **34**; the 56 `Function`s carry their own bytecode sizes (39…3,336). A per-property
   value field cannot produce a size determined by the property's class alone.
2. **Three same-class properties are byte-identical apart from the per-object counter at byte 2**
   (derived): `fAfterBurnerRumbleCutoffTimeMultiplier`, `fAfterBurnerRumbleCutoffStartStrength`,
   `fAfterBurnerRumbleStrengthTimeMultiplier` — masked identical: **True**. Three different
   properties cannot share every byte if a value were stored between them.
3. **The names are absent from the grab's tag streams**: **96 of the 97** names do not occur as a
   named property tag on any of the 20,128 objects. The single hit is `UpgradedGeneratorBonus` on
   `JokersBatmobile` (`RVehicleBatmobile`, `Playable_BatmobileJoker_SF` export 3180, an
   `ArrayProperty` at class offset 8608) — a different package's archetype, not the default.

So: the class-default payloads are **descriptors** (`0000` terminator at byte 0, then a 26/30-byte
record whose fields are a per-object counter at byte 2 and a name index at byte 18), and the
default *values* are **UNKNOWN where they live**: not in these objects, not in the grab's tag
streams, and `BmScript` — where such defaults would be authored — is not on disk.

## 5. UNKNOWNs (with why)

1. **Where the 97 class-default property values are** — the payloads are fixed-size descriptors
   and three of them are byte-identical apart from a counter (§4a), and 96/97 names never appear
   as tags; they would be in the class's serialized instance data or in `BmScript` (not on disk).
2. **The member names of the decoded CDO offsets** (`StructProperty` @0x200, `ObjectProperty`
   @0x13c, `FloatProperty` @0x16c) — the tags decode, but `OFFSETS.json` carries no layout for
   `ParticleSystemComponent` / `CylinderComponent` / `SVehicleWheel` / `StaticMeshComponent`, so
   which field each offset is stays UNKNOWN (the BmSDK-AK layout question G3-01 raised).
3. **The 3 untagged objects not reached by the decoded graph** — non-reachability is not proof of
   irrelevance; a class default or a native lookup could still use them. Needs the runtime oracle
   (G3-07).
4. **The 6 CDO component payloads past the 512 MiB decode budget** — refused by design; raising
   the budget would decompress ~645 MiB of the Startup image.
5. **The card's Vehicle 4 / materials ~36 partial counts** — not reproduced by any of the three
   definitions I tried (9 and 61 under the definition that does reproduce Weapons 10 and
   Projectiles 8); the extra filter is unknown.

## 6. Limitations

- Everything here compares files to files. No runtime measurement exists yet (G3-07).
- `REMAINDER.json` embeds only the first 24 bytes of each untagged payload plus the start-offset
  walk results; the full payloads stay in the install and are re-read by `--check`.
- The tool reads `Startup.upk` lazily (`grab_packages_g305.PartialPackage`), so payloads past its
  512 MiB budget are reported unread, never substituted.
