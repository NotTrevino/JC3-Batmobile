# G3-10h — the second body of a JC3 constraint, read from the consuming code

STATUS: done

The stored partner is **not a body at all**: the 24-byte `hknpConstraintCinfo` record carries one
real body (`bodyA`, `+0x08`) and one **invalid-body marker** (`bodyB`, `+0x0c` = `0x7fffffff` in
494/494 shipped records). The engine's own code says what that marker means — it writes the value
into a `+0xc` body field to *detach* a body — so `0x7fffffff` is "no body here", not body 0, not a
hidden index.

The task's hypothesis ("the second id is the fixed world body, id 0 in the world") is therefore
**neither confirmed nor refuted by the record**: what is decoded is that the second body is absent
from the data. No cinfo → `hknpConstraint` construction site was found, and none of the four
sentinel sites substitutes `0`, so what fills an invalid `bodyB` at simulation time stays UNKNOWN.

All of it is static: `D:/Games/Just Cause 3/JustCause3.exe` (51,083,264 B, base `0x140000000`,
187,702 `.pdata` functions) was opened read-only and disassembled with capstone. No process was
started, attached to or injected into.

## What is decoded

**1. The record's schema, from the engine's own class registry** (`hknpConstraintCinfo` at
`0x142dbc9a0`, objectSize `0x18` = 24, members `constraintData +0x00`, `bodyA +0x08`,
`bodyB +0x0c`, `flags +0x10`; the four offsets tile the object exactly, which is what validates the
`offset << 16` packing). Cross-checked on `hknpConstraint` (0x38 bytes, `bodyIdA`/`bodyIdB` members).

**2. The field map over all 494 records in 50 fleet `.physicsc` files:** `+0x04` is the high half of
the 8-byte `constraintData` reference and is 0 in every record (so G3-10d's "body 0" reading is a
field that does not exist); `+0x08` is a valid body index in 494/494; `+0x0c` is `0x7fffffff` in
494/494; `flags` is `0x0`. `+0x08` reproduces G3-10g's "recorded body" in 494/494.

**3. The engine-side meaning of `0x7fffffff`** — the new part. A decoded block detaches a body by
writing the sentinel into the body field *before* the unlink call:

```
0x14194326f  or   dword ptr [r8 + 0x18], 1
0x141943274  mov  ebx, dword ptr [r8 + 0xc]
0x141943278  cmp  ebx, 0x7fffffff
0x14194327e  je   0x141943257          ; already detached: nothing to do
0x141943280  mov  edx, ebx
0x141943282  mov  rcx, rax
0x141943285  mov  dword ptr [r8 + 0xc], 0x7fffffff
0x14194328d  call 0x141507350
0x141943292  test al, al
0x141943294  je   0x141943257
```

**4. Every site that tests a `+0xc` body field against the sentinel (4, all decoded):**

| test | function | load | after the test |
|---|---|---|---|
| `0x14028169f` | `0x140281430-0x1402817ea` | `mov eax, dword ptr [rbx + 0xc]` | `je`, then `lea r8, [rax + rax*8]` (index scaling) |
| `0x140281887` | `0x1402817ea-0x1402818a1` | `mov eax, dword ptr [rbx + 0xc]` | `je`, then a call with `[rdi + 0x310]` |
| `0x1415e5d72` | `0x1415e5d40-0x1415e5d89` | `mov ebx, dword ptr [r10 + 0xc]` | `je`, then `test byte ptr [r10 + 0x18], 5` |
| `0x141943278` | `0x141943257-0x1419432a2` | `mov ebx, dword ptr [r8 + 0xc]` | the detach block above |

The third site indexes its records with `lea r10, [rax + rax*2] ; shl r10, 5` (**96 = 0x60**, the
part-node stride G3-07a documented at `+0x60`/`+0x68`), so two independent consumers treat a `+0xc`
dword as a body id whose `0x7fffffff` value means "none".

**5. Stride inventory for a 24-byte walk** (every `.pdata` function ≤ 2500 bytes, decoded from raw
bytes): 187,702 functions decoded; **5,647** contain an `add`/`sub reg, 0x18` pointer step, of which
**25** also test `0x7fffffff` (all container/vector growth); **24** use `imul reg, reg, 0x18`, and
**0** of those read both `+8` and `+0xc`. So no function walks the cinfo array while reading both
body offsets, and no constraint constructor is identifiable from these anchors.

## Defects found and fixed while doing this

1. **The prior scan could not have found anything.** It matched the operand text `+ 0x8]`, but
   capstone prints 8 as `+ 8]`, so its "strict/loose candidates = 0" was an artifact of the regex,
   not a fact about the image. Re-run with the text capstone actually produces, the same scan finds
   5,647 / 25 / 24 sites.
2. **`.pdata` end bounds truncate these functions.** `img.dis(fn)` stops mid-body (e.g. the
   0x1415e5d40 function ends after 0x1415e5d83 while the code continues to 0x1415e5e12), so the
   walk decodes from raw bytes with an explicit size cap instead.
3. **A check tuple with evidence text crashed `main()`** ("too many values to unpack"); the runner
   now accepts `(name, ok)` and `(name, ok, detail)`, and the detail is stored in the JSON.

## UNKNOWN

- **What fills an invalid `bodyB` at simulation time.** Tried: the class registry (no enum), every
  `imul reg, reg, 0x18` in the image (24, none reading both body offsets), the 5,647 `add reg, 0x18`
  functions (25 also test the sentinel, all container code), the four `+0xc` sentinel sites (all skip
  or detach, none substitutes `0`), and cross-references to the class-name strings and registry
  record (loader only). Where it would be found: `hknpPhysicsSystem::addConstraint` /
  `hknpConstraint::create(cinfo)` in the `havok_common-2014.1.0.3.2.3.1039349` tree the strings
  name — no name-bearing reference to it exists in this image.
- **Whether the hypothesis itself holds.** The record does not store a second body, so "world id 0"
  can only be a runtime substitution, which is not decoded. G3-10g's 49.6% fit for body 0 is
  compatible with it and is not evidence for it.
- **Why every shipped constraint has an invalid second body.** Not attempted: the 50 fleet files are
  vehicle physics assets whose constraints come from the .epe part tree (G3-10g H3); whether the
  cooker or the exporter writes the invalid marker is outside this card.
