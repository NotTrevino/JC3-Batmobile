# Smart search, made portable

## The split, in one line each

- **Generic**: `candidates(query) -> [{id, source, route, snippet}]` → judge once per candidate → cache verdict on `sha256(model + "\0" + exact prompt)` → resume by skipping known ids → calibrate on known values with reach reported separately from recall → fixed exit codes.
- **JC3**: the two scanners behind those candidates (`ROUTES = ("exe", "text")`, `chase_candidates.py:556`), the disassembly/`key=value` snippet shape, the prompt's six JC3-specific ways a snippet lies, and a calibration corpus built from `MODES.json` + `FOOTAGE.md` + the curve/struct/FName negatives.

Everything else — the cache layout, the offline path, the run folders, the score/render/check verbs, the threshold sweep — carries no JC3 concept and ports as is.

## What is proven worth copying (from this repo, with evidence)

| mechanism | where | why it earned its place |
|---|---|---|
| model-aware cache key | `smart_search.py:54` | a prompt revision or a model change invalidates by construction; no stale verdict can be reused |
| nothing cached when offline | `:135` | an offline run lists candidates **unjudged**, exports nothing, exits 3 |
| `None` for unparsable, kept with `raw[:500]` | `:170` | an unparsable reply is visible, never silently a `false` |
| reach vs recall | `literal_in`, `:102` | separates a search miss from a judge miss — the single most useful number |
| per-case run folder + `_search.txt` | `chase_calibrate.cmd_run` | a run is self-describing; two judges never overwrite each other |
| `--check` re-verifies provenance | `cmd_check` | the report cannot drift from the data, and no number is hand-typed |
| `--sweep` on stored `p` | `chase_calibrate.sweep` | re-thresholding costs zero model calls; this is what exposed that Jeb buys no recall at any threshold |
| `best_threshold()` tie-break | `best_threshold` | highest recall at zero false positives, ties to the lower threshold |

The measured lesson, stated plainly: on 38 cases (20 positive / 8 found / 10 negative) the frozen `v1`
search half made the known value reachable **28/28**, and the 4B Qwen judge returned `found=true` **once**;
Jeb at 0.5 returned none (0 FP) and at 0.3 bought 3 false positives without one true recall. Numbers live in
`tmp/freebuff/reports/smart-search.md` (generated by `--render`) and `jeb-vs-qwen-calibration.md`. So the
portable claim is **diagnostic value**, not accuracy: a small judge's recall is the binding constraint, and
a two-stage harness is worth building mainly because it tells you *which* stage failed.

## quiz_parser: what is already there, and the three real defects

Already present (so the port is mostly extraction, not invention): a ranked three-way candidate list
(`final_coverage.candidates`, `:155`), a justified cheap pre-filter and typo/word-swap rules
(`quizbank._find` `:198`, `_word_swap` `:234`, `_typo` `:249`), a judge with `temperature 0` and
`enable_thinking: False` (`quizbank.judge_same` `:311`, `final_coverage.Judge.ask` `:90`), a correct
offline policy (`None` → not merged; `EXACT/NEAR/NONE` + exit 3 at `:224`), and a held-out seed in
`--calib` (`:179`). Ground truth is abundant: every saved attempt carries `Correct Answer` markers.

Defects found while reading (all three are in the doc's migration step 1, and none is a JC3 issue):

1. **Cache keys ignore the model.** `quizbank.py:315` and `final_coverage.py:92` both key on
   `sha256(prompt)` alone, so pointing `QB_JUDGE_URL` at another model silently reuses the old model's
   verdicts. The JC3 key includes the model name for exactly this reason.
2. **`final_coverage`'s cache write is not atomic** (`:118`, whole-file `write_text`): two workers can tear
   it. `quizbank._judge_save` already does the right thing (`:282-295`, merge + `os.replace`).
3. **No prompt version anywhere.** `final_coverage_cache.json` entries cannot be attributed to the prompt
   that produced them, so after an edit the old verdicts are uninterpretable. Start a fresh cache dir when
   the port lands rather than migrating.

## Port plan (concrete)

New files in `quiz_parser/quiz_parser/`, nothing existing edited in step 1:

```
judge_kit.py       health probe + size guard (JUDGE_MIN_B=4) + cache key w/ model + atomic per-hash write
                   + parse()->None + ask() -> {verdict, rank, why, p?}
quiz_search.py     stage-1 wrapper + CLI: --json-out, --expect, --no-cache, exit 0/2/3
quiz_calibrate.py  --build/--run/--score/--render/--check/--sweep over calib.jsonl
calib_runs/<promptver>/<case>.json + _search.txt
```

Swaps: `member_candidates` → `bank_candidates(question, answer, k=12)` over the three rankings; routes
`exe,text` → `text,answer,keyword`; `PROMPT` → `quizbank.JUDGE_PROMPT` (SAME/DIFFERENT) or
`final_coverage.PROMPT` (4-way, with answers); verdict `{found,value}` → `{verdict,rank,why}` with
`rank = RANK[verdict]`; `literal_in` → `answer_in` using `match_option`'s exact-then-refuse-on-tie rule;
`owner/offset` from `FOOTAGE.md` → `(question, answer)` with `graded/<file>.txt` provenance; fixed
`E:\Modding\...` paths → a `QB_CACHE` env or package-relative dir.

Calibration mapping (the part that makes it more than a demo):

| JC3 family | quiz_parser equivalent |
|---|---|
| positive: value agreed by four packages | **held-out recovery**: rebuild the bank excluding the attempt that confirmed the answer, then require the same question back **and** the same answer |
| found: chase row with a recorded literal | **reach**: the question's normalized text appears in the candidate list (precision of the judge alone = recall at reach) |
| negative: curve / struct / FName / null ref | **word-swap pairs** the code already names: changed number, best/worst, BFS/DFS, start/destroy, true/false, True-False vs MC with disjoint options — generated from real bank entries |
| — | **coverage direction**: a merely RELATED bank item must not count as COVERS (the docstring already warns the 8B judge errs strict) |

Order: (1) model in the keys + atomic write; (2) extract `judge_kit.py`; (3) `quiz_search.py`;
(4) build the held-out + word-swap cases; (5) score/render/check; (6) sweep only if a scored (`p`) judge is added.

## UNKNOWNs

1. Whether the word-swap negatives actually separate the models on the quiz corpus — **no calibration was
   run** (read-only), so the false-positive rate is UNKNOWN.
2. Whether held-out recovery leaks: `quizbank.lookup()` searches every other quiz, so an excluded attempt's
   answer can return through the graded quiz. The builder must also check the returned entry's `sources`;
   not implemented, therefore UNKNOWN.
3. The right judge size floor for this corpus (the `>= 4B` guard comes from one 1.5B observation).
4. Whether the port improves anything measurable at all. The JC3 numbers suggest a 4B judge recalls very
   little; `quiz_parser`'s deterministic rules may already beat it on lexical cases. That is a hypothesis
   for step 4 to test, not a result.
