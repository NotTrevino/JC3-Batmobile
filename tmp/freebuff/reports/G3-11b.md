## What the re-check found (measurements, not opinion)

1. **G3-11's "no physicsc reader" was false.** 430 objects, 16 classes, 62 body-table entries;
   `bm_colhull.selftest` re-encodes 54/54 hulls byte for byte, `bm_colmesh.selftest` passes on
   this file, 54/54 hulls are convex.
2. **The world hull is provably the built render mesh's hull**, not a chosen shape: every one of
   the 11,197 LOD2 vertices lies on or inside the 96-vertex body-0 polytope, max protrusion
   2.1e-08 m.
3. **A root compound AABB is 1.593 cm short of that hull.** `0xd3c80` (the physics compound;
   children include the static compounds) still carries the box B-10b refit, and B-10c replaced
   body 0's hull afterwards without refitting it. Its `hkcdDynamicTree` is stale by the same
   0.01593 m — the one tree of 20 that does not refit. `0xd0820` (the raycast compound) covers
   the hull. This is the first measured inconsistency in the built collision found by reading,
   not by playing.
4. **Only four station records moved**: relative to the vanilla extract, 44 bytes differ, all
   inside body entries 22, 23, 36, 37 at byte offsets 0x30–0x3b (the translation lane);
   everything else in the 20,912-byte `hknpPhysicsSystemData` is identical, and it matches
   `test-091` exactly.
5. **`.epe` rows are now decidable by name.** 467 object elements, 466 classed, 46 classes, 243
   named objects; `name_hash` = `hash_jenkins(name)` holds on the 12 presets the lights module
   resolves. Two G3-11 `string` verdicts were substring artifacts (`T-FX17`, `T-FX21`).
6. **Light counts the ledger states are wrong in the build**: 18 module rows (not 21),
   28 `SVehicleLight` (22 in `_Default` + 6 in `Sport_Muscle`), 12 referenced by preset hash,
   6 module rows carrying `preset_id 0` (the T-18 custom entries, rows 12–17).

   the mapping is not in the JC3 files, so it can be neither confirmed nor refuted by bytes.
   Next source: G3-01c / `COLLISION_FRAME.md`.
2. **The row-index frame of `T-L8`…`T-L35`.** Those rows say "donor row 8". The built module's
   row 8 is `Sport_Muscle_Rear_Break_Left`, not the preset the row names. Tried: resolving the
   built rows' `preset_id`s to graph names (done above); not tried: the donor's own

   the rows or the ledger counted another file. The task named the built `.epe` as the evidence
   side, so this is left open rather than assumed.
3. **`hknpExternMeshShapeData` vertex dequantization.** Count, AABB, sections and the
   Codec3Axis6 tree are decoded and oracle-proved; the 3×u16 → position rule is still unpinned,
   so no chassis vertex position is claimed from the packed array (the `hkGeometry` arrays are
   decoded, which is what made the LOD2 check possible).
4. **`hknpStaticCompoundShapeData`** (2 objects) remains NAMED-ONLY: `bm_colmesh` refits only

5. **`hknpPhysicsSystemData` field meanings.** The 96-byte entries are compared byte for byte
   against two donor files but not decoded field by field (G3-10b's scope), so this audit can
   say "these 44 bytes moved" but not "this field is the wheel station".

   `RESET_FINDINGS.md` §4 UNKNOWN 1 (no runtime oracle) still stands, and nothing in this card

7. **Why the world compound was not refitted.** The bytes say the tree and the compound box are
