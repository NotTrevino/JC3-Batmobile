# smart_search — one call for any member, calibrated on known values

**STATUS: done (with one finding: the judge, not the search, is the bottleneck).** The tool exists,
runs, caches and falls back offline; it is calibrated on 38 cases whose values the project already
knows, and the calibration says the search half surfaces the known value in **28 of 28** reachable
cases while the local judge returns it on **1**. The report below gives every number and the
generated block is re-derived by `--check`.

## Usage line for agents

```
python Tools/scripts/chase/smart_search.py --member <Name> --owner <Class> --offset 0x<hex> --type <float|int|bool|...>
```

Optional: `--max N` (candidates judged, default 40), `--routes exe,text`, `--json-out <path>`,
`--quiet`, `--url`/`--model`, `--search v1` (calibration only). Output: the `found=true` hits first
(`source`, `value`, `why`), then the counts. Exit codes: 0 judged, 2 bad arguments, 3 judge offline.
`found=true` is a **lead**, never evidence — verify the address before a value enters a record (R4).

The single-member search is importable too: `chase_candidates.member_candidates(member, owner,
offset, type, routes)`. The all-rows mode (`--write` / `--check` / `--list-rows`) still behaves as
it did; `tmp/chase_candidates.before-sSmartSearch.py` is the pre-change copy.

## Calibration design

`calib.jsonl` is generated by `chase_calibrate.py --build`, never hand-written:

| family | what | n | provenance |
|---|---|---:|---|
| a `positive` | G1-21 fields serialised in all four packages with an identical scalar value | 20 | `Research/BatmobileGrab/MODES.json` (field, owner, offset, value) |
| b `found` | chase rows already FOUND with a literal | 8 | the chase line that records the value (`chase-01.md`, `chase2-02/03/05.md`) |
| c `negative` | members whose data proves **no scalar literal default** exists (curves, 24-field structs, FName, object refs, runtime-state rows) | 10 | `FOOTAGE.md`, `MODES.json`, `MECHANICS.md`, `chase-04.md`, `chase-05.md`, `chase2-03.md` |

`--check` re-verifies every known value against its own provenance (MODES.json values,
chase-file line text, FOOTAGE owner/offset, MECHANICS.md curve), so the cases cannot drift
silently. A bool **positive** cannot be built: the only decoded bool value is the unnamed
`ImpactShake` member (`MODES.md`: `0x90 BoolProperty true`), so the bool slot is the negative
`BattleModeMoving` (F-40) instead — stated, not filled.

Metrics per case: `reachable` (the known literal appears in at least one candidate snippet —
`smart_search --expect`), **recall** (some `found=true` value equals the known value, float within
1e-6), **precision** (right `found=true` / all `found=true`, negatives counted as wrong), and
**unparsable** (no JSON). `s/candidate` counts only verdicts actually sent to the model.

## Two runs, and why they differ

The judge prompt and the search half were both **changed by a concurrent session at 01:55–01:56**
while this task was running (`chase_judge.py` hash `aabe0532` → `51c8dd3c`; `chase_candidates.py`
gained a mechanical `store_verdict` rejection that dropped every candidate for these members). The
first partial run was discarded rather than mixed, and the calibration was re-run twice against the
code that is actually on disk:

- **live search + current prompt** — 38 cases, **0 candidates on every case**: the new
  `store_verdict` filter rejects all store sites the corpus offers for these 38 members, so the
  judge is never consulted (recall 0, precision 0 by construction: nothing found).
- **frozen search `v1` + current prompt** — 38 cases, **reach 28/28**: the known value is in front
  of the judge in every positive and found case. Recall **0.036** (1/28), precision **1.000**
  (1 found, 1 right), unparsable **0**, 5.63 s/candidate.

So the loss is not in the routes any more — the value is there and the judge refuses it. The one
hit is `F35 ImpactShakeAbandonedVehicleFactor` = 3.0 in a text candidate; every other case the
judge answers `found=false` ("per-frame update", "value not visible", "offset table" are the
reasons it prints). That is the honest reading of a 4B local model on 4–7 KB of annotated
disassembly.

**Prompt revisions.** The rule is "if recall < 0.8 or precision < 0.5, try at most two prompt
revisions". Recall is 0.036, so the threshold fired, but the prompt was **already revised** during
this task by the session that owns `chase_judge.py` (`aabe0532` → `51c8dd3c`), and this task did
not author a further one: overwriting a file another session is actively editing would have thrown
away their work, and the measured diagnosis (reach 28/28) shows the next useful step is a prompt
that accepts an incremented/clamped store as a default, which is theirs to make. The revision
budget was therefore spent **0 of 2** by this task. For reference, the pre-revision prompt, which
must not be lost, is kept below:

```
# PROMPT v0, sha256[:8] = aabe0532 (chase_judge.py before the concurrent revision)
You check ONE search hit. Answer ONLY with one JSON object, nothing else.

Question: does this snippet SET the default value of the member `{member}` (declared on `{owner}`,
type {type}, field offset {offset})?
- For disassembly: found=true only if an instruction stores a constant (an immediate, or a float
  loaded from a constant address shown in the snippet) into [reg+{offset}] AND the surrounding code
  looks like it initialises an object (constructor / defaults), not a per-frame update. Give the
  constant as the value.
- For text (config, script defaults): found=true only if the text assigns `{member}` a literal value.
- If unsure, found=false. Never guess a value that is not written in the snippet.

Source: {source}
Snippet:
{snippet}

Reply exactly: {"found": true or false, "value": "<literal from the snippet or empty>", "why": "<one short sentence>"}
```

The revision in force (`51c8dd3c`) adds a list of things that are "never a default" (offset-shaped
numbers, counts, register-sourced values, stack-frame stores, delta-scaled updates, our own JSON
records) and requires the literal to be visible on the store's line. It is stricter and it shows:
recall fell from the pre-revision measurement of **0.321** (recorded at the time with the same
scoring code on the original prompt; that run's verdict files were discarded when the concurrent
rewrite invalidated them, so this figure is quoted, not re-derivable) to **0.036**, while precision
rose to 1.000.

A third row now sits in the block below: the Jebadiah 9B decision-model judge on the same frozen
search half (`jeb_340c7b55_v1search`), added by the `jeb-vs-qwen-calibration.md` comparison. The two
qwen rows are unchanged; that report has the sweep, the disagreements and the verdict.

## Limits worth knowing before using the tool

- **The search half cannot read packages.** All 20 family-a values and 7 of 8 family-b values live
  in the archetype/CDO bytes of `.upk` packages; neither route decodes packages, so those cases are
  only reachable because the literal also appears in a decoded text dump or an exe constant. A
  member whose value is package-only needs the package reader (`ch1_dlo.py`), not this tool.
- **The live search currently returns 0 candidates for these members** (see above). Until that
  filter is relaxed, `smart_search` will look empty on this corpus.
- The corpus is shared and other sessions keep writing into `E:/Modding/_BmAKgrab/chase/`; the
  single-member route excludes verdicts, selftests, the cache and `calib_runs`, but a newly written
  `.json` in that tree can still change text results.
- `chase_candidates.py --check` (the row mode) has failed since 01:19 for a reason outside this
  task: files added to `_BmAKgrab/chase` after `candidates.jsonl` was written at 01:06 change the
  text scan. The pre-change script fails the same way, so this task did not cause it.
- The judge is a 4B model on annotated disassembly; treat every verdict as triage.
