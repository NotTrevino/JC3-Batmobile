Head = `u8 version=5` + `Attributes` 0x68 + `MaterialConsts2` 280 B + texture
table 457 B (20 slots, 4 used). Header layout: on-disk reference
`Tools/JCMR-src/.../renderblockgeneralmkiii.cc` (which stops at `// read buffers
// TODO`); buffers: the project's own `jc3geom.py` GeneralMkIII decode.

20-byte attribute record, as the bytes show it:

`{s16 u, s16 v, s16 32767, s16 0}` + `{f32 a, f32 b, f32 0x487FFFFF}`

* `(u,v)/32767` is a UV set: the signed UV area carries the same sign on
  224/224, 33/33 and 4/4 triangles and the texel density spread is 2.06x /
  4.12x / 1.52x (p90/p10) - a chart, not a coincidence.
* the three markers are exact on 176/176, 55/55 and 12/12 vertices (243 in
  total) - format markers, not coordinates.
* `0x487FFFFF` is the float one ULP below 2^18 (262143.9844); the float pair is
  inside [0,1) under that scale on every vertex of all three files.
* rejected by oracle, with the numbers in `DECODE_DEPTH4.md` §4: octahedral /
  2-component / float-triple normals (best mean dot with the face normals
  0.006..0.136), tangents (|dot with the surface normal| 0.28..0.59), the float
  pair as a UV chart (mixed winding 136+/88-), skin weights (no weight/index
  field pair; the block is unskinned).

Fleet cross-check (§5 of the report): 126 `GeneralMkIII` blocks / 56,319
vertices over the Serpente bundle plus 12 of the 233 vehicle bundles. Positions
inside the block AABB 126/126, `0x487FFFFF` at +16 on 106/126, the float pair
inside ±2^18 on 126/126. The unorm16 pair is a single-sign chart on only 28/126,
so the *field widths* are the block type's but the *semantics* are not
fleet-wide - the report says exactly that rather than generalising from these
three files.

## UNKNOWNs

1. **Meaning of the two floats at +8/+12 of the attribute record.** What was
   tried: normal (octahedral, 2-component, 3-component), tangent, UV chart,
   affine function of the UV chart or of a position axis, skin weights - each
   with an oracle, each rejected - plus per-byte constancy, correlation with
   position components and with the UV chart, and identical-value tests on
   coincident vertices. Established: per-vertex, inside ±2^18, +8 identically 0
   at coincident positions (a function of position), +12 not, and the last float
   is a constant 0x487FFFFF marker. Where the answer is: the shipped
   `generalmkiii` vertex-shader body (only `generalmkiii.vb.txt`'s reflection
   header is on disk - 73 lines, input signature POSITION0 / TEXCOORD2 /
   TEXCOORD3 - no instruction list), or a dump of the engine's vertex-element
   table for this material.
2. **Fleet-wide attribute semantics.** 126 blocks sampled: the field widths are
   constant and `0x487FFFFF` holds on 106, but `s16@+4` is 32767 on 28 blocks and
   0 on 73, and the unorm16 pair is a single-sign chart on only 28/126 (10 of
   the 32767 group, 18 of the 0 group). So no discriminator for the variants was
   found; the C++ header stops before the buffers and `Attributes.packed` (32 B)
   is not a vertex-format declaration that this script could read.
3. **The interleaved variant.** 2 blocks (`oldjeep_antenna_lod1/lod2`) have
   position stride 16 and an attribute region that does not divide by the vertex
   count. Not decoded here - the same 20-byte record is not in them. Where: the
   `jc3geom` interleaved-position case plus the extra 8-byte attribute that is
   interleaved with the position record.
