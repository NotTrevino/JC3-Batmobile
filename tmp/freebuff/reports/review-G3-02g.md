## 4. Issues

### I1 - no input hashes are recorded (minor, provenance)

The card says which paths it read but not which bytes. Given exactly this project's history
(three ini files rewritten 64 min after another card was generated), a rule fitted to a
mutable engine-written oracle should carry `sha256` for all five inputs and a generation
timestamp. Fix: add the five sha256 values and the oracle's mtime to §1 and to the JSON
`chain` block; `--check` already re-reads them, so it can also fail on hash drift.

### I2 - "the only one of 8 candidates" contradicts the table below it (minor)

The intro says the rule is "the only one of 8 candidates that reproduces `BmInput.ini`", but
§2's table marks **two** rows `reproduces BmInput.ini` (`append`/exact and
`replace_exact`/exact). §2.2 later explains they are the same function on this data, so the
table is right and the sentence is wrong. Fix: "the only **pair** of readings that
reproduces ... (append and replace-if-identical are indistinguishable here)".

### I3 - one losing-candidate row does not reproduce (minor)

Card §2: `replace_name`/exact = "42/366, fails at Engine.PlayerInput[6]". My replay of the
same rule gives **17/366** body-equal (19/366 name-equal), total merged 234, first divergence
at `Editor.EditorViewportInput[0]`. The winner rows and the `minus=name` row (208/366,
`Engine.PlayerInput[24]`) reproduce exactly, so this looks like a different, unstated
"entries matched" metric rather than a wrong conclusion - but as printed the row is not
reproducible. Fix: state the metric (per-index body equality? name equality? in section
discovery order or alphabetical?) and recompute the four losers.

### I4 - metric labels in §2 are stated as decoded but are derived (minor)

"Prefixes as written in the inputs (decoded)" is fine; the "entries matched (prefix, in
order)" column is a derived count of a replay whose comparator is not defined (I3). The
section header does not separate the two. Fix: one sentence defining "matched", then the
column is honest.

## 5. What I could not check

- **That the engine implements this rule.** The card itself says so: the executable supplies
  no prefix-dispatch evidence (§3) and the rule rests on the oracle. I did not re-scan the
  exe for `Bindings` / `Unknown array` strings, nor the `+`/`-`/`.` immediate census; that
  part of the card is **unchecked here**, not refuted.
- **Cross-package effects.** The merged array is `BmInput.ini`'s; nothing here says which
  array the running game consumes, or whether a later user write-back changes it.
- **The `…`-truncated rows beyond their first tokens.** For A/B/X/Y/RightShoulder I compared
  the first N printed tokens and the source line's existence, not the card's (unprinted)
  continuation.
- **Why `BmInput.ini` was rewritten at 02:37.** Same UNKNOWN as review-G3-03; mtimes and the
  change shape are consistent with an engine write-back, unproven.
