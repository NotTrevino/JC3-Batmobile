# G3-12e - the Serpente `.epe` round trip: which bytes differ, and why

STATUS: done

## Summary

G3-12 left `v0300_car_kensington_sportsmuscle_civilian_01.epe` PARTIAL because
`Gibbed.JustCause3.ConvertProperty.exe --e` then `--i` does not return the vanilla bytes
(first difference at `0x765`). This card ran that round trip on a scratch copy and
attributed **every** differing byte, using the RTPC layout the tool itself implements.

The vanilla member is 109,526 B, sha256 `f67bc17ebb16b70f35a6a131ffc8a1c5ca772ee5dac2b5524ae0603c93c22c32`
(re-extracted from `editor/entities/jc_vehicles/01_land/v0300_car_kensington_sportsmuscle/v0300_car_kensington_sportsmuscle_civilian_01.ee`
through `bm_rc`/`eetoc`; byte-identical to the earlier card's `tmp/g319/a.epe`). The
re-imported file is the same length with sha256 `f5a11052b5fc8f3a6492926e5fa2f3c3552f7392937e7e67d4e7c6806370e413`
(byte-identical to `tmp/g319/b.epe`), and **2,293 bytes differ (2.09%)**, in exactly two
classes with nothing left over:

| class | bytes | what it is |
|---|---:|---|
| alignment padding | **2,189** | vanilla fills the gap with `0x50` ('P'); the tool leaves it `0x00` |
| float32 inside a `Matrix4x4` (type 8) payload | **104** (75 words, 35 payloads) | 7-significant-digit decimal-text round trip |
| unexplained | **0** | - |

So the answer to the card's either/or is: **2,189 bytes are pure canonical re-encoding**
(no structure refers to those bytes at all), and **104 bytes are values that change** - 75
float words, each moved by at most 7 steps of the raw 32-bit word (max relative change
`4.3e-07`). The changed values are listed one by one in
`Research/JC3Grab/DECODE_DEPTH7.md` section 4a (with node, offset, field index and the XML
line).

Three of the four causes the card listed are **ruled out by the bytes**, not by argument:
all 450 node records and all 6,521 property records come back **byte-identical**, so
ordering, the string table and the hash table contribute nothing. The tool's property order
is hash order (`PropertyContainerFile.cs:153,223`) and the vanilla file is already in it; the
string table is deduplicated by value in both (1,014 string properties over 381 distinct
spans, 633 spans reused); names are only XML text (`Program.cs:309-314, 349, 371`) and every
one re-hashes to the hash already in the binary.

The mechanism for the value class is measured, not assumed. The tool writes floats as
`ToString(InvariantCulture)` (`FloatVariant.cs:51`, `Matrix4x4Variant.cs:74-97`), which on
.NET Framework is `G7`, and re-parses that text (`FloatVariant.cs:46`,
`Matrix4x4Variant.cs:53-72`). Applying that round trip at a fixed digit count to all 3,136
float words in the file reproduces the changed set exactly at **7 digits (75/75)** and at no
other count (6 -> 149, 8 -> 1, 9 -> 0, 10 -> 0). It is not a matrix-only code path: the 679
inline `float` properties and the 89 vec/vec4 components simply carry values that 7 digits
reproduce exactly, and the same rule predicts 0 changes there.

Two facts make this harmless for the Batmobile, and both are measured:

* the tool is a **fixed point** after one pass - `b`, `b2`, `b3` are the same sha256 and the
  two XML exports are identical - so the rounding happens once and does not accumulate
  across edits;
* the `.epe` the Batmobile build already carries
  (`Builds/bm-009/.../..._civilian_01.epe`, 105,430 B, sha256 `1778816d...`) round-trips
  **byte-identically** through the same tool, and its 2,131 pad bytes are already `0x00`:
  a file built through ConvertProperty *is* the canonical form, so the vanilla-vs-tool
  difference is a one-time canonicalisation, not a lossy pipeline.

Relative to the earlier pass (`Tools/scripts/decode_depth3.py`, G3-19, which read the same
`tmp/g319/a.epe`/`b.epe` pair and also reported 0 unexplained bytes): the two classes are
the same, but this card replaces that pass's `rel < 1e-5` float heuristic with an exact
digit-sweep oracle, proves the layout/ordering/string/hash equality, adds idempotence and
the Batmobile-file check, and corrects one label - `b.epe` is the `--i` output, not what
`--e` writes (G3-19's docstring says otherwise).

## What the oracles pin, in one line each

- **O1** the file measured is the vanilla member G3-12 graded, pinned by sha256, re-extracted
  by this script rather than taken from another card's scratch.
- **O2** the round trip is reproducible and length-preserving, so the diff is positional, not
  a size change.
- **O3** roles + padding = the whole file with no overlap: the byte map is total, so "padding"
  is not a bucket for bytes that were not understood.
- **O4/O5** the pad map is identical in both files and only its fill value moved (`0x50` ->
  `0x00`), on every one of the 2,189 bytes.
- **O6** 450 node records and 6,521 property records are byte-identical, which is what makes
  "ordering / string table / hash table unchanged" a measurement instead of a guess.
- **O7** the diff closes: 2,293 = 2,189 + 104 and 0 unexplained.
- **O8** the changed set is reproduced exactly by a 7-digit decimal round trip and by no other
  digit count - the check that would fail if the mechanism were something else.
- **O9** the tool is a fixed point: `b == b2 == b3` and the XML is stable, so the perturbation
  is applied once.
- **O10** the `.epe` the Batmobile already ships is in that fixed point, i.e. the difference is
  the *vanilla* file's, not the build's.
- **O11** the name the export prints for the changed property re-hashes to the hash in the
  binary, so the name list is not silently rewriting ids.

## UNKNOWNs

1. **Whether the 75 re-rounded matrix floats are acceptable to the engine.** The magnitude is
   bounded here (<= 7 raw 32-bit steps of the binary word, max relative `4.3e-07`, max
   absolute `3.8e-06`, on a translation of 23.409853), but no oracle in the project runs the game, and this task may not
   attach to one. Would be found by loading a build that uses the re-imported `.epe` and
   comparing transforms, or by a post-load dump of `world` matrices.
2. **Why the cooker padded with `0x50`.** The value is decoded on 100% of the pad bytes and
   the tool's `0x00` is fully explained, but the *reason* for the fill byte is not in the
   file. Would be in the engine's serializer, which is not in the project.
3. **Whether other `.epe` files behave the same way.** Only this member was measured (G3-12
   graded exactly one `.epe` PARTIAL). The rule itself (G7 text) is a property of the tool, so
   it should apply to every `.epe`, but the pad fill and the share of affected values would
   have to be measured per file.
4. **The meaning of the unnamed matrix property `0xa04c3b1e`** (12 of the 75 changed words).
   It has no entry in the fork's name list, so the object it belongs to is known only by hash
   (`0x2736e6f9`, `0x37b52bf9`). Would be found in the engine's class definitions or in a
   name list that covers it.
