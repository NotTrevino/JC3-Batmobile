# Review — T-13 · Interaction translation

Reviewer: independent pass (did not write the card). Read-only: nothing outside this report was
modified; no game launched, nothing committed.

## VERDICT

**minor issues**

The card's outputs all exist and are regenerated by the script, `--check` passes and is a real
rebuild-and-compare (json dict equality, md byte equality, then the Done-band invariants), and the
transform table is genuinely derived from the mesh and the donor json — the four numbers I
re-measured independently reproduce exactly. What keeps it short of "sound": several doc numbers
are **typed literals inside `render_md`** (the "70 of 85" claim is true today only by coincidence of
the source), the card's explicit **plane-fit method is not implemented** (dead `up_faces`/
`plane_anchor` remain in the script), the **donor-clearance metric was chosen without saying so**
when the same record holds three different values, and the MODLOG's seat-distance corroboration
compares two unrelated measurements.

## Issues

1. **`Tools/scripts/t9_interaction.py:362-363, 369` — typed prose numbers in the generated doc
   (R11).** `render_md` hard-codes `"...the three stunt areas (0.048 m hood, 0.1474 m roof)..."`,
   `"...a chosen 0.10 m..."`, `"...(70 of 85)..."` — doc lines 151-152 and 158. The "70" is correct
   today (`INTERACTION.json` `counts.world_source.inherited = 70` of 85, verified), but nothing
   computes it: if the donor file changed, `--write` would emit the same "70 of 85" and `--check`
   would still PASS, because the literal lives inside the renderer that `--check` compares against
   itself. The same applies to 0.048/0.1474/0.10, which *are* available as
   `d["anchors"][k]["donor_gap_m"]` / `SIDE_CLEARANCE` and simply are not used there. R11 says the
   numbers in the doc come from the script; these come from the author's typing.

2. **The card's plane-fit method is not implemented and its absence is not disclosed
   (`t9_interaction.py:63-86`, `57`).** The card: *"Stunt areas → planes fitted to the Batmobile
   roof/deck faces (normals within 20° of up)."* `up_faces()` and `plane_anchor()` (with
   `UP_COS = cos(20°)`) exist and are never called; `anchor_table()` uses `top_hit()`, a single
   vertical ray at one fixed z, instead. The resulting point transforms satisfy the Done rule, and
   doc §2 honestly says "found by a ray cast", but neither doc nor MODLOG says the plane fit was
   dropped — a reader comparing doc to card sees the card's method silently replaced, plus ~24
   lines of dead code whose presence suggests it was tried and bypassed.

3. **`Working/Translation/T9_INTERACTION.md:23-24` (and json `anchors.*.donor_gap_m`) — the donor
   clearance metric is picked without saying which field, when the record holds three that
   disagree.** G2-18 stores per area `center_gap_m` (front 0.048, main 0.1474),
   `bat_center_surface_m` (0.1035, 0.0197) and `bat_center_geom_surface_m` (0.1512, 0.0746). The
   doc calls its value "the donor stunt-area gap" as if there were one, and the script picks the
   **smallest** metric for the hood and the **largest** for the roof (`clearance_for` →
   `max(gap, 0.06)`); the roof objects consequently float 0.1453 m above the canopy while a
   centre-based reading would put them at 0.02 m. Field name is a legitimate provenance anchor,
   but the choice among three competing measurements should be stated (R4), not left to the field
   the author happened to read.

4. **`MODLOG.md:12913` — false corroboration of the socket distance.** *"`interaction.seat.driver`
   is a socket 27.9 mm from the nearest triangle, consistent with COCKPIT.md's 24 mm above the
   cushion"*. Two different quantities: 27.9 mm is the 3-D distance from the socket to the nearest
   `body_lod1.rbm` triangle (the outside body shell), 24 mm is the vertical gap between socket
   y 0.8647 and the `BatmobileV3_Cockpit_Seat` cushion top y 0.8407 (`COCKPIT.md:14,41`) in a
   different mesh. They agree only numerically; calling one "consistent with" the other presents
   an unverified relation as a confirmation. The doc's own row is fine (`nearest 0.0279`,
   `inside by design`); it is the MODLOG gloss that overreaches.

5. **`t9_interaction.py:231-232` — `forward` for side anchors is an invented convention, pointing
   into the car, and the doc does not state it.** `forward = [-a["normal"][0], 0, 0]` with the
   comment "side anchors face the body": the left-side entry therefore gets `forward [1, 0, 0]`,
   `yaw 90°` — i.e. +x, across the vehicle — while the left anchor's outward normal is −x. The
   donor records carry no orientation at all (`INTERACTION.json` `points[]` union keys: position,
   scale, state, class, verdict… — no rotation), so a chosen convention is unavoidable; but doc
   §6 only gives the `atan2` formula and says yaw is "derived from the anchor normal", and MODLOG
   repeats that, when the code negates the normal for sides. Anyone consuming `yaw_deg` 90 for an
   entry will be 180° wrong about which way the entry faces. Should be labelled chosen, with the
   inward/outward decision stated.

6. **Card clause "rear deck for `point.stunt.rear`" is vacuous and says so nowhere.** No donor
   object name contains `rear` (checked all 85), so there is nothing to place; doc §2's anchor
   table has hood/roof/left/right only, and neither doc nor MODLOG notes that the rear case never
   arises. Low severity, but the card's enumeration implies a case the doc should dismiss
   explicitly rather than silently.

7. **Doc §6 "one station per side" understates the collapse.** All 19 `stunt` rows plus
   `interaction.seat.stunt` and the six `trigger.stunt*` rows share one identical roof point
   (0.0005, 2.2467, −0.5), and 30 of the 77 placed rows sit on two side points. Doc §4 shows the
   duplicated positions, and the card only asks for placement "at the analogous location", so this
   is within spec — but the doc should say that the transform table is four anchors × N objects,
   not 77 distinct positions, since a future consumer could read the table as per-object layout.

Checked and found sound: the 85/77/6/1/1/77 counts (json `counts` and doc §3 agree, and sum
correctly); role counts (driver 29, passenger 25, hood 9, stunt 19, three seats = 85); the six
dropped rows are exactly `*pull.out*` / `*pulled.out*` and D-9 is resolved "no"; no dropped or
placed row reports `inside` true; the `Driver` socket equals COCKPIT.md §2 (−0.0025, 0.8647,
−1.0654) and `invariant_checks` fails if it moves; mesh counts in the doc header (20,000 triangles,
28,940 vertices) match the loaded mesh; no guess is presented as a game value — the 0.10 m side
clearance is labelled "chosen"/"not decoded - UNKNOWN" in doc §2 and §6, and
`interaction.seat.passenger1` is UNKNOWN rather than fabricated.

## Suggested rework (not applied)

- Derive the §6 sentences from `d` (pass `counts.world_source` and the anchor gaps through the
  json) instead of literals in `render_md`; add the lineage counts to the json so `--check` can
  see them.
- Either implement the card's plane fit via the existing `plane_anchor`, or delete `up_faces`/
  `plane_anchor`/`UP_COS` and add one line to doc §2 and MODLOG saying the points are placed by
  ray cast because the Done rule is point-based.
- State the `center_gap_m` field name in doc §2 (and why that metric, given the two alternatives).
- Reword MODLOG:12913 to "27.9 mm to the nearest body triangle; separately, the socket is 24 mm
  above the seat cushion per COCKPIT.md".
- Add the side `forward` convention (inward, +x on the left side, chosen) to doc §2/§6.
- Note that no `point.stunt.rear` object exists in the donor, and that the 77 placed rows collapse
  onto four anchor points.
