# The suspension unit bridge, built from data (T-S6)

Generated by `Tools/scripts/t_s6_bridge.py --write`; `--check` recomputes every number from the same files. Read-only.
`decoded` = a value read at a stated file; `derived` = rule + inputs shown; `UNKNOWN` = not in the files, with the searches listed.

## 1. The question

BmAK stores `SuspensionTravelUp 30` / `SuspensionTravelDown 40` (cm) and `BMRearWheelMaxDroop 100` on the wheels, `BMWheelSuspensionStiffness 3000` / `BMWheelSuspensionDamping 300` / `BMWheelSuspensionBias 50` / `BMFrontWheelSuspensionBias 10` on `RVehicleSimBatmobile`, and JC3 has a `Suspension` module with a different vocabulary. T-S6 is blocked until the numbers share a unit and a rule. This note builds both from the files, shows the arithmetic, and reports the fit error.

Units are derived, not assumed:

- JC3 radius is **m** because the same file's `RigidBody.mass` is kg and the radius values (0.20-1.80) match real tyres only in metres.
- BmAK's package length unit is **cm**: `WheelRadius 64.0` = 0.64 m, and the same package's class defaults carry `BattleModeLength 430.0` and `PursuitModeWidth 220.0`, which are 4.30 m and 2.20 m for this car. Hence `CM = 0.01` in the tool.
- `strength` is **s^-2** (a rate normalised by mass), not N/m: the T-S6b sag oracle fits 164/166 vehicles on the mass-normalised reading and 0/166 on N/m.

## 4. Fit 1 - travel to spring

The only dimensionally closed rule the fleet supports is the static-sag rule: each spring carries `m*g/4`, and because `strength` is mass-normalised the mass cancels,

```
sag(m)   = m*g / (4 * k)          with k = strength * m   (T-S6b)
         = g / (4 * strength)
f        = sag / length = g / (4 * strength * length)     (dimensionless)
```

`f` is the fraction of the authored travel the car sits into at rest. Over the 126 vehicles that have both numbers:

| f | p5 | p25 | p50 | p75 | p95 | sag > length |
|---|---:|---:|---:|---:|---:|---:|
| `g/(4*strength*length)` | 0.182 | 0.327 | **0.454** | 0.454 | 0.681 | 2 |

**Fit result: the fleet sits at `f = 0.4542` (median), IQR 0.327-0.454.** The rule's own scatter is the fit error: p5 and p95 are 0.182 and 0.681, i.e. -60% / +50% around the median. The 2 violations (v0510_car_solar_modernroadster / v0510_car_solar_modernroadster_civilian_01.ee.json, v0510_car_solar_modernroadster / v0) are the expected failure mode (a spring whose rest sag is longer than its travel).

## 5. Fit 2 - bias

**JC3 has no bias member: 0 rows in all 166 `Suspension` modules contain `bias`** (`--check` oracle `no_bias_member`).

The closest carrier is `hardpoint_offset_along_spring`, a fraction of the spring length (negative = the wheel hangs below the hardpoint). Its fleet distribution is -0.375 .. 0.500, median -0.100 (front) and median -0.090 (rear). The candidate bridge is the straight reading of BmAK's percent as a fraction:

```
offset = -bias / 100
front: -10 / 100 = -0.10     fleet front median = -0.100     error 0.0%
rear : -50 / 100 = -0.50     fleet min (any axle) = -0.375   outside every authored value
```

So the *front* bias is placeable with a perfect match to the fleet median; the *rear* bias of 50 cannot be expressed without leaving the authored range. The largest magnitude the fleet ever authors is `-0.375`, i.e. bias 37.5 - a 25.0% short of 50. The sign/scale reading is therefore derived from one agreeing point, not proven.

## 6. The bridge, number by number

With `length = SuspensionTravelDown = 40 cm x 0.01 = 0.40 m` and `f = 0.4542`:

```
strength = g / (4 * f * length)
         = 9.81 / (4 * 0.4542 * 0.40)
         = 13.500 s^-2

BmAK stiffness 3000 must then equal strength * mass:
mass = 3000 / 13.500 = 222.2 kg
decoded SVehicle.ChassisMass class default = 210.0 kg
error = 222.2 / 210.0 - 1 = +5.8%

read the other way, at the decoded 210 kg:
k/m = 3000/210 = 14.286 s^-2 -> sag = 9.81/(4*14.286) = 0.1717 m
f   = 0.1717 / 0.40 = 0.4292   vs fleet 0.4542   error -5.5%
```

Both readings give the same residual: **the Batmobile's decoded stiffness and the decoded 210 kg default agree with the fleet's travel-to-spring rule to 5.8%.** That is the fit error of the stiffness placement, and it is smaller than the rule's own p5-p95 spread (-60%/+50%).

### The damping check (independent)

`zeta = c / (2*sqrt(k*m))` with BmAK's own 300 / 3000 / 210:

```
zeta = 300 / (2 * sqrt(3000 * 210)) = 0.1890
fleet zeta = compression / (2*sqrt(strength)): median 0.198, p5 0.091, p95 0.331
error = -4.4%
```

A damping number that the bridge never used lands within 4.4% of the fleet's median damping ratio - independent support for the 210 kg reading.

To place it, JC3 needs two integers (`compression`, `relaxation`). Carrying the ratio `zeta_bmak` back: `compression = zeta*2*sqrt(strength) = 1.39`, so the nearest integer pair at the fleet's comp/relax ratio (median 0.50) is **1 / 2**, which realises zeta = 0.136 (-31.1% against the fleet median). Integer quantisation, not the bridge, is the error here.

### The pursuit-mode number

```

sag    = 9.81 / (4 * 3.571) = 0.6867 m = 172% of the 0.40 m length
```

750 cannot sit on the same car with the same travel: its rest sag is 172% of the authored length, and the fleet has 2 vehicles over 100%. Placing it needs either a 1.51 m travel (a member that exists as `length`, but no JC3 vehicle has one that long at this radius) or a separate mode rate (no member). **UNKNOWN / gap.**

## 9. What can be placed, and what cannot

**Placeable in a private copy (with the error above):** `SuspensionTravelDown 40` -> `front.length`/`rear.length` 0.40 m; `BMWheelSuspensionStiffness 3000` -> `strength` 13.50 s^-2 (+5.8% against the mass anchor); `BMWheelSuspensionDamping 300` -> `compression 1 / relaxation 2` (-31% zeta); `BMFrontWheelSuspensionBias 10` -> `hardpoint_offset_along_spring -0.10` (0.0% against the fleet median).

**No member (gap for BUILD):** the BmAK numbers the JC3 module has no channel for:

1. `BMRearWheelMaxDroop 100` (1.0 m). `length` is a single travel; `min_length` and `max_length_offset` exist as members but are 0 on all 166 vehicles, and 1.0 m would be 2.5x the compression travel. The build must author `max_length_offset` (closest member, unit m) and the engine's reading of it is UNKNOWN.
2. `SuspensionTravelUp 30` (0.30 m). The same single-`length` limitation: JC3 carries no separate bump/rebound travel. Closest: `max_length_offset 0.30`, same UNKNOWN. The alternative is to treat `length` as total travel (0.70 m) - that reading sits at fleet p82.5 for length/radius, against p51.6 for the 0.40 m reading, so 0.40 m is the better-fitting assignment.
3. `PMWheelSuspensionStiffness 750` / `PMWheelSuspensionBias 20` / `StationaryWheelSuspensionBias 5`: no member carries a per-mode spring rate or a stationary bias. The mask has to come from a separate module (/script) in BUILD.

## 10. UNKNOWN, and what would settle each

- BmAK mass unit and the per-vehicle mass: no body setup serialises one; ChassisMass 210.0 is the class default (INERTIA.md:210).
- The unit of BMWheelSuspensionStiffness (3000) and Damping (300): no paired vehicle decodes it; the 210 kg default is the only anchor.
- The semantics of JC3 max_length_offset / min_length: 0 on all 166 vehicles.
- Whether the engine reads hardpoint_offset_along_spring at run time as a rest position.
- PM mode's 750: no JC3 member carries a per-mode spring rate.
