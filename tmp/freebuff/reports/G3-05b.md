```
  MaterialInstanceConstant Batmobile_MK2_Body_MIC                        1106 B tags 5 vectors 4 scalars 2 textures 4
  MaterialInstanceConstant Batmobile_MK2_WheelArchs_MIC_INST             1950 B tags 5 vectors 5 scalars 16 textures 3
  Material               Batmobile_MK2_WheelArch_MAT                   1358 B tags 10 vectors 0 scalars 0 textures 0
  playable slot 2 master: ['Batmobile_Worn']
```

How the slot array is decoded (and why it is not guessed): the array is **not** a property tag.
It is `int32 count` then `count` × `int32` object references in the mesh's untagged data. The
containment oracle: every non-zero reference resolves to a `MaterialInstanceConstant` or
`Material` export of the same package, and no other run of 8+ such references exists in the
first 32 KiB of the payload, so the location is unique. The independent oracle: for the
baseline `Batmobile_V2` the decoded order equals the `Materials[19]` list in
`Working/Appearance/grab/Playable_Batmobile_SF/SkeletalMesh3/Batmobile_V2.props.txt` (an umodel
props dump, not this decoder) — same 19 names, same order, checked on every `--check` run.

Per-slot chains are followed through object references of class `MaterialInstanceConstant` /
`Material` up to the master `Material` (max 8 hops), with each step's
`ScalarParameterValues` / `VectorParameterValues` / `TextureParameterValues` and the master's
`DiffuseColor` / `SpecularColor` / `SpecularPower` / `Normal` / `EmissiveColor` slot →
expression map — the same shape as `MATERIALS.md`, and the master chain for the standard car
reproduces `COLOUR.md`'s body slot (`Batmobile_V3_Mainbody_NEW_MIC` →
`Batmobile_V3_WheelArchs_NEW_MIC` → `Batmobile_Worn`, with `Material0_BaseColour`
`[0.02579, 0.02579, 0.03, 1]` and `Diffuse_Adjust` `[2.2, 2, 2, 1]`, i.e. the T-MA3 value).

## 4. UNKNOWNs (why, and where each would be found)

1. **`Showcase_Batmobiles_Standard`: the mesh's collision asset.** The package carries no
   `PhysicsAsset` export at all (export census by class). Which asset the skin uses in game is
   not in these bytes — it would be a reference from the archetype or the level actor, which
   G3-01 covers for the drivable car only.
2. **`Showcase_Batmobiles_MK2`: the mesh's collision asset.** Same census result.
3. **Slot names (the `FName` beside each slot's material).** The cooked slot element is a
   single 4-byte object reference — there is no name field in the mesh payload, so a slot is
   identified by its material object. `MATERIALS.md`'s slot numbering is the same object order,
   not a second stored field.
4. **The mesh geometry behind the 20 MB of bulk data** (vertex counts, bones, bounds per LOD).
   This card decodes the mesh's property tags, slots, sockets, LOD blocks and collision; the
   bulk vertex/index blocks are not decoded here. `MESHES.md`'s vertex/material counts come from
   an umodel export, a different read. Would need the bulk-data layout.
5. **The 662 bytes that differ after the tag stream** between Standard's and Playable's
   `Batmobile_V2`. The meshes differ in 1,345 bytes total; the tag layouts are identical, all 19
   decoded slot references resolve to the same names, and 2 of the 363 leftover clusters have a
   4-byte reading whose two values resolve to the same object name. The rest are in the bulk
   data where no field is decoded: telling them apart needs the vertex/index/section layout.
   Deliberately **not** summarised as "geometry is identical".
6. **Which skin the drivable car selects, and when.** The packages hold four meshes; the code
   that swaps `Batmobile_V2` for `Batmobile_MK2_Skin` / `Batmobile_Jokerfied_Skin` is not in
   them — it would be a class default or a Kismet action (G3-02 / G3-06).
7. **The on-screen effect of any decoded material difference.** The parameters are decoded; the
   shader that consumes them is not (see `COLOUR.md` for what is missing between a parameter and
   a pixel).

Also open, and deliberately not filled in: what the Jokerfied chassis body's AggGeom bytes after
its two box records are (1,771-byte payload, boxes at byte 92 and 210; header word 3 = 1397 is
larger than any convex count this project's decoder accepts, so `grab_collision_convex.py`'s
convex path is not asserted here), and what `PhysicsAssetInstance`'s 10 `RB_BodyInstance`
objects (2–10 bytes each) hold — they are counted, not decoded.

## 5. Limitations

- No runtime oracle exists in the project; everything here compares files to files. Whether the
  game ever loads these showcase skins, and what they look like on screen, is not measured here.
- The card's `Out` was `SKINS.md`; `SKINS.json` was added as the machine-readable twin (this
  task's own OUT line asks for both), and `--check` keeps the two byte-identical to a rebuild.
