## What was searched, and what was found

Searched: the archive index (`Research/JC3Grab/INDEX.jsonl`, 81,952 entries) for any path naming input,
control, keymap, action, button, keybind, gamepad or joystick — the only matches are
`settings/keymap_gamepad.bin` and `settings/keymap_keyboard.bin` (plus unrelated `*_control_tower_*`
levels and dialogue names). Both exist in **two archive layers** (base and patch), so four files were
decoded. The 232 decoded vehicle `.ee` dumps in `E:/Modding/_shared/gamedata/JC3grab/entities` were then
searched byte-wise for every action name and for `keymap`.

Container decode (decoded from the bytes, not assumed): `RTPC`, version 1; root record at 8 (hash
`AA7D522A`), list record at 20 (hash `49267ABC`), one 12-byte record per binding from 32; each
binding's two 9-byte property records (`7935F00C` = input, `8613CCD3` = action, both type 3 = `stringZ`)
are written inline, then the literal `"PP"`, then whichever of its two names is not already in the
string pool (names are deduplicated), 4-byte aligned. Binding id = the action id: it equals the Jenkins
hash of the action name for 448 of 474 bindings (measured, other candidates 0; the exceptions are stable
across base and patch).

## How an entity selects its scheme, and what it can change

* **Selected scheme**: decoded = the class is the root object of the entity's `.epe` (`CCar`, `CBoat`,
  `CHelicopter`, `CAirPlane`, `CTrain`, `CMotorBike`, from `FORCEPULSE.md` §owners). Measured = **0 of
  232** vehicle `.ee` dumps contain the string `keymap` or any input action name, so nothing on the
  entity side selects or references the binding table. Which class consumes which action is native
  (UNKNOWN).
* **Can change without code**: the graph/objects/states a vehicle carries — entry and exit nodes,
  trigger volumes, seat points, weapon components, and module blocks. Decoded example: the tuning block
  `arcade.nitro_boost` (`torque_multiplier`, `grip_multiplier`, `push_force`, `boost_blend_time`,
  `extra_top_speed`, and their `_upgraded` twins) on **145** of 232 entities.
* **Cannot change**: a button → action binding. The only button → action tables are the two
  `settings/*.bin` files; no entity names them.

exit, and the rest has no JC3 action to map onto.

## UNKNOWNs (with why)

1. **Which action fires nitro / the afterburner** — no action name matches NITRO or (vehicle) BOOST;
   only `WINGSUIT_BOOST` exists. The data side exists (`arcade.nitro_boost` on 145 entities), so the
   trigger is native or in a graph no decoded file names.
2. **Whether `NEXT_WEAPON` / `PREV_WEAPON` reach a vehicle** — both names exist (keyboard only) but no
   file says which mode consumes them; G2-11 found 2 driver weapon slots with no switch action.
3. **How the class-specific action sets are selected at runtime** — the class is the `.epe` root object,
   but nothing in the keymaps or the entities names a class to pick a scheme.
4. **What a turret aims with** — no `TURRET` action exists; `PRECISION_AIM` and the `LOOK_*` axes are
   the only candidates, and the hinge wiring is native (`TURRET.md`).
5. **Whether a replaced `settings/keymap_*.bin` is honoured from a dropzone** — G2-27 showed path
   overrides work for `.ee`, but no test exists for a `settings/*.bin` entry (no game runs here).
6. **Why 26 binding ids are not `H(action name)`** — ids are stable across base and patch for the same
   action, so they were fixed before the current name or by another rule; no decoded file says which.
7. **What the `PP` prefix on the stored input string encodes** — it is on every input string in both
   files; nothing decoded explains it.
8. **Which layer the game loads (base vs patch)** — both are in the install and differ (14 and 22
   binding changes); `MOUNT_RANK` says patch wins a path lookup, but no runtime observation was made.

## Self-corrections the oracles forced (recorded, not hidden)

1. The first layout oracle assumed a per-binding block and a fixed stride; it failed at binding 10 and
   the bytes showed **string deduplication** (an input name shared by several actions is stored once).
2. The first node-hash claim ("not a name hash of either string") was **false**: recomputing
   `hash_jenkins` gave 448/474 hits on the action name. The text was replaced by the measured counts.
3. Two determinism bugs in my own `--check` (tuple→list JSON round-trip; an unsorted set in the evidence
   strings) were caught by `--check` itself and fixed; the third bug found there — a fidelity test that
   searched for the offset bytes instead of reading the string at that offset — is fixed and now reports
   474/474.
