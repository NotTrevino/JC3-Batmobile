# Review — G3-02b (CONTROLS_CONSUMERS)

Independent review. I did not write the card. Read-only: no existing Research/ or Tools/ file was modified; no
game was launched, attached to or memory-read; nothing was built or committed. No earlier review of G3-02b
existed (only `review-G3-02.md` for the parent card), so this is a fresh review.

Subject: `Research/BatmobileGrab/CONTROLS_CONSUMERS.md` + `.json`, generated by
`Tools/scripts/grab_controls_consumers.py` (re-read in full, 460 lines).

Labels used here: **decoded** = re-read by me from the raw source (package export bytes via
`upk_read.Package(path).data(index)`, `pkg.names`, the ini line, or the export record itself); **derived** =
computed here with the rule stated; **UNKNOWN** = not established, with what blocked it.

## VERDICT: minor issues

No wrong value. Every value I re-read from raw bytes matched (7 of 7, including the 5 required spot-checks),
`--check` reproduces both outputs byte for byte, and the card's honesty machinery (labels, unexplained-byte
counts, UNKNOWN list) is genuinely present and mostly well used.

What is not right is confined to **verdict 4 (LB)** and one derivation rule, and it is all in the same
direction — the card claims slightly less than the bytes support, and in one place states an absence as
decoded fact:

1. `verdicts()` line 255 prints a flag that cannot vary (rule defect), and the md presents it as evidence.
2. Verdict 4 says no `DualPlayAction` call site exists. A `0x2B`-prefixed operand equal to the name index of
   `DualPlayAction` sits inside `DualPlayPressed` — the function the card already links to LB.
3. Verdict 4 says "any exit is not decoded". The exit call (`DriverLeave`) *is* decoded, in `DualPlayAction`
   itself, which the card already walks.
4. Verdict 4 calls a 17-byte, 9-unexplained-byte function "with a 0.001 float (decoded)". That float is an
   unaligned byte pattern, not a proven token.

Nothing here is "needs rework": the measured content is correct, and three of the four points above would be
fixed by relabelling rather than re-deriving. But verdict 4's conclusions should not be quoted as written —
they understate the decoded exit path.

## Issues (file, value, why)

### I1 — `Tools/scripts/grab_controls_consumers.py:255`, cited as evidence at the md's *Verdicts §1* — derivation rule cannot vary

Value printed: `BattleMode/PursuitMode state bodies reference aLeftTrigger: False`.

Why: the rule is `r["function"].startswith("BattleMode") or "PursuitMode" in r["function"]`, but `r["function"]`
is a fully qualified path — `pkg.object_path(10546)` is `RVehicleBatmobileBase.BattleMode.Tick` (decoded), which
does not start with `"BattleMode"` either. The first test can therefore never be true, so the printed `False`
is a property of the code, not a measurement of the package, and the md labels it "(decoded walk)".

The conclusion is nevertheless correct: only 5 scripts reference export 107288 (aLeftTrigger) — `CapeGlide.PlayerTick`,
`DrivingMode.IsBatmobileFireButtonHeld`, `DrivingMode.PlayerTick`, `RPlayerController.PlayerTick`,
`RShowcaseCamera.UpdateFrame` — and none is a BattleMode/PursuitMode function (decoded). So: right answer,
non-evidence bullet. Fix: `"BattleMode" in r["function"] or "PursuitMode" in r["function"]`.

### I2 — md *Verdicts §4*, bullet 3 (script line 298) — "no call site for `DualPlayAction` exists in the package (decoded)"

Why it does not hold as stated: the scan only accepts `0x1B` (virtual) and `0x1C` (final) prefixes, and the file
itself reports 9 of `DualPlayPressed`'s 17 script bytes as unexplained. Those bytes are, at export 105001
(decoded):

```
0:61 1:18 2:1e 3:6f 4:12 5:83 6:3a 7:28 8:2b 9:14 10:6d 11:00 12:00 13:4a 14:4a 15:16 16:04
```

Offset 8 is `0x2B` and offsets 9–12 are `14 6d 00 00` = **27924** = `pkg.names[27924]` = `"DualPlayAction"`
(decoded). That token is not in `bmak_damage.py`'s table — which is precisely why the card's walk could not see
it. `0x2B <name index>` is verifiably a *name-literal argument* in this build: in `ToggleBattleMode` (see SC2)
the same token carries 5269/61474 into `TryToChangeMode`, whose only parameter is a `NameProperty`
(export 10551, class `NameProperty`, name `ModeName`, outer `RVehicleBatmobileBase.TryToChangeMode`) (decoded).

Caveat that keeps this an issue rather than a fix: 27924 is *also* a valid export index (`ByteProperty
CanInterrupt.HackType`), so **which index space `0x2B` addresses is UNKNOWN** — I did not prove it is a name
rather than an object. The corpus rate is suggestive but confounded by the two index spaces overlapping
(`0x2B` operands landing in `[0, 84813)` = 12,896 / 18,161 = 0.710, base rate for a random int = 1.97e-05;
`0x1B` = 0.61, `0x48` = 0.47, control `0x4A` = 0.026) (decoded measurement).

Correct label: "no `0x1B`/`0x1C` reference to export 105007; one `0x2B`-prefixed 27924 = name `DualPlayAction`
inside `DualPlayPressed`, token unidentified". The claim "`DualPlayAction` has no call site" should not be
stated as fact.

### I3 — md *Verdicts §4*, bullet 2 (script line 297) — "17 bytes with a 0.001 float … (decoded)"

Why: the float is a byte pattern at script offset 2 (`0x1E` + `6f 12 83 3a` = 0.001f, decoded), but bytes 0
(`0x61`), 1 (`0x18`), 7 (`0x28`), 8 (`0x2B`) and 13–14 (`0x4A`) are not in the token table, so no token boundary
is established for this script — and if `0x18` were `EX_Skip`, the float would sit *inside* its 4-byte operand.
The card's own walk reports 9/17 unexplained bytes. So the float is a **candidate literal**, not a decoded
constant. (The second half of the bullet — "no virtual or final call to an exit function" — is robust: there is
no `0x1B` or `0x1C` byte anywhere in the 17, whatever the alignment.)

### I4 — md *Verdicts §4*, UNKNOWN line (script line 299) — "(or any exit) is not decoded"

This is wrong, and it is the most load-bearing error in the card, because it understates what the tool already
decoded. From the tool's own walk of `DualPlayAction` (export 105007, script 1199 B) (decoded):

```
0x1B VCALL  DriverLeave                        @ 1054
0x1B VCALL  RemoveBatmobileBindsAndSetBatmanBinds @ 932
0x1B VCALL  SwitchPlayer                       @ 223
0x1C FINAL  Core.TriggerEventClass             @ 47 and @ 128  (arg OBJCONST RSeqEvent_BatmobileRiddlerButton)
```

`EjectFromVehicle` (104931) *also* `0x1B`-calls `DriverLeave` (offset 365) (decoded). So the vehicle-exit call is
named twice in the package, once inside the very function the card says contains "no exit". What is genuinely
missing is only the LB → `DualPlayAction` link.

Related omission, same verdict: `RPlayerController.DualPlayPressed` (export 105768, class `Function`, outer
`RPlayerController`, script 636 B, size 674 B) appears in the card's own `vcall_sites` table
(`DualPlayPressed`: … `RPlayerController.DualPlayPressed@37`) but is never mentioned in any verdict. Its body
(decoded) `0x1B`-calls `DualPlayPressed@37` (the DrivingMode state function), `SwitchPlayer@497`,
`CallBatmobileToMe@629`, `CanDoCombat@169`, `IsFiring@442`, `DualPlayTakedown@484`, `CanGlideAttack@530`,
`CanPerformNextComboMove@619`. That is the only function in the package whose name equals the LB command's
`DualPlayPressed`, and it is the natural script-side handler.

### I5 — `precise.TryToChangeMode_names` (script line 319) — the "derived" parenthetical is a tautology

Label text: "decoded name indices; the calls in ToggleBattleMode pass them as 2B-tokened operands (derived: the
name index equals the state name in the names table)". The parenthetical restates how 5269/61474 were chosen
(`names[i] == state name`), so it proves nothing about the calls. The evidence it wants does exist and I
verified it (offsets 151 and 194, `0x2B`-prefixed, right after the final call to 10552) — the label should be
`decoded (ToggleBattleMode offsets 151, 194)`, not `derived`. Value correct, reasoning mislabelled.

### I6 — md *Bindings* section (script line 409) — silent truncation

`A("- %s %s" % (k, v[:240]))` cuts binding text at 240 characters with no marker. Line 270 (`XboxTypeS_Y`) is
rendered ending `… | Button bVehicleBoostButton | TogglePhysImpact | Han` — the word `HangFromVantagePoint` is
cut mid-word, and a reader of the md cannot tell the command list continues. The json holds the full line. Purely
cosmetic; the affected line is not the subject of any verdict.

### I7 — `precise.LT_threshold` key name (script line 316) — asserts more than the value proves

The key names the value a threshold; the label is careful ("operator UNKNOWN, so whether it is a hold threshold
is UNKNOWN"). 0.05 is decoded at offset 257 (SC4) and is adjacent to `aLeftTrigger`/`LastTriggerAmount` reads,
so the placement claim is fine — but the only place a *threshold* is asserted is the key name. Nit: key should
be `IsBatmobileFireButtonHeld_float_const`, or the value listed without "threshold" in the key.

### I8 — md *Command names in the package* — scope of a completeness claim

The list is the tool's hand-picked 16 names. The commands actually on the LT and LB lines are not all in it:
`DeepScanOut` (name 22120), `DebugMenuQualifyOnT` (21997), `DebugMenuQualifyOffT` (21995), `DebugMenuPrevPage`
(21991), `DualPlay` (27922), `BatmobileSonar` (5127), `CallBatmobileToMe` (14685) all exist in the name table
(decoded), and three of the four LT-page commands are referenced as calls (`SpecialMove.DeepScanOut`,

not make verdict 1 wrong — none of them is a mode switch — but "no mode command is bound to LT (decoded)" is
only proven over the card's own list, not over the line. Should say so.

## Resolvable UNKNOWNs

Each of these is answerable from the bytes already on disk; none needs the game.

- **R-a — what `0x2B` (and `0x4A`) are.** `0x2B` is not in `bmak_damage.py`'s table, yet it carries name indices
  into a decoded `NameProperty` parameter twice in `ToggleBattleMode` (151, 194) and appears 18,161 times corpus-
  wide with a 0.710 name-range rate. Adding a table entry and re-running would (a) turn the `DualPlayPressed`
  → `DualPlayAction` link from UNKNOWN to decoded or refuted, and (b) remove the `0x4A` "unexplained byte" from
  every QuickGadget/ReleaseQuickGadget walk. How to settle the index space: resolve the same operand both ways in
  the two `ToggleBattleMode` sites where the target parameter type is known (`NameProperty`, export 10551).
- **R-b — which call consumes the `"DualPlayAction"` literal.** `DualPlayPressed`'s 17 bytes still hold `0x61`,
  `0x18`, `0x28`, `0x4A 0x4A` unidentified. `0x4A` occurs exactly once in the proven `QuickGadgetB` call
  (`1B 69312 26 4A 16 04`) between the last argument and `0x16`, so it is an argument/parm marker (derived from
  position, not decoded). Decoding `0x18` as skip-vs-float matters: it decides whether the 0.001 is a real
  literal (I3).
- **R-c — LB's script-side handler.** Read `RPlayerController.DualPlayPressed` (105768) bytecode. With R-a/R-b
  settled, the LB chain has bytes for every link (`exec DualPlayPressed` → state `DualPlayPressed` →
  `DualPlayAction` → `DriverLeave` / `SwitchPlayer` / `RemoveBatmobileBindsAndSetBatmanBinds`) and the only
  remaining gap is the engine's command→function dispatch, which is a different (native) question. This is
  strictly more than the card's "no route decoded".
- **R-d — "weapon class per mode".** Not merely unresolved: I compared the three property exports (decoded).
  `BattleModePrimaryWeapon` (export 9850) and `PursuitModePrimaryWeapon` (9851) are `ObjectProperty` exports
  under `RVehicleBatmobileBase` whose 34-byte payloads differ **only** in the 4-byte word at +2 (9849 vs 9850,
  i.e. their own predecessor index); the other 30 bytes are identical (`01000000 00000000 01000000 d5450100 …`).
  `SecondaryWeapon` (9859) carries zeros where they carry `01 00 00 00 01 00 00 00 d5 45 01 00`. So the package
  holds no *per-mode-distinguishable* weapon value here: the `d5 45 01 00` word = 83413 is the same for both
  modes and what it references is UNKNOWN (the property-export payload layout is not decoded by me — flagged as
  a limit below, not as a finding). To get the weapon classes you need the `Default__RVehicleBatmobile` CDO tag
  stream (`upk_read.walk_tags`) or runtime. The card's UNKNOWN stands; it can now say *why* (identical defaults)
  instead of "not resolved here".
- **R-e — make the LT/LB negative claims exhaustive.** Decode the consumers of the seven LT/LB-line commands
  that exist in the name table (I8). That converts "no mode command is bound to LT (decoded)" from a
  list-scoped statement into a property of the whole binding.
