# RC5 size-pin reconciliation - the RC4 `.ee` and `receipt.json`

Date: 2026-11-08. Offline, read-only on `Builds/bm-RC4`. Every figure below was re-derived from the
bytes with `stat` + SHA-256; nothing was copied from an earlier report. The only files written are
`Tools/scripts/rc4_pins.py`, `tmp/freebuff/rc5-pins.json`, `tmp/freebuff/rc5-stale-pins.json` and

**The artifact is 11,225,533 B / `b72690d3…`.** The build's own receipt is the witness twice over:
its `steps[7]` literally reads `packed v0300_car_kensington_sportsmuscle_debug.ee (11,225,533 B), 696
listed files round-trip, .toc 714 records`, and its `files[0]` records `bytes: 11225533` with
`sha256: b72690d3…`, which is what the file on disk hashes to. `install.ps1` pins the same 64-hex
digest for the same path. All 9 drop entries rehash to their receipt values.

**Neither 11,225,532 nor 11,225,534 is an artefact of counting the current file.** A tree-wide scan
of every `.ee` under `Builds/` (97 files) finds **exactly one** at 11,225,533 B - the RC4 payload - and
**none** at 11,225,532 or 11,225,534 B. Both retired figures belong to revisions that were packed over:
build-d13 recorded 11,225,534 B together with sha `a233c93d…`, a digest the shipped file does not
have. The "+1 B / -1 B" reading is therefore a coincidence of two successive revisions, not a
trailing-byte miscount of this one. Whether build-d13's +1 byte was a real byte or a counting slip in
the packer is **UNKNOWN** - those bytes no longer exist anywhere in `Builds/`, so it cannot be tested.

`Working/Q` does **not** carry 11,225,534: `Working/Q/APPROVAL_REQUEST.md:17` already says
11,225,533. The pin that is stale is in `Tools/scripts/v01_rc4.py`'s **docstring** (line 7) and in
build-d13, not in `Working/Q`. The receipt is not 215,445 B either; that figure exists only in V-01's
report and the operator digest.

## 1. How this was measured

```
python Tools/scripts/rc4_pins.py --write   # WRITE_EXIT=0
python Tools/scripts/rc4_pins.py --check   # CHECK_EXIT=0
  PASS: tmp/freebuff/rc5-pins.json matches the bytes (763 files re-hashed)
```

`rc4_pins.py` derives every pin with `os.path.getsize` and `hashlib.sha256` over the file (8 MiB
chunks), reads `receipt.json` as the witness, and then scans `Tools/scripts`, `Working/Q`,
`Working/Translation`, `tmp/freebuff/queue/done` and `tmp/freebuff/reports` for every literal that is
not the authoritative one. `--check` re-derives and compares; stale literals print but do not fail,
because they are the expected state until RC5 replaces the pins.

## 5. Timeline that explains all five figures

| when | event | `.ee` | `receipt.json` |
|---|---|---|---|
| build-d13 | `bm_rc4.py` packed after registering 12 unlisted overlay files (`11,188,402 → 11,225,534 B`) | 11,225,534 `a233c93d…` | 211,711 `8c361822…` |
| 12:27 | V-01 reads a tree that is being rebuilt (it sees 0 B, then a missing file, then 11,225,532) and writes its report | 11,225,532 | 215,445 |
| 12:59:52 | final pack lands | **11,225,533** `b72690d3…` | - |
| 13:00:07 | `install.ps1` + `receipt.json` written from that pack | - | **217,652** `1812e436…` |
| 13:01:54 / 13:02:26 | V-01's script pins and `verify/files.{md,json}` regenerated against the settled tree | 11,225,533 | 217,652 |
| 20:32-21:00 | V-06 and the digest quote the brief's 11,225,534 / `df23485d…` and V-01's 215,445, without re-statting them | 11,225,533 measured | 215,445 repeated |

So the "three numbers in circulation" are one artifact, one superseded artifact, and one pre-final
read. The receipt's 2,207 B growth from 215,445 to 217,652 is the final write, not corruption.

No `DELTA vs the pinned build-d13 facts` suffix: every term of `want = {ee: 11225533, toc: 68675,
install: 6535, receipt: 217652}` equals the bytes, the 9 drop entries match the receipt, and all 696
`aaf` hashes match. **The verdict is GREEN.** The RED in `verify-v01-file-gates-rc4.md` is a stale
page: its script was corrected at 13:01:54 and its generated record regenerated at 13:02:26, but the
prose report at 12:27 was never rerun, so the chain kept quoting a failure that no longer exists.

This does not make RC4 green overall: V-03's 7 dangling values and the T-ST7 miss remain open, and the
runtime is still untested.

## 7. The RC5 consumer

`python Tools/scripts/rc4_pins.py --write` writes:

* `tmp/freebuff/rc5-pins.json` - schema 1, `build`, `derived_from: "bytes on disk"`, `pins` (ee,
  ee_toc, install_ps1, install_sha256 + hex length, receipt_json, drop_files, drop_total_bytes,
  tree_files, tree_total_bytes, aaf_files), `witness` (receipt's own claim and whether it agrees) and
  the full `drop` list with `path`, `drop_path`, `bytes`, `sha256`.
* `tmp/freebuff/rc5-stale-pins.json` - the same pins plus every scanned `row` (`file`, `line`, `pin`,
  `literal`, `state`, `why`).

`--check` re-derives all 763 files and exits 1 on any drift from `rc5-pins.json`, so RC5 can consume
the list knowing it still describes the tree.

## 9. UNKNOWNs

* **Whether build-d13's +1 byte (11,225,534 vs 11,225,533) was a real byte.** The `a233c93d…` payload
  is not in `Builds/` (97 `.ee` files checked: only 11,225,533 survives), so the "writer counting a
  trailing byte" hypothesis cannot be confirmed or refuted - only that the two figures belong to
  different payloads.
* **What `df23485d…` is a truncation of.** It is 32 hex and matches neither the shipped installer's
  SHA-256 nor its MD5; build-d13's table labels the column `sha256 (32)`, so it is a rendered
  truncation, but of which revision of `install.ps1` is not recoverable from the tree.
* **Why V-06 quoted the brief's numbers at all.** Its own table measures 11,225,533 B, so the
  quotation is disclosure, not measurement; the 215,445 B figure is not in V-06 at all - it comes from
  V-01 and the digest.
* **Runtime.** Nothing here says the car loads; the test ban stands.
