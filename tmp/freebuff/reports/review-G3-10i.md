# review-G3-10i — the runtime behaviour of a constraint with an absent second body

**VERDICT: minor issues.**  Every instruction, branch target, stride and field the card quotes
for the loop at `0x141569d00` is byte-exact: the six invalid-body branches really do all land on
`0x141569fc1` (`add rbx, 0x18`), the loop body contains exactly one call (the add) and no store,
nothing substitutes a fixed/root/chassis body, and the sentinel the loop tests is byte-identical
to the value stored in 494/494 fleet records.  But the card's completeness claim — "only one
function tests both body offsets", used as evidence that no other consumer can repair an invalid
body — is **false**: there are **two**.  A second 24-byte-record walker at
`0x1415e6030-0x1415e6651` tests `+0xc` and then `+8` against `0x7fffffff`; its sentinel branches
go to an error-report block, not to a body, so the conclusion survives.  Two smaller statements
are also wrong (`hknpWorldCinfo` members shown as "exactly these" are 7 of 25; the two name
strings are listed against the opposite addresses).  No conclusion needs to be withdrawn; two
evidence sentences must be corrected.

## Method, and one caveat about ordering

The brief asked me to write down the branches without looking at the card's table first.  That
ordering was not achievable as stated: the brief's first instruction is to read the card, whose
table was in the file.  The mitigation is that the branch table below is produced mechanically
from the section bytes and is asserted by `--check`, and that the `.text` scan was re-implemented
with a *wider* rule than the card's — which is exactly what found the second function.  So the
decode is independent of the card's text even though the card was read first.

## Claim 2 — the six invalid-body branches land on the loop increment `0x141569fc1`

**Holds, 6/6, at exactly the addresses quoted.**  My decode of every conditional branch in the
function gives 22 branches; six target `0x141569fc1` and the other 16 target the body-prep loops
or the loop entry/exit.  The six:

| branch | encoding | target |
|---|---|---|
| `0x141569f74 je` | `74 4b` | `0x141569fc1` |
| `0x141569f81 jae` | `73 3e` | `0x141569fc1` |
| `0x141569f94 je` | `74 2b` | `0x141569fc1` |
| `0x141569f9f je` | `74 20` | `0x141569fc1` |
| `0x141569fa3 jae` | `73 1c` | `0x141569fc1` |
| `0x141569fb2 je` | `74 0d` | `0x141569fc1` |

and the target is `add rbx, 0x18` (`48 83 c3 18`), i.e. the next record.  The card's guard table
matches this address for address, including the sentinel/range/live order for `+0x08` and then
`+0x0c`, the `and edx, 0x3fffffff` mask and the `lea rax,[rax+rax*8]; add rax,rax` scaling to the
0x90-byte body stride.  A reader counting calls in `0x141569f34-0x141569fc8` will see two; the
second, `0x141569f57 call 0x141520f70`, is the pre-loop capacity growth (`cmp [rsi+0x130], edi` /
`jae`), outside the loop body — my first wider span counted it and the narrowing resolved it.

## Claim 3 — nothing substitutes a fixed or root body (the record is dropped)

**Holds inside the loop**, three ways:

1. the loop body `0x141569f60-0x141569fc8` is 29 instructions, contains **one** call
   (`0x141569fbc call 0x1414e7200`) and **zero** stores;
2. the only write to `r8` (the cinfo pointer, which becomes the add's third argument) is the
   per-iteration `0x141569f67 lea r8, [rbx + rax]`; after the guards it is not reloaded;
3. the only `0x7fffffff` immediates in the whole function are the two body tests
   (`0x141569f6f cmp eax, 0x7fffffff` = `3d ff ff ff 7f`, `0x141569f9a` = `3d ff ff ff 7f`).

Supporting sites also reproduce: the add's only sentinel constant is `0x1414e7229
cmp dword ptr [rcx + 0x13c], 0x7fffffff` (the card's free-list head) and its `.pdata` range ends
exactly at the card's `0x1414e735e`, so the scan range is not truncated; the copy helper
`0x141557a30` (`.pdata` `0x141557a30-0x141557bf9`) contains no sentinel constant; the body ids
are stored verbatim at `0x141557aca mov dword ptr [rbp], edi` / `0x141557acd mov dword ptr
[rbp + 4], ebx`.

The card's negative claim about `hknpWorldCinfo` (`0x142dbb758`, `0x100`) also holds — no member
is a body id, only the buffer members `bodyBufferCapacity +0x0` and `userBodyBuffer +0x8` — but
the table is **not** "exactly these members": the registry record carries **25**, including
`materialLibrary +0x38`, `gravity +0x60`, `broadPhaseAabb +0x80`, `collisionFilter +0xa8`,
`solverTau +0xc4`.  The card's truncation is presentation, not a wrong negative.

## Claim 4 — "only one function tests both body offsets" — **refuted**

My scan (follows register copies, accepts indexed addressing and direct-memory compares, window
16) finds **two** functions that test both `+0x08` and `+0x0c` against `0x7fffffff`:

```
0x141569d00-0x141569ff0   compares 0x141569f6f (+0x8), 0x141569f9a (+0xc)
0x1415e6030-0x1415e6651   compares 0x1415e61bc (+0x8), 0x1415e60f9 (+0xc)
```

The second one is a record walker of the same shape, and its raw bytes are unambiguous:

```
0x1415e60f0  498b7050               mov rsi, qword ptr [r8 + 0x50]      ; 0x18-stride array
0x1415e60f4  49637c360c             movsxd rdi, dword ptr [r14 + rsi + 0xc]
0x1415e60f9  81ffffffff7f           cmp edi, 0x7fffffff
0x1415e60ff  0f844d020000           je 0x1415e6352
0x1415e61b7  4963743608             movsxd rsi, dword ptr [r14 + rsi + 8]
0x1415e61bc  81feffffff7f           cmp esi, 0x7fffffff
0x1415e61c2  0f8436010000           je 0x1415e62fe
0x1415e62dd  4983c618               add r14, 0x18
```

Both sentinel targets (`0x1415e6352`, `0x1415e62fe`) start an error-report block
(`mov r8d, 0x200`; `call 0x14119c010`; `call 0x1411b77f0`; `mov r9d, <line>`;
`call 0x14119bf50`) and then `jmp` to the function exit — so this consumer treats a sentinel body
id as a **fatal error**, not as "no body", and substitutes nothing.  That is why the card's
conclusion survives while its evidence sentence does not.

Cause of the miss: the reviewed scan matched the operand text `[reg + 8]` / `[reg + 0xc]` only.
Here the load is `[r14 + rsi + 0xc]`, an indexed form, so it never matched.  This is the same
class of defect as G3-10h's own documented "defect 1" (a regex over capstone's operand spelling).
The card's counts (1407 functions / 843 comparisons / 8 sites) and mine (1407 / 853 / 31) differ
in rule width, not only in this one site; but "one function tests both" is a claim about the
image and it is wrong.

Consequence for the card's argument: the paragraph "there is exactly one place in
`JustCause3.exe` where a record's two body ids are both read and checked against the invalid
marker" must be replaced, and the row in the report's table ("only one function in the image
tests both body offsets … 1 function tests both") is wrong.  The load-bearing derivation is
unaffected, because the second consumer rejects the sentinel rather than repairing it.

## Claim 5 — the `0x7fffffff` tested is the value stored in 494/494 records

**Holds.**  Independent re-sweep of `E:/Modding/_shared/gamedata/JC3grab/**/*.physicsc`: 50 files with
records, 494 records, `bodyB == 0x7fffffff` in 494, `bodyA == 0x7fffffff` in 0, no out-of-range

## What I could not check

1. **Whether the object passed in `rcx` is a `hknpWorld` or a `hknpPhysicsSystem`.**  The card
   calls `rsi` the *system* in §2 and the *world* in §3, and names `0x1414e7200`
   `hknpWorld::addConstraint` from the two source strings alone (`hknpworld.cpp`,
   `Unsupported constraint type…`).  The instruction evidence proves *an* add on that object, not
   its class.  This is a labelling tension in the card, not a decode error; where it would be
   settled: a class-registry record for `hknpPhysicsSystem` with a size matching the `0x690`-byte
   allocation, or a vtable at `[rsi]` with a matching name reference.
2. **Whether `[rsi+0x2c] & 0x3fffffff` is a capacity**, and whether bits 0..1 of the body's
   `+0x40` byte mean "live".  Both are readings of the guard; the branch *targets* do not depend
   on them, so the drop conclusion is unaffected.  Would be settled by the body writer's use of
   the `+0x40` byte and of `[+0x2c]`.
3. **Whether a loader rewrites `+0xc` on the way into memory.**  My re-sweep reads the file bytes;
   if an in-memory rewrite existed, the derived "494 rejected / 0 survive" would change.  No
   writer was searched.  The card's own UNKNOWN 2 says the same.
4. **What the second consumer's records are.**  Its array is at `+0x50`/`+0x58` (not
   `+0x140`/`+0x148`) with the same 0x18 stride and the same `+8`/`+0xc` ids; whether that is an
   `hknpConstraintCinfo` array of another object or a different class with the same shape is not
   decided here.  `hknpPhysicsSystemData` did not resolve as a registry name in my parse, so I
   could not tie the two arrays to one schema.
5. **The 0x80-byte body-cinfo source stride** in the card's §2 prose.  I confirmed the
   `[r15+0x130]`/`[r15+0x138]` slots and the `0x90` runtime stride, not the `0x80` input stride.
6. **Who dispatches the walker** (the card's UNKNOWN 1).  Not re-investigated: it does not bear on
   the guard.
