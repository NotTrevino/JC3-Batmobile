# G3-04e1 - the on-disk format of the material uniform records

STATUS: done

The 6,934 records are **not** a table with a stride or a length prefix. Each record is
self-delimiting, and its length is *derived* from its own fields:

```
record :=  i32    n          ; 2..300, length of the name INCLUDING its NUL
           u8[n]  name       ; printable ASCII, name[n-1] == 0
           u8[16] guid       ; distinct per record
           u8[16] zero       ; 0 in every record
           u32    count      ; 1..64
           entry[count]

entry  :=  u32 class        ; FName index, 2040..2055 (FMaterialUniformExpression*)
           u32 class_number
           u32 parameter    ; FName index into the package name table
           u32 param_number
           f32[4] value     ; 16 B, for the vector class

span   =  40 + n + 32 * count
```

The layout is proven at every candidate offset of the region, not at one example: the
header predicate accepts **7,278** offsets, of which **6,966** are all-vector records
(**9,582** entries) that satisfy `span == 40 + n + 32*count` with no overlap. 32 B is the
only entry stride that resolves every class word (28 and 36 fail on all 592 records with
`count >= 3`).

**The brief's 6,934 is a subset, not the population.** It is exactly reproduced (6,934)
by re-running G3-04d's own rule - a name regex capped at 60 characters plus its width
table - over these 7,278 headers. G3-04e's 6,943 likewise (80-character cap, 16-byte
entries only). The layout itself accepts 6,966. The 32 names G3-04d's regex cannot match
at all are listed in `UNIFORM_FORMAT.md` section 7 (long names such as
`Grate_Steel_Liftable_MATGRATE_Church_Liftable_DEBUG_SUPERBRIGHT`, and names starting
with a digit or containing `-`, `#`, `/`).

The format stops at **`0x8ac162b`**, entry 3 of `Joker_Young_Shirt_MASTER_MAT`
(record at `0x8ac1586`): the entry is `FMaterialUniformExpressionAppendVector`, and where
a parameter FName and a value should be it carries **further class FNames**
(`FoldedMath`, `FoldedMath`, `ScalarParameter`) - a nested expression tree whose encoding
(operand order, per-class payload, termination) is UNKNOWN. 312 of the 7,278 headers
leave the 32-byte entry shape for that reason, and they are not decoded.

Scope respected: nothing here says what a record computes or how a parameter reaches a
constant-buffer slot.

## What each value is

**decoded** (bytes at a stated offset, or an install file):

| value | source |
|---|---|
| record region starts `0x8ab3e03` (end of the DXBC container run), first header `0x8ab4005` | `CombinedShaderCache-PC-D3D-SM5.upk` export 1, offsets |
| name length word, name, guid, 16 zero bytes, count, entries | the layout above; `UNIFORM_FORMAT.md` section 3, one offset per field per record |
| 7,278 header-accepted offsets, 6,966 all-vector records | the predicate at every one of the 13,486 candidate offsets |
| 9,582 entries, all `FMaterialUniformExpressionVectorParameter` (FName index 2055) | entry class words |
| class FName number `0` in all 9,582 entries; parameter FName number in `{0,2,3,4,5}` | entry words 2 and 4 |
| `Batmobile_Worn` at `0x8bc1f56`, guid `5e56a7942acfba4493fbad0c769a1976`, 14 entries | record bytes |
| 514 B between container run and first record (`e71fbcf9be6f3b1b...`) | file bytes |
| 6,934 / 6,943 / 6,966 | three acceptance rules over the same headers |

**derived** (arithmetic on the above):

| value | rule |
|---|---|
| `span = 40 + n + 32 * count` | 4 (length) + n (name) + 16 (guid) + 16 (zero) + 4 (count) + 32*count |
| Σ record spans 764,817 B = 7.7% of the 9,893,119 B region | sum of spans over 6,966 records |
| 9,127,700 B outside record spans; 88 B tail | region − (prefix + spans + tail); gaps between records |
| record ends at `0x94232aa`, file at `0x9423302` | offset + span of the last record |
| 312 headers leave the shape = 206 `AppendVector` + 78 `FlipBookTextureParameter` + 28 `FoldedMath` | class word at the first non-vector entry |
| anchor cross-check 12 of 12 at 1e-4 | record RGBA vs `COLOUR_PARAMS.json` declared defaults |

**UNKNOWN** (not in the bytes; where it would be):

1. **The nested-expression entry encoding** (`AppendVector` and the like). 312 of 7,278
   headers. The entry starts with a class FName and then continues with operand class
   FNames of varying width, so its own width depends on a tree. Would need the cooker's
   serialiser for `FMaterialUniformExpression*`, which the project does not have.
2. **The single byte before a nested expression in the post-record block** at
   `0x8bc225d` (`0x02`, then `0x803` = `ScalarParameter`). It sits *after* the record, so
   it does not affect any record's extent; its meaning is not decoded. Same class of
   unknown as (1).
3. **What the 16 zero bytes at `+20+n` mean.** Zero in all 7,278 records, so four u32
   zeros, two u64 zeros and one 16-byte zero field are indistinguishable from the bytes.
4. **The 9,127,700 B that is not record span** (92% of the region). The header predicate
   was tested at all 13,486 candidate offsets, so no further record header exists there
   under this layout; whether some non-record structure of another shape lives there is
   not decoded (that is the per-material payload, G3-04e's blocks and material data).
5. **The mapping from a parameter name to a `cb0` slot.** Out of scope by the brief, and
   absent from the caches: 0 `RDEF` in 38,201 + 2,098 DXBC containers
   (`SHADER_COMBINE.md`). The record carries no slot field: after `count` entries the
   record is exhausted.
6. **Why guids recur outside the record.** Each of 200 sampled guids occurs >= 2 times in
   the file (the record plus material-asset sites); the other sites are not decoded here.

## The cross-checks, and what would fail if the split were wrong

| oracle | result | fails if |
|---|---|---|
| string length words match the strings | 7,278/7,278 (`n == len(name)+1`, NUL at `n-1`, all bytes printable) | the length word is not a length |
| every reference is in range | 0 of 9,582 parameter indices outside the 5,058-name table; 0 class indices outside 2040..2055 | the entry is not two FNames + value |
| declared counts sum to the decoded entries | 9,582 declared = 9,582 decoded | `count` is not the entry count |
| span formula | 6,966/6,966 records: `span == 40 + n + 32*count` | any field is missing, extra or mis-sized |
| stride | 32 B valid in 592/592 records with count >= 3; 28 B and 36 B in 0 of them | the entry is not 32 B |
| record boundary | the u32 immediately after every record is a plausible next-list count (<= 512) in 6,966/6,966 | the record ends anywhere else |
| no overlap | 0 record overlaps; starts strictly increasing; last end `0x94232aa` <= EOF | records share bytes |
| round-trip | the 30 samples re-parse from their own printed hex, 30/30 | the rendering or the split is off |
| count reconciliation | 6,934 and 6,943 reproduced from these same 7,278 headers | the three passes counted different structures |
| anchor identity | `Batmobile_Worn` found by guid; 12 of 12 vector defaults match `COLOUR_PARAMS.json` at 1e-4 | the record is a lookalike |

Note on the anchor: this card cross-checks **12** vectors, not the 7 G3-04d reported,
because `COLOUR_PARAMS.json` now carries 18 vector defaults for `Batmobile_Worn` and 12 of
the 14 record entries are among them. 0 mismatches.

## Changes to the script (and how to revert)

`Tools/scripts/grab_uniform_format.py` is this card's own script, pre-existing from an
interrupted run. Its *logic* needed no change - all 15 oracles already passed against the
install file. Three prose/rendering defects were corrected, because an unmodified
`--check` would have republished them as fact:

1. **Docstring** said 241 `AppendVector` + 71 tiling records; the code measures 206
   `AppendVector`, 78 `FlipBookTextureParameter`, 28 `FoldedMath`, of which 51 tile with
   borrowed widths (33 of those landing on a plausible next count) and 261 never tile. It
   also pointed at "section 7" for the stop, which is section 8. Change: that paragraph of
   the module docstring. Why this file: it is the card's own generator, and the docstring
   is the text a reader trusts first.
2. **Oracle O10** was named "the region's bytes are fully accounted for", which was
   vacuous (gaps were *defined* as the remainder). Renamed to state the partition and to
   add the record share (7.7%) and the fact that the predicate was tested at all 13,486
   candidate offsets, so no further record header hides in the remainder. Change: one
   entry in the `checks` list.
3. **Section 2 rendering**: my first attempt at the record-share note spliced a paragraph
   between two table rows and printed a literal `7.7%%`. Change: one block in `render()`;
   the note now follows the table and the percentage is computed, not hardcoded.

Revert: each is a single textual block in that one file - restore the old `checks` entry,
the old `render()` block, and the old docstring paragraph (the originals are quoted in the
`--check` output above: the old O10 detail line "514 B prefix + 764817 B proven records +
9127700 B between them + 88 B tail == 9893119 B region"). No other file changed, so no
other revert is needed. The logic that produces 7,278/6,966/9,582/6,934/6,943 was
untouched by all three edits.
