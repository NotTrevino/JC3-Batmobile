## Issues

### 1. The JSON's verdict sentence uses a different denominator from every other surface

`WEAPONS.json` → `verdict`: "**0 of 332 fields** compared across the 18 multi-variant objects
differ"; the same file's `counts` has `variant_fields: 332` **and** `variant_comparisons: 1065`, and
`WEAPONS.md` §3 says "**0 of 1065 field comparisons differ**" while the MODLOG says "1,065 field
comparisons, 0 differences". Both numbers are right (332 field slots compared across their
instances), but the verdict's wording ("fields compared") reads as a contradiction with the 1,065 in
the `.md` and the log. Generated by `grab_weapons.py:690-704`; a wording fix ("0 of 332 field slots
differ across 1,065 comparisons") makes the three surfaces agree.

### 2. The MODLOG's quoted output and file sizes no longer reproduce

`MODLOG.md` G1-08 block quotes `wrote … WEAPONS.json (589,459 bytes)` / `WEAPONS.md (112,106 bytes)`
and a PASS line ending at "0 variant differences". Today the files are **728,842** / **150,104 B** and
the PASS line carries the projectile/FX/AkEvent clauses. The cause is documented elsewhere —
`GRAB_BACKLOG.md:1277` shows G1-09 done and its product is "`WEAPONS.md` §4", i.e. the same two files
were extended — but the G1-08 section itself does not say so, so a reader comparing the quoted run
with a re-run sees a mismatch with no adjacent explanation. The card's Done still holds; this is
record currency, not a wrong value.

### 3. The Done's "one section per class" and "every reference resolves or is listed" are not asserted

`--check` gates only the two files' bytes. That the `.md` has one section per class is structural, and
that references partition into `resolved`/`missing-object` is structural too (`collect()` assigns one
of the two), so nothing is currently wrong — but if a future edit silently skipped a class, or emitted
a third status, `--check` would happily regenerate the same self-consistent output. A cheap
`raise`/`assert` on `len(sections) == len(classes)` and `set(statuses) == {"resolved",
"missing-object"}` would turn the Done's two prose halves into gates.

### 4. Minor: §12's product cell names only the `.md`

`GRAB_BACKLOG.md:1276`: `| G1-08 | done | Research/BatmobileGrab/WEAPONS.md + MODLOG §"G1-08 · Weapons
record written" |`. The card's `Out` is `WEAPONS.json`, `WEAPONS.md`, `grab_weapons.py --check`; the
`.json` and the script are not in the row, so a reader following §12 alone would not know the machine
record exists. The MODLOG block names all three.

### 5. R5 / R4 audit: clean, with the one interesting case verified

The card's gadget quantities all come from member paths (`RBatmobileCannon.ChainGunDamage`,
`RVehicleWeapon.FiringInterval`, …), and the 26 bit-packed bools are kept as `offset 0x…` in §21
rather than given names. The Joker 999 is a real field, not a name-match: `path:
RBatmobileCannon.ChainGunDamage`, `offset 2916` (0x0B64), `type: IntProperty`,
`named_by: sdk-layout`, which is also the `.md` §8 row `| RBatmobileCannon.ChainGunDamage | 0x0B64 |
IntProperty | 999 |`. The two quantities the card names that the grab does not carry
(`Projectile.LifeSpan`/`Lifetime`, `InaccuracyVsHeat`) are recorded as 0 matching fields and not
claimed — the card's own Stop rule, honoured.
