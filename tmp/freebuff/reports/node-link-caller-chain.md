# Does a caller chain of `0x1400a9690` reach a container or global that holds the spawned node?

**One question, one answer.** `Research/JC3Grab/RUNTIME_LAYOUT4.md` §7 / UNKNOWN 1 left
**`0x1400a9690`** open: it writes an 8-byte value at both `+0x150` (`0x1400a97f6`) and `+0x158`
(`0x1400a97e8`), the widths §3's readers load. This card answers whether its caller chain reaches a
container or global holding the spawned node.

**Answer: UNKNOWN — no chain reaches such a container or global, and the candidate itself is REFUTED
as the node writer.** `0x1400a9690` is a **constructor**, and the 8-byte value it stores is the
constant **0**. It is a null initialiser, not a node:

```
1400a96ba  33 d2                 xor edx, edx          ; rdx = 0
...
1400a97e8  48 89 93 58 01 00 00  mov qword ptr [rbx + 0x158], rdx
1400a97f6  48 89 93 50 01 00 00  mov qword ptr [rbx + 0x150], rdx
```

`RUNTIME_LAYOUT4.md`'s width oracle could only see that 8 bytes are written. Read at the register
level, those 8 bytes are zero.

Full card: **`Research/JC3Grab/RUNTIME_LAYOUT5.md`** (+ `.json`), generated by
**`Tools/scripts/jc3_runtime_layout5.py --write`**, re-derived and compared by `--check`.
`RUNTIME_LAYOUT4.*` was not touched (md 27,107 B, json 306,468 B, both unchanged).

## 2. Direct callers of `0x1400a9690` — one, with bytes

| site | function | kind | call-site bytes | instruction |
|---|---|---|---:|---|
| `0x14015e603` | `0x14015d310`..`0x14015ff03` | `call rel32` | `e8 88 b0 f4 ff` | `call 0x1400a9690` |

The caller prepares it as an **allocate-then-construct**, and the object arrives in `rcx`:

```
14015e5ec  b9 d8 02 00 00           mov ecx, 0x2d8        ; 728-byte object
14015e5f1  e8 5a 3d ea ff           call 0x140002350       ; allocator
14015e5f6  48 89 44 24 40           mov qword ptr [rsp + 0x40], rax
14015e5fb  48 85 c0                 test rax, rax
14015e5fe  74 0a                    je 0x14015e60a         ; null-check
14015e600  48 8b c8                 mov rcx, rax           ; this = the new object
14015e603  e8 88 b0 f4 ff           call 0x1400a9690       ; <== construct it
14015e608  eb 03                    jmp 0x14015e60d
14015e60a  48 8b c7                 mov rax, rdi
```

Two facts about the call:

- **`rcx`** is the freshly allocated 728-byte (`0x2d8`) object. The constructor zeroes it from `+0x30`
  up past `+0x1c8`, zeroes a 16-entry table at `+0x80`, then writes four constants (`[+0x2c0]` 2,
  `[+0x2c4]` 4, `[+0x2cc]` `0x3f000000` = 0.5f, `[+0x2d4]` 1), and returns it in `rax`.
- **`rdx`** is never written between the allocator and the call (`0` writes in the gap), and the
  caller's loop above the call uses `rdx` only as a **base** register
  (`mov qword ptr [rdx + r11 - 0x328], rax`) — i.e. it is leftover loop state, not an argument.

## 3. Type verdict for the one caller

**The value passed in `rdx` does not have the type §3's readers load.**

| test | result |
|---|---|
| is `rdx` a live 8-byte pointer (the type at `+0x150`/`+0x158` in §3) | **no** |
| what reaches the field | the callee's own `xor edx, edx` at `0x1400a96ba` — **0** |
| what a §3 reader would do with it | dereference it (`mov rdi, qword ptr [rcx + 0x150]`), so a null cannot serve as a node |
| does the caller load a global into `rcx`/`rdx` on the way | 56 RIP-relative `mov`/`lea` exist in the function, **none** between the allocation and the call |

So for this single caller the answer is unconditional: whatever `rdx` held, the constructor replaces it
with zero before either store. **The field is initialised to null here; the node is stored somewhere
else, and that writer is still UNKNOWN.**

## 4. The chain above the caller, with hit counts

Edges are `call rel32` / `jmp rel32` whose target is a **function entry** (a `.pdata` chunk start);
intra-region tail-jumps are excluded so they are not counted as callers.

| node | depth | edges into it | distinct caller entries |
|---|---:|---:|---:|
| `0x1400a9690` | 0 | **1** | 1 |
| `0x14015d310` | 1 | **1** | 1 |
| `0x14019ec40` | 2 | **1** | 1 |

That is the whole chain within three hops, and it is a single line: **`0x14019ec40` → `0x14015d310` →
`0x1400a9690`**. Nothing in it loads from a global holding nodes; the only global-shaped accesses in
the depth-1 function are 56 RIP-relative `mov`/`lea` of unrelated data (strings, tables, singletons),
and none of them is the value stored at the two offsets.

**Therefore: no chain reaches a container or global that holds the spawned node.** Stated as the brief
requires — **UNKNOWN**, with each caller searched and its hit count listed above; there is nothing else
to search at depth 1, and depth 2 is a single edge.

## 8. Limits

- Static only: `D:/Games/Just Cause 3/JustCause3.exe` opened read-only, 51,083,264 B, sha256
  `a53c2d6b2837f45d…`; no process started, nothing attached or injected, no game file written.
- Every "no global" statement is a **scan of the decoded instructions of the named functions**, not a
  whole-program alias analysis: an indirect `call [reg]` into the constructor would not appear in the
  `rel32` edge list. The cache records `458,970` direct call sites and no indirect ones, so an indirect
  entry is **not excluded** — it is simply not visible to this method.
- `0x141ebb6f8` (the one call inside the constructor) was not walked: it takes `edx = 0x10`, `r8d = 3`,
  `r9` = a code address, and `[rsp+0x20]` = another — it is a registration-style call, and whether it
  stores anything at the two offsets is out of scope for this question.
