- 50 ADF files decoded with `jc3adf` (21,804 member rows) - the modules, the tune files and the

- 1 parts module decoded with `bm_parts.decode_parts` - 61 parts (`parts[i].<field>` rows).
- 633 non-ADF files scanned for carried strings (`.ee`, `.epe`, `.effc`, `.trim`, `.ddsc`, `.rbm`,
  `.lod`, ...).
- `.epe` via `rtpcdump` - 467 RTPC nodes / 7,322 properties, name hashes unresolved (see UNKNOWN 1).
- 5 `*_ai.vmodc` AI-driver modules are decoded but **excluded from member evidence**: they are the
  AI driver's copy of a module, so a row about the vehicle's own tuning that matched only there
  would be citing the wrong file. They are listed in the JSON (`inputs.build.adf_ai_excluded`).

Matching rules (also in the JSON `rules` block, so they can be re-run):

- **member match**: both sides split on `.` after removing `[...]` and `/`; a match is a contiguous
  slice of the other, or a suffix of one equal to a prefix of the other (this second case is what
  lets the container hint `land_global.base_wheel_hardpoint_positions` reach the leaf
  `base_wheel_hardpoint_positions[0].y`). Container members decode to `''` and are ignored.
- **value match**: `|built - row| <= max(1e-9, 1e-4*|row|)`; strings exact. A 1-digit integer is
  only trusted when the row's hint selected exactly one built member.
- **string match**: a token the row names, >= 8 characters and containing `/` or `_`, found as
  ASCII bytes in a **non-ADF** built file (an ADF header lists every declared member name whether
  or not a value was built, so a hit there would prove nothing). `@files.xml`, `*.stringlookup`
  and `*.fmod_guids` are name tables and are not searched.
- **GUESSED**: value or string found **and** the row carries one of `by hand`, `hand-set`,
  `chosen`, `assum`, `unsourced`, `estimate`, `approx`, `guess`, `tuned`, `not law`, `probe`,
  `picked`, `eyeball`, `trial`.

Text is normalised before matching: U+2212 becomes `-`, en/em dashes, `±`, `×` and NBSP become
spaces (the ledger writes negatives as `−0.3`; without this those rows never matched).

## UNKNOWNs (with what was tried)

1. **`.epe` member names.** `rtpcdump` parses the container (467 nodes / 7,322 properties) but
   every node and property prints as `<id:XXXXXXXX>`: no JC3 namelist is present in the repo or in
   `_gamedata/JC3grab` (`find -iname "*name*"` found only `Tools/Gibbed/GenerateNameList.exe`).
   So the `.epe` can be byte-searched but not read at member level; the 28 `T-14` light rows rest
   on string-containment evidence only.
2. **Effect references in the `.ee` are not path strings.** The built `.ee` (11,390,571 B) contains
   `b'effects/'` 0 times and `b'.effc'` 0 times. A Jenkins-hash oracle was tried instead - 3 effect
   paths x 4 path forms (full, no extension, backslashes, basename) x original/lower = 8 variants
   each - and **every count was 0**:
   ```
   effects/jc_vehicles/exhaust/car_cycle_base_dual_nitrous.effc D1B4FAE3 count=0
   effects/jc_vehicles/exhaust/car_cycle_base_dual_nitrous    A7A2AA5F count=0
   car_cycle_base_dual_nitrous.effc                           C5ECBE66 count=0
   ```
   So "carried: the donor `.ee` lists the effect" cannot be verified with the oracles tried; those
   rows are NOT TRANSLATED, not because the effect is absent but because no checkable reference was
   found. The only place those paths appear in the build is `@files.xml` (the manifest), which the
   audit deliberately does not count.
3. **Collision.** `sportsmuscle.physicsc` (902,384 B) is not decoded by any wired reader, so
   collision rows (`T-P3`, hull/slot claims) have no byte evidence.
4. **Audio.** `sound/fmod_banks/vehicles.bank` (210,781,376 B) and `weapons.bank` (177,586,080 B)
   are not parsed; the 14 NOT TRANSLATED `T-15` rows have no byte check available at all.
5. **`now` vs `proposed` cannot be separated.** The ledger was written by splitting markdown rows
   on commas, so a comma inside a sentence shifts every later cell (`T-K2`'s BmAK-source cell is
   spread over 4 cells). The audit therefore reads each row as text and reports "row says X"
   without claiming which cell X came from; a value matching the *build's current* number and a
   value matching the *proposal* are reported identically.
6. **The card's two examples are not rows in this ledger.** No id in `T_ROWS.jsonl` begins `ALB`
   (so `ALB-2 PAINT_ALBEDO_GAIN` has no row here), and every `doc = T-13` row is an effect row
   (`T-FX7`..`T-FX23`), not a clearance row - the only clearance row is `T-G4`
   (`land_global.ground_clearance`, classified GUESSED above). Which rows G3-11 meant is UNKNOWN;
   nothing was classified by analogy to them.
7. **`string` tier proves carry, not value.** 44 rows are TRANSLATED because the name they claim is
   present in a built file; that shows the asset/socket/part is carried, not that a value was set.
   The tier is recorded per row so these can be read separately from the 48 `value` rows.
