# G3-07a — JC3 runtime layout for a read-only sampler (static half)

**STATUS: done, with the physics half decoded and three links honestly UNKNOWN.**

What is decoded (each tied to the instruction that uses it, re-derived by `--check`): the part
node's fields (`+0x100`/`+0x101` byte flags, `+0x140` runtime record, `+0x150` world, `+0x158`
raycast world), the physics world's body-slot array (`+0x68` count, `+0x60` base), the body-slot
record (`+0x0c` flags, `+0x30`/`+0x40` float4s, `+0x50` shape, `+0x60` per-slot byte), the shape
(`+0x10`, `+0x13` bytes, `+0x14` float), and the exact crash instruction `+0x151410f`
(`movss xmm0, [rax + 0x14]`) that MODLOG recorded from a live dump.

What is not: the global that leads to a spawned vehicle's part tree, which slot field is the world
transform versus the AABB, the render-instance transform, and the loaded-resource (path-hash)
table. Each is recorded with what was tried and where it would be settled, not guessed.

## The oracles (8/8, each can fail)

| oracle | what proves it |
|---|---|
| `O1-image` | image base `0x140000000`, 7 sections, 188,670 `.pdata` functions; `.text` 36,308,735 B, `.pdata` 2,262,760 B |
| `O2-crash-instruction` | the byte at `+0x151410f` is `movss xmm0, dword ptr [rax + 0x14]` — the address MODLOG's dump names, now tied to the instruction |
| `O3-slot-use` | `0x1415140f0` reads `[rcx+0x50]` (shape), `[rcx+0x0c]` (flags), `[rcx+0x40]`, `[rcx+0x30]`, and `[rax+0x14]` |
| `O4-node-update` | `0x140201de0` reads `[rcx+0x100]`, `[rcx+0x101]`, `[rcx+0x140]`, and loads the stack cookie at `.data 0x142e15310` (non-zero), proving the disassembly is aligned to the real image |
| `O5-raycast-read` | `0x1402020d1` loads `[rbx+0x158]`, does `shl rcx, 7`, and adds `[rdi+0x60]` — the `handle * 128 + world[+0x60]` slot arithmetic, decoded rather than inferred |
| `O6-slot-enum` | `0x140222ef0` reads `[rcx+0x150]`, `[rdi+0x68]` count, `[rdi+0x60]` base, tests `[rcx+rax+0x60]` per slot, and takes the address of `.data 0x142dad020` |
| `O7-tolerance-vector` | `.rdata 0x142343bb0` is four float32 `0.001` bit for bit — the vector the raycast path copies into its argument block |
| `O8-call-verification` | the `E8` byte scan is only accepted where the instruction boundary decodes to a `call` with that target: 4 sites for `0x141505490`, 4 for `0x1415140f0`, 3 for `0x140201de0`, **0** for `0x140201d4e` (it is reached indirectly) |

## What a sampler reads (the chain, decoded)

```
part node  (reached from its parent; the root is UNKNOWN, see below)
  +0x150 -> world            [0x140201f83]
  +0x158 -> raycast world    [0x1402020d1]
      world +0x68 = slot count (int32)          [0x140222f39]
      world +0x60 = slot array base             [0x14020210b / 0x140222f88]
          slot = base + handle*128              [shl ...,7 + add [rdi+0x60]]
          slot +0x0c = flags dword (bit 0, bit 3 tested)   [0x141514128]
          slot +0x30 = float4                   [0x14151411f]
          slot +0x40 = float4                   [0x141514105]
          slot +0x50 = shape pointer            [0x1415140fe]
          slot +0x60 = byte tested per slot (free/occupied) [0x140222f8c]
              shape +0x10 = byte flag           [0x14151413c]
              shape +0x13 = byte compared to 1  [0x141514132]
              shape +0x14 = float               [0x14151410f]  <- the crash address
```

Verified call sites put the chain in one place: `0x1402020d1` → `0x141505490` (the world-pointer
query) → `0x1415140f0` (the slot reader that crashed). `0x140222ef0` is the enumeration that turns
a world into a list of live handles, which is what a sampler would iterate.

## UNKNOWNs (with what was tried)

1. **The root that leads to a spawned vehicle.** No anchor reaches a global; the two entry-point
   functions `0x140201d4e` and `0x2020d1` have **0 verified call sites** (indirect), so a static
   call graph cannot climb from them. The only `.data` object on the path is `0x142dad020`, and it
   is loaded with `lea` (its address passed as an argument); it holds a value pair, not a pointer
   to a part tree. *Where it would be settled:* a read-only probe that scans `.data` for a pointer
   whose target holds the node layout this card decodes (`+0x150`/`+0x158` non-null and
   `world+0x68` a small positive count) — the same self-validating method `bmak_runtime_sampler.py`
   uses for `GNames`/`GObjObjects`.
2. **Which slot field is the world transform and which is the AABB.** `0x1415140f0` copies
   `+0x40` and `+0x30` as float4s and `0x140201ebd` builds a 3×4 from node `+0xc8..+0xf8`, but no
   instruction in the anchors writes an AABB or compares min/max. "Transform" versus "bounds" is
   a reading, not a decode; the card labels it as such.
3. **The render-instance transform.** The anchors are physics-side; nothing on their path
   dereferences a draw instance. *Where:* the draw/instance path, which no MODLOG dump names.
4. **The loaded-resource table (path hashes).** Not on any anchor's path. The only hash-keyed
   structure the project has decoded is asset-side (the `.epe` palette reference, Jenkins
   `0x6187A56B` at `0x266`), and a static search for a runtime table would need a name list plus an
   xref oracle this card does not have.
5. **Whether a slot handle is global or per-world.** `0x140222ef0` enumerates `0..count-1` of one
   world into a caller buffer; the transfer into the parts' `+0x100`/`+0x102` fields is outside that
   function.

## Limitations

- Every claim here is static. Nothing confirms that the fields hold what their names suggest at
  runtime — that is exactly what the sampler this card enables would measure, and it cannot be
  measured without running the game (forbidden by the reset and by this card).
- The record's field table names the *instruction* that touches each offset, not the engine's
  member name; the engine's own names are not in the image.
- `0x140201d4e`'s walk is documented from `MODLOG.md:19847-19851` plus my own disassembly; its
  callers are 0 verified, so its entry point in a running process is unknown.
