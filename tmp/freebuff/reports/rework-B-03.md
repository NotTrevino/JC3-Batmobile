## Per-issue verdicts

### 1. Manifest had no pivot/frame; arch lamps body-space with wheel parents — CONFIRMED, fixed

Evidence before the change: the lamp entries carried `part, kind, side, parent, bones, clusters,
faces_lod0, face_indices, lod_files, lod_budgets, faces_per_lod, vertices_per_lod, bytes_per_lod,
bbox_m, block, window_block, window_reason, sockets, t18_rows` — no pivot; `bm_lights.py` line 26
promised "part, parent, pivot, faces, T-18 rows"; B-02's `parts_manifest.json` carries `pivot_m` and
its part RBMs are pivot-relative (`wheel_f_l_lod1.rbm` spans [-0.363, -0.678, -0.670]…[+0.690,
+0.710, +0.670] with `pivot_m` [-1.208, 0.7047, -2.5699]), while the old arch RBMs were absolute
(`wheel_f_l_arch_lod1.rbm` [-1.271, +0.744, -3.137]…[-1.145, +1.262, -2.811]); B-04's card requires
`parent_space_offset = pivot`. Adding the wheel pivot to those vertices would have put the lamp at
x ≈ −2.48, z ≈ −5.70.

Fix: `parent_frames()` joins the donor parent index → name (`Research/JC3Grab/PARTS_TABLE.jsonl`
`sportsmuscle_vehicle_parts` `parts[].i`/`n`) → B-02 entry/pivot (`parts_manifest.json`
`entries[].pivot_m`), and each lamp's vertices are written as `Vw - pivot`. A parent the two files
cannot join is now fatal (`SystemExit`), never defaulted. The manifest records `pivot_m`,
`parent_part`, `parent_part_source`, `frame`, `bbox_body_m`, and `part_index` (`42`/`43` for the two
front arch lamps, where `t14_lights.json` assigns them; the other six are `null` with
`part_index_source` saying B-04 assigns the next free). New check `pivot_applied_exactly` compares
LOD1's absolute bbox (vertices + pivot) with the source faces' bbox for the six lamps whose LOD1 kept
every face (the rear arches are decimated at LOD1 and are not counted; `pivot_check.lamps_checked` =
6). Absolute positions are unchanged: `sportsmuscle_wheel_f_l_arch` body-space bbox is still
[-1.2708, +0.7436, -3.1375]…[-1.1452, +1.2617, -2.8111], now as `bbox_body_m`.

### 2. "21 T-18 rows" count vs set, incl. two unmapped rows — CONFIRMED, fixed (count detail corrected)

Verified: B-03 hosted 21 rows including `T-L22` and `T-L23`, both `targets: []` / `mapped: false`;
`t14_lights.json` `light_parts` hosts a *different* 21-row set. Fix: `t18_hosting()` now derives the
diff: `rows_hosted_count` 21, `rows_hosted_mapped` 19, `rows_hosted_unmapped` `[T-L22, T-L23]`,
`rows_in_t18_map_not_hosted` `[T-L17, T-L24, T-L35]`, `rows_hosted_outside_t18_map`
`[T-L22, T-L23]`, and `moved` (each row T-18 put elsewhere and B-03 puts on a lamp part). The summary
line and §12 evidence now state "21 T-18 rows (19 mapped, 2 unmapped)".

**Review detail rejected:** the review said "only 18 of the 21 coincide". The diff shows `T-L20` *is*
in T-18's map (`light_parts` puts it on `sportsmuscle_wheel_f_l`), so 19 of the 21 hosted rows are in
the map (21 − the 2 rows outside it), and B-03 moves `T-L20` from the wheel part to the front-left
arch part. The substance of the issue (count match over a different set) stands.

### 3. No T-18 value in the `CarLight` block — CONFIRMED, recorded as UNKNOWN (card Do not met)

The block's material parameters are undecoded (`MODLOG` §102d), so every one of the 24 blocks is a
byte-exact clone of the donor header/mid-static/texture table (verified: `spec_check --lights`
asserts equality for all 24). Writing a T-18 colour into those bytes would be a guess (R4). Fix:
`manifest.block_values` now states `t18_values_in_block: 0`, `status: "UNKNOWN"`, and quotes the
unmet Do step, so the row no longer implies it was done. No value was invented.

### 4. No `Window` block; blanket reason contradicted by the donor — CONFIRMED, fixed (claim + census)

Verified: 44 donor light meshes, 38 carry `CarLight` + `Window`; the only never-with family is
`sportsmuscle_taillight_r_c` (all four LODs); `taillight_r_l`/`_r` are mixed (LOD4 drops the Window);
every head-lamp family is always-with. Fix: `window_census()` derives that census into
`manifest.window.census` (files 44 / with 38 / without 6; `families_always_with_window`,
`families_never_with_window`, `families_mixed`), and the per-lamp reason is now specific
("no Window block is authored … whether the game needs the pair is UNKNOWN (phase Q)") instead of
asserting the donor never ships one. The pair is still not authored: writing a second shell would be
invented geometry, and the card's Do step therefore stays unmet and is now flagged as UNKNOWN.

### 5. "16 sockets … with their `LightColor`" was 6 of 16; colours collapsed — CONFIRMED, fixed

Verified: `HeadLight1`, `HeadLight2`, `LWheelLight`, `RWheelLight`, `BrakeLightL`, `BrakeLightR` carry
a colour; the 10 flare-only sockets have `colour: null` in T-18 itself (they are
`LensFlareComponent`-only). The old `socket_rows()` kept only the first `LightColor` per socket, so
`HeadLight1` lost T-L11's [223, 91, 75, 0] and T-L18's [255, 0, 0, 0]. Fix: each socket now carries
`t18_rows_on_socket`, `t18_colours` (one entry per row: row id, colour, mapped, components, BmAK type)
and `primary_light_colour_rgba`; the summary line prints "16 lamp sockets (6 with a T-18 LightColor)".

### 6. "no light mesh has more [than three LODs]" was false — CONFIRMED, fixed

Verified: `family_lods` = {3: 8, 4: 5}; five taillight families ship `lod1..lod4`. The real rule is
the minimum across families (the head-lamp families stop at LOD3), which `vanilla_ladder()` already
implemented but described wrongly. Fix: the generated `lod_ladder.what` now reads "the fewest LODs any
donor light family ships (… lod1..lod4; only the levels every family shares are kept, so LOD1..LOD3),
ceiling = the largest CarLight triangle count at that level over the 13 donor light families…", with
the numbers injected from the measured census (`lod_ladder.census`).

### 7. Four of the twelve "PASS" checks were tautologies — CONFIRMED, fixed

Verified in the old code: `template_header_identical = True`, `sum_reported_not_hidden = True`,
`no_face_lamps_measured = len(NO_FACE) == 3`, `lamps_with_faces_8 = len(entries) == len(LAMPS) == 8`,
and `faces_total_4576` compared against a literal. Fix: replaced by real checks — the header check
compares all 24 blocks' pre-static + mid-static + texture table; `sum_equals_parts` compares total RBM
bytes with the sum of the manifest's `bytes_per_lod`; `no_face_lamps_measured` requires all three
measured distances > 0 and `no_face_lamps_not_hosted` requires none of the three sockets is hosted by a
lamp; `faces_total_4576` compares the cut with `SLOTS.json` slot 5's `lod0_faces`; the
`lamps_with_faces_8` tautology is gone. There are now 16 checks, all listed in the check output below.

### 8. Typed `lenses` feeding LOD budgets; "named by the dominant bone" overstated — CONFIRMED, fixed as far as the data allows

`lenses` (3/3/3/3/3/3/1/1) is an authored number: the rear arch lamps have no socket at all, and 14
clusters do not imply 3 lenses, so no decode exists for it. Fix: renamed `lamp_elements` and recorded
per lamp with `lamp_elements_source` = "AUTHORING parameter (no decoded lens count); the budget it
multiplies is capped by faces_lod0", so it is no longer presented as derived. The docstring now says
the nose bone feeds both head lamps (split by the cluster's X sign) and the rear arches / tail strips
are named by hand, instead of "named by the dominant bone of each cluster". The budgets themselves
remain generated (`min(faces, cap × elements)`), and `faces_total_4576` /
`lod_budget_within_vanilla_ladder` are unchanged.

### 9. "no lens geometry" overstated the measurement — CONFIRMED, fixed

The old text said the material "gives the dashboard and boot lamps no lens geometry"; the measurement
only shows no Emissive-slot face within 1.5565 m / 1.5827 m (and 0.3909 m for `Headlight_Centre`).
Fix: each no-face row now carries `claim` ("no Emissive-material (slot 5) face lies within this
distance of the socket") and `not_claimed` ("absence of lens geometry (other material slots were not
examined); whether Headlight_Centre shares the nose lenses is UNKNOWN"), plus the measured distance.

### 10. Done check was manifest-driven; stray RBM and side swap invisible — CONFIRMED, fixed

Verified: the old `check_lights()` iterated only `man["lamps"][*]["lod_files"]`, so a stray RBM in
the directory was never read. Fix: `spec_check.py --lights` now also requires the directory's `*.rbm`
set to equal the manifest's set (stray = fail, manifest entry missing = fail, tested below), and
`socket_side_matches_lamp` asserts every socket's X sign matches its lamp's side (16 sockets; a left /
right swap fails, demonstrated in memory).

**Review detail rejected:** the review proposed testing "socket X inside the lamp's X range". Measured:
the four brake/trail sockets sit at x ≈ ±0.476…±0.511 while the corner strips span ±1.10…±1.49, i.e.
0.63–1.19 m inboard, so that test fails on correct data. The check uses the side sign instead, and the
manifest now records `nearest_lamp_face_m` per socket (0.0023–0.0079 m for the lamp-on-lens sockets,
0.63 m for `BrakeLightL/R`, 1.16–1.19 m for `BrakeTrailL/R`) so the association's strength is visible.

### 11. The "Done check (verbatim)" block was not verbatim — CONFIRMED, fixed

The old block showed only the PASS line; the real `bm_lights --check` prints the 24
`blender: DECIMATED` lines first. The rework's own entry quotes the full output, Blender lines
included. No number changed.

### 12. Budget net is accounting, not a build measurement — CONFIRMED (note), no change

Recomputed: 288.6 KB lights (295,518 B / 1024), B-02 4,790.9 KB, sum 5,079.5 KB, paint-equivalent
184,158 B, net 4,899.6 KB of 4,915 KB. It stays an accounting figure until B-04 re-emits the body; the
manifest's `budget.note` and UNKNOWN #7 say so. No code change was needed.

### Extra defect found (not in the review): `--fast` missed a tampered header bbox

While tampering I flipped one byte of the 1,085 B header and `bm_lights --check --fast` still passed:
`decode_only()` compared the cloned bytes, counts and re-encode, but not the file-header bbox against
the geometry (a decode/re-encode of a tampered bbox is still byte-identical). Fix: `--fast` now checks
`m.bbox_min/max == geometry`; the tamper now fails both the full check and `--fast`.
