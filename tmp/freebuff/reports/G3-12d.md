# G3-12d - the 45 `.ddsc` tails and the 4 `.pfxc` sections

STATUS: done

G3-12b (`Research/JC3Grab/DECODE_DEPTH2.md`) left 45 of the 116 `.ddsc` PARTIAL (a non-zero
84-byte table at header 0x2C..0x80) and all 4 `.pfxc` PARTIAL (512 bytes after the Havok
packfile that nothing read). Both are now decoded and byte-accounted to EOF:

- `.ddsc` 116/116 **FULL**. The 84-byte tail region is exactly 7 slots of 12 bytes and holds
  one record `(u32 offset, u32 size, u32 tag)` per mip of the full chain that is **not** stored
  in the file: count `k = mip_count_full - mip_count_in_file`, record `i` = level `k-1-i`,
  offset = prefix sum, tag = `0x01000010` on all 78 records, slots after the last record zero.
  The oracle is the full-chain identity - levels `0..full-1` cost `size_body + sum(records)`
  on 116/116 - so the table is the absent texel bytes (30,408,704 of them), not a lookalike.
- `.pfxc` 4/4 **FULL**. There is no trailing blob: G3-12b read the `__data__` record's last
  field (1920) as an absolute offset when it is the section's length. The data section starts
  at 0x244 and is 1920 bytes, so the packfile runs to 0x9C4 = 2500 = EOF. Byte accounting on
  every file: 68 wrapper + 256 packfile header + 256 `__classnames__` + 0 `__types__` +
  1600 object bodies + 128 local + 96 global + 96 virtual fixups = 2500. What depth2 called
  the blob is the last 512 bytes of `__data__`: 192 bytes of object-body end plus the three
  fixup tables, and those tables are exactly the ones `jc3hkx` already reads (16/7/7 entries).
  Inside the bodies, `hknpConvexPolytopeShape`'s face records and 24-corner list are decoded
  and match its own `vcount/pcount/icount` = 8/6/24 and `jc3hkx.decode_polytope`.

15/15 checks pass, including the two that could break every reading: a wrong level numbering,
block size or table meaning fails the full-chain identity; a wrong section-length reading
fails the region tiling (68+...+96 = 2500 on 4/4).

## UNKNOWNs

Byte ranges are all attributed; these are the fields whose **meaning** is still unproven, each
with what was tried:

- `.ddsc` record tag `0x01000010` (78/78 records): it is not the block size (format 71 blocks
  are 8 bytes) and not per-record varying. Tried: u16/u32 reads at every record offset against
  level, size and offset. It is a constant; the table closes without reading it.
- `.ddsc` u32 at 0x28 = 16 (116/116): not the block size, not a floor on mip size (format 71's
  1x1 mips are 8 bytes). Meaning UNKNOWN.
- `.ddsc` byte at 0x06 (values 0, 5, 6, 8, 9): not a function of (format id, width) - format 77
  at width 1024 carries both 5 and 9. Meaning UNKNOWN.
- `.ddsc` flags at 0x12 (0, 1, 8, 9): two files with the same format, width and mip counts
  (77, 1024, 11/11) carry 0 and 8, so it is not a function of those. Meaning UNKNOWN.
- **why** a `.ddsc` stores the small mips and lists the large ones as absent: the identity
  proves what the table is, not the exporter's reason. No byte states it, and testing it means
  loading the game, which the reset forbids.
- `.pfxc` face code byte (5th field of each face record: 123/127/102/121/120): record offset and
  corner count are proven, the code is per-file and unnamed.
- `.pfxc` global fixup section field (always 2): decoded value, unnamed.
- whether a `.pfxc` is honoured for debris collision in game: not testable under the reset.
