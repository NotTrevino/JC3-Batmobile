# G3-04d - shader cache: what the cooked DXBC carries, and where the binding stops

STATUS: partial

## Summary

Both cooked shader caches exist under the install and both are decoded here:

| file | bytes | contents |
|---|---:|---|
| `BmGame/CookedPCConsole/CombinedShaderCache-PC-D3D-SM5.upk` | 21,268,515 | one `ShaderCache` export, 155,333,378 B: **38,201 DXBC containers** + 6,934 material uniform records |
| `BmGame/CookedPCConsole/GlobalShaderCache-PC-D3D-SM5.bin` | 12,873,519 | `BMSG` v863, shader-type name, **2,098 DXBC containers** from 0x80 |

The card asked for the pixel shader bound to the Batmobile's parent material and a disassembly
showing `BaseColour` and `Diffuse_Adjust` reaching the output colour. **That last step cannot be
taken from these files, and the reason is a property of the bytes, not a decoder failure:**

- Every container in both caches holds only `ISGN`, `OSGN`, `SHEX`. There is **no `RDEF` chunk
  anywhere — 0 of 38,201 and 0 of 2,098.** `RDEF` is the chunk that names constants and their
  constant-buffer slots. Without it the bytecode reads `cb0[..]` by number only.
- None of the parameter names occurs in the bytecode region: 0 hits for `Material0_BaseColour`,
  `Diffuse_Adjust`, `Material1_Basecolour`, `Material2_BaseColour` in 145,440,259 B, and 0 for
  `Batmobile_Worn`.
- The material→blob link is absent too: `Batmobile_Worn`'s GUID (`5e56a794…`) appears 5 times,
  **all in the record region, 0 before it**; no record word equals a blob start; and what
  follows the record is a second uniform list, not a shader index.

What *is* decoded is substantial and new: the **`Batmobile_Worn` uniform record** at `0x8bc1f56`,
14 vector entries (`FName class, FName parameter, value`), whose values reproduce G3-04c's
authored defaults to 1e-4 — `Material1_Basecolour` [0.623595, 0.39245, 0.329779, 1],
`Material2_BaseColour` and `Material3_BaseColour` [0.423977, 0.609159, 0.752809, 1],
`Rain_Size_Multiplier` [1, 2, 0, 1], `Material3_Anisotropic_thin_Colour`
[0.674157, 0.647211, 0.375439, 1], `Batman_Rain_Direction` [0, 0, -1, 0], `Damage_Chapter`
[0, 0, 0, 0]. That oracle is what proves the record belongs to this material. It also carries
`Material0_BaseColour` as [0, 0, 0, 1] — the material default, which is **not** the MIC's
[0.025787, 0.025787, 0.03, 1], so the override is a runtime MIC value and the cache holds the
default.

So the chain now reads: parameters (G3-04c, decoded) → uniform list in the shader cache
(decoded here) → **gap: which blob is this material's PS, and which `cb0` slot each parameter
occupies (UNKNOWN)** → PS arithmetic → output colour.

### Rejected oracles, kept in the report because they were wrong

Three checks I wrote first failed against the bytes and were corrected rather than loosened:

1. "each container's u32 at offset-6 equals its total" — **0/38201**. The framing between
   blobs is variable (gaps 310-2044 B, 642 distinct lengths); the claim was mine, not the
   file's. Replaced by "no two containers overlap", which is what is proven.
2. "no record word indexes a blob" — 5 accidental matches in ~140k words (38,201 blob starts
   make collisions likely). Replaced by the exact-offset test scoped to the material's own
   record and its trailing list, where the answer is 0.
3. "the record ends where the next record begins" — false: 2,589 B follow it. Inspecting them
   showed a second uniform list (26 entries, stopped at
   `FMaterialUniformExpressionFoldedMath`), so the honest statement is "a second uniform list,
   not a shader index".

## What the caches do and do not contain

| question | answer | evidence |
|---|---|---|
| is the pixel-shader bytecode present? | **yes** | 38,201 `SHEX` chunks; every container has `OSGN` |
| does the bytecode name its constants? | **no** | 0 `RDEF` in 38,201 + 2,098 |
| do the parameter names occur near the bytecode? | **no** | 0 hits / 145,440,259 B |
| is the material's uniform list present? | **yes** | 14 vector entries at `0x8bc1f56`, values match G3-04c |
| does any record point at a blob? | **no** | 0 words equal to a blob start |
| does the material GUID sit beside a blob? | **no** | 0 of 5 sites before the record region |

## UNKNOWNs

1. **Which of the 38,201 blobs is `Batmobile_Worn`'s PS.** No name, no GUID and no offset links
   the record to the blob region. Would be found in an uncooked build's shader map, or by
   reconstructing the cooker's material→shader hash.
2. **The `cb0` slot of `Material0_BaseColour` and `Diffuse_Adjust`.** Needs `RDEF`, absent from
   every shipped blob. A slot assignment from the uniform-list order alone would be a guess.
3. **The combine operator** (what multiplies what, in which order). It is in the PS arithmetic,
   which is present but unnamed; reading it means matching blobs to materials by eye.
4. **The value width of `FMaterialUniformExpressionFoldedMath`** — the class that stops the
   second list at entry 11. Its width is not in the bytes read here, so those 15 entries stay
   unparsed.
5. **Lighting, reflection-probe and tonemap terms.** Same bytecode, same gap.
