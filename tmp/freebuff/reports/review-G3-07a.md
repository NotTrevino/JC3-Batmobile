# review-G3-07a — static map of JC3's vehicle physics in memory

`STATUS:` **done**.

**VERDICT: the offsets hold, the evidence layer does not.** All 27 claimed offsets in
`Research/JC3Grab/RUNTIME_LAYOUT.md` §4 are real fields at the claimed displacements on the
claimed structs, and `JustCause3.exe+0x151410f` is byte-exactly `movss xmm0, dword ptr
[rax + 0x14]`. But **4 of 27 citations point at an instruction that does not use the offset**,
one bit list is wrong, the "0.001-tolerance test follows" parenthetical is wrong, the headline
call chain `0x1402020d1 -> 0x141505490 -> 0x1415140f0` is **refuted**, the handle sentinel in the
recipe is imprecise, and the six "functions" are `.pdata` chunks (4 of them fragments of larger
functions) so their byte counts are not function sizes. None of this is detectable by the
reviewed script's own oracle suite: it prints `OK 8/8 oracles` on a mutated copy whose field
table contains a nonexistent offset (`0x501`) and a bogus address (`0x1409ff999`).

Worked from `D:/Games/Just Cause 3/JustCause3.exe` only (read-only, sha256
`a53c2d6b…dac293`, 51,083,264 B, image base `0x140000000`, 188,670 `.pdata` chunks). The game was
never run, attached to or read from memory.

## 2. Refutations and imprecisions (not offset errors, but wrong statements)

1. **The call chain is wrong.** §5 step 6 and the script docstring say
   `0x1402020d1 -> 0x141505490 -> 0x1415140f0`. `0x141505490` does **not** call `0x1415140f0`.
   Its callees are `0x1414387a0`, `0x141513fa0`, `0x141514070` and `qword ptr [rax + 0xf0]`;
   `0x1415140f0`'s only callers are `0x141409152`, `0x1414387e5`, `0x141438a22`, `0x141439558`.
   Consequence for the recipe's "every read above is a fixed offset from a pointer already
   dereferenced by the game's own code path": the `+0x50/+0x0c/+0x30/+0x40` reads are *not* on
   the raycast path. The raycast path reaches the same slot struct as `slot_query`'s second
   argument — `slot_query` reads slot `+0x0c` itself at `0x141505501` and hands the slot pointer
   to `0x141513fa0` (writes `+0x00/+0x10/+0x20/+0x30`) and `0x141514070`.
2. **"bit 3 and bit 0 tested"** → bits 3 and 5 (see above). No bit-0 test exists on that dword
   anywhere in the 380-byte chain.
3. **The six "functions" are `.pdata` chunks; 4 are fragments.** Contiguous chunks that fall
   through into each other:

   | anchor | document body | contiguous chain | real entry | chain ends |
   |---|---|---|---|---|
   | `part_list_walk` | 122 B | **163 B** | `0x140201d30` (0 callers at `0x201d4e`) | `0x140201dd2 ret` |
   | `part_node_update` | 76 B | **943 B** | `0x140201de0` | `0x14020218e ret` |
   | `raycast_body_read` | 157 B | **943 B — the same chain as node_update** | `0x140201de0` (0 callers at `0x2020d1`) | `0x14020218e ret` |
   | `body_slot_query` | 38 B | **249 B** | `0x141505490` | `0x141505584 jmp` |
   | `body_slot_use` | 80 B | **380 B** | `0x1415140f0` | `0x14151426b ret` |
   | `body_slot_enum` | 315 B | 315 B (complete) | `0x140222ef0` | `0x14022302a ret` |

   `0x140201d4e` and `0x1402020d1` are *not* function entries: both have 0 call sites and live
   in registers set by the enclosing function (`rbp`/`rsi`/`edi` for the first, `rbx`/`rbp` for
   the second). This is why their "body" cannot be 122 B / 157 B.
4. **The recipe's handle rule is imprecise.** The handles live in the runtime record as two
   **int16 words** at `record+0x100` and `record+0x102` (`0x140201e35 movzx eax, word ptr
   [r8 + 0x100]`, `0x140201e55 movzx eax, word ptr [r8 + 0x102]`, `r8 = [rcx+0x140]`). A
   negative value is *replaced* by the sentinel **`0x7fff`** (`0x140201e30 mov esi, 0x7fff`;
   `test ax,ax` / `jns` / `mov word ptr [rbp-0x69], si`), and the lookup is skipped when the
   word equals `0x7fff` (`0x140201f75`, `0x140201f7a`, `0x1402020c7`). A sampler must test
   `h == 0x7fff`; "h < 0 means none" happens to be safe but is not the game's rule. This also
   answers part of the document's UNKNOWN 5: the two handles are per-part record fields, not
   transferred from the enumeration buffer.

## 3. Claims whose oracle would still pass if the offset were wrong

This was the specific question. The answer is **yes, for most of the table, and structurally
for all of it**.

### 3.1 The whole offset table is unchecked (end-to-end proof)

`doc["fields"]` in `jc3_runtime_layout.py` is a hand-written literal. No oracle reads it;
`--write` renders it and `--check` compares the file to `render(same literal)`. I copied the
script, changed `"offset": "0x101"` → `"0x501"` and the `+0x140` row's `"src": "0x140201e25"` →
`"0x1409ff999"`, and ran its own write+check:

```
wrote Research/JC3Grab/RUNTIME_LAYOUT.md and .json
  image 51,083,264 B, 7 sections, 188670 .pdata functions
  oracles 8/8, functions 6, fields 27, call sites {'node_update': 3, 'part_list': 0, 'slot_query': 4, 'slot_use': 4}
  unknowns 5
OK 8/8 oracles, 6 functions, 11 call sites, 5 unknowns, md+json byte-identical
```

and the emitted document contains the wrong values:

```
72:| `0x501` | second byte flag | `0x140201e18` |
75:| `0x140` | runtime part record pointer | `0x1409ff999` |
```

A nonexistent offset and a bogus address fit `OK 8/8`. So *every* one of the 27 offsets and 27
citations could be wrong and `--check` would still pass, as long as `--write` was re-run.

### 3.2 Rows with no oracle leg at all — 14 of 27

`part_node 0x0`, `0x2d`, `0x46`, `0x102`, `0x104`, `0x170`, `0x178`, `0x17c`;
`body_slot 0x0`; `shape 0x10`, `0x13`; `runtime_part_record 0x120`, `0x124`, `0x128`.

### 3.3 Legs that pass for a different displacement — 11 of 14

Each `has_read(chunk, base, disp)` leg passes for every displacement that also occurs with that
base register in the same chunk:

| leg | wrong offsets that still pass |
|---|---|
| `O3.flags` (`0x0c`) | `0x30`, `0x40`, `0x50` |
| `O3.f30` / `O3.f40` / `O3.shape` | the other three of `0x0c/0x30/0x40/0x50` |
| `O3.shape_radius` (`rax+0x14`) | `0x10`, `0x13` |
| `O4.b100` / `O4.b101` / `O4.rec140` | the other two of `0x100/0x101/0x140` |
| `O6.base60` / `O6.count68` | each other (`0x60` ↔ `0x68`) |
| `O6.world150` | `0x60` |

Concretely: swapping `body_slot`'s roles — "`+0x0c` float4, `+0x30` flags" — or writing "`+0x40`
shape pointer" still yields `8/8`. The only discriminating legs are `O2` (it hardcodes the
instruction text, so it validates the image rather than the table), `O5.add60`,
`O5.load158` and `O6.flag60` (exact addressing-string matches).

Three more oracle weaknesses, each visible in the code:

- **Size- and direction-blind.** `has_read` accepts any access width and either direction, so
  "flags **dword**" passes on a byte read and "shape **pointer**" passes on a byte read. The
  widths in the table are right — but they are right because I checked them, not because the
  oracle did.
- **Provenance-blind.** The `O3` leg `has_read(chunk, "rax", 0x14)` never establishes that
  `rax` is the shape. It passes if `rax` were loaded from `[rcx+0x48]`. (The claim itself is
  correct: `0x1415140fe` loads `rax` from `[rcx+0x50]`.)
- **Cross-function citation.** The `part_node +0x150` row cites `0x140201f83`; `O6.world150`
  checks the same displacement in a *different* function (`0x140222f10`). The citation could be
  any address and `O6` would pass.

## 4. What the document gets right and should keep

- All 27 displacements, structs and widths; `physics_world+0x60` as a **pointer** to a
  128-byte-stride slot array, cross-confirmed in three functions including `slot_query`.
- The crash instruction, byte for byte, at the crash address.
- The 0.001 vector's value and its use as a 4-float argument on the raycast path (O7's *content*
  is right; only its bearing on `shape+0x14` is wrong).
- The immediate byte-adjacency of `+0x100/+0x101` gates and the `+0x140` record pointer, with
  the record's `+0x120/+0x124/+0x128` floats scaled by `node+0x170`.
