# Re-verification of the pre-reset PHY-1 card (BMAK PHYSICS)

STATUS: done

## Summary

Reviewed: `Research/BatmobileGrab/PHYSICS.md` / `.json`, generated by `Tools/scripts/grab_physics.py`.

**One claim is false and is corrected here.** The card says the four vehicle packages "carry
byte-identical collision layouts". The AggGeom payloads are **not** byte-identical: they differ
at exactly one u32, offset **+12** — `2846` in `Playable_Batmobile_SF`, `2851` in
`Playable_BatmobileMK2_SF`, `3120` in `Playable_BatmobileJoker_SF`, `2836` in
`Playable_BatmobileFunhouse_SF`. The old docstring had already noticed the field and dismissed
it as "constant 2846 on every record"; it is not constant. Every other byte matches, and the
parsed tuples (bone, extents, centre) are identical on all 32 bones, which is why the old card's
`--check` could not see the difference: it compares its own rendered files, never a payload hash.

**Everything else holds.** 32 `RB_BodySetup` bodies per package, 128 records total, each one box
and zero spheres, extents and centres identical to the old card's numbers on all 32 bones.

**Attribution is correct and is now proven at byte level.** All 32 bodies in every package are
outered to `Batmobile_V2_Mesh.Batmobile_V3_Destroyed_Physics`, and none of the four packages
contains an export named `Batmobile_V3_Physics` at all. So the 32-body list is the **destroyed
wreck's**; the drivable car's asset is a different asset in a different package
(`Physics.Batmobile_V3_Physics`, export 158266, bodies 169750 `Batmobile_Chassis` and 169751
`Batmobile_Rig_Weapons_Trans` per G3-01b). The two lists share no bone name, so they cannot be
confused by name either: 0 of the 32 bones match `Batmobile_Chassis` or
`Batmobile_Rig_Weapons_Trans`, and the wreck list contains no chassis/hull bone.

## Findings, claim by claim

| claim in `PHYSICS.md` | verdict | evidence |
|---|---|---|
| 4 packages x 32 bodies = 128 records | **holds** | 32 `RB_BodySetup` exports in each; 128 read |
| every body is 1 box, 0 spheres | **holds** | box counts `{1: 32}`, sphere counts `{0: 32}` |
| extents and centres as tabulated | **holds** | 32/32 agree with the old `.json` |
| "all four carry byte-identical collision layouts" | **FALSE** | differ at +12 only: 2846 / 2851 / 3120 / 2836 |
| asset is `Batmobile_V3_Destroyed_Physics` | **holds, and now proven** | outer chain 32/32 to `Batmobile_V2_Mesh.Batmobile_V3_Destroyed_Physics` |
| "there is no chassis body" | **holds for this asset** | 0 bones matching chassis/hull |
| this is the drivable car's collision | **false** (the card says so too) | no `Batmobile_V3_Physics` export exists in these four packages |

The one number worth carrying forward: the differing u32 at +12 has values 2846, 2851, 3120 and
2836 across the four packages. It is not a shape field (extents, centre, box and sphere counts
are identical), so the per-package variation is metadata the old card mislabelled as a constant.

## UNKNOWNs

1. **What the u32 at +12 means.** It varies per package (and per body within a package), but no
   oracle here ties it to geometry or to `PreCachedPhysDataVersion`. Would be found in the
   `FKAggregateGeom` layout in an uncooked build or the engine's serializer.
2. **The drivable asset's bodies were not re-decoded here.** Export 158266 and bodies
   169750/169751 are cited from G3-01b's `COLLISION_GEOM.md` / `COLLISION_BOXES.md`; that package
   was not opened in this pass. The claim used here is only that it is a *different* asset whose
   bones do not intersect the 32.
3. **Why four wreck assets exist at all.** The payloads differ only in that one word, so whether
   the cooker emitted four near-copies or one shared asset with a per-package counter is not
   determinable from the bytes read.
