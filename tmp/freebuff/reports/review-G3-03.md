Reasoning, in the order the evidence supports it:

cited for line numbers in `BmEngine.ini` / `BmSystemSettings.ini` / `BmInput.ini` or for the Apex values.

## Issues (file, value, why)

### I1 — the whole artifact is stale: `CONFIG.md` / `CONFIG.json` vs the install (major)

Value affected: every row whose line number or value lives in `BmEngine.ini`, `BmSystemSettings.ini` or
`BmInput.ini`; the file table (bytes/lines/sha256) for those three; the containment rows for two of them; the
`profile_basedon` line numbers for `BmSystemSettings.ini`. Why: the files were rewritten at 02:37 (decoded:
mtimes), 64 min after the card (01:33), and `--check` now fails (verbatim output above). Concrete decoded
mismatch: `ApexGRBSkinWidth` is published as `0.025000` at `BmSystemSettings.ini:134`; line 134 now reads
`ApexGRBSkinWidth=0.025`. Fix: re-run `--write`, then re-read the 41 changed rows; nothing in the script needs to
change. Consider having `--write` print the newest input mtime so the capture moment is on record.

### I2 — `tmp/freebuff/reports/G3-03.md`: "17 lines are not `key=value` (they start with `//` or `#`)" — wrong for 2 of 17

Decoded: of the 17 malformed rows, 15 start with `//` or `#`, but two do not —
`BmGame/Config/DefaultEngine.ini:749` `-;PlayerDataStoreClassNames="Engine.UIDataStore_InputAlias"` (starts with
`-`) and `Engine/Config/BaseEditorUserSettings.ini:222` `SliderRange_Low_Falloff-0` (no `=` at all). CONFIG.md
lists all 17 verbatim, so the note itself is fine; only the report's characterisation (and, for the
`-;` row, the absence of a reason why a `-`-prefixed key with a `;` is treated as malformed rather than as a
disabled setting) is inaccurate. Fix: say "15 comment-style lines and 2 others" and name the two.

### I3 — `CONFIG.md` "Files (decoded)" table: the `chain` column is derived, not decoded

The table header labels the block `(decoded)`, and every column except `chain` is a read from the bytes. `C01…C20`
are computed by the `build_chains` walk (the `BasedOn` text is decoded; the chain id and terminal assignment are
derived). Minor label leak of exactly the kind the project bans. Fix: retitle to `Files (decoded; chain = derived)`
or move the chain column to the chains section.

### I4 — resolution rule is stated more generally than it is implemented

The note says each `BasedOn` "is resolved against `BmGame\`", and that is what `resolve()` does. But this only
produces the right path because every text in the set begins with `..\` (so `BmGame\` + `..\BmGame\Config\X`
collapses to `BmGame/Config/X`). A `BasedOn` written without the leading `..\` would double `BmGame`. The oracle
(existence) covers the present data, so no value is wrong — the rule's precondition is just unstated. Fix: say
"resolved as `BmGame\` + the text as written; every edge begins with `..\`, which is what makes this equal to the
install root".

### I5 — "Rows per category" in the note is a derived count presented inside a decoded sentence

`"Rows per category (derived, ...)"` — actually correctly labelled. No action. (Recorded because I checked it and
it is fine; the counts are unchanged at 768/164/143/155/664 even though 41 members changed, which is only
consistent because rows were replaced in place, not added.)
