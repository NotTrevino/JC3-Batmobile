# Names, strings and icons: where the game says "KERNER SERPENTE R" (G2-32)

Generated by `python Tools/scripts/jc3strings.py --write`, re-derived and compared
byte-for-byte by `--check`. The card asked for one thing: every place the donor's name and
icon appear, with a file and an id for each.

**The answer in one line.** The name is a **32-bit Jenkins hash of the entity leaf name**
(`v0300_car_kensington_sportsmuscle_civilian_01` -> `D2B46B49`) resolved inside
**`profile/online.stringlookup`**, which is the only store that holds it; the vehicle's own
`.stringlookup` carries interaction prompts and no name; `ui/ui_localization.stringlookup`
does not contain it at all; and the icon is a plain texture file named after the same leaf
(`textures/ui/vehicle_icons/<leaf>.ddsc`).

## 3. What the entity itself carries, and what it does not

`v0300_car_kensington_sportsmuscle_civilian_01.stringlookup` (patch copy) is **2226 B**, one `StringLookup` instance,
**1 entry** across 11 languages - an interaction prompt, not a name:

| hash | English |
|---|---|
| `A2B9F82C` | Get in Vehicle |

**It holds no vehicle name and no description** - the name is looked up from the item,
not from the entity. A Batmobile build that keeps this file keeps the vanilla prompts;
changing a name here changes nothing.

The build's own copy: **2210 B**, byte-identical to the **base** copy of the same path. The **patch** copy is **2226 B** and differs only in padding - its
decoded strings are identical, so the mod shipping the base table loses nothing.

`ui/ui_localization.stringlookup` (`923,234 B`, 11 languages, 780,266 B of text) is the HUD/UI store and **does not hold
the name**: the donor's two hashes resolve to nothing there, and the only entries mentioning
"Serpente" in the whole file are the 2
Weaponized-Serpente DLC banners (`0x749CD88C`, `0xED2B9C80`):

| banner id | English |
|---|---|
| `0x749CD88C` | Add-on Weaponized Serpente available! |

The bridge is exact across the fleet's drop list: of **45** vanilla
vehicle items, **45** resolve their `UIName` to text in
`profile/online.stringlookup` and **45** have a
`textures/ui/vehicle_icons/<UIImagePath>.ddsc`. So `UIImagePath` is the icon key **and** the
same string hashed is the name key: one leaf name drives both.

There are **113** files in `textures/ui/vehicle_icons/` (including `placeholder`), and
**17** in `textures/ui/store/` under a different naming scheme.

## 5. Does any movie or the frontend name it?

**No `.gfx` movie contains the leaf name, the name hash or the `vehicle_icons` string.**
The menu is data-driven: the movie asks for a string by id and a texture by path, so
neither the name nor the icon is compiled into the Scaleform file.

`global/frontend_global.blo` (patch, 95864 B): leaf name present, name hash little-endian absent, big-endian absent.

The frontend lists the **entity**, not the string: it can name the car only by the same
item lookup the drop menu uses.

## 6. What this means for the Batmobile build

1. **Keep the leaf** `v0300_car_kensington_sportsmuscle_civilian_01` and the car spawns and
   shows as KERNER SERPENTE R with the vanilla icon - no string work at all.
2. **Rename** only by adding a pair for the new leaf's hash in `profile/online.stringlookup`
   (name) and, if wanted, `<leaf>_desc`; the item's `UIName`/`UIImagePath` must hash to the
   same leaf that the `.ee` is actually named. Three things must agree: the `.ee` leaf, the
   item `Name`/`UIName`, and the string pair.
3. **New icon**: drop `textures/ui/vehicle_icons/<leaf>.ddsc` (18,688 B in the vanilla set -
   same size for every vehicle, so the format is one ADF-compressed texture; the exact
   channel/format is UNKNOWN until a decoder reads one) and the menu picks it up by name.
4. **Map icon**: nothing to do. There is no per-vehicle map marker file, so a Batmobile would
   use whatever sprite the map draws for cars - UNKNOWN which, and not vehicle-specific.

## 7. UNKNOWNs

- **Which `.gfx` symbol draws the drop-menu name/icon**: the movies are compiled Scaleform
  and contain neither string (proven above). The binding is code-side.
- **The map marker for a vehicle**: no per-vehicle map icon exists in the index; the sprite
  set the map uses is shared and its member names are UNKNOWN.
- **The name shown in the driving HUD**: JC3 shows no persistent vehicle name in the HUD
  movie for this car (hud.gfx has no reference), and the entity path that would supply one is
  empty. If a name toast exists, its source is UNKNOWN.
- **`textures/ui/store/v0300_sportsmuscle_01.ddsc`**: the file exists, the naming is not the
  leaf, and no index file references it by name; which page loads it is UNKNOWN.
- **Language order**: the store carries no language-name field, so the order is read off the
  text itself (English first, then fr/de/it/es/ru/pl/ja/pt/es-MX/ar) - observation, not a
  decoded enum.
- **The 4-byte hash function**: `hash_jenkins` reproduces every id used here (it is the same
  function G2-26 proved on 196 items), but a collision-free guarantee across the whole
  string space is UNKNOWN.
