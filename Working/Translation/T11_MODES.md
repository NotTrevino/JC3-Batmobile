## 1. The three compromise kinds

A hybrid is not "both modes at once": it is one car that has to pick a value for every
mode-only behaviour. Each row declares which pick it made.

| kind | meaning | rows |
|---|---|---:|
| `carried` | the single car carries the value unchanged - either the behaviour is mode-independent or JC3 is already always-on | 8 |
| `inside band` | the battle value falls inside the band the one car already holds, so no value changes; only the mode *switch* is missing | 1 |
| `omitted` | the requirement needs a member or mode switch JC3 does not have: a named omission that keeps the BmAK numbers on the page | 6 |

## 3. The BmAK numbers, and where each came from

The four packages declare the same 107 mode fields, but they do **not** carry the same values:
46 of them are serialised and 61 are absent from every package, and of the 46 serialised only
**31 are identical on all four**. The other 15 differ, so a number quoted without its package
set is only the value the packages that carry the field agree on. The fields that differ are
`TransformationReverseDirectionIntoPursuitModeSound`,
`TransformationReverseDirectionIntoBattleModeSound`, `BattleModePrimaryWeapon`,
`ImpactRoadAssistSceneryDuration`, `ImpactRoadAssistEnemyDuration`, `BattleDodgeImpulse`,

no tag in Joker, so its row prints the per-package values. A declared field that no package
serialises is `UNKNOWN`, not zero: 61 of the 107 are in that state and are named where a row
depends on them.

## 6. UNKNOWNs and limits

- **`StandardTorqueVSpeedCurve` is not one of the 107 `MODES.json` fields** - it lives on
  `RVehicleSimBatmobile`, outside the mode families G1-21 records - so this doc reads it from the
  G1 object stream instead: 6 points, identical in all 4 packages (row `T-MD4`). That is a
  **record boundary, not an absence**: the values exist and are quoted in §3.
- **The curves' y axis has no documented scale.** `BattleModeVSpeedCurve` is recorded with the
  unit string "curve (cm/s -> factor)" on the "type" basis, and the torque curves carry no unit
  declaration at all, so the out values are printed raw: 60/40/30 for the battle curve and
  0/200/200/170/150/105 for the standard torque curve, and neither set is asserted to be a
  factor, a percentage or a multiplier. Nothing is rescaled.
- **61 declared mode fields carry no value** in any package (`TransformationAnimNode`,
  `BattleModeMaxSpeed`, `BattleModeSteerBias`, the whole `Strafe*` family, the battle camera
  config struct on the *vehicle* class, and others). A field that declares without serialising is
  `UNKNOWN`: the engine's or BMScript's default would run.
- **`ArmourModeDamageReduction` is 0 on the 3 packages that serialise it** and its unit is
  undocumented; the row therefore carries *no* reduction. A non-zero value would need its own
  unit bridge - none exists.
- **`BattleModeThrottleSpeed` (10) is carried raw**: the field's own unit is undocumented, so
  nothing is converted from it.
- **The battle camera's spring/distance fields are not translatable**: the decoded composition is
  in centimetres with no unit bridge to a `.ctune` (T-CAM9 stays blocked); only the FOV has a
  bridge, and 60 deg already sits inside the delivered 55-63 deg band.
- **No battle light behaviour exists.** The fleet's 9 light behaviours have none, so T-18 maps
  BmAK's `VEHLT_BattleModeLight` lamps onto `HeadLight`: they light with the headlights.
- **No game was launched** (R6); every `verify` cell is a §9b probe that can fail.

`--check` re-derives 15 rows over MOD-1/MOD-2, compares both files byte-for-byte,
cross-checks the ledger and **re-reads every number its own cells print** from the inputs named
at the top - so a change in `objects.jsonl`, `MODES.json`, `CAMERA.json`, `CAM_TUNE.json`,
`WEAPONS.json`, `USAGES.json`, `t12_audio_map.json` or `t14_lights.json` turns this check red
instead of leaving a stale doc green. Values that live in another card's row set (T-11's
weapon ids, T-12's part angles, B-12/B-13's status) are cited, not re-read.
