# T-MD14b - does JC3 change a vehicle's handling at runtime, and can it carry Pursuit/Battle?

Generated by `Tools/scripts/t_md14b.py`; `--check` re-derives every number from the same
bytes. **decoded** = read from a file at the quoted offset; **derived** = a stated rule over
decoded facts; **UNKNOWN** = not in the files, with what was tried.

## 0. Answer

**No JC3 vehicle has a runtime mode switch that changes handling.** A fleet-wide scan of
232 vehicle builds and 51 module types for
the state vocabulary (`vtol`, `hover`, `_mode`, `state_machine`, `_switch`, `alternate`,
`gear_up/down`, `retract`, `deploy`, `rotor_tilt`, `thrust_angle`, `amphibious`, `two_mode`,
`transform_`, `model_swap`, `convert`) returns **1 member**, and
it is not a handling switch at all:

| member | module | value | what it actually is |
|---|---|---|---|
| `Limit_Pitch_Yaw_Switch` | `AirplaneAI` | -1 | an AI flight-authority limit on the two plane AI graphs; `-1` = off |

The only *alternative handling* the engine demonstrably holds is **three parallel boost
blocks** on one module - `nitro_boost`, `nitro_boost_upgraded`, `heat_boost` - each a full
performance block at its own struct offset. They are alternatives chosen by state the files
do not name, not a mode machine: no member selects one, and there is no `current mode`,
`variant` or `SetMode`-style member anywhere in the fleet. So the closest structural carrier
for a Pursuit/Battle switch exists (two same-shaped blocks that the engine reads in place of
each other), but the **selector** does not, and the switch itself is **UNKNOWN / code bridge**.

| # | BmAK switch part | JC3 carrier | can it express it? |
|---|---|---|---|
| S1 | a mode enum that the sim reads | none: 0 `_mode`/`state_machine` members | **no** - UNKNOWN, no data member |
| S2 | a per-state call that sets the mode | none: no state machine on a vehicle | **no** - UNKNOWN, native only |
| S3 | two alternative value sets (drive vs battle) | the three parallel boost blocks (S3.1) | **structurally yes, operationally no**: three blocks per module are shipped, the selector is not |
| S4 | per-mode torque/steer fields | `AirGlobal`/`CustomLandGlobal` families are per-vehicle, not per-mode | **no** - one value set per vehicle |
| S5 | the transformation pose/audio | `VehicleParts.model_swap` (visual swap, not physics) | **no** - visual only |

### 1.2 Visual and aerodynamic carriers (not handling modes)

* `VehicleParts.parts[i].model_swap` / `.model_swap.hash` - a per-part mesh swap, shipped as
  the empty string / 0 on every build that carries it (trains). It swaps a **mesh**, not a
  physics block; using it for the transformation stance changes nothing the sim reads.
* `Rotors.rotors[i].does_steer` - decoded values: . A rotor doubling as a steering surface is how a helicopter yaws; it is continuous
  authority, not a mode.
  * `HelicopterModel` / `HelicopterSteering` - 70 + 20 members (`add_forward_force`,
  `add_lateral_factor_pull_up`, `bank_max_velocity_kmph`, `return_pitch_limit`): the whole
  hover-to-forward transition is a curve family inside one state, not a switch.
  * `AirSteering` / `AirplaneAI` - axis timing curves and control-point tables; `AirplaneAI`
  is on 2 builds and its only `_switch` member is the limit above.

## 2. BmAK's switch, and the comparison

Quoted from `Research/BatmobileGrab/DRIVE_MODES.md` (G3-02l, 8/8 oracles, its own check):

| part | carrier | value | label |
|---|---|---|---|
| enum | `EBatmobileDriveMode` | 0 `BMDM_Drive`, 1 `BMDM_TurnOnSpot`, 2 `BMDM_BattleMode`, 3 `BMDM_MAX` | decoded |
| selector | `RVehicleSimBatmobile.DriveMode` | ByteProperty at 0x03b0; CDO tag `None` = 0, shipped sim inherits it | decoded |
| state -> mode | `PursuitMode.BeginState` | `SetDriveMode(0)` at script offset 69 (NPC twin 58) | decoded |
| state -> mode | `BattleMode.BeginState` | `SetDriveMode(2)` at script offset 88 (NPC twin 103) | decoded |
| no state | `BMDM_TurnOnSpot` | no decoded body passes 1; `ForceTurnOnSpotMode` has no writer | UNKNOWN |
| per-mode fields | `BattleMode*` family | 40 fields on the sim, e.g. `BattleModeSteerAngleFactor` 2.5 at 0x0300, `BattleModeMaxSteering` 80 at 0x02cc, `BattleModeLatSlipScale` 4 at 0x02d4, `BattleModeMaxSpeed` 1200 at 0x02f0 | decoded |
| torque split | `TurnOnSpotFront/RearTorqueFactor` | 0.6 / -0.5 at 0x01c8 / 0x01cc: opposite signs = front/rear counter-torque | decoded |
| native arithmetic | `RVehicleSimBatmobile.SetDriveMode` | 5-byte native declaration; the per-mode maths is in the executable | UNKNOWN |

So BmAK's switch is a **state-driven byte**: entering a state writes the drive mode, and the
sim's field family changes what the car does (steer factor 2.5, max steering 80, lat/long
slip 4/10, max speed 1200, front/rear counter-torque 0.6/-0.5). The JC3 side has the *shape*
of the second half - a module can hold several alternative performance blocks at once - and
none of the first half.

### 2.1 Verdict

* **Pursuit/Battle switching cannot be expressed in JC3 data.** No mode byte, no state
  machine, no selector member, and no per-mode field family: the 145 land builds each carry
  exactly one `CustomLandGlobal` value set. Label: **decoded absence**, consequence
  **UNKNOWN** for a code bridge.
* **The nearest carrier is the parallel-block pattern**: `nitro_boost` at 120,
  `nitro_boost_upgraded` at 132, `heat_boost` at 144 on `AirGlobal` - three same-shaped
  blocks the engine reads selectively. A Pursuit/Battle pair could be modelled the same way
  *if* something could select the block, and nothing in the files can.
* **What an amendment would need**: either a second `CustomLandGlobal` instance per vehicle
  with a selector the engine honours (no such selector is decoded - UNKNOWN), or a code
  bridge that swaps the live values on the mode input exactly as `SetDriveMode` does in BmAK.
  The BmAK side of that bridge is fully decoded (enum + four call sites + 40 fields); the JC3
  side is the missing half.
* **The 30 `BattleMode*` rows are not carryable as data**, so T-MD14's 'no second variant'
  holds for values as well as for audio. This does not approve dropping them: the row stays
  an unapproved compromise until the operator accepts it or a bridge is built.

## 3. What was tried, and the UNKNOWNs

1. **VTOL / hover / transform member.** *Tried:* the token scan over every member path of
   every module on all 232 builds (1 hits, both
   in section 0), plus the full member lists of `AirGlobal`, `AirSteering`,
   `HelicopterSteering`, `HelicopterModel`, `Rotors`, `AirEngine`, `TrainGlobal`,
   `VehicleParts`, `BoatGlobal`. *Result:* none. *Where it would be:* a native aircraft
   class the entity graph does not expose.
2. **A selector for the three boost blocks.** *Tried:* the same member scan for `mode`/
   `state`/`variant`/`toggle`/`switch`, and the byte-level type dictionaries of `AirGlobal`
   and `CustomLandGlobal`. *Result:* no member. *Where:* native (the upgrade/heat system).
3. **Whether `heat_boost` is a runtime state at all.** The block exists on 145 land builds
   with values that differ from `nitro_boost` (`extra_top_speed` up to 120 vs 30-60), but no
   member says when it applies. UNKNOWN.
4. **How far the byte-level offset claim reaches.** `INDEX.jsonl` carries 13 `*_air_global.vmodc` and 3 `*_custom_land_global.vmodc`; the offsets
   above are those builds'. A module that is not indexed per entry has no byte offset
   here (its member names and values are still decoded from the row cache), so the
   offsets are representative of the type, not re-read on all 145 land builds.
5. **HP/armour mode.** BmAK also has `ArmourModeDamageReduction`; JC3's nearest is
   `VehicleDamage`'s armour value, one value per vehicle, no mode. Not a carrier.
