# T-FX3B - is there ANY JC3 carrier for a vehicle exhaust / boost flame?

Generated by `Tools/scripts/t_fx3b_exhaust.py`. `--check` re-decodes the module, re-scans
`FX_TABLE.jsonl` and rebuilds this file byte for byte. Read-only: no install write, no launch.

## Answer: **YES**

T-FX3's wording ("no usage slot for an exhaust flame") is **wrong as an engine claim**: JC3 has a
general vehicle effect-attachment carrier, and the fleet uses it for exhaust, nitro, jump-trail,
helicopter and boat boost flames. What the row actually hit is narrower and is stated in section 5.

The carrier is an entity object, not a slot in a stat module:

- class `SAttachedEffect`: **5342** objects, `SDynamicAttachedEffect`: **4344**, tables **1678** / **1212** over **232** vehicle detail files (decoded, `USAGES.json`).
- the table itself is the generated module `*_effect_attachments.vmodc`; the donor's is `Builds/bm-001/aaf/editor/entities/jc_vehicles/01_land/v0300_car_kensington_sportsmuscle/modules/generated/v0300_car_kensington_sportsmuscle_effect_attachments.vmodc` (12,163 B).
- the effect is a pooled `.effc`: the donor's nitro flame is `effects/jc_vehicles/exhaust/car_cycle_base_dual_nitrous.effc` and the fleet ships it in **43** exhaust/boost effect files across **296** cargo containers (base, dlc, patch).

## 1. Module, member, offset (decoded)

`jc3adf.Adf` on the vanilla module gives its instances; the type table gives the member offsets.


| instance | type hash | data offset | size |
|---|---:|---:|---:|
| `EffectAttachments` | `600100251` | 80 | 10576 |

Every member's byte offset is read from the type table, not inferred (`jc3adf.py` header line 14:
a member is `(name index s64, type hash, size, offset, default type, default value u64)`).
`EffectAttachment` as this module declares it:

| member | type hash | offset | size |
|---|---:|---:|---:|
| `deform_point` | `2788046073` | 0 | 8 |
| `effect` | `2788046073` | 16 | 8 |

Type `3213548423` = `EffectAttachment`, struct size 32 B. The values sit
inside an `A[EffectAttachment]` array, so an offset above is relative to one element.

So this struct carries only a **point name** (`deform_point`) and an **effect** reference: the
attachment itself has no usage and no transform. Both come from elsewhere, and both are decoded:

`EffectAttachments` (type `600100251`, 48 B), the module's instance:

| member | type hash | offset | size |
|---|---:|---:|---:|
| `all_effects` | `459717905` | 0 | 8 |
| `part_effects` | `468153434` | 16 | 8 |
| `usage_effects` | `3128759027` | 32 | 8 |

`usage_effects` (offset 32 above) is the array whose element is `UsageEffectAttachments`,
whose own `usage` member sits at offset 0 - the full path of a usage id is therefore
module -> instance member `usage_effects` +32 -> element `UsageEffectAttachments.usage` +0.

The trigger-bearing members, wherever they are declared in this module:

| member | declaring type | offset | size |
|---|---|---:|---:|
| `deform_point` | `EffectAttachment` (`3213548423`) | 0 | 8 |
| `effect` | `EffectAttachment` (`3213548423`) | 16 | 8 |
| `usage` | `UsageEffectAttachments` (`2674124397`) | 0 | 8 |

The donor's two emitters carry `usage` = EngineNitro (4197885156) and `world` = `-3e-06,1,1.17e-10,0,1,3e-06,-3.9e-05,0,-3.9e-05,0,-1,0,-0.009578,0.537762,3.393177,1` (decoded, `Working/Effects/bm_fx_edits.json`).

The transform (`world`) is **not** in this module at all: it is a member of the `.epe` object
(`SAttachedEffect`), and an `.epe` is an RTPC container (`rtpcdump.py`: magic `RTPC`, version 1),
not an ADF file, so `jc3adf` cannot list its typed struct offsets. Two byte probes of the donor's
`.epe` (124,488 B) show how the matrix is stored:

| probe (literal bytes) | result |
|---|---|
| the edit's position text `-0.4101563` | not found |
| the edit's rotation text `-4.371139E-08` | not found |

So the matrix is stored as binary floats: the text B-08 quotes in `old`/`new` is a decoded
rendering, not the bytes on disk (that is why `bm_fx.py` writes the new matrix numerically).
Struct offset of `world` inside the RTPC object: **UNKNOWN** - this project's `.epe` reader walks
nodes and properties, not typed struct members. Where it would be found: an RTPC property-level
decode of the `SAttachedEffect` node (node record offset + property record offset), which no
current script does; `decode_depth7.py` labels the RTPC layout but not per-object members.

## 2. How it is triggered (decoded + derived)

- each attachment names a **usage id**; the vocabulary has **155** distinct
  values with name provenance {'SValueDrivenEffectUsage name': 4, 'UNKNOWN': 85, 'module effect name': 60, 'module usage name': 6} (decoded, G2-22).
- the flame's usage is `EngineNitro` = 4197885156 on the donor's
  two exhaust emitters; the name comes from the module (`6`
  rows are named that way).
- the same trigger family is the arcade nitro field: `heat_boost` x145, `nitro_boost` x145, `nitro_boost_upgraded` x145, `turbo_jump` x145, `turbo_jump_upgraded` x145 (decoded,
  `USAGES.json` `nitro.arcade.carriers`), i.e. the effect fires from the vehicle's own boost state.
- derived: a *looping* flame is a `usage` the engine can hold on (Looping usage, e.g. nitro while
  boosting); a *triggered* one (jump trail, damage flame) is a one-shot usage. Both are the same
  carrier class - the difference is the usage and the effect file, not the attachment type.

| usage id | names | modules | effects (vehicles) |
|---:|---|---:|---|
| 2819629913 | `EngineRunning` | 69 | `EngineNitro` (20), `dynamic_exhaust` (46) |
| 3877802965 | `EngineTurboJump` | 11 | `dynamic_tjump` (11) |
| 4197885156 | `EngineNitro` | 18 | `EngineNitro` (4), `dynamic_nitrous` (14) |

(usage ids and names decoded from `USAGES.json` `usages[]`, which keys each row by `hash` and
lists `names`; the corpus-wide name provenance split is {'SValueDrivenEffectUsage name': 4, 'UNKNOWN': 85, 'module effect name': 60, 'module usage name': 6}.)

The other half of the trigger story is a **value-driven** usage - a condition held true, not a
one-shot event. These are named in the fleet's `.epe` objects (decoded, `USAGES.json`

`IsInAir`, `IsInWater`, `IsPlayerControlled` and `z80_speed_threshold` are exactly the shape a loop

## 5. What the row really hit, and what stays UNKNOWN

- **Not a missing carrier.** The carrier, the table, the usage vocabulary and the effect files all
  exist and are decoded above.
- **The real limit** is that the usable slots are the fleet's own `usage` values: an attachment only
  fires when the vehicle's state machine raises that usage. `EngineNitro` is raised by the arcade
  nitro field, which the build ships - so a boost flame is reachable; a *new* usage (a Batmobile-only
  state) is not decodable from the shipped data, and inventing one is exactly what this task forbids.
- **UNKNOWN**: whether a usage can be raised by a script/condition outside the arcade nitro fields.
  The name vocabulary is 155 values with only 6 named from the module, so most usages have no decoded
  semantics; the search that would settle it is a `USAGES.json` + module-name sweep for a trigger member
  that is not `usage`.
- **UNKNOWN**: whether the `world` matrix alone is enough for a flame to follow the exhaust point on a
  moving car - B-08's Q-1 #5 records the row-2 axis semantics as undecoded.
