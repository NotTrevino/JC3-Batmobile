# T-MD14b - the real BmAK banks and events, and what can fire them in JC3

Generated by `Tools/scripts/t_md14b.py --write` (schema `t-md14b/1`); `--check` rebuilds it
from the decoded files and fails on any change. Static only: no game process, no install,
no git, no edits to another task's files.

Second pass on audio. T-MD14 answered "nearest JC3 event per battle event", which is not
lore. This pass names the events BmAK's Batmobile actually fires, their bank, whether B-11
carries them, and the JC3 member that could fire each one. Pairings from T-MD14 are not
reused: `DoorOpeningStart`/`DoorClosingEnd` appear below only against the cockpit, flap and
seat mechanisms, which is what those roles are.

## 0. Answers

- **BmAK events:** 91 distinct event names in the car's two modes (30 battle-mode, 61 pursuit families), from 361 rows over 4 Batmobile packages.
- **Banks:** 11 distinct banks resolve (`BML_Batmobile`, `BML_Engine`, `BML_Tyres`, `BML_Burnout`, `BML_Battlemode`, `VEH_Batmobile_MK2_Engine`, `BML_Batmobile_Subjective`, `BML_Sonar`, `CHR_BatmanDisruptor`, `WEA_Rain_Materials`, `SEQ_BatWing_VS`).
- **Carried by B-11: none.** The manifest's five slot rows are JC3 rows (`A-02` nitro, `A-05` chassis creak, `A-06` door open, `A-07` door close, `W-03` minigun) and its 45
  `.fmod_guids` are JC3 event pins. No BmAK event name or id appears anywhere in it.
- **JC3 trigger:** 50 events have a decoded donor carrier (an `SAttachedEffect`
  role, or `weapons.bank` for the gun), and 41 are UNKNOWN - every one of the 30
  battle events among them, because the donor pins no mode-transform event and adds none.
- **Custom bank:** a bank file *can* be named in `master.banklist` (26 lines, 434 B, plain text),
  but a new *event* cannot be added - route b is refused because the events are authored in the
  FEV graph and pinned by 16-byte GUID (`JC3_AUDIO.md` section 10). The working route is a sample
  swap inside a copy of an existing bank (route a/c), so BmAK audio can only ride JC3's events.

## 1. How a JC3 vehicle names its bank and fires an event

| layer | member | what it stores | evidence |
|---|---|---|---|
| entity | `.ee.fmod_guids` | 45 event GUIDs in 758 B across 3 banks (`vehicles`, `character`, `effects`) | `JC3_AUDIO.md` section 1; `JC3_AUDIO_EVENTS.json` `donor` |
| entity graph | `SAttachedEffect` object | `name` (role: `engine_running_sound`, `DoorOpeningStart`, ...) + `usage` int | `JC3_AUDIO_EVENTS.json` `donor.events[].roles` |
| vehicle module | `land_audio` `.vmodc` | `min_rpm` 1000.0, `max_rpm` 10000.0 - parameters, not media | `JC3_AUDIO_EVENTS.json` `land_audio` |
| bank list | `sound/fmod_banks/master.banklist` | 26 bank file names, `vehicles.bank` among them | `JC3_AUDIO_EVENTS.json` `banklist` |

**Hash space:** the entity does not name events. It carries 16-byte GUIDs; the bank holds events
keyed by those GUIDs; the FEV graph (not shipped) is where a GUID is bound to a tree. JC3's
`vehicles.bank` has 257 events / 257 tunes with `evts_role_name_hits: 0`, i.e. no role name
resolves inside the bank at all. So the mapping is *role -> GUID pin -> event*, and only the
first hop is decoded.

The BmAK ids on the left are a different space again: they are **assigned short ids, not name
hashes**. No rule reproduces them - `fnv1(lower)` 0/91, `fnv1(name)` 0/91, `crc32(lower)` 0/91, `crc32(name)` 0/91 - and the
battle variants count up (`Play_BattleMode_In_A..F` = `0xB70656E1..E6`). So a BmAK event cannot
be matched to a JC3 event by id; only the role name carries across.

## 4. UNKNOWN, and the amendment for each

- **Which class or script fires a BmAK event.** `AUDIO_FEATURES.json` carries package, name, id,
  bank, WEMs, RTPC and loop data - no caller field. The blueprints that call `PostEvent` are not
  in the grab, and a grep of the JC3 entity corpus for `Play_BattleMode` returns 0 files (T-MD14),
  which only confirms JC3 does not name them. Amendment: none needed for lore - the events are
  named and their banks known; the caller only matters for ordering.
- **Battle-mode transforms.** 30 events, bank `BML_Batmobile`, no donor role. Amendment: the
  carrier member exists (`SAttachedEffect` + `.fmod_guids` pin), the *trigger* does not - a mod-side
  AkComponent call would be needed, and that call is UNKNOWN.
- **Impacts and the tracking shot (`0x6BB2C66E`).** No bank among the 117 searched carries the
  tracking-shot id (G3-14b answer: UNKNOWN, every bank searched). The impact names are
  `missing-bank` in the feature rows, so their bank is UNKNOWN too.
- **Sonar / tracker / rain.** No donor role for any of them among the 45 pinned events, so the
  JC3 trigger is UNKNOWN even though the BmAK bank is known (`BML_Sonar`, `CHR_BatmanDisruptor`,
  `WEA_Rain_Materials`). Amendment: pin a GUID and add a role - again a code change.
- **Whether a swapped sample is the right sample.** Bank swap keeps the JC3 event and tune; the
  tune chooses the wave, and tune -> wave is not stored (G2-24 section 5), so the pairing is by
  name and audition, as test-060 did.
