# T-ST7b - is 0.5 s a JC3 steering floor? (all modules, by class and role)

Generated by `Tools/scripts/t_st7b.py`; `--check` re-derives every number from the same
entity bytes. **decoded** = an entity module row; **derived** = a stated rule over decoded
values; **UNKNOWN** = not in the files, with what was tried.

## 0. Answer

**0.5 s is not a JC3 floor and the claim is false as stated.** Of the
**6,045** decoded vehicle modules (232 entities), **271** are steering modules; player copy and
`_ai` twin are counted separately throughout:

| class / role | min `t_to_full_steer_s` | modules at that min | below 0.5 s |
|---|---:|---:|---|
| `LandSteering` player (cars) | 0.5 | 6 | 0 |
| `MotorbikeSteering` player (bikes) | 0.3 | 2 | 9 |
| `LandSteering` AI twin | 0.25 | 4 | 4 |

* **A player module does ship below 0.5 s**: the bikes (`MotorbikeSteering`) carry
  **0.3 s** on 2 player modules, so the player steering path is
  not floored at 0.5 in the data; the class difference (bike vs car) is the only thing that
  separates them.
* **0.25 s exists in the fleet**: 4 `LandSteering` AI twins ship it
  (`t_to_full_steer_s`), and the AI `max_speed_t_to_full_steer_s` reaches
  **0.2 s**. Same member, same parser, same type - only the role differs.
* **No player module reaches 220 deg/s**: the best player rate is
  **116.7 deg/s** (`MotorbikeSteering`, `v3501_bike_solar_modernmoped__v3501_bike_solar_modernmoped_civilian_01.ee.json`), the best player **car** rate is
  **80 deg/s** (`v0405_car_mugello_moderncircuitracer__v0405_car_mugello_moderncircuitracer_civilian_01.ee.json`), and
  the car minimum time is 0.5 s on 6 modules. So the honest
  statement is *"no player car ships below 0.5 s"*, not *"JC3 cannot be quicker"*.

**Engine clamp: UNKNOWN.** 22 files in the repo name the executable
(4 of them mention steering at all, 0 name this member), but none decodes the
steering update, so no clamp on `t_to_full_steer_s` can be shown or excluded - see section 4.
Nothing in the ADF data clamps the member, and nothing here proves the player update
honours <0.5 s either. The AI twin at 0.25 s is evidence that the member and
parser accept it, not that the player path uses it.

## 4. The clamp question

Searched every `.md` under `Research/` and `Working/` for `(?i)(justcause3\.exe|jc3\.exe)`:
**22 files** name the executable, and the repo does carry real exe
decodes (`CONSTRAINT_CODE.md`, `RUNTIME_LAYOUT*.md`, `PHYSICS_LIMITS_REVIEW.md` -
PE headers, Havok constraint atoms, property layouts). Of those files
**4** mention steering at all and
**0** name this member (`t_to_full_steer_s` / `SteerSpeed`),
so the steering update itself is not decoded anywhere here: **no clamp can be shown or
excluded: UNKNOWN.** *Where it would be:* a disassembly of the land-vehicle steering
update in `JustCause3.exe` (the same `pefile`/`capstone` method the existing notes use), or
the one-variable probe T_ST7_FLOOR.md §6 describes (0.25 written into a build, measured at
standstill), which the test ban forbids.

## 5. What this changes in T-ST7

* T-ST7's reason ("the fleet's fastest rack is 0.5 s") is **wrong on the data**: the
  player bike class ships 0.3 s (9 modules) and the AI car class ships 0.25 s
  (78 modules, 0.2 s for the high-speed member).
* T-ST7's *decision* (0.8 s low / 0.6 s high on the Batmobile) is not disproven by that:
  no **player car** module ships below 0.5 s, so 0.8/0.6 is still a defensible in-family
  pick - it is just not forced by a floor.
* Therefore T-ST7's `blocked` disposition is **not justified as a limit**. It is a
  compromise: the car could carry 0.25 s by data (R1) and the fleet shows the member
  accepting it, but nobody has written or measured it. It stays UNAPPROVED in
  `COMPROMISES_T.md` until the operator rules.
