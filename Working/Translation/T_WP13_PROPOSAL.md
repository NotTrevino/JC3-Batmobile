# T-WP13 - the largest BmAK weapon set JC3's driver slots can carry

Generated by `Tools/scripts/t_wp13.py --write`; `--check` re-reads every input and
fails on any change.  Static only: no game process was started or attached to.

## 1. Answer

**Two weapons can be bound at once; a third index is addressable but has no member.**
The fleet's own root properties hold at most **2** driver weapons (38 of 53 entity
graphs bind one), and the `DrivingMode` state machine calls
`SelectVehicleWeapon(1/2/3)` from its QuickGadgetB/X/Y states, i.e. it addresses **3**
indices.  Only indices 1 and 2 have a decoded root property to point at, so
`main_weapon` + `secondary` is the largest set that can be written without inventing a
member.  No vehicle-scoped next/previous action exists: `NEXT_WEAPON` and
`PREV_WEAPON` ship on the keyboard (MWHEELUP/MWHEELDOWN) but are scoped on-foot and
nothing in the files says a vehicle consumes them.

Against D-7's 11 weapons: **3 addressable** (2 decoded binds + 1 index with no member), **8 lost** (WPN-4, WPN-5, WPN-6, WPN-7, WPN-8, WPN-9, WPN-10, WPN-11).

## 3. How a driver slot picks its weapon

`DrivingMode` (G3-02, `DRIVINGMODE.md`) binds one state body per quick-gadget button:

| state | call |
|---|---|
| `QuickGadgetB` | `SelectVehicleWeapon(1)` |
| `QuickGadgetX` | `SelectVehicleWeapon(2)` |
| `QuickGadgetY` | `SelectVehicleWeapon(3)` |

The integer is the only selector in the decoded state machine; the literals are
decoded, but **which weapon object an index resolves to is UNKNOWN** (the same gap
`DRIVINGMODE.md` §4 records).  Firing is separate and has exactly two actions:
`FIRE_VEHICLE_WEAPON_PRIMARY` (gamepad RSHOULDER, keyboard MOUSE1) and
`FIRE_VEHICLE_WEAPON_SECONDARY` (LSHOULDER, MOUSE2).

## 6. What is lost

- **8 of 11 weapons.** Only the cannon and the Vulcan have a decoded driver slot;
  the missiles are addressable only through the third `SelectVehicleWeapon` index,
  whose member no fleet vehicle has, and the other seven have no carrier at all
  (EMP burst = entity pulse, winch / hacker / sonar / tracker / riot = proven absence,
  booster = a button, not a slot).
- **The per-mode split.** BmAK wants every weapon in battle and pursuit mode; JC3 has
  one vehicle mode and no decoded mode-to-slot table, so 'both modes' cannot be
  expressed even for the two weapons that fit.
- **Switching by input.** `NEXT_WEAPON`/`PREV_WEAPON` exist only in the on-foot scope,
  so a driver cannot cycle slots; the only in-vehicle selection is the three
  quick-gadget indices, two of which are bound.
- **The HUD's 5 BmAK slots** (primary + secondary + 3 special states) against JC3's 2
  clips (`MCI_vehicle_weapons0/1`).

## 8. UNKNOWN

- **What the third `SelectVehicleWeapon` index selects.** The literal 3 is decoded;
  the object behind it is not in the state body, and no fleet root carries a third
  driver property.  Where: the native `RPlayerController.SelectVehicleWeapon` body,
  which is not in the decoded packages.
- **Whether a vehicle consumes `NEXT_WEAPON`/`PREV_WEAPON`.** Both exist on the
  keyboard with on-foot scope; no file maps them to a vehicle state.
- **A per-mode slot table.** No file splits weapons by battle/pursuit mode.
