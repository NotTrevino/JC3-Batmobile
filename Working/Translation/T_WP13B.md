## 0. Answer

**Yes - the entity carries four slot properties and two spare object pointers, and the fleet
already ships weapons no slot points at. What JC3 limits is not the slot count but the number
of *fire paths*: two.**

- Root slots, all four on every one of the 54 fleet roots:
  `main_weapon` x54, `mounted_weapon` x54, `mounted_weapon_2` x54, `secondary (id:00568A74)` x54.
  Driver-fired: **2** (`main_weapon`, `secondary (id:00568A74)`), 62 bound pointers
  across 53 armed graphs. Gunner seats own the other two (19 bound).
- Each root also holds two more object pointers, `id:8580BA42`, `id:CA86AA17`: present on
  54 roots, **non-null on none**. Same class, same root, same object
  reference shape as a weapon slot - the only decoded place to write a third and fourth
  driver weapon. Whether the engine fires a weapon behind them is **UNKNOWN**.
- Weapons without a slot already ship: max **3** weapon components on one entity, and
  7 graph(s) carry a component no slot points at. Three weapons on a vehicle
  is normal engine data; *firing* the third from the driver seat is the missing member.
- BmAK's own car does not use a switchable pair. `DrivingMode.SelectVehicleWeapon` is a **fire**
  body (`RVehicleWeapon.TryToFireWeapon` twice), and BmAK addresses **four** indices, one
  button each: 1 -> `XboxTypeS_B`, 2 -> `XboxTypeS_X`, 3 -> `XboxTypeS_Y`, 4 -> `XboxTypeS_DPad_Up`.
  So BmAK's model is "N slots, one button each"; JC3's primary/secondary pair is the borrowed
  thing to amend, not a ceiling. Under the operator's 2026-11-05 rule (BmAK buttons win inside
  the car) the amendment is legitimate: add fire paths, do not wait for a JC3 switch.

Against the 11 weapons: **2 decoded slot carriers** (WPN-1, WPN-2), **2 spare pointers** that
can hold WPN-3/WPN-4 if the engine test passes, **slot sharing by mode** for the rest - which
is precisely how BmAK behaves (B is EMP in battle, Tracker in pursuit) - and **3 decoded
absences** that need no slot at all (WPN-5 entity pulse, WPN-6 tether, WPN-11 nitro block).

## 4. What could switch between them

### 4a. BmAK's own model (decoded)

**An index is a fire path, not a selection.** `DrivingMode.SelectVehicleWeapon` (export
104971) calls `ReadyToFire()`, `IsFiring()`, `RVehicleWeapon.TryToFireWeapon()` twice, and
raises `RSeqEvent_BatmobileRiddlerButton`; `QuickGadgetB/X/Y` forward the literals 1/2/3 and
d-pad up binds literal 4. No decoded body stores an active-slot variable. Press a button, the
car fires that button's weapon - that is the model JC3 has to be given.

Weapon *selector* actions in the shipped keymaps: `NEXT_WEAPON`, `PREV_WEAPON`.
`land-vehicle` scoped: **none**. `NEXT_WEAPON`/`PREV_WEAPON` are keyboard-only and
`on-foot`, so nothing shipped lets a driver cycle or select a slot. The vehicle-scope buttons
still free are `USE_VEHICLE_MOD` (d-pad right - now the winch) and `VEHICLE_RELEASE_GRAPPLE`
(d-pad down).

**Consequence.** Do not add a switch; add *fire paths*, one button per weapon, exactly as BmAK
does. The two HUD clips and two fire actions are then what must be extended - not the slot
count, which the entity already exceeds.
