**Derivation rule** (one rule, used for every correction):

```
drivable boxes        = every decoded `- box N: extents [...]` line  = 3
drivable convex boxes = header convex counts 43 + 13                 = 56
drivable shapes       = boxes + convex element boxes                 = 59
largest drivable box  = max by longest axis                          = [690.305, 374.536, 207.5] cm
box_m                 = extents_cm / 100
```

### Why the old numbers are wreck numbers, not drivable ones

- `32` is `PHYSICS.md`'s per-vehicle body count of `Batmobile_V3_Destroyed_Physics` - the
  asset the game hands to the **destroyed** car, whose own doc says it has no chassis body.
- the `316.155 x 63.418 x 109.881 cm` triple is that asset's `SUSP1_Wheel_Rear_Left_Mesh`
  box. It is not even the wreck's largest: `SUSP1_Wheel_Rear_Right_Mesh` carries
  317.942 cm on X, so the row quoted the second-largest wreck box.
- `3.1615 x 0.6342 x 1.0988 m` is that same box in metres (x 0.01) - **derived**, and still a
  wreck box.
- T-P3's `11 / 21` split is a *partition of the wreck's 32* - 0 wheel/suspension + 0 doors + 0 cockpit = 11, the other 21 debris/root/turret/fin - so calling the 11 "driveable boxes" is the error, not the
  arithmetic.

## 3. What to do with the wreck block

The `bmak` block of `t16_collision.json` is **valid data about the wrong asset**. Suggested
shape of the edit (not applied, and not encoded in the JSON above): keep every field, rename
the block `wreck`, and add a `drivable` block with the values in section 2. Deleting the wreck
block would lose the 32-body census that `T-CO2` and the debris work already cite.

## 4. What this does not fix

- `T-CO2` - already corrected by G3-11d; not re-opened here.
- `T-PA3`, `T-CO3` - clean: they quote the JC3 donor part table, no BmAK box figure.
- Any downstream consumer of `t16_collision.json` that reads `bmak.bodies` / `largest`
  (`t22_collision.py`'s slot binding, the `11 -> 7` map, radius x k). Correcting this file
  does not re-point those; they read the fields this sheet proposes to change, so applying
  the edit needs that consumer checked in the same pass. That is **UNKNOWN** here: the
  consumer's use of each field was not re-read for this card.
- Whether the drivable asset's own numbers are *the car's real collision* - the 3 boxes are
  the physics-asset bodies and the 56 convex elements are the mode-switched setups; which
  mode is active in play is `COLLISION_GEOM.md`'s own UNKNOWN.

## 6. UNKNOWN

1. **Which mode's convex set is live** - `COLLISION_GEOM.md` records
   `active_mesh_per_mode: UNKNOWN` (the mode enum is not serialised). The corrected count
   therefore states *both* setups (43 + 13), not one.
2. **The chassis boxes' rotation** - `COLLISION_GEOM.md` decodes extents and centres, and
   says the rotation is not decoded, so the 690.305 x 374.536 x 207.5 cm box is its local
   frame, not a world AABB.
3. **The axes** - the doc's own oracle says "Frame axes are not proven", so the corrected
   triple is quoted in the doc's X/Y/Z order unchanged; no axis re-mapping is claimed.
4. **How many of the 3 boxes the build actually uses** - T-22's slot binding is built on the
   wreck census; re-deriving it from the drivable boxes is not in this card.
5. **Whether an edit to `t16_collision.json` breaks its own consumers** - see section 4.
