# SMART_SEARCH.md — smart search, split into the reusable half and the JC3 half

Smart search is one question with two stages: **find candidates cheaply, then have a small local model
judge each candidate**, with every verdict cached so a repeat costs nothing and a run can resume. The
machinery is generic; only the search corpus, the snippet format and the prompt's wording are JC3's.
This document separates the two, then gives the port plan for `quiz_parser` and the outline for a Claude
skill that packages the generic half.

Files this describes (all read for this document, none modified except by their owners):

| file | role | size |
|---|---|---|
| `Tools/scripts/chase/smart_search.py` | the two stages, the cache, the exit codes | 263 lines |
| `Tools/scripts/chase/chase_judge.py` | the text judge kit: `PROMPT`, `ask`, `parse`, the resumable JSONL runner | 114 lines |
| `Tools/scripts/chase/jeb_judge.py` | the decision-model judge: `noul` question, `P(true)`, `window()`, `prompt_version()` | 136 lines |
| `Tools/scripts/chase/chase_calibrate.py` | calibration on known values: `--build/--run/--score/--render/--check/--sweep/--compare` | 747 lines |
| `Tools/scripts/chase/chase_candidates.py` | **JC3 only**: the EXE and text scanners behind `member_candidates` | 556+ |
| `tmp/freebuff/reports/smart-search.md` | the calibration numbers, generated by `--render`, never hand-typed | — |

## Part 1 — The generic part (any project)

### 1.1 Stage 1: a search function with a fixed return shape

```python
candidates = member_candidates(member, owner, offset, ftype, routes)   # ranked, best first
# -> [{"id", "source", "route", "snippet", ...}]
```

The contract is deliberately thin: **a list of dicts with `source` (a human-locatable address or path),
`route` (which scanner found it) and `snippet` (the text the judge will read)**. Ranking is a pure
function of the corpus, so it can be replaced or frozen. `smart_search` never re-implements search; it
imports it (`import chase_candidates as cc`, `smart_search.py:40`), and a frozen copy can be selected
for calibration (`search_mod()`, `:85`).

Two knobs that made it usable: a hard snippet cap (`SNIPPET_CAP = 12 * 1024`, `chase_candidates.py:75`)
and a `max_n` truncation *after* ranking (`cands[:max_n] if max_n else cands`, `smart_search.py:99`).

### 1.2 Stage 2: a judge with a fixed return shape

Text judge (`chase_judge.py`):

```python
PROMPT  = "... one JSON object ... {member} {owner} {type} {offset} {source} {snippet}"
raw     = ask(url, model, PROMPT.format(...))     # temperature 0, max_tokens 400, timeout 600
verdict = parse(raw)                              # {"found": bool, "value": str, "why": str} or None
```

`parse` accepts the **first** `{...}` anywhere in the reply (`re.search(r"\{.*\}", raw, re.S)`) and
returns `None` unless `found` is a real bool. `None` is the important case: it means **unparsable**, and it
must never become a `false`.

Request shape that matters for small models, copied verbatim from `chase_judge.ask`:

```python
json.dumps({"model": model, "messages": [{"role": "user", "content": text}],
            "temperature": 0, "max_tokens": 400,
            "chat_template_kwargs": {"enable_thinking": False}})
```

Decision-model judge (`jeb_judge.py`) — same question, different surface: a typed `noul` question
(`question()`), `P(true)` from one forward pass (`judge()` → `{"found": p >= threshold, "value", "lit", "p",
"why"}`), and a **window** (`WINDOW_LINES = 12`, `WINDOW_CHARS = 2400`) because the model's prompt limit
is 2,048 tokens. A decision model cannot quote the literal, so `literal()` reads it from the snippet by
regex and stores it as `lit` **whether or not the verdict was found** — that is what makes the threshold
sweep free (`chase_calibrate.sweep`).

### 1.3 Cache: content-addressed, model-aware, never partial

```python
PROMPT_VERSION = hashlib.sha256(cj.PROMPT.encode()).hexdigest()[:8]     # smart_search.py:46
key  = sha256((model + "\0" + prompt).encode()).hexdigest()             # :54
path = <cache>/<key[:2]>/<key>.json                                     # :58
```

- The key is the **exact prompt plus the model name**, so (a) a repeat costs nothing, (b) a prompt
  revision invalidates every stale verdict by construction, (c) the same question asked of two models
  never shares an entry.
- Writes go to the final path only after the JSON is complete; an offline judge writes nothing
  (`if not cands or not judge_online(base): ... return rec` — `:135`). **A partial verdict is never cached.**
- Unparsable replies are cached with `found: null` and their `raw[:500]` kept (`:170`), so the failure
  is visible instead of silent.
- `--no-cache` and `--fresh` exist for calibration runs that must not reuse anything.

### 1.4 Resumable state, two ways

1. **One JSONL, append-only, skip known ids** (`chase_judge.main`): read `--out` into `done = {id}`,
   `continue` on a known id, `write` + `flush` per verdict. Kill it at any point; rerun and it continues.
2. **One JSON per case in a run folder** (`chase_calibrate.cmd_run`): `<runs>/<prompt_version>/<case>.json`,
   skipped when the file exists. The folder carries `_search.txt` recording search half, judge, threshold,
   prompt version and model, so a run is self-describing and two judges never overwrite each other
   (`run_dir()` prefixes Jeb folders with `jeb_`).

### 1.5 Calibration on values the project already knows

Three case families, and the distinction between them is the whole point:

| family | what it proves | known value source |
|---|---|---|
| **positive** | a value decoded independently (here: serialised identically in all four packages) | `MODES.json` |
| **found** | a row already marked FOUND, re-verified against the line that records it | `chase-*.md:<line>` |
| **negative** | no scalar literal exists (curve, struct, runtime state, name, object reference) — so any `found=true` is a **false positive** | FOOTAGE / MODES / MECHANICS |

The harness is six verbs and one rule — **nothing is typed by hand**:

- `--build` writes `calib.jsonl` from provenance records (`chase_calibrate.build`).
- `--run` shells out to `smart_search.py` once per case with `--expect <known>`, storing JSON per case.
- `--score` aggregates: positive recall, found recall, precision, negative false positives (cases and
  verdicts), unparsable rate, s/candidate, cache hits.
- `--render` writes the numbers into the report between `<!-- CALIB-BEGIN -->` / `<!-- CALIB-END -->`.
- `--check` re-scores, re-renders, **re-verifies every known value against its provenance** and diffs the
  report block; returns 1 with `FAIL <reason>` lines (this is the anti-rot check).
- `--sweep t1,t2,...` re-thresholds stored `p` values with **no model call**; `--compare` lists the cases
  where two judges disagree, with the provenance's own answer.

Two derived metrics carry most of the diagnostic value:

- **reach** —  does any candidate snippet contain the known literal (`literal_in`, `smart_search.py:102`)?
  Reach separates a **search miss** (the value was never offered) from a **judge miss** (it was there and
  was refused). Without reach, a low recall number is uninterpretable.
- **recall at reach** — recall counted only over cases the search actually offered. This is the judge's own
  score; the headline recall is the product of both stages.

The calibration on this project (38 cases: 20 positive, 8 found, 10 negative) is why the split matters: on
the frozen `v1` search half reach was 28/28 — the value was in front of the judge every time — and the
Qwen judge returned `found=true` once, while Jeb at threshold 0.5 returned nothing at all (0/20, 0/8, 0
false positives) and at 0.3 bought 3 false positives without a single true recall. `positive: 106
verdicts, max P(true) 0.333`. A small model's recall, not its speed, is the binding constraint; store `p`
so the threshold can be re-decided for free. Numbers: `tmp/freebuff/reports/smart-search.md` (generated),
`tmp/freebuff/reports/jeb-vs-qwen-calibration.md`.

### 1.6 Interface rules learned the hard way

1. **The judge only triages.** `found=true` must be verified against the address it names before the value
   enters a record (R4). The tool's docstring says so; the calibration exists to keep it honest.
2. **Offline is a first-class outcome, not an error to paper over.** `GET <base>/health` with a 3 s timeout
   (`judge_online`, `:77`); offline → print `judge offline`, list the candidates **unjudged**, write no
   cache, **exit 3**.
3. **`None` ≠ `False`.** Unparsable is reported as `found: null` and counted separately.
4. **A window change is a prompt change.** Jeb's `prompt_version()` hashes instructions, criteria, window
   lines/chars and the window spec, so a new window gets a new run folder instead of silently replacing
   the old calibration.

### 1.7 Exit codes (the contract a wrapper can rely on)

| code | meaning | where |
|---:|---|---|
| 0 | ran; verdicts may be found or not — the exit code does not judge | `smart_search.main` |
| 2 | bad arguments (e.g. an unknown route name) | `smart_search.main` |
| 3 | judge offline: candidates listed, nothing judged, nothing cached | `smart_search.main` |
| 1 | `chase_calibrate --check` found a provenance or report mismatch, or no run folders | `cmd_check` |

## Part 2 — The JC3-specific part

### 2.1 Routes and scanners

```python
ROUTES = ("exe", "text")                                  # chase_candidates.py:556
def member_candidates(member, owner=None, offset=None, ftype=None, routes=ROUTES):   # :559
```

- **`exe`** — a store scanner over the executable's dumped code: finds a write into `[reg+offset]` and
  returns a disassembly window around it, including the annotator comment `; [0x...] = float X`.
- **`text`** — a scanner over `.ini` / script / data text: returns the `key=value` line that assigns the
  member.
- Ranking promotes a hit whose window names the owning class or looks like object initialisation
  (constructor defaults), demotes per-frame updates.

**These two route names are the only hard-coded vocabulary**: `--routes exe,text` is validated against
`cc.ROUTES` in `main` and rejected with exit 2 otherwise. A port must replace that tuple, not the code
around it.

### 2.2 Snippet format

- exe: a window of disassembly lines, anchored on the store, with the annotate comment kept (the comment
  sits on the store's own line — `_anchor()` in `jeb_judge.window()` has a branch for exactly that line).
- text: a record fragment whose field key is the member name.
- Cap 12 KiB before the judge sees it; Jeb trims to 12 lines / 2,400 chars around the anchor.

### 2.3 The prompt's negative list is a JC3 artefact list

`chase_judge.PROMPT` enumerates, verbatim: a number equal to the field offset (an offset table), a count of
files/packages containing the name, a value from a register or memory with no constant visible, a store into
a stack frame (`[rsp+...]`/`[rbp+...]`), the field's own value changed (`+=`, `-=`, times delta time), and
"a JSON/analysis record written by the search tool (offset maps, name counts, verdicts)". Those six are the
ways this corpus lies. None of them is generic; a port must write its own list from its own failure modes.

### 2.4 The calibration corpus is JC3 data

- positives: `Research/BatmobileGrab/MODES.json` — same value in all four packages, `declared_type` float/int.
- found: `FOUND_CASES` with `(row, member, value, chase-file, line)` in `chase_calibrate.py`.
- negatives: `NEG_CASES` in the same file — `FInterpCurveFloat`, `FName`, `AnimNodeSequence`, `RVehicle` null
  reference, a 24-member `FFreeCameraConfig`, a runtime timer, a 3-point curve, a 6-point curve.
- owner/offset for every case come from `FOOTAGE.md` rows (`cc.parse_footage()`, `:98`), never from the case file.

### 2.5 Fixed paths and report

`E:\Modding\_shared\gamedata\BmAKgrab\chase\{cache, calib.jsonl, calib_runs}`; report
`tmp/freebuff/reports/smart-search.md` with the `CALIB-BEGIN/END` markers. The data lives outside the repo;
only the generated block is inside it.

## Part 3 — Port plan for `quiz_parser`

Target: the same two-stage shape over a question bank, calibrated on answers the bank already confirms.
Read-only inspection; nothing in `quiz_parser` was modified.

### 3.1 What `quiz_parser` already has (so the port is mostly extraction)

| generic capability | existing code | note |
|---|---|---|
| cheap stage-1 candidate list | `final_coverage.candidates()` — top `k/3` by question-text ratio, answer-text ratio, keyword Jaccard (`final_coverage.py:150`) | three rankings, de-duplicated; exactly the "ranked, capped" contract |
| cheap pre-filter with justified thresholds | `quizbank._find` (`:198`) — length bound, `real_quick_ratio`/`quick_ratio` floors at `JUDGE_FLOOR = 0.85` (`:257`), full ratio only for survivors | the same "rank cheap, cap, then look closely" idea as stage 1 |
| deterministic pre-judge decisions | `_word_swap` (`:234`), `_typo` (`:249`), `_same_words` (`:341`) in `quizbank.py` | typo → same; number change or ≤2 one-for-one swaps → different; else judge |
| judge call | `quizbank.judge_same` (`quizbank.py:311`) and `final_coverage.Judge.ask` (`final_coverage.py:90`) | both `temperature 0`, both strip ` thinking` |
| cache | `merge_judge_cache.json` (`quizbank.py:260`) and `final_coverage_cache.json` (`final_coverage.py:35`) | flat JSON, key = `sha256(prompt)` |
| offline behaviour | `judge_same` → `None` → not merged; `final_coverage` → `EXACT`/`NEAR`/`NONE` and `sys.exit(3)` (`final_coverage.py:224`) | already the right policy |
| held-out calibration seed | `final_coverage --calib` hides exact text matches "judge check" (`final_coverage.py:179`, applied in `candidates`, `:155-161`) | this is a positive family waiting to be built |
| known-answer ground truth | every saved attempt with `Correct Answer` markers (`quizbank.parse_d2l`), plus per-question `points/max` | the bank is *built from* the answers, so ground truth is abundant |

### 3.2 What to copy verbatim (no JC3 concepts)

1. `cache_key(prompt, model)` and the two-level `<xx>/<hash>.json` layout — **including the model name in
   the key**. This is a real defect today: `quizbank.judge_same` keys on `sha256(prompt)` alone (`:315`)
   and `final_coverage.ask` likewise (`:92`), so pointing `QB_JUDGE_URL` at a different model silently
   reuses the previous model's verdicts. The JC3 key is `sha256(model + "\0" + prompt)`.
2. The per-verdict atomic write. `quizbank._judge_save` already merges disk then `os.replace`s a temp file
   (`:282-295`) — keep it and add the model to the key. `final_coverage.ask` writes the whole cache
   non-atomically (`CACHE_FILE.write_text(...)`, `:118`): two workers can tear it. Replace with the
   per-hash file layout; no merge, no race.
3. `judge_online()` (health probe, short timeout) + exit 3 + "list the candidates unjudged". `quizbank`
   has a `/v1/models` probe with a **   size guard** (`JUDGE_MIN_B = 4`: "a 1.5B model calls everything SAME", `:259`) — that guard is a genuinely portable insight and belongs in the kit.
4. `parse()` returning `None` for anything that is not a valid verdict, and `None` never being cached as a
   decision. `final_coverage` already refuses to cache unparsable output (`:114-115`).
5. The append-only JSONL runner (`chase_judge.main`) — 20 lines, `done = {id}` from `--out`, skip, flush.
6. The calibration skeleton: `--build/--run/--score/--render/--check`, provenance re-verification, the
   `CALIB-BEGIN/END` generated block, and `--check` returning 1.
7. `--sweep` for any judge that exposes a score (`p`) rather than a label — free threshold tuning, no model call.
8. `best_threshold()` tie-break: highest recall at zero false positives, ties to the **lower** threshold.

### 3.3 What to swap

| JC3 thing | quiz_parser replacement |
|---|---|
| `member_candidates(member, owner, offset, type, routes)` | `bank_candidates(question, answer, k=12)` wrapping `final_coverage.candidates()`; return `{"id", "source", "route", "snippet"}` where `source` = `<quiz key>/<norm hash>` and `route` ∈ `("text","answer","keyword")` (which of the three rankings found it) |
| `--routes exe,text` | `--routes text,answer,keyword` (validate against the port's own tuple) |
| `PROMPT` (member/owner/offset, set-the-default question) | `quizbank.JUDGE_PROMPT` (SAME/DIFFERENT, two-question merge) **or** `final_coverage.PROMPT` (SAME/COVERS/RELATED/UNRELATED with answers) — two prompts, two tools, one kit |
| verdict `{found, value, why}` | `{verdict, rank, why, p?}`; `rank = RANK[verdict]` (0..3). Keep a `found`-style boolean only as `rank >= 2` for SUMMARY compatibility, never as the stored truth |
| `literal_in(snippet, expect)` | `answer_in(candidate, expect)` — exact raw text, else  `match_option`-grade similarity with the ambiguity refusal (`quizbank.match_option`, `:440`) |
| `owner/offset` from `FOOTAGE.md` | `(question, answer)` from the graded attempt that supplied them; provenance string = `graded/<file>.txt` + the normalized key |
| fixed `E:\Modding\...` cache path | `Path(__file__).parent / "judge_cache"` or `QB_CACHE` env; no absolute paths |
| `MODES.json` four-package agreement | see §3.4 — held-out attempts are the equivalent proof |

### 3.4 Calibration mapped onto the bank's known answers

The bank has something JC3 does not: **the answer is the ground truth and it is textual**. Build the three
families mechanically, no hand-typing:

- **positive (held-out recovery).** Pick a question whose `correct` answer is confirmed in attempt A
  (D2L `Correct Answer` marker, or a full-score graded quiz). Rebuild the bank with attempt A excluded
  (the bank is rebuilt every run from `graded/`, `quizbank.build_bank`, so this is a flag, not a fork).
  Ask the pipeline the question; the known value is the answer text; success = the same question merged
  back **and** the same answer. This is `final_coverage --calib` generalised into a scored case.
- **found (reach).** For a question already in the bank with a known answer, `reach=true` when any
  candidate's normalized text is identical. Recall at reach then measures the judge alone — the metric
  `quiz_parser` cannot see today.
- **negative (must not merge).** `quizbank._word_swap` already enumerates the families that make two texts
  look close and mean different things: a changed number, `best`/`worst`, `BFS`/`DFS`, `start`/`destroy`,
  `true`/`false`, and a True/False statement versus a multiple-choice set with **disjoint options**
  (`_find`'s option-overlap guard). Generate these pairs from real bank entries (replace one word
  with its opposite from a small list of pairs the bank actually contains). Any SAME on such a pair is a
  false positive. Cost: zero model calls to build, one verdict each to score.
- **negative (coverage direction).** A bank question that merely **RELATED**-covers an exam question must
  not be counted as COVERS; `final_coverage`'s docstring already warns the 8B judge "errs strict: close
  paraphrases sometimes come back RELATED" — so calibrate the *false-negative* direction too, with
  human-confirmed paraphrases as the positives.

Mapping of the shared metrics:

| metric | JC3 | quiz_parser |
|---|---|---|
| positive recall | known float re-found | held-out answer recovered |
| precision | right `found=true` / all `found=true` | right SAME (answer matches) / all SAME |
| negative FP | literal default claimed on a curve/struct | SAME on a word-swap pair |
| reach | literal in a snippet | exact question text in the candidate list |
| unparsable rate | non-JSON reply | non-`{verdict}` reply |
| s/candidate | uncached judge seconds / verdicts | same |

### 3.5 File layout and migration order

Port into `quiz_parser/quiz_parser/` (read-only today; these are new files, nothing edited):

```
judge_kit.py       # Judge class: health probe, size guard, cache key w/ model, atomic per-hash write,
                   # parse()->None, .ask() -> verdict dict; no corpus knowledge
quiz_search.py     # stage 1 wrapper + CLI, exit 0/2/3, --expect/--json-out/--no-cache
quiz_calibrate.py  # --build/--run/--score/--render/--check/--sweep over calib.jsonl
calib.jsonl        # generated
calib_runs/<promptver>/<case>.json + _search.txt
```

Order, smallest first — each step is independently verifiable:

1. **Add the model to both cache keys** (`quizbank.judge_same`, `final_coverage.Judge.ask`) and switch
   `final_coverage`'s cache write to atomic replace. No new files; behaviour only becomes correct.
2. Extract `judge_same`/`Judge.ask` into `judge_kit.py`; make `quizbank` and `final_coverage` import it.
3. `quiz_search.py` + `--json-out`, so one question can be inspected with candidates and verdicts.
4. `--build` the held-out positive family and the word-swap negatives from `graded/`.
5. `--run`, `--score`, `--render` into a generated block; `--check` with provenance re-verification
   (the answer text must still be in the file it came from).
6. `--sweep` only if a scored judge is introduced (a `noul`/`p` model); label judges need none.

Expected win, stated honestly: on this project the two-stage design's value was **diagnostic** (reach vs
judge recall) more than accuracy — the small judge recalled one of 28 reachable values. `quiz_parser`'s
current no-LLM path (`_find`'s typo/word-swap rules) is already stronger than a 4B judge on the
lexical cases, so the calibration should be read as "when is the judge worth calling", not "replace the
rules".

## Part 4 — Claude skill packaging

The generic half is a good skill because it is a **procedure with contracts**, not a codebase. Outline:

```markdown
---
name: smart-search
description: Find a value or a matching record in a large local corpus by searching cheaply, then
  judging candidates with a small local model, with caching and calibration on known answers. Use when
  grep/ripgrep over thousands of files or a disassembly is too noisy to read by hand.
---

# Smart search

## When to use / when not
- use: many candidate hits, a local llama-server available, some known answers to calibrate on
- do not: a handful of hits (just read them); no ground truth at all (build three by hand first)

## The two stages (contracts)
- stage 1: candidates(query) -> [{id, source, route, snippet}], ranked, capped, snippet <= 12 KiB
- stage 2: judge(prompt) -> {found|verdict, value|why, p?}; unparsable -> None, never false

## The cache
- key = sha256(model + "\0" + exact prompt); path cache/<key[:2]>/<key>.json
- never cache a partial or an unparsable verdict; --no-cache for calibration

## Offline
- health probe, 3 s; offline -> print candidates unjudged, write nothing, exit 3

## Calibration (the part that makes it trustworthy)
- three families: positive (known value), found (reach), negative (no literal exists)
- --build from provenance, never hand-typed; --score; --render into a marker block; --check re-verifies
- report reach separately from recall: search miss vs judge miss

## Exit codes
0 judged, 2 bad args, 3 judge offline, 1 calibration check failed

## Worked example
scripts/smart_search.py --query ... --expect <known> --json-out case.json

## Checklist before trusting a hit
1. was it reachable? 2. did the judge see the literal? 3. verify the source line yourself
```

Packaging notes:

- **Progressive disclosure.** `SKILL.md` stays a one-screen procedure; the working code goes in
  `scripts/` (`judge_kit.py`, `smart_search.py`, `calibrate.py`), the prompt templates in
  `references/prompts.md`, the calibration shapes in `references/calibration.md`.
- **Keep every JC3 noun out.** No `chase_candidates`, no `MODES.json`, no `exe`/`text` route names, no
  `E:\Modding` path, no R4. The skill's example corpus should be a generic one (log lines, source files).
- **Ship the negative list as a template, not a rule.** The six JC3 ways the corpus lies become a
  `references/prompts.md` section titled "how a snippet lies", with a slot per project.
- **Ship the two judge adapters**, because the decision-model path (`p`, window, `prompt_version()`) is the
  non-obvious part and is model-specific.
- **Say the limitation in the description.** On a 4B judge the recall, not the speed, is the constraint;
  the skill should tell the reader to calibrate before trusting, and to prefer deterministic rules when
  they already decide the case.

## What is still UNKNOWN

1. **Whether the port's negatives transfer.** The word-swap families are enumerated from real files here,
   but no quiz_parser calibration has been run (read-only), so their false-positive counts are UNKNOWN.
2. **The right judge size for quiz_parser.** The size guard (`JUDGE_MIN_B = 4`) is a heuristic from one
   1.5B observation; the quiz corpus may need a different floor. Settled by step 4 of the migration.
3. **Whether held-out recovery leaks.** `lookup()` searches every other quiz for a question, so a held-out
   answer can come back from the *graded* quiz. The builder must exclude the source attempt **and** check
   `sources` on the returned entry; not implemented, therefore UNKNOWN.
4. **Cache invalidation across prompt edits in quiz_parser.** `final_coverage_cache.json` has no prompt
   version and no model; both files predate the versioning, so old entries cannot be attributed. Do not
   trust them; start a fresh cache directory when the port lands.
