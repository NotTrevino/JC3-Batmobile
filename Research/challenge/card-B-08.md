## 1. B08-01 — `Effect` = `hash_jenkins(full .effc path)`

**Why the card rests on it.** Everything in Done 1 is a hash→path lookup. `bm_fx.py`'s
`effect_vocabulary()` builds `mask(hash(path)) → path` from `FX_TABLE.jsonl`, and `plan()` decides an
object *is* the flame by comparing its `Effect` value to that hash. If the encoding were wrong (name
without extension, basename, backslashes, …), the decode would still look plausible and the Done line
would be measuring the wrong thing.

**Test — encodings.** For each of three fleet exhaust effects I computed the hash of six plausible
encodings and counted matches in the 955-path vocabulary:

```
--- effects/jc_vehicles/exhaust/car_cycle_base_dual_nitrous.effc  hash=3518298851
    full path        matches=1 ['effects/jc_vehicles/exhaust/car_cycle_base_dual_nitrous.effc']
    path minus ext   matches=0
    basename         matches=0
    basename-noext   matches=0
    backslash+path   matches=0
    UPPER path       matches=0
--- …/car_cycle_base_dual.effc        hash=2168109282   full path matches=1, the other 5 = 0
--- …/car_cycle_base_nitrous.effc     hash=1989271107   full path matches=1, the other 5 = 0
```

**Test — the signed/unsigned bridge.** The XML writes `-776668445`; `USAGES.json` records
`3518298851`. `bm_fx.umask()` adds 2³² for negatives, and `sint()` reverses it. Both directions
round-trip on the two emitters and on all 32 hashes.

**Result: HOLDS.** The encoding is the full lowercase path with extension, hashed by the project's
same Jenkins function (`bm_entity.h`), and it is the *only* encoding that matches. This is a genuine
decode, not an inference.

## 2. B08-02 — 32/32 resolve to exactly one path

**Why the card rests on it.** The Done line's phrasing ("resolve to exactly one") is a uniqueness
claim: if two `.effc` paths hashed to the same 32-bit key, "resolved" would be ambiguous.

**Test — collisions and counts.** Over the 25,025 `.effc` rows (955 distinct paths):

```
$ python  # mask(h(path)) -> set(path)
distinct effc 955
hash collisions among 955: 0 []
distinct 32 objects 48
```

**Test — is 32/32 surprising?** A random 32-bit value lands in a 955-element set with probability
955/2³² ≈ 2.2×10⁻⁷; 32 independent hits would be ≈ 7×10⁻⁶. The rate of hits is therefore evidence
that the hash really is the path hash, not a coincidence.

**Result: HOLDS.** One correction to the wording: the object count is not 48 "effect objects" in the
graph — 48 of the **89** objects in the four effect classes carry an `Effect` value; the other 41 are
sound-only attachments. Counts re-derived: 47 `SAttachedEffect` + 20 `SDynamicAttachedEffect` + 12
`SAttachedEffectTable` + 10 `SDynamicAttachedEffectTable` = 89 class objects, 48 with `Effect`.

## 4. B08-04 — Done 2 is evidence about B-08's edit

**Why the card rests on it.** §12 quotes *"89 (usage, object) pairs, 0 outside the 155-value fleet
usage vocabulary"* as the proof that the usage hash is valid.

**Test — what the vocabulary is.** `USAGES.json` `inputs.detail_files = 232`; the donor graph is one
of those 232 files (`E:\Modding\_JC3grab\detail\v0300_…_civilian_01.ee.json` exists and its objects
carry these usages). The 155 values are the union over those graphs. So for any value already in the
donor graph:

```
$ python  # distinct usage values in bm-008's .epe
pairs 89 distinct values 57
rarest usage carriers among the 232 (count,value):
  [(14, 309669749), (14, 2102817021), (22, 3156189656), (27, 802437523), …]
```

Every one of the donor's 57 values is carried by ≥14 of the 232 entities, i.e. the set is a union
that contains the subject. `0 outside` is therefore arithmetic, not a measurement. The tamper test

**Test — did B-08 create the usage?** No. The two emitters' `Usage -97082140` is in the **base**
`bm-005` graph, unchanged by the edit; the diff (§17) does not touch `Usage`. Done 2 was already true
before B-08 ran.

**Result: WEAK.** The Done line is satisfied, literally, and the card is entitled to it. But it is
not evidence that the value is semantically right, and it cannot fail on any untouched object. The
useful guard the tool does add — `emitter_usage == [4197885156]` and `emitter_usage_name ==
["EngineNitro"]` — depends entirely on the `EngineNitro` name (B08-07).

## 11. B08-11 — the decoded socket basis is a safe orientation

**Why the card rests on it.** The card writes one matrix for both emitters and ships it. Limit 1
says the emission axis is `UNKNOWN`, but the artifact nonetheless commits to a specific basis.

**Test — read both bases in the vehicle frame.** `bm_entity.mat` writes rows 0–2 = local X/Y/Z,
row 3 = origin (`X = up × forward`). With the socket's `forward_jc3 ≈ (0,0,−1)` and `up_jc3 ≈
(1,0,0)`:

| row | donor matrix (bm-005) | new matrix (bm-008) | car-space meaning of the new row |
|---|---|---|---|
| 0 | (1, 0, 0) | (0, 1, 0) | **+Y = up** |
| 1 | (0, 0, 1) | (1, 0, 0) | **+X = the car's right** |
| 2 | (0, −1, 0) | (0, 0, −1) | **−Z = toward the nose** |

Frame facts, all from `SOCKETS_JC3.json`: `+Z` is the rear (`Headlight_*` z ≈ −3.0,
`Afterburner` z = +3.39, `body_box` z ∈ [−3.42, +3.605]); `+Y` is up (`body_box` y ∈ [0.091, 2.362]);
`LWheelLight` x = −1.208 so `+X` is the car's right side.

**Test — which row must the emission axis be?** A car exhaust at the rear must emit toward `+Z`.
Among the donor's three rows, **exactly one** is `+Z`: row 1. Rows 0 (+X, sideways) and 2 (−Y, into
the ground) are impossible for a rear exhaust on *both* pipes with identical bases. So the
fleet-consistent reading is: **emission axis = local Y**. In the new matrix local Y = `+X` → the
plume is yawed **90° to the car's right**. Under the card's alternative reading (emission along the
socket's forward = row 2) it points **−Z, i.e. 180° into the car**. Under row 0 it points **straight
up**. There is no row that points out of the jet.

**Test — count the frame.** Both matrices are proper rotations (determinant +1), so this is not a
degenerate/left-handed case; it is a real 90° yaw plus a 90° roll relative to the donor.

**Result: BROKEN.** The "unknown semantics" limit is honest, but the written basis is not neutral: in
the only frame reading that is geometrically possible on the donor's own matrices, it is 90° wrong,
and in the card's own reading it is 180° wrong. A Q-1 observation will see a flame that is sideways
or firing into the chassis, not a flame whose direction is merely unverified.

## What this means for the card

1. **Keep the hash work.** B08-01/02/06/08 are solid and independently reproducible: the effect and
   usage members are exact Jenkins hashes of the paths/names, with no collisions and no alternative
   encoding. That part of the card is better than its own wording.
2. **Fix the basis before anything installs.** The written matrix has no rearward axis; the donor's
   has exactly one. Either flip/rotate the socket basis (using the donor's own matrices as the
   convention) or record the emitters as position-only and prove the orientation in Q-1 — but do not
   call the current matrix "the socket's decoded basis" as if it were safe. A cheap offline test
   exists: build the same matrix from the donor's basis (local Y → +Z) and compare.
3. **Use one emitter or the single effect.** The fleet's own convention for a one-nozzle car is one
   object; `car_cycle_base_nitrous.effc` exists in the same vocabulary. Two objects at one point is a
   configuration no fleet vehicle uses.
4. **Move or disable the six other emitters.** `exhaust`/`exhaust2`/`tjump*` are inside the Batmobile
   body at the Serpente's rear. T-17 already names `SideExhaustL`; if the card's Do really excludes
   them, the release must not ship them at donor coordinates.
5. **Re-open T-FX9 and T-FX13.** Both "no carrier" rows are refuted by files in the card's own
   vocabulary (`car_speedrom_heater.effc` + `z80_exhaust_heat_l/r`; `bullet_eject_capstone.effc` +
   the graph's own `ShellEjection`). The method that missed them is a keyword search over 955 paths,
   not a search over attachments.
6. **Regenerate the build.** bm-008 is stale against the B-05 rework and its Done check now exits 1;
   the base-sha guard must compare against the *published* hash, not a hash recomputed in the same
   run.

## Limits of this review

- No game was launched and no `.effc` was rendered, so "the flame points sideways" is a frame
  inference from the matrices and the vehicle's own geometry, not an observed frame. The `.effc`
  decode used here (`jc3fx.decode`) is header/rows only; I did not try to prove what "dual" means
  inside the effect (two plumes vs two pipes) — the fleet usage pattern (17 dual cars, 115 single
  cars, 6 single-object dual cars) is the evidence used instead.
- `EngineNitro`'s *trigger* is not decoded anywhere in the repo; B08-07 is marked WEAK for exactly
  that reason, and only a game probe (Q-1) can settle it.
- `bm_fx.py --check` was not executed (it writes `tmp/b08/built.xml`); §17 reproduces its one
  substantive comparison in memory with the same `bm_entity`/`jc3wiring` functions.
- All external reads were the documented R10 grab under `E:\Modding\_JC3grab\` (detail + entities),
  read-only; nothing there was written.
