## A4 · The traffic table keys on the full path string

**Claim.** T-WLD18: *"`settings/spawn_vehicle_defs.bin` (27,513 B, 86 records, 8 keyed) keys on the
**full path string**, not the leaf hash"* — the load-bearing reason the row is `keep`.

**Test.** Read the entry out of the archive and look for both hashes:

```
name_hash D2B46B49 LE: 1 hits at [896]      BE: 0
path_hash FC21B7E3 LE: 0 hits               BE: 0
# every parsed record's own leaf-name hash:
record name hashes found in first 4KB: 86 / 86
offsets: 44, 56, 68, 80, … max 1064 | distinct offsets mod 12: [8]
```

All **86** records have a `hash_jenkins(leaf)` entry, at a 12-byte stride in the file's first
1,064 bytes — a hash-keyed index with one entry per record. The **path** hash appears **zero**
times in the whole 27,513 B. The "record" the generator trusts is a string-adjacency heuristic
(`jc3traffic.py:99 def spawn_records` — it finds strings ending in `.ee` containing `entities`,
then looks for the leaf name in the *next two* strings and splits the intervening strings as tags);
it never reads the key. The donor's record body is one backslash path plus one NUL-terminated
comma-list:

```
…sportsmuscle\v0300_…_civilian_01.ee\0vehicle,ground,car,civilian,racing,modern,muscle,
kensington,sports,unarmed,unarmored,ambient,liberated\0v0300_…
```

**Does the *decision* survive?** Yes, and it can be proven better than the card proves it:

```
new leaf  hash 1A6A8B37 (443190071) LE occurrences: 0 | ASCII occurrences: 0
donor leaf hash D2B46B49 (3535039305) LE occurrences: 1 | ASCII occurrences: 2
```

**Verdict: BROKEN** as written (the key is the leaf hash, not the path; the path string is
payload; `8 keyed` counts pool keys, not records). The `keep` disposition and the "0 records"
conclusion **hold**.

Also in this section: *"satisfies 1 of 41 selectors"* — the 41 is a heuristic population
(`rules_from()` filters every string in `global.blo` by a token regex and the tag vocabulary), and
`t15_world.py:644` *asserts* `if selectors != 41: problems.append(...)`. The number is pinned, not
re-derived from a decoded rule table. **WEAK.**

## A5 · `BaseName` is `hash_jenkins(<family prefix>)`, and nothing more

**Claim.** §3: `| BaseName | 276735921 | derived (hash_jenkins("v0300"), holds 45/45 vanilla
vehicle drops) |`; §6 restates it as "strong but not a decoded field description".

**Tests.**

```
distinct prefixes among the 45: 40   distinct BaseName values: 40   holds per item: 45/45
```

So the rule is real across 40 families (not one family tested 45 times) — the arithmetic case is
stronger than the card claims. **But** the field's *meaning* is a string key, and the store proves
it:

```
vehicle items whose BaseName resolves in the store: 45 / 45
  v0300_car_kensington_sportsmuscle_civilian_01  Base=276735921 langs=11 en='KERNER SERPENTE R'
  v0603_car_urga_smalltank_rebel_01             Base=565126345 langs=11 en='URGA BKOLOS 2100'
  … every BaseName resolves in 11/11 languages to that family's model name
```

`hash("v0300") = 276735921` **is a pair in `profile/online.stringlookup`**, and its text is the
donor's name. Consequences the card never states: (a) the recipe's `BaseName` therefore still
points the Batmobile's family-name key at **"KERNER SERPENTE R"**, which is a name surface WLD-2
("everywhere JC3 names the vehicle") does not count; (b) the shipped mod does the opposite — all
45 added items have `BaseName == Name` (`mod_added_base_eq_name: 45`) while **0/80** vanilla
vehicle items do (`vanilla_vehicle_base_eq_name: 0`), i.e. two conventions ship and nothing decoded
says which one the game reads. That the mod's items work in-game is therefore evidence *against*
reading `BaseName` as a required family key.

**Verdict: WEAK.** The numeric rule holds (better than claimed); "derived family hash, nothing
else" under-reads a field that resolves to display text, and the one write precedent contradicts
the convention.
