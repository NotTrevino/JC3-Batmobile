### 4.2 `q3_session.py` — the four modes

1. **`--plan`** parses §9b between `#### Q-3` and `#### Q-4`, takes its 7 numbered items, and joins
   each to a `Working/Q/predictions.json` row (`Q3-1 … Q3-7`). Sub-checks whose prediction row is
   `blocked` are emitted as `band: null, status: "blocked: <id>"`; it never invents a band. The
   weapon takes are read from `t7_weapons_edits.json` (`T-WP1` fire rate/velocity, `T-WP2` burst),
   and the weapon-vs-target take reads `damage_predict.py table` at run time.
2. **`--preflight`** (run at the session, never offline) checks in order: game closed (`um win ps`);
   `um backup` receipt for the save folder; the RC installed and `install.ps1 -Action Verify` green;
   `MODLOG.md` carries `VX-APPROVAL:` whose approved `.ee`/`.toc` sha256 equal
   `Builds/bm-RC1/receipt.json`; `t23_closeout.py --check`, `t15_world.py --check`, `t_rows.py check`
   and `status_audit.py --check` all exit 0; windowed fixed size; one `um win shot` + 10 s
   `um win record` smoke test. It never launches the game; the user starts it and supplies the PID.
3. **`--record <id>`** validates the recording exists, its duration covers the check window, the
   measured value is inside the band (or the row is honestly `blocked`), and writes the per-check
   JSON. A value outside the band is written `FAIL`; it is not re-read until it passes (§9b).
4. **`--check`** proves the Done line: every sub-check has a `RESULTS.md` row with `measured`, `band`,
   `pass|fail` (or `blocked: <id>`), `recording` and `timestamp`; every recording path exists and its
   timestamp is inside the session window; each measured number equals the per-check JSON; every
   `blocked` row names a blocker that also exists in `Q3_CHECKS.json`; every §9b item 1–7 has at
   least one row. It prints `PASS: 7/7 items, N/N sub-checks recorded (K blocked), 0 missing` and
   exits 0 only when no row is missing or malformed.
