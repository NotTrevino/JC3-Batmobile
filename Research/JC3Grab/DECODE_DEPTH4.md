# JC3 Serpente decode depth 4 (G3-19b) - the `GeneralMkIII` payload, decoded

Generated by `Tools/scripts/decode_depth4.py --write`; `--check` recomputes
every number below and diffs it against the committed JSON. Nothing here was
run in the game: the `.rbm` bytes come out of the JC3 `.ee` archive through
`bm_rc`/`eetoc`, exactly as G3-19 took them.

Labels: **decoded** = file + offset, read from the bytes; **derived** = rule +
inputs, shown in place; **UNKNOWN** = what was tried and where the answer would be.

## 1. What the block is, by its hash

Each of the three files is header + three blocks, each `u32 type_hash` + payload
+ `u32 0x89ABCDEF`. G3-19 left the *middle* block undecoded, which is why the
block after it was never reached.

| file | size | block 0 | block 1 | block 2 | sum == size |
|---|---|---|---|---|---|
| `sportsmuscle_missile_base_signature_lod1.rbm` | 45912 | `CarPaintMM` 13051 B | `GeneralMkIII` 7126 B | `CarPaintMM` 25658 B | yes |
| `sportsmuscle_missile_base_signature_lod2.rbm` | 21842 | `CarPaintMM` 8587 B | `GeneralMkIII` 2592 B | `CarPaintMM` 10586 B | yes |
| `sportsmuscle_missile_base_signature_lod3.rbm` | 14590 | `CarPaintMM` 5455 B | `GeneralMkIII` 1214 B | `CarPaintMM` 7844 B | yes |

Block 1 is `GeneralMkIII`, hash **0x2CEC5AD5** (`rbm_geom.BLOCK_NAMES`), the block
type G3-19 could not enter. Blocks 0 and 2 are `CarPaintMM` (0x483304D6) and
decode to their exact end with the published decoder.

## 3. The 20-byte attribute stream, decoded

The shader's own reflection header (`generalmkiii.vb.txt`) says the vertex
carries POSITION0 (float, uses xyz), TEXCOORD2 (float, uses xyzw) and TEXCOORD3
(float, uses xy) - four components that are not position plus seven. The 8-byte
position record accounts for the four `POSITION` components (the `32767` is the
`w = 1.0`); the remaining three live in the 20-byte stream. Its fields, read at
the boundaries the bytes themselves show:

| offset | width | field | distinct | min | max |
|---|---|---|---|---|---|
| +0 | 2 | uv_u (s16 unorm) | 44/23/8 | 1906/1906/1906 | 32767/32767/32767 |
| +2 | 2 | uv_v (s16 unorm) | 21/9/3 | 24171/24262/28269 | 32767/32767/32767 |
| +4 | 2 | sentinel 1.0 (s16) | 1/1/1 | 32767/32767/32767 | 32767/32767/32767 |
| +6 | 2 | pad 0 (s16) | 1/1/1 | 0/0/0 | 0/0/0 |
| +8 | 4 | float x | 38/22/10 | 123.496/12484.8/21895 | 31488.5/51934.3/44924 |
| +12 | 4 | float y | 48/53/11 | 1679.63/2683.69/25081.6 | 63383.6/52851.9/48050.1 |
| +16 | 4 | marker 0x487FFFFF (f32) | 1/1/1 | 1.21635e+09/1.21635e+09/1.21635e+09 | 1.21635e+09/1.21635e+09/1.21635e+09 |

(Columns are lod1 / lod2 / lod3.) Three of the fields are constant on every
vertex of all three meshes - 243 vertices in total - so they are format markers,
not coordinates:

| file | `s16 @+4` == 32767 | `s16 @+6` == 0 | `u32 @+16` == 0x487FFFFF | vertices |
|---|---|---|---|---|
| `sportsmuscle_missile_base_signature_lod1.rbm` | 176/176 | 176/176 | 176/176 | 176 |
| `sportsmuscle_missile_base_signature_lod2.rbm` | 55/55 | 55/55 | 55/55 | 55 |
| `sportsmuscle_missile_base_signature_lod3.rbm` | 12/12 | 12/12 | 12/12 | 12 |

So the record is: `{s16 u, s16 v, s16 1.0, s16 0}` then `{f32 a, f32 b, f32
0x487FFFFF}`. The marker `0x487FFFFF` is the float one ULP below 2^18
(262143.9844), i.e. the same "1.0 in this field's own units" idea as the `32767` in
the position record - and it is the scale under which the float pair is unit-
ranged:

| file | a / 0x487FFFFF | b / 0x487FFFFF | both in [0,1) |
|---|---|---|---|
| `sportsmuscle_missile_base_signature_lod1.rbm` | 0.000471 .. 0.120119 | 0.006407 .. 0.241789 | 176/176 |
| `sportsmuscle_missile_base_signature_lod2.rbm` | 0.047626 .. 0.198114 | 0.010237 .. 0.201614 | 55/55 |
| `sportsmuscle_missile_base_signature_lod3.rbm` | 0.083523 .. 0.171371 | 0.095679 .. 0.183297 | 12/12 |

## 4. Candidate layouts, and what the oracles say

Each candidate was decoded and then measured against an oracle that is not
satisfied by accident. Verdicts: **UV set** (chart test), **rejected** (the
number is shown), **UNKNOWN** (nothing on disk decides it).

| candidate | oracle | measured | verdict |
|---|---|---|---|
| `(u,v)` s16 pair as UV | signed UV area keeps one sign on every triangle; texel density spread | 224/224 same sign, density p90/p10 2.06; 33/33 same sign, density p90/p10 4.12; 4/4 same sign, density p90/p10 1.52 | **UV set** |
| float pair / 0x487FFFFF as UV | same | 136+/88-, density spread 1.78e+03; 21+/12-, density spread 39.7; 1+/2-, density spread 7.52 | **rejected** - not a chart |
| `(u,v)` as octahedral normal | mean dot with the adjacent face normals ~1 | mean 0.126, min -0.812; mean 0.136, min -0.808; mean 0.113, min -0.658 | **rejected** |
| float triple as a normal | mean dot with the face normals ~1 | mean -0.284, normalized z 0.968..0.998; mean -0.261, normalized z 0.974..0.997; mean +0.006, normalized z 0.977..0.990 | **rejected** |
| float triple as a unit vector | \|v\| / 0x487FFFFF == 1 | worst rel err 0.033; worst rel err 0.027; worst rel err 0.023 | **rejected** - off by up to 3.3% |
| float triple as a tangent | \|dot with the surface normal\| ~ 0 | absmean 0.294; absmean 0.362; absmean 0.281 | **rejected** |
| s16 pair as a tangent | same | absmean 0.593; absmean 0.495; absmean 0.526 | **rejected** |
| skin weights | a weight set needs 0..1 weights summing to 1 plus joint indices | max float 6.338e+04; max float 5.285e+04; max float 4.805e+04 | **rejected** - the record holds no weight/index field pair, and the block is unskinned (single 20-byte stream; the skinned shader variant declares an extra `uint4` input) |

The one positive result is not marginal *for these three payloads*: the unorm16
pair's signed UV area carries the same sign on every triangle of every file, and
its texel density does not vary by more than a factor of ~4 across the mesh -
which is what a real unwrap looks like and what neither a normal encoding nor a
colour can produce. Section 5 shows how far that carries across other blocks.

The float pair is *not* a second chart of this surface (mixed winding, above),
is not a normal (a constant third component puts every normalized triple within
14 degrees of +z - z in 0.968..0.998 - while the geometry's face normals point
everywhere, so the best mean dot any of the three reaches is 0.006), and is not an affine
function of the UV chart or of a position axis: the best fit against the chart or
against position leaves a worst residual of 45%/47%/48% of the field's own range (lod1/
lod2/lod3). What *is* established about it: the float at +8 is a function of
position - identical across coincident vertices in 40/12/0 of the 40/20/6 groups - while the
float at +12 is not (0/0/0) and neither is the unorm16 pair (0/3/2 - those are the UV
seams) - and both are per-vertex. Their joint meaning stays **UNKNOWN**
with the answer in the shipped shader body, which is not in the project - only
the reflection header is (`generalmkiii.vb.txt`, 73 lines, no instruction list).

## 5. The same invariants elsewhere in the archive

To separate the *block format* from these three meshes' accident, the same
fields were read from every `GeneralMkIII` block in a fixed sample: all `.rbm`
entries of the Serpente bundle, then the meshes of a sorted strided slice of the
233 vehicle bundles in the game index.

| item | value |
|---|---|
| `.rbm` files opened (Serpente bundle + 12 vehicle bundles) | 3261 |
| files carrying a `GeneralMkIII` block | 117 |
| `GeneralMkIII` blocks framed / vertices | 126 / 56319 |
| blocks with a uniform 20-byte record | 126 / 126 |
| marker `0x487FFFFF` at +16 on every vertex | **106 / 126** |
| `s16` at +4 == 32767 on every vertex | 28 / 126 |
| `s16` at +4 == 0 on every vertex | 73 / 126 |
| `s16` at +6 == 0 on every vertex | 101 / 126 |
| float pair inside +-2^18 after / 2^18 | 126 / 126 |
| positions inside the block AABB | 126 / 126 |
| unorm16 pair is a UV chart (one winding sign) | 28 / 126 |
| ... of the blocks with `s16@+4 == 32767` | **10 / 28** |
| ... of the blocks with `s16@+4 == 0` | 18 / 73 |

What the sample settles: the *shape* of the record - 8 bytes of unorm16, two
floats, and a float last - is the block type's (all 126 blocks divide into 20 bytes
per vertex), and the last float is the `0x487FFFFF` marker on 106 of them.

What it does **not** settle is the fields' meaning. The field at +4 is 32767 on
28 blocks and 0 on 73 (the three target files are in the first group); the
unorm16 pair is a single-sign chart on 28 of the 126 blocks, and the split does not
follow +4 either (10 of the 32767 group, 18 of the 0 group). So the three target
payloads are decoded, and the block *type* keeps the same field widths, but the
attribute semantics are **not** fleet-wide: on most blocks the same 20 bytes carry
something this script cannot name. Per-block witnesses, all framed the same way:

* `sportsmuscle_missile_base_signature_lod1.rbm` - 176 vertices, 672 indices, stride 8, `(u,v)` distinct 44/21, `s16@+4` 32767, float pair +0.000..+0.242 of marker, marker 0x487FFFFF
* `apc_weapon_mount_horizontal_lod1.rbm` - 876 vertices, 1968 indices, stride 8, `(u,v)` distinct 144/149, `s16@+4` 0, float pair -0.249..+0.249 of marker, marker 0x487FFFFF
* `oldjeep_antenna_lod1.rbm` - 289 vertices, 984 indices, stride 16, `(u,v)` distinct n/a/n/a, `s16@+4` n/a, float pair no uniform 20-byte record, marker n/a

2 block(s) in the sample have no uniform 20-byte record at all: they are the
interleaved-position variant (position stride 16, `jc3geom`'s second case), whose
attribute region does not divide by the vertex count, so the framing of section 2
does not apply to them unchanged. That is a limit of this script, not a decode.

Blocks that did not satisfy the invariants: oldjeep_antenna_lod1.rbm: no uniform 20-byte record (interleaved stride); oldjeep_antenna_lod2.rbm: no uniform 20-byte record (interleaved stride); buggy_vdova_89_base_l_signature_lod1.rbm: UV chart flips (104+/348-); buggy_vdova_89_base_l_signature_lod2.rbm: UV chart flips (51+/134-); buggy_vdova_89_base_l_signature_lod3.rbm: UV chart flips (20+/49-); buggy_vdova_89_base_l_signature_lod4.rbm: UV chart flips (10+/26-); buggy_vdova_89_base_r_signature_lod1.rbm: UV chart flips (348+/104-); buggy_vdova_89_base_r_signature_lod2.rbm: UV chart flips (129+/54-); buggy_vdova_89_base_r_signature_lod3.rbm: UV chart flips (45+/22-); buggy_vdova_89_base_r_signature_lod4.rbm: UV chart flips (25+/11-).
