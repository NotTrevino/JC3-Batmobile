### 2.1 Texel block size per format

Solved, not assumed: per file each candidate in {8, 16, 32, 64} bytes per 4x4 block is
tried and only the one whose chain sum equals the payload survives (O3); the survivors
must form a function of the format id (O4).

| format id | files | bytes | base texels | bytes per 4x4 block | bytes/texel | name (project precedent only) |
|---|---:|---:|---:|---:|---:|---|
| 77 | 66 | 68988624 | 57386496 | 16 | 1.00 | glass BC3 (`tex2ddsc.py:20-22`) |
| 71 | 46 | 4088832 | 32075776 | 8 | 0.50 | colour BC1 (`tex2ddsc.py:5-7`) |
| 87 | 3 | 541056 | 135168 | 64 | 4.00 | UNKNOWN |
| 83 | 1 | 22000 | 4194304 | 16 | 1.00 | normal BC5 (`tex2ddsc.py:6`) |

Format 87's 64 bytes per 4x4 block is 4 bytes per texel, and its three files store
exactly width x height x 4 bytes at level 0 (`t_spherical_ramp`, `t_flare_headlight_ramp`:
256 x 256 x 4 = 262144 = payload; `erosion_smallcurve_soft`: 256 x 16 x 4 = 16384).  That
is consistent with an uncompressed 4-channel format, but no project decoder or export
proves the channel layout, so its identity stays UNKNOWN.

The names column is **not** byte evidence: no project reader decodes the blocks into
pixels, and the id -> codec names come from `Tools/scripts/tex2ddsc.py`, whose docstring
records them as the formats `ConvertTexture.exe` was driven with.  The block *sizes* are
decoded here; the codec identities are precedent.

### 2.2 The 84-byte tail is the omitted-mip table

`k = mip_count_full - mip_count_in_file` (78 records over 116 files).  Record `i` is
`(u32 offset, u32 size, u32 tag)` describing the level `k-1-i` - the levels the file does
*not* store, listed largest-absent first.  `size` equals that level's block price,
`offset` its prefix sum, `tag` 0x01000010 on every record, and the rest of the 84 bytes
is zero.  The identity that closes it:

    full chain (levels 0..mip_count_full-1) == payload + sum(record sizes)
    104034368 B == 73625664 B + 30408704 B

Stored mips: 1013 over 116 files, laid down from offset 128, tiling to EOF with zero residue
(first stored level: {'0': 71, '1': 21, '2': 16, '3': 7, '4': 1}).  71 of 116 files store the whole chain and 45 omit levels; the
table is empty on those 71, which is why its pad is zero on all 116.

## 5. UNKNOWNs

1. **Texel contents.** The block *layout* is decoded (size, offsets, tiling); no decoder
   turns a block into pixels.  Would need a BCn decoder and a reference image; not
   attempted here, and not needed for byte accounting.
2. **Format 87's codec.** Its block size is decoded (see 2.1); no name is.  Would need a
   texture that uses it exported by `ConvertTexture.exe`, or the engine's format enum.
3. **Header fields of unknown meaning.** `0x06` (values ['0', '5', '6', '8', '9']), flags `0x12` (values ['0', '1', '8', '9']) and
   the constant 16 at `0x28`.  Values are decoded on every file; their meaning is not
   carried by any check here.
4. **Why a mip level is omitted.** The table says which levels are absent and what they
   cost; why the cooker dropped exactly those (streaming size, editor setting) is UNKNOWN.
