**Grading rule (stated because G3-12b's numbers are quoted against it).** FULL means every
byte of the file belongs to exactly one decoded region whose offset and size are proven, the
regions tile `[0, len)` with zero residue, and every *variable* field is either decoded or
in a named UNKNOWN range. It does not mean every field's meaning is known - section 4 lists
what is still unnamed. G3-12b graded a file PARTIAL for holding bytes nothing read; none of
the 120 files holds such a byte any more.

### 1.1 The table G3-12b called opaque

`mip_count_full - mip_count_in_file = k` and the table holds exactly `k` records of
`(u32 offset, u32 size, u32 tag)`:

- record `i` describes the mip of level `k-1-i`, i.e. the absent levels are listed from the
  largest absent level down to level 0 (**derived**: `k` and the record index),
- `size` is that level's stored byte count under the format's block size (**derived**; it
  equals the mip price of section 1.2 on all 78 records),
- `offset` is the prefix sum of the sizes before it (**derived**: the records reproduce
  `0, s0, s0+s1, ...` exactly on all 78 records),
- `tag` is `0x01000010` on every record of every file (decoded: 78/78 records).
- the slots after the last record are zero (**decoded**: `tail_rest_zero` on 116/116), and
  `k <= 4` so the 84-byte region is exactly 7 slots of 12 bytes.

The oracle is not the sum but the **full-chain identity**: the mips of levels
`0 .. mip_count_full-1` cost `size_body + sum(record sizes)` on 116/116 files. That is what
makes the table the absent texel bytes rather than a coincidental number sequence: it would
fail if a level were misnumbered, a block size wrong, or the table a list of something else.

`k` distribution over the 116 files: 0 -> 71, 1 -> 21, 2 -> 16, 3 -> 7, 4 -> 1. The 71 files with `k = 0` are exactly the files
whose stored chain is the whole chain (G3-12b's zero-tail FULLs); no file has both a
complete chain and a non-zero table.

## 2. `.pfxc`: a 68-byte wrapper around one packfile that runs to EOF

### 2.1 The wrapper

`PFX\0` at 0, then four u32 = [1, 1, 3, 0] on 4/4, then zeros to 0x44 (decoded: the 48 bytes
0x14..0x44 are zero on 4/4); `0x57E0E057` sits at 0x44 and is found by its own magic, not
assumed.

### 2.2 The packfile, tiled by its own sizes

Header words: magic `0x57E0E057`, version `0x10C0C010` (`hk_2014.1.0-r1`), layout rules
`0x01000108`, 3 sections, contents index 2. The header is 64 bytes of fixed fields plus 3
section records of 64 bytes = 256, and `__classnames__` starts exactly at 256.

| region | offset | size | source of the number |
|---|---:|---:|---|
| PFX wrapper | 0 | 68 | the packfile magic at 0x44 |
| packfile header | 68 | 256 | `__classnames__`'s data offset |
| `__classnames__` | 324 | 256 | the section record's data + end fields |
| `__types__` | 580 | 0 | empty (data 512, end 0) |
| `__data__` object bodies | 580 | 1600 | the data record's local-fixup offset |
| `__data__` local fixups (16 x 8) | 2180 | 128 | lf..gf |
| `__data__` global fixups (8 x 12) | 2308 | 96 | gf..vf |
| `__data__` virtual fixups (8 x 12) | 2404 | 96 | vf..ex |
| | | **2500** | = the file length on 4/4 |

**Why G3-12b saw 512 unread bytes.** It read the `__data__` record's last field (1920) as an
*absolute* packfile offset, so the packfile appeared to end at 0x7C4 and 512 bytes appeared
to follow it. The data section's own fixup offsets show the field is the section's **length**:
the local fixup slots start 1600 bytes into the section and they are the table at file 0x884,
1600 bytes past the section start 0x244. Bodies 1600 + local 128 + global 96 + virtual 96 =
1920, and 0x244 + 1920 = 0x9C4 = 2500 = EOF. The 'trailing blob' was the data section's own
tail: 192 bytes of object-body end - the end of `hknpConvexPolytopeShape`, all of
`hkRefCountedProperties` and all of `hknpShapeMassProperties` - followed by the three fixup
tables.

Objects (**decoded** from the virtual fixup slots through the class-name table, extents
derived as the next object's offset):

| data offset | class | extent |
|---:|---|---:|
| 0x0 | `hkRootLevelContainer` | 160 |
| 0xA0 | `hkxScene` | 336 |
| 0x1F0 | `hknpPhysicsSceneData` | 64 |

### 2.3 Inside the bodies: the polytope's faces and corner list

`hknpConvexPolytopeShape`'s body is 400 bytes at data offset 0x460 and straddles the offset
depth2 called the blob start. Its own header words at +0x30 / +0x44 / +0x48 give
`vcount pcount icount` = 8 / 6 / 24 (**decoded**).

Body layout, closed to the byte (`400` = its extent, `1700` = data offset 0x460):

| region | offset | size | reading |
|---|---:|---:|---|
| header | 1700 | 80 | shape words, vcount/pcount/icount at +0x30/+0x44/+0x48 |
| vertices | 1780 | 128 | 8 x 16 bytes |
| planes | 1908 | 96 | 6 x 16 bytes |
| sentinel slots | 2004 | 32 | 2 x `(0,0,0,0xFF7FFFEE)`, identical on 4/4 |
| face block | 2036 | 32 | 6 records of (u16 corner offset, u8 count = 4, u8 code) + 8 bytes of 0x7F fill |
| corner list | 2068 | 24 | 24 vertex indices, all < 8 |
| 0x7F fill | 2092 | 8 | jc3hkx's PAD_BYTE tail |

The face-record rule (record `i`'s u16 = 4i, u8 = 4) occurs exactly once in each file, so the
block is located rather than fitted.

The records address the corner list exactly: record `i`'s u16 is the sum of the counts
before it (`[0, 4, 8, 12, 16, 20]`), each count is 4, so `pcount * 4 == icount` (**derived**). Each of the 8
corners appears exactly 3 times across the 6 quads (**decoded**: the multiplicity map),
i.e. a closed hull of 8 corners and 6 faces.

Independent cross-check: `jc3hkx.decode_polytope` on the same object returns the same
24 indices byte for byte and the same vcount/pcount/icount on 4/4 files.

## 4. UNKNOWNs and why

Each is a named field or range whose bytes are attributed but whose meaning is not proven.

- `.ddsc` tag `0x01000010` on every omitted-mip record: value decoded, meaning UNKNOWN. It is
  not the block size (format 71's blocks are 8) and not a per-record value (identical on all
  78 records); tried: per-record u16/u32 reads against level, size and offset - no field
  mapping. The table closes without it, so it stays a named constant.
- the u32 at 0x28 (= 16 on 116/116): value decoded, meaning UNKNOWN. Not the block size and
  not a floor on mip size (1x1 mips are 8 bytes in format 71).
- the byte at 0x06 (0, 5, 6, 8, 9): value decoded, meaning UNKNOWN.
  It is not a function of (format id, width): format 77 at width 1024 carries 5/9.
- the flags at 0x12 (0, 1, 8, 9): values decoded, meaning UNKNOWN.
  Not a function of (format, width, mip counts): those are equal for 0/8 yet the flags
  differ (format 77, width 1024, mips 11/11).
- **why** a file stores the small mips and lists the large ones as absent: the identity in
  section 1.1 proves *what* the table is, not why the exporter split the chain that way. No
  byte in the file states it, and testing it means loading the game (forbidden by the reset).
- `.pfxc` polytope face codes (the 4th byte of each face record: 123/127/102/121/120): the
  record's offset and count are proven, the code byte is per-file and unnamed.
- `.pfxc` global fixup section field (always 2): decoded value, unnamed.
- whether a `.pfxc` is honoured for debris collision in game: this task decodes the files and
  does not test them in game.
