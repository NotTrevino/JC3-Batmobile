## 2. The byte map (O3-O6)

The RTPC layout used here is the one ConvertProperty itself implements
(`Tools/GibbedSrc/Gibbed.JustCause3.PropertyFormats/PropertyContainerFile.cs`):
a 8-byte header (`RTPC`, version 1), one 12-byte record per node
(`RawNode.Size = 4+4+2+2`), a 9-byte record per property (`RawProperty.Size = 4+4+1`),
and, for every property whose type is not `Integer`/`Float`, a `u32` offset to a
payload whose shape is fixed by the type (`Variants/*.cs`).  Every byte of both files
is labelled from that parse; unlabelled bytes are alignment padding.

`107337 role bytes + 2189 pad = 109526` exactly, with no byte labelled twice (O3).  The two
files have the *same* padding map - 750 runs, lengths [1, 2, 3, 4, 8, 10, 12] - so the tool lays the file
out at identical offsets (O4).

The structure itself is byte-identical between the two files (O6):

* `450` node records (name hash, data offset, property count, child count);
* `6521` property records (name hash, 4 data bytes, type);
* every payload offset, hence `2372` distinct payload spans.

That is what rules out three of the four causes the card listed:

* **ordering** - unchanged.  Node records and property tables are written in the
  same order; the tool sorts properties by hash (`PropertyContainerFile.cs:153`,
  `:223`) and the vanilla file is already in that order, so canonicalising the order
  changes nothing.
* **string table** - unchanged.  1014 string properties address 381 distinct string
  spans; the writer deduplicates identical strings (`:168-186`) and the vanilla file
  uses the same dedup, so every string offset in the property table is already the
  deduplicated one.  Payload spans reused across the whole file: 633.
* **hash table** - not consulted for the bytes.  Names appear only in the XML
  (`Program.cs:309-314, 349, 371`: `name=` when the name list knows the hash, `id=`
  otherwise) and import re-hashes them (`Program.cs:388-410`).  The export writes 3260 names and

  so every name re-hashed to the hash that was already in the binary (O6), and the
  one name quoted in the value list below re-hashes to its property hash (O11).

## 3. Class 1: 2189 bytes of alignment padding (O4, O5)

The vanilla file fills every alignment gap with `0x50` ('P'); the tool leaves those
bytes zero.  Decoded: the 2189 pad bytes of the vanilla file have the single value
`0x50` on all of them, and every pad offset in the re-imported file is `0x00`.

The mechanism is in the writer: it *seeks* to the alignment instead of writing
fill bytes (`PropertyContainerFile.cs:177,202,220` - `data.Position =
data.Position.Align(...)`), and the stream is a zeroed `MemoryStream` (`:113`), so
whatever the seek skips stays zero.  The alignments themselves come from the
variant (`StringVariant.cs:71-73` = 0, `Matrix4x4Variant.cs:112` = 16, the counted
array variants = 4).  Nothing reads those bytes back: they are outside every node
record, property record and payload (O3).

A byte map of one such gap, the first difference at `0x765`:

```
0x760  43 43 61 72 00        "CCar" string payload (offset taken from a property record)
0x765  50 50 50              <- vanilla padding, 3 B up to the next 4-aligned payload
       00 00 00              <- tool: same gap, zero-filled
0x768  ..                    next payload
```

This class is **canonical re-encoding only**: no value, offset, count or hash moves.

## 5. After one pass the file is stable (O9)

`b -> --e -> --i -> b2` and `b2 -> --e -> --i -> b3`:

| file | sha256 |
|---|---|
| b1 | `f5a11052b5fc8f3a6492926e5fa2f3c3552f7392937e7e67d4e7c6806370e413` |
| b2 | `f5a11052b5fc8f3a6492926e5fa2f3c3552f7392937e7e67d4e7c6806370e413` |
| b3 | `f5a11052b5fc8f3a6492926e5fa2f3c3552f7392937e7e67d4e7c6806370e413` |

All three are identical, and so are the two XML exports: the tool is a **fixed
point** after its first pass.  The rounding therefore does not accumulate across
edits; it happens once, when a vanilla file is first imported.

That is the answer to the practical half of the card.  The Batmobile's `.epe` was
built through this tool, and it is already canonical:

```
Builds/bm-009/aaf/editor/entities/jc_vehicles/01_land/v0300_car_kensington_sportsmuscle/v0300_car_kensington_sportsmuscle_civilian_01.epe
105430 B, sha256 1778816d26ce5505e43079a7fed57745380361f24f4394c3ecd184d40c41cf96
--e then --i -> sha256 1778816d26ce5505e43079a7fed57745380361f24f4394c3ecd184d40c41cf96 (identical)
its 2131 pad bytes are all ['0x0']
```

So the discrepancy G3-12 measured is a **one-time canonicalisation of the vanilla
file**, not a lossy pipeline: the shipped `.epe` no longer differs from the tool's own
output, because it *is* the tool's own output (O10).
