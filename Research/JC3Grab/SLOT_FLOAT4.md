question stays **UNKNOWN** and the table in section 4 is the result.

What the instructions do decode, independently of that rule:

- `+0x30` is the **fourth row of the 4x4 at +0x00**: `0x141513fa0` writes rows `+0x00`, `+0x10`,
  `+0x20`, `+0x30` in sequence from a four-float4 source, so `+0x30` is row 3 of that
  matrix, not a group of its own.
- `+0x40` is the float4 that follows the matrix and is **multiplied by the matrix's three
  3x3 rows** by `0x1415140f0` (`mulps` against `[rsi]`, `[rsi+0x10]`, `[rsi+0x20]` with `rsi`

- Neither offset is compared against a minimum or maximum. The AABB in this path is the
  caller's buffer `[r12]`/`[r12+0x10]`: the shape's virtual method fills it and
  `0x14151424f` expands it by the shape radius with `subps` / `addps`.

## 3. How a slot-record base register is proven

`RUNTIME_LAYOUT.md` O5 already pinned the index idiom: `shl R, 7` (handle x 128 =
`sizeof(body_slot)`) followed by `add R, qword ptr [B + 0x60]` (the world's slot array
base). The image contains **893** verified `shl r64, 7` instructions (byte scan accepted
only where the bytes decode as that instruction at an instruction boundary);
**132** of them are followed by the slot-base add and become seed S1, **3** by an add of
a register loaded from `[B+0x60]` (S2), **0** by an add after `imul R, R, 0x80` (IM).

| step | count |
|---|---|
| functions with a seed | 135 |
| functions reached by the taint (fixpoint over call arguments) | 139 |
| all reads at `[base+0x30]` / `[base+0x40]` from a tainted base | 425 |
| accepted: the same function also touches `+0x0c` / `+0x50` / `+0x60` | 4 |
| rejected: no slot fingerprint (unrelated 128-byte-stride records) | 421 |

An instruction is a **read** when the memory operand is not the destination. A read is
only accepted as a slot consumer when its function also exposes the record's
distinguishing fields (`+0x0c` flags, `+0x50` shape pointer, `+0x60` free byte) through a
tainted base; that is what removes the other 128-byte-stride structures the `shl 7`
scan also finds.

## 7. What is still UNKNOWN

- **the either/or in the brief.** Only `0x1415140f0` classifies `+0x40` and only it classifies
  `+0x30`; `0x141505820` copies both groups without classifying them. Two independent agreeing
  consumers do not exist, so no verdict is issued. Where a second one would be: a
  consumer reached through a slot pointer that is stored in the record's parent rather
  than computed by `shl 7`; the taint only follows computed indices and call arguments.
- **whether `+0x40` is a position or a scale/extent vector.** It is multiplied by the
  matrix both as a broadcast (one lane against each of the three rows) and as a point
  (`0x14119fa30`), which fits either reading. Proving it needs the shape virtual method at
  `[shape+0x30]`, whose target is a vtable slot resolved at run time.
- **`+0x30`'s use after the copy.** The consumer copies it to its frame and adds one
  float4 to it (`addps`), then the value is not read again on that path; no comparison
  against a bound uses it.
- **421 reads at `+0x30`/`+0x40` from a tainted base that failed the slot fingerprint.**
  They belong to other 128-byte-stride records (the same `shl 7` idiom); no oracle here
  separates them from body slots beyond the fingerprint, so they are listed as rejected
  rather than as contradictions.
