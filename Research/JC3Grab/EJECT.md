# Exit, bail-out and eject (G2-20)

Generated by `Tools/scripts/jc3eject.py` (digest `8dca980204969198`). The donor is
`v0300_car_kensington_sportsmuscle__v0300_car_kensington_sportsmuscle_civilian_01`; the fleet figures are all
232 vehicle `.epe` graphs in `E:/Modding/JustCause3/_grab\detail`.

**The short answer.** JC3 has no eject. An exit in this game is a *state name* plus a set of
gates, and the only numbers any exit carries are the gates. Nothing in the graph or in the
vehicle's modules can push the driver upward; the one upward impulse the data does carry,
`turbo_jump`, moves the **car**. Exiting above the speed gate selects
`exit.driver.moving.parachute` → `S_EXIT_VEHICLE_PARA` — that is the
carrier MOD-3 gets, and the launch half is UNKNOWN with a Q-1 probe below.

**There is no launch field.** Members whose *name* suggests one (`velocity`, `impulse`,
`launch`, `force`, `speed`): **0**. Keys outside the set above,
anywhere in the fleet: **0**.

The graph vocabulary is **104** classes. Those with Velocity/Impulse/Launch/Eject/Force in the name: **2** —
`CForcePulse`, `CInteractionGraphParentVelocityCondition`.
`CInteractionGraphParentVelocityCondition` has
4057 instances and is a
**condition**: it gates an exit, it does not carry the player anywhere. The other is the
vehicle's own explosion pulse (`CForcePulse`, G2-17), which pushes away from the **car** and
has nothing to do with a seated driver. Neither is an exit action.

**State-machine refs.** An exit's state string appears twice in the donor's `.epe`: as the
exit's own `state`, and inside its `ExitObstructedCondition` (the same string, under the
hashed key `id:A3CC001A`). There is no vehicle state machine to carry it - the index has 0
`jc_statemachine/vehicles/` files, and the 142 state machines it does carry are character-side
(G2-19, `SEAT.md`). So the exit hands the game a name and the name's behaviour lives in
native code plus Rico's animation set - not in a file the mod can edit.

## 7. The mapping for MOD-3 (launch → glide)

| BmAK behaviour | JC3 carrier that exists | take that can fail | verdict |
|---|---|---|---|
| leave the car while moving | `exit.driver.moving.parachute` → `S_EXIT_VEHICLE_PARA` (gated 5..999) | exiting above the gate must play the para state, not the plain one | **stated** |
| leave the car at rest | `exit.driver.default` → `S_EXIT_VEHICLE` (gate 0..5) | at rest the plain exit must play | **stated** |
| side roll-out (fast, no chute) | `exit.driver.roll.out` → `S_ROLL_OUT_EXIT_VEHICLE` (gate 5..999) | both fast exits pass their gate; which one wins is code | **stated carrier, selection UNKNOWN** |
| **launch upward** (`EjectUpMove`, `EjectUpDist`) | **none** — 0 launch members in 4,832 exits, 0 in 232 module graphs | a data-authored upward impulse would have to exist; it does not | **UNKNOWN → Q1-EJ-A** |
| glide after the launch | the parachute state the exit selects | the para state must leave the player airborne with the chute available | **carrier named, behaviour UNKNOWN → Q1-EJ-C** |

So MOD-3's honest position: **the exit half maps onto `exit.driver.moving.parachute`**, one
name and one state string, and the build can carry it unchanged (it is the donor's own exit,
already parented to `point.driver`). **The launch half has no JC3 carrier.** A build cannot
author an upward impulse from entity data; the choices are (a) accept exit + glide without
the launch, (b) a Q-1 probe to see whether the para animation already pops the player up, or
(c) use the vehicle's `turbo_jump` to jump the *car* at the same moment — visibly different,
and not what the lore asks for.

## 8. UNKNOWNs, and the probes that would close them

1. **The upward impulse.** No member carries it. Q1-EJ-A: exit the donor at a steady speed
   above the gate (e.g. 8 units, comfortably over 5) on flat ground with no input after the
   exit. Expected, hypothesis H1 (no launch): Rico's vertical velocity is ≤ 0 within 0.2 s
   and his apex is 0.0 m above the exit point (±0.2 m). Hypothesis H2 (launch): vertical
   velocity > 0 and apex > 1.0 m above the exit point. One launch, one variable (R13). The
   thresholds are probe design; the exit and its gate are the data.
2. **Which fast exit wins.** Both `roll.out` and `moving.parachute` pass their gate. Q1-EJ-B:
   exit at just over the gate; expect `S_ROLL_OUT_EXIT_VEHICLE` (side roll, no chute) or
   `S_EXIT_VEHICLE_PARA` (chute state). Observable without any new file: the two states look
   different.
3. **Whether the chute is automatic.** The exit only names a state; whether `S_EXIT_VEHICLE_PARA`
   deploys the parachute by itself or needs the usual chute input is UNKNOWN - Q1-EJ-C: exit
