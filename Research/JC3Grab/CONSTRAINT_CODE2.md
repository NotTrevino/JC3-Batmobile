# What the runtime does with a constraint whose second body is absent (G3-10i)

Generated by `Tools/scripts/jc3_constraint_code2.py --write`; `--check` re-decodes
every instruction quoted below from `JustCause3.exe` and re-sweeps the 494 records,
failing on any drift.  Static only: the executable was opened read-only and nothing
was run or attached.

- executable: `JustCause3.exe` (51083264 bytes, base 0x140000000, 188670 `.pdata` functions)
- fleet: 50 `.physicsc` files, 494 cinfo records

## VERDICT

**None of the three.  The engine substitutes nothing: a constraint record whose
second body is `0x7fffffff` is validated and *dropped before the add call*.**

The choice is made at `0x141569d00`, in the loop that builds an `hknpPhysicsSystem` from an
`hknpPhysicsSystemData`.  Both body ids are checked - sentinel, then range, then
the body's own live-flag - and every failing branch jumps to the loop increment at
`0x141569fc1`, which is the *next record*, not the call.

So the three candidates in the brief are all refuted as *substitutions*:

| candidate | verdict | why |
|---|---|---|
| the world's fixed body | **not substituted** | the guard branches away before the call; and `hknpWorldCinfo` has no body field at all (below) |
| the system's root body | **not substituted** | same branch; there is no `rootBody` member in either class schema |
| a body supplied by the vehicle at spawn | **not substituted for an invalid id** - but this is the only way a second body does appear | game code assembles a cinfo from two live ids and adds *that*, e.g. `0x140280a1c` (below) |

Decoded consequence for the modding question: the 494 shipped records with
`bodyB = 0x7fffffff` do not become world constraints through this path.  A vehicle
joint that must exist at runtime is created by game code calling the same add with a
cinfo it filled with two live body ids - the second body is supplied by the caller,
never read out of the record.

## 2. The cinfo loop and its guard chain

`0x141569d00` is the `hknpPhysicsSystemData` -> `hknpPhysicsSystem` builder: it allocates the
system (`0x690` bytes) and first copies the `0x80`-byte body cinfos at
`[data+0x130]` (count `[data+0x138]`) into `0x90`-byte runtime bodies, then walks the
`0x18`-byte constraint cinfos at `[data+0x140]` (count `[data+0x148]`).

The constraint part of the loop, verbatim (one line per instruction, all decoded
from the bytes; the comment column is the reading, not the disassembly).  The class
name is the string the fleet files carry for this object (`hknpPhysicsSystemData`,
decoded by `jc3_physics_roles6.scan`), and the strides agree with the file writer:
`0x80` body cinfos, `0x18` constraint cinfos.

Both invalid-body tests (`+0x08` and `+0x0c`) and both range tests jump to
`0x141569fc1`, which is the instruction that advances `rbx` by `0x18`.  No path from an
invalid id reaches the `call`: there is no write-back to the record, no copy from a
world/root body, and the record is simply not turned into a constraint.

### How the loop is reached

The cinfo loop has **0** direct callers; its address occurs in **2** data
slot(s) (sections: `.pdata`, `.rdata`) - i.e. `.pdata`'s unwind entry plus one `.rdata` slot.
That non-`.pdata` slot, `0x142c16158`, is an `(RVA, int)` pair `(0x141569d00, -1)` inside a
`.rdata` table of such pairs.  So the function's address is taken by data and its
caller is not a direct `call`; the table that dispatches it is **UNKNOWN** (section 6).
The add function is likewise address-taken (``0x142c063cc``), but its 13 decoded `call` sites
are the entry points into it.

## 6. UNKNOWN

- **Who dispatches the cinfo loop.** No `call`/`jmp` in `.text` targets `0x141569d00` and no
  qword slot holds it; the single `.rdata` slot (`0x142c16158`) is an `(RVA, int)` pair
  `(0x141569d00, -1)` inside a table whose owner is not identified.  Where to look:
  the packfile/resource loader that instantiates `hknpPhysicsSystemData` objects.
- **Whether the guard is the only consumer in practice.** The derivation "494 of 494
  records rejected, 0 surviving" assumes the data object really carries the file's ids.
  If a loader rewrote `+0x0c` on the way in, this loop would see something else - but
  no such rewrite was found: `0x141569d00` copies the record, and `0x141557a30` copies its ids verbatim.
- **What the vehicle actually wants.** Whether the 494 sentinel records are inert by
  design (game code builds the joints, as at `0x140280a1c`) or the fleet files are templates
  that the game never instantiates through this path is not decided here; that needs
  a live-world test, which is out of scope for a static card.
