## VERDICT

**The 24-byte record has two body fields, and neither is at `+0x04`.**
The engine's own class registry gives `hknpConstraintCinfo` a size of `0x18` = 24
bytes and four members: `constraintData` at `+0x00`, **`bodyA` at `+0x08`**, **`bodyB`
at `+0x0c`**, `flags` at `+0x10`. So:

| offset | field | what the 494 shipped records hold |
|---|---|---|
| `+0x00` | `constraintData` (8-byte reference) | inline 0, resolved by the packfile fixup map in 494/494 records |
| `+0x04` | high half of that reference | **0 in 494/494** - not a body id at all |
| `+0x08` | `bodyA` | a real body index in 494/494 (97 distinct, range 0..104) |
| `+0x0c` | `bodyB` | **`0x7fffffff` in 494/494**, never a body index (0 such) |
| `+0x10` | `flags` | `0x0` |

Two readings die here and one survives:

1. **G3-10d's `+0x04` is not a body field.** It is the upper half of the 8-byte
   `constraintData` reference; it is zero in every record because the file stores a
   small offset in the low half. The number `0` was real, the *field* was not.
2. **The partner is not a body of the system.** `bodyB` is a single constant,
   `0x7fffffff`, in all 494 records: the maximum signed 32-bit value, not an index into
   the body array (every `bodyA` is < the file's body count, `bodyB` never is).
3. **The task's hypothesis is not confirmed either.** The stored second id is not
   `0`. Whatever `0x7fffffff` means at runtime - "no second body", "the world",
   "the fixed body" - is **UNKNOWN** (see section 5); what is decoded is that it is
   the same non-body constant in every shipped constraint.

## 4. The code that consumes the record

`bodyB` is not a hidden body index: the engine's own code uses `0x7fffffff` as the
**invalid body id** and writes it back to *detach* a body. Decoded block:

```
or dword ptr [r8 + 0x18], 1
mov ebx, dword ptr [r8 + 0xc]
cmp ebx, 0x7fffffff
je 0x141943257
mov edx, ebx
mov rcx, rax
mov dword ptr [r8 + 0xc], 0x7fffffff
call 0x141507350
test al, al
je 0x141943257
```

`mov dword ptr [r8 + 0xc], 0x7fffffff` is the detach: the field is set to the invalid
id *before* the unlink call, and the `je` skips the work when the field already holds
it. So a `+0xc` body field holding `0x7fffffff` means "no body here" - not
"body 4294967295", and not "body 0".

### What this does to the task's hypothesis

The hypothesis was "the second id is the fixed world body, id 0 in the world". The
bytes say something weaker and different: the record's second body is **absent**,
flagged with the engine's invalid id. Two consequences, kept separate:

- **decoded:** the 24-byte record carries one real body (`bodyA`, `+0x08`, always a
  valid index into the file's body table) and one invalid marker (`bodyB`, `+0x0c`);
- **not decoded:** what an invalid `bodyB` becomes at simulation time. The four sites
  above skip or detach, none substitutes `0`, and no creation site was found, so
  "the world", "the fixed body" and "a part pair resolved elsewhere" all remain
  UNKNOWN. G3-10g's 49.6% fit for body 0 is compatible with a world reading but is not
  evidence for it, which is exactly why the geometric route stalled.
