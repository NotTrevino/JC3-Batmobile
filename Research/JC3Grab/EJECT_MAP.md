# EJECT_MAP - the BmAK eject, step by step, against JC3 (G3-08b)

Generated by `Tools/scripts/jc3_eject_map.py --write`. Do not edit by hand; `--check` re-reads every source and compares.

**Short answer.** BmAK's eject is one button, a guard, a scripted `DriverLeave` on the pawn, a cockpit-open, a car velocity of `(0,0,0)` on one branch, and an animation special move whose names end `_To_Glide`. The launch is authored as a **move**, not as a velocity. On the JC3 side the two actions the operator names - *jump to roof* and *parachute out* - are **both on one control in both JC3 binding tables**, which is the press/hold pair's fingerprint but not its proof: neither table carries a hold flag or a duration, so the press/hold split is the **game's own menu** (operator screenshots) and the **holding time is UNKNOWN** in every file on this machine. The two tables also **disagree about which control it is**: the shipped `keymap_gamepad.bin` puts both on **RPADDOWN** and binds **no face button at all** (0 A/B/X/Y rows), while the player's export puts both on **A**. The only vehicle-context condition in JC3's data is the donor's parent-speed gate on the driver exit: below 5 the exit is `S_EXIT_VEHICLE`, from 5 up it is `S_EXIT_VEHICLE_PARA` - at speed the driver does leave through a parachute state. Nothing in the data aims the driver upward.

Labels: **decoded** = read from a file (path + offset/line); **derived** = computed from decoded facts, rule given; **operator-stated** = the operator's statement, not a file; **quoted** = a number another card decoded that this script does not re-read; **UNKNOWN** = what was tried, where it would be.

3. **Which action a vehicle consumes.** No vehicle entity names an input action (`keymap` in 0/232 dumps); the action -> exit link is native.
4. **The launch trajectory.** BmAK's `TriggerSpecialMove` carries a reference only; the special-move asset is outside `BmGame.upk`, and JC3's exits carry 0 launch members.
5. **BmAK's double-press window and first-press behaviour.** A timestamp is written; no window constant exists in the body.
6. **The battle-mode moving condition and boost fallback.** `BoostingOut` (6 refs) and `CurrentEjectType` are present, but 385 of 1297 bytes are unattributed jump tokens, so the branch is not decoded.
7. **The car's post-eject rotation.** Operator-stated; no decoded vector, and no JC3 exit member can carry it.
8. **`CantEjectFromBatmobile`'s condition.** First call at `+3` with two unnamed 1-byte tokens; its body is not decoded.
