# The armour step: how `*_armor` is addressed in JustCause3.exe (G2-28b)

Generated by `python Tools/scripts/jc3_armor_step.py --write`; re-derived and
compared byte-for-byte by `--check`. Machine half: `ARMOR_STEP.json`.

**The short version.** `DAMAGE_MODEL.md` step 4 asks how `*_armor` and `*_armor_strength` compose. This card settles the half the executable can: the armour values are **not data-driven by name or by hash**. The ADF vocabulary block is dead data - 0 code references to its 473 names, and the jenkins hash of every one of the 30 members occurs **0** times in the 51,083,264-byte image. The only handle the code has is the module's ADF **type** hash, `0xaca39a2d`, used in exactly one instruction; the values themselves are compiled struct members of a **128-byte** blob.

So the composition rule is still **UNKNOWN**, but it is now known to be compiled
code reading `+0x04…+0x40`, not a table lookup - and one correction to the data
model follows from the bytes: the `*_armor_strength` members are **IEEE float32**,
not ints.

## 1. The question, and what would count as an answer

Step 4 of the damage chain is: a hit carries a damage type; that picks one of
eight channels; each channel ships `<channel>_armor` and
`<channel>_armor_strength`; those two numbers, with the hit's damage, decide how
much reaches health. Three models are carried in `DAMAGE_MODEL.md` (H0 ignore,
H1 percentage gate, H2 threshold plus pool). Deciding between them statically
needs the code that reads the two numbers. Finding that code needs a handle, and
there are only three possible kinds: a member name string, a member name hash, or
a struct offset. Sections 2 and 3 eliminate the first two as sets - not just for
the armour members but for the whole type - which leaves the offset, and section 4
recovers the offsets.

## 2. The vocabulary in the image is inert

The ADF member-name block sits in `.rdata` as 473 adjacent
NUL-terminated strings, from `EulerAngles` (0x142476660) to
`UVScale` (0x1424786ed); `VehicleDamage` is entry
303 and its 30 members follow it in
declaration order. Two measurements over that whole block:

| measurement | result |
|---|---|
| instructions that address any of the 473 names (RIP-relative, end-of-instruction verified) | **0** |
| 8-byte pointers anywhere in the image that hold one of those name addresses | **0** |

So neither a named accessor nor a pointer table exists: the block is vocabulary
kept for the asset pipeline, exactly as the palette names are in `COLOUR.md`
(`jc3_colour_native.py` measured 0 references there too). The oracle
`vocabulary_names_have_no_code_reference` fails the moment one name acquires a
reader.

## 4. What the code does know: the type hash, and a 128-byte struct

The module's own type library (`lave_health_medium.vmodc`) declares:

| `VehicleDamage` | `0xaca39a2d` | 1 | 128 | 8 |
| `PartDamageType` | `0x9724e4c1` | 1 | 32 | 8 |
| `A[PartDamageType]` | `0xb2477bdd` | 3 | 16 | 8 |
| `HashString` | `0xa62e34f9` | 1 | 16 | 8 |

image that u32 occurs 3 times: `0x140271010`, `0x1422b9150`, `0x14246ec6c`.

That is the typed accessor: it walks the entity's modules, compares each module's
type hash against the `VehicleDamage` constant, and returns the blob. Its one

of the armour values reaches the 128-byte blob through that pointer. Nothing in
the path needs a member name or a member hash, which is consistent with neither
occurring in the code.

## 5. The armour block, decoded from the bytes

The instance data begins at file offset `0x50`. The first
19 members sit at 4-byte strides, so each word has two readings -
int32 and float32 - and the field's own value domain decides between them. No
reading is assumed: an armour word must land in [-1, 5000], a strength word in
[0, 100], and a word that satisfies both must be 0.

Result: 8 words decode only as int32
(`max_health`, `bullet_armor`, `bullet_heavy_armor`, `explosion_armor`, …),
7 decode only as float32 - **every one of them a
`*_armor_strength`** - and the rest are zero words where both readings are 0.

This is the correction to `DAMAGE_MODEL.md`: it prints the strengths as integers
(`5000 @ 99`), but the shipped byte is `0x42c60000`, i.e. `99.0f`. The fleet's
strength domain 0..100 is a float domain, and any gate built on it is float
arithmetic on a converted int (`cvtsi2ss`), not integer division.

## 6. The arithmetic: what the evidence supports and what it does not

| question | answer | evidence |
|---|---|---|
| are the armour values looked up by name? | **no** | 0 code references to the member names |
| by hash? | **no** | 0 occurrences of 30 member hashes |
| by struct offset? | **yes** | the type is found by its module type hash; the blob is the compiled image; the block decodes at 4-byte strides |
| is there a table (offset table, curve, coefficient block) driving the gate? | **no table found** | the type hash is used once, in a compare; the only data-side artefacts are the values themselves |
| armour type | int32 | section 5 |
| strength type | **float32** | section 5 |
| the composition rule | **UNKNOWN** | below |

Three whole-image sweeps were run to find the consumer, each a candidate
generator whose survivors were read by hand:

| sweep | shape searched | candidates | outcome |
|---|---|---:|---|
| A | channel-indexed reads of an int32 pair 4 bytes apart (`[base+idx*8+d]`, `[base+idx*8+d+4]`) | 211 | none indexes the `VehicleDamage` block |
| B | an int32 read with a float32 read 4 bytes later, from one base | 910 pairs in 330 functions | none reads eight such pairs at 4-byte stride from a struct |
| C | sweep B intersected with `cvtsi2ss` plus a `100.0`/`0.01` float constant | 4 | none is the gate |

The structural reason the sweeps fail is the one section 4 gives: the block is
reached through a cached `VehicleDamage*` at `[this+0x10]`, and virtual dispatch
between the accessor and the gate hides the call edge from a static caller walk.
Naming the rule would need a live debugger, which the project rules exclude.

## 7. Where to look next

Two RTTI-visible classes bracket the consumer, both static anchors:

| class | vtable | slots |
|---|---|---:|
| `CVehicleDamageState` | `0x1423bbc38` | 12 |
| `CDamageControllerArmor` | `0x142445818` | 44 |

`CVehicleDamageState` is the health state; `CDamageControllerArmor` is the
destructible armour object and carries the hash-addressed `damage_type` binder of
section 3. A future pass that reads the `CVehicleDamageState` slots against a
`VehicleDamage*` would start where this one stopped; the JSON carries every slot
address so the reader can pick up the thread without redoing the RTTI walk.

## 8. UNKNOWNs

- **the arithmetic that composes `<channel>_armor` with `<channel>_armor_strength` and the hit's damage** - tried: three whole-image sweeps, all recorded in section 6: (a) functions reading a channel-indexed pair of int32s 4 bytes apart - 211 candidates; (b) functions reading an int32 with a float32 4 bytes later - 910 pairs in 330 functions; (c) that second set intersected with `cvtsi2ss` plus a 100.0/0.01 float constant - 4 candidates.  Every survivor was read and none indexes the `VehicleDamage` block. Still unknown because the gate is compiled code, not a table: the eight pairs are reached by struct displacement, the type is only ever found by its module type hash, and the executable has no name or hash handle on any armour member to anchor the search on.  The consumer sits behind the accessor at 0x140270fe0, whose cached result is written to `[this+0x10]`; locating it needs either a live debugger (excluded: the game must not be run) or a much wider read of the call graph through virtual dispatch.
- **whether `max_health` is an absolute pool or a scale** - tried: the struct image: `max_health` is int32 2000 at +0x00, i.e. the same domain as the shipped values (500..4000). Still unknown because the field decodes, its unit does not; DAMAGE_MODEL.md step 6 already carries this and nothing in the type library names a unit.
- **the layout of the `VehicleDamage` members after `deform_scale` (+0x4c)** - tried: read the instance as 4-byte words: from +0x4c the bytes are 0x00fa041a, 0x0014000a, not a 4-byte-strided run. Still unknown because the tail of the blob switches to a narrower encoding (1050 and 250 - the medium tank's `smoke_threshold` and `burn_threshold` - fit as two u16s at +0x4c), so the remaining 11 members cannot be laid out by stride alone; the armour block this card is about ends before that.
