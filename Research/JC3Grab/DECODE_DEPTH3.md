# JC3 Serpente decode depth 3 (G3-19) - the four PARTIAL files, closed or bounded

Generated by `Tools/scripts/decode_depth3.py --write`; `--check` recomputes every
number below and diffs it against the committed JSON. Nothing here was run in the
game: the `.rbm` blocks come out of the JC3 `.ee` archive through `bm_rc`/`eetoc`,

Labels: **decoded** = file + offset (or archive member + offset), read by this

## 1. The three `.rbm` - full byte accounting, two of three blocks decoded

Each file is: header, then three blocks, each `u32 type_hash` + payload + `u32
0x89ABCDEF`. The accounting is closed by requiring the sum to equal the file size
exactly (oracle 1) and by requiring `rbm_geom.decode_carpaintmm` to consume a
block to its exact end (oracle 2).

| file | size | header | block 0 | block 1 (GeneralMkIII) | block 2 | sum == size |
|---|---|---|---|---|---|---|
| `sportsmuscle_missile_base_signature_lod1.rbm` | 45912 | 53 | CarPaintMM 13051 B decoded | 7126 B **undecoded payload** | CarPaintMM 25658 B decoded | yes |
| `sportsmuscle_missile_base_signature_lod2.rbm` | 21842 | 53 | CarPaintMM 8587 B decoded | 2592 B **undecoded payload** | CarPaintMM 10586 B decoded | yes |
| `sportsmuscle_missile_base_signature_lod3.rbm` | 14590 | 53 | CarPaintMM 5455 B decoded | 1214 B **undecoded payload** | CarPaintMM 7844 B decoded | yes |

So the earlier PARTIAL status was caused by one block in the *middle* of each
file: `rbm_geom.decode()` stops there because it has no serializer for
`GeneralMkIII`, which is why the block after it was never reached. The block
*after* it is `CarPaintMM` again and decodes to its exact end, header AABBs and all.

### 1a. What *is* decoded inside `GeneralMkIII`

Its head is byte-identical in all three lods (decoded: hex dump in the JSON,
`rbm.mkiii.head_hex`). It starts with `u32 5` and twelve zero bytes, then a run of
numbers that is **not** 4-byte aligned. Reading the same bytes on the eight
possible byte offsets gives this (derived scan, `rbm.mkiii.grid_scan`):

| byte shift | words that look like parameters (1e-4..1e4) |
|---|---|
| 0 | 0 of 8 |
| 1 | 6 of 8 |
| 2 | 0 of 8 |
| 3 | 0 of 8 |
| 4 | 0 of 8 |
| 5 | 6 of 8 |
| 6 | 0 of 8 |
| 7 | 0 of 8 |

So the numeric run starts at payload +0x11, one byte off the word grid (`u32 5`,
then twelve zeros, then one byte, then the run - i.e. there is a sub-4-byte field
at +0x10 whose size is what shifts the grid). Read there (decoded bytes):

|---|---|---|
| +0x11 | 1157234688 | 2000.0 |
| +0x15 | 1065353216 | 1.0 |

What the values *mean* is **UNKNOWN**: 2000.0 followed by 1.0/0.0/1.0/1.0, a
u32 1 at +0x25, then 1.571/0.480/1.439, is the shape of a small parameter block,
but no oracle in the project names any field of `GeneralMkIII`, so only the read
bytes are claimed. (The 4-byte-aligned reading of the same area is in the JSON as
`head_fields` only to show that it yields nothing plausible.)

Inside those ranges the vertex/attribute layout is **UNKNOWN**. What was tried,
and where the answer would be:

* A stride solver over `prefix + n*(u32 count, count*stride)` for `prefix` in
  0..96 step 4 and strides 2..64, requiring the parse to land exactly on the
  block checksum. It found **one** accidental closure (lod2, prefix 36, one
  stride-8 buffer of 319 entries) that does not exist for lod1 or lod3, so it is
  rejected as a coincidence rather than a layout.
* Arithmetic from the index list: with the implied vertex counts, the pre-index
  region admits these integral `header + verts*stride` splits (derived, *not* a
  decode - several fit per file, which is why none is claimed):
  * `sportsmuscle_missile_base_signature_lod1.rbm`: region 5778 B, 176 vertices -> stride 32 with 146 header B
  * `sportsmuscle_missile_base_signature_lod2.rbm`: region 2390 B, 55 vertices -> stride 40 with 190 header B, stride 41 with 135 header B, stride 42 with 80 header B, stride 43 with 25 header B
  * `sportsmuscle_missile_base_signature_lod3.rbm`: region 1186 B, 12 vertices -> stride 83 with 190 header B, stride 84 with 178 header B, stride 85 with 166 header B, stride 86 with 154 header B, stride 87 with 142 header B, stride 88 with 130 header B
* A float3 (stride-12 position) scan of the whole payload against the AABB the
  file header itself carries: **0** hits in total across the three lods.
  So the naive reading - "the same vertex layout as the `CarPaintMM` block,"
  is ruled out on the bytes: no 12-byte run anywhere in `GeneralMkIII` decodes to
  a point inside the model's own bounding box. The answer would be in the
  serializer for `GeneralMkIII` (block type hash 0x2cec5ad5); Gibbed's JC3 RBM
  writer does not implement it, and no published layout exists in the project.

## 2. The `.epe` - round trip, every differing byte classified

Vanilla member `editor/entities/jc_vehicles/01_land/v0300_car_kensington_sportsmuscle/v0300_car_kensington_sportsmuscle_civilian_01.epe`, 109526 B, sha256 `f67bc17ebb16b70f35a6a131ffc8a1c5`.
`tmp/g319/a.epe` is byte-identical to it (`identical_to_vanilla`: **True**);
`tmp/g319/b.epe`, 109526 B, is what `Gibbed.JustCause3.ConvertProperty.exe --e` writes
back after reading it. The two are the same length (oracle 4 applies directly):

| class | bytes | runs |
|---|---|---|
| original `0x50` -> written `0x00` (padding) | 2189 | 750 |
| inside a float32 whose value moved by a decimal-text round trip | 104 (75 fields) | 75 |
| **unexplained** | **0** | - |

The float class is not hand-waving: relative change is 6.338e-08..4.30692e-07 (one float32 ULP
at these magnitudes), and 97 of the 104 changed float bytes sit in fields that
print identically at seven significant digits - i.e. the writer emits the value
as text and re-parses it, so the low bits are lost by the decimal form, not by a
layout difference. Largest absolute change: 3.814697265625e-06.

That closes the `.epe`: 0 unexplained bytes, and the two classes are both named
with the reason for them. The `.epe` therefore needs no further byte accounting;
what it does *not* establish is that the re-serialisation is lossless enough for
the engine - that is a runtime question, not a byte question, and stays OPEN.
