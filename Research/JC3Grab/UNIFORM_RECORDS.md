## 1. Answer

**The records name their parameters and carry their values, and no record maps a name to
a cbuffer offset.** Every proven record's entry is exactly 32 B - an FName pair and one
RGBA - and the record's span is exactly `40 + name + 32 x count`, so no byte is left over
for a slot, buffer or offset field.  Of the 9582 entries, **0** name a member of the 32
CarPaintMM `cb2`/`cb6` members that `CB0_SLOTS.md` decoded (0 expected: those are JC3
names, these are Arkham's).  `hash_jenkins` of the two BmAK names therefore has nothing
to attach to: `BaseColour` -> **3472103038**, `Diffuse_Adjust` -> **2130409324**, and neither value occurs
anywhere in the record region as a slot, nor as an FName index (0 and 0 occurrences).

So the paint-colour combine rule stays **UNKNOWN**.  What the records add is the paint
material's own parameter set and values (section 4), not the constant-buffer layout; that
layout is the JC3 reflection headers' (`CB0_SLOTS.md`), which name `cb2`/`cb6`/`cb7`
members directly from files on disk.

## 4. Names, hashes, and the comparison with the BmAK parameters

`hash_jenkins` is the project's archive-path Jenkins function (`Tools/scripts/rbmhdr.py`),
the same recipe that names JC3 paths.  The records do not store hashes: a parameter is
written as an `FName` index into the package name table, so a hash can only be compared
against the FName **index**, the name **string**, or raw bytes.

| BmAK parameter | `hash_jenkins` (dec) | `hash_jenkins` (hex) | in the name table as a string | hash as an FName index | hash as a u32 in the region |
|---|---:|---|---:|---:|---:|
| `BaseColour` | 3472103038 | `0xcef4167e` | no | no | 0 |
| `Diffuse_Adjust` | 2130409324 | `0x7efb776c` | yes | no | 0 |

A parameter->slot field would show up as a per-name constant integer in the entry.  Testing
all 9582 entries, and the 300 parameter names that occur more than once:

| entry word | distinct values | min | max | nonzero | constant per name (of 300) |
|---|---:|---:|---:|---:|---:|
| `class_id` | 1 | 2055 | 2055 | 9582 | 300 |
| `class_number` | 1 | 0 | 0 | 0 | 300 |
| `param_index` | 696 | 3 | 5055 | 9582 | 300 |
| `param_number` | 5 | 0 | 5 | 46 | 289 |

The only word constant per name is the parameter's own name index (by construction).  A
cbuffer offset would have to be another per-name constant; the only other integer is the
FName number, whose values are 0 and small disambiguators.  **0 entries carry any number
word in the offset range 8..316**, and no entry has a fourth integer at all.

Of the 32 CarPaintMM `cb2`/`cb6` members named by `CB0_SLOTS.md`, **0** occur as a
parameter in any record.  That is the expected result, not a gap: the JC3 paint members
exist in JC3's reflection headers, while these records are Arkham materials keyed by
Arkham parameter names (`BaseColour`, `Diffuse_Adjust`); no file joins the two dialects.

## 6. UNKNOWN

- **Which cbuffer slot a paint parameter lands in.**  Tried: all 6966 records, 9582 entries,
  every field split at its own offset; the entry has no slot field, no class carries a
  slot, and the BmAK name hashes resolve to nothing.  Still unknown because the binding
  is written by the cooker into `RDEF`, which is absent from all 40,299 containers
  (G3-04d's shader-cache result); it would need a build that keeps `RDEF` or a live
  constant-buffer capture.
- **How `BaseColour` and `Diffuse_Adjust` combine.**  The records give their values
  (`Material0_BaseColour` `[0.0, 0.0, 0.0, 1.0]`, `Diffuse_Adjust` `[1.0, 1.0, 1.0, 1.0]`)
  but no operator graph: the material functions' `FunctionExpressions` are stripped
  (`COLOUR_PARAMS.md` section 6), and these records hold values only.  Still unknown; it
  needs the SHEX body or the stripped graph.
- **The 312 headers that leave the 32 B shape.**  Reported, not decoded: their first entry
  has a class word outside 2040..2055 or a parameter index outside the name table, so the
  width of that class is not proven here.  They add no paint parameter (the paint records
  are all in the proven set), so they do not change the answer.
