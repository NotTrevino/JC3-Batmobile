number from the same bytes and fails if this file drifted. Labels: **decoded** = read
from a file (path + archive + offset, or a struct member offset), **derived** = computed

## 0. Answer

Sources: 232 decoded vehicle builds, 232 `.epe`
graphs, 145 of them land vehicles with a player `LandGlobal`;
51 module types; the **bytes** of 54 patch-layer `*_land_global.vmodc` modules decoded with `jc3adf`; and
4 keymap files (base + patch).

**The fleet has no per-wheel drive, no differential and no camera-relative vehicle
control.** A token scan of every module member path on every build finds 0 members
matching per-wheel drive / differential vocabulary, and the only camera / strafe /
dodge matches (6 members) sit in `Propellers` - boat and aircraft docking limits, not in
a land driving module (section 2). A car has one `Transmission` (one `final_drive`, one gear
set) and two `Tire` modules (front axle, rear axle) - there is no per-wheel or
per-axle drive value anywhere, so **four-wheel drive cannot be expressed as data**: all
JC3 cars are a single driveline. The only per-axle asymmetry in the fleet is grip
(`front_wheels`/`rear_wheels.arcade_friction_multiplier`), which is tuning, not drive.

## 3. Pursuit: spin in place when stationary

### 3.1 The only steering-through-torque carrier: the drift block (C1)

`CustomLandGlobal.drift.*` is a 20-member block on 145 builds. It is the only
place in a land vehicle where the car is rotated by a torque rather than by a front
wheel angle, and it has a speed gate of its own:

| member | donor (fleet min .. max; builds) | what it does |
|---|---|---|
| `drift.min_speed_to_drift_kmph` | 10 (0 .. 60; n=145) | speed below which no drift is entered |
| `drift.max_drift_torque` | 5000 (0 .. 35000; n=145) | yaw torque / slide shaping |
| `drift.constant_drift_torque` | 0 (0 .. 20000; n=145) | yaw torque / slide shaping |
| `drift.steering_sensitivity` | 4 (0.5 .. 4; n=145) | yaw torque / slide shaping |
| `drift.max_drift_angle_deg` | 45 (20 .. 60; n=145) | yaw torque / slide shaping |
| `drift.counter_steer_torque_handbrake` | 30000 (0 .. 100000; n=145) | yaw torque / slide shaping |
| `drift.keep_velocity_strength` | 1 (0 .. 1.5; n=145) | yaw torque / slide shaping |
| `drift.velocity_rotation_amount` | 80 (20 .. 100; n=145) | yaw torque / slide shaping |
| `drift.velocity_rotation_start_angle` | 15 (0 .. 30; n=145) | yaw torque / slide shaping |
| `drift.velocity_rotation_end_angle` | 40 (25 .. 65; n=145) | yaw torque / slide shaping |

`drift.min_speed_to_drift_kmph` reaches **0** on 4 builds (1 chassis: `v0400_car_mugello_vintagesports`),
so a value exists that does not gate the block on speed. What that does **not** prove is
that a car with that value rotates at zero velocity: the drift path is a slip-angle path
(`drift_entry_slip_angle`, `drift_exit_slip_angle`, `lat_tire_*` curves), and a slip
angle needs a velocity to exist. The arithmetic is native - **UNKNOWN**, and it is the
one cheap experiment this card cannot run.

### 3.2 Per-axle grip is the only asymmetry the fleet has (C2)

| member | donor | fleet |
|---|---|---|
| `front_wheels.arcade_friction_multiplier` | 1 (0.8 .. 4.4; n=145) | |
| `rear_wheels.arcade_friction_multiplier` | 1 (1 .. 6; n=145) | |

Across the fleet the rear axle is stiffer than the front on 108 builds, softer on 0 and equal on 37 - so the
front/rear balance is a real tuned axis, and it is the only per-axle drive-adjacent

This is a static per-axle multiplier (one number per axle, not per wheel): dropping the
rear axle's grip lets the drift block rotate the car more easily, which is the closest
data-side approach to steering-through-torque, but it still needs the drift path and
therefore motion. It cannot make a stationary car rotate.

## 4. Battle: move in the stick direction, car faces the camera; four-wheel drive

### 4.1 No member and no action expresses it (C4, C5)

The camera-relative regex returned 6 
module members, all six in `Propellers` (docking strafe limits on boats and planes) and
none in a module a land vehicle uses. The `.epe` graphs do carry camera classes (a
`CCameraModifier` object is on every vehicle), but a camera modifier frames the camera;
it is not a control path. There is no member a stick direction could drive.

They are all discrete (accelerate, reverse, turn left/right, brake, fire, exit...) -

| input | action |
|---|---|
| `LSTICKGENERIC` | `MOVE_ALL` |

`MOVE_ALL` on `LSTICKGENERIC` is the one generic 2D-stick binding in the game, and its
name scope is on-foot. Whether a vehicle could consume it is **UNKNOWN** - nothing in
the keymap files or the 232 entity builds names a class to action set (INPUT.md reaches

keymap are: `WINGSUIT_BOOST`.

For four-wheel drive the answer is structural rather than a missing name: there is no
per-wheel torque member to set, because a `CCar` has one `Transmission` and one `Tire`
module per axle. Making the Batmobile four-wheel drive in the data is **not expressible**;
a carrier would have to be a code bridge (a new module type the engine does not read) or
an amendment that drops the 4WD part of the requirement.

## 5. The one new carrier: `LandGlobal.steering_type` (bytes only)

The 54 patch-layer `*_land_global.vmodc` modules in `INDEX.jsonl` decode
with `jc3adf` to a row the cached row set does not contain: **`steering_type`**, a
hashed-string enumeration. Histogram over those modules:

| value | modules |
|---|---|
| `(absent)` | 3 |
| `FrontSteered` | 51 |

The decode is self-checking: the name's Jenkins hash equals the hash stored beside it
(`FrontSteered` 17C23DF5 = `hash_jenkins` 17C23DF5).

**Every readable module says `FrontSteered`**, and the three builds whose module is not
in INDEX carry no `steering_type` member at all. So the fleet ships one steering mode
(front axle) and the enum is not a rear-steer or all-wheel-steer switch a mod can set to
a new value: no other value is shipped, and the value domain is not in the file.

### 5.1 A contradiction inside the project's own evidence

The cached row set replaces that member with two int8 flags, `is_all_wheel_steered` and
`is_rear_steered`. On the donor build:

* bytes only: `steering_type.hash`, `steering_type.string`
* cache only: `is_all_wheel_steered`, `is_rear_steered`
* shared members that disagree in value: 0

That matters because `TANKTURN.md` uses `is_all_wheel_steered` to name the three
monster-truck builds as the fleet's only all-wheel-steered vehicles. The bytes say
those builds are `FrontSteered`:

| cached build | chassis | cache flag | bytes `steering_type` |
|---|---|---|---|
| `v0803_car_na_monstertruck__v0803_car_na_monstertruck_civilian_01.ee.json` | `v0803_car_na_monstertruck` | 1 | `FrontSteered` |
| `v0803_car_na_monstertruck__v0803_car_na_monstertruck_civilian_01_z80.ee.json` | `v0803_car_na_monstertruck` | 1 | `FrontSteered` |
| `v0803_car_na_monstertruck__v0803_car_na_monstertruck_debug.ee.json` | `v0803_car_na_monstertruck` | 1 | `FrontSteered` |

So the cached flag is not a member of the shipped module. TANKTURN's *conclusion*
(no pivot carrier) does not depend on it - the module member sets are identical and no
pivot name exists - but its candidate row `is_all_wheel_steered` should be read as a
cache artefact, not a shipped value.

## 6. The other driving moves

### 6.1 Power Slide (left stick + RT + X) - C8, carrier found

| member | donor (fleet min .. max; builds) | what it gives |
|---|---|---|
| `Brakes.rear.handbrake` | 1 (1 .. 1; n=145) | rear axle is the handbrake axle |
| `Brakes.front.handbrake` | 0 (0 .. 0; n=145) | front axle is never handbraked |
| `Brakes.handbrake_friction_factor` | 1 (1 .. 10; n=145) | how hard the handbrake bites |
| `Brakes.rear.max_brake_torque` | 10000 (500 .. 10000000; n=145) | torque budget |
| `CustomVelocityDamper.handbrake_spin_damping` | 0 (0 .. 4; n=145) | how much spin the handbrake keeps |
| `CustomLandGlobal.drift.counter_steer_torque_handbrake` | 30000 (0 .. 100000; n=145) | yaw torque while countersteering on the handbrake |
| `CustomLandGlobal.drift.min_speed_to_drift_kmph` | 10 (0 .. 60; n=145) | entry speed for the slide |

`Brakes.rear.handbrake` is 1 on 145 builds and `front.handbrake` on 0: JC3's handbrake is a rear-axle
lock, which is exactly the mechanism a power slide needs, and the drift block already
has a handbrake-specific yaw torque. This is a **tune**, not a code bridge: the input is
`HANDBRAKE` (bound to RPADLEFT in the patch gamepad map) and the values are the four
members above. Amendment needed: BmAK binds it to X together with RT, and the angles and
torques have to come from the T rows, not from these defaults.

Note on the donor column: the values above are the **player** copy. The donor's `_ai` twin
carries `handbrake_friction_factor` = 2 against the player's 1, which is why
`VOCABULARY.md` shows 2: its donor column read the AI instance. Player copies are the
ones the game drives, so they are the ones quoted here (the same rule as `jc3tankturn.py`).

The `arcade.nitro_boost` block is on 145 of the 232 builds (matching T-WP13's 145), and the `VehicleMisc` nitro
timers are on 232 - every vehicle, so the
duration and refill model exists even where the boost block does not. What the chain
already gives an Afterburner:

* flat extra top speed on top of the driveline (`extra_top_speed`, donor +40 km/h;
  `_upgraded` +80),
* a torque multiplier (donor x2) and a push force (15,000 N; 20,000 upgraded),
* a grip multiplier (donor x2), so the boost changes handling as well as speed,
* a blend time (0.2 s) - the boost ramps instead of snapping,
* a finite burn (`full_nitro_use_time` 4 s, 8 s upgraded) and a refill rule

native or un-named; the operator lead that JC3's nitrous is "hold B" is consistent with
the data side existing and the action side missing, and stays **UNKNOWN** as data. Also
amended: the 4 s budget refilled by driving is JC3's arcade model, not a hold-while-
pressed afterburner; the timers are tunable, the semantics are not.

## 8. Validation and limits

`--check` re-reads the decoded cache, the 54 module entry offsets and the keymap bytes,
re-derives every number above, and fails if this document or the JSON drifted. Invariants
asserted: 145 land builds; 51 module types;
0 per-wheel/differential members; 0 camera/strafe/dodge members inside a driving module
(the six propeller-docking rows are checked to stay outside it); every sampled
`steering_type` hash equal to the Jenkins
hash of its own name; the donor's byte rows and cached rows agreeing on every shared
member; the keymap byte accounting tiling exactly; no camera-relative action in either
keymap.

**Limits.** Static only: no game was launched, no install written, no process touched.
The byte-level fleet scan covers the 54 `land_global` modules that `INDEX.jsonl` lists -
the other vehicle module types are not indexed per entry, so their fleet-wide statement
rests on the decoded row cache (the same source the rest of G2 uses). The `.epe`-side
statement is a class census, not a property walk: the decoded graphs carry classes and
parts, not every object property.
