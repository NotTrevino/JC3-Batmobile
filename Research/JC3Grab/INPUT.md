## Where JC3 defines vehicle controls (decoded)

Two `settings/*.bin` entries in the archives are the whole input definition. Both are `RTPC` containers (the same container the `.epe` graphs use): a root node, one list node, and **one child record per binding**. Each binding's two 9-byte property records are written inline, followed by its two strings (`"PP"`+input, then the action), 4-byte aligned.

Layer in use below: `settings/keymap_gamepad.bin` → **patch**, `settings/keymap_keyboard.bin` → **patch** (derived: `MOUNT_RANK` of `jc3index.py`; the patch layer wins a path lookup).

**Byte-accounting oracle** (decoded, per file): each binding owns one block - 18 B of property records, then the literal `"PP"`, then whichever of its two names is not already in the string pool (names are deduplicated across bindings), padded to 4. The blocks must tile the file exactly from the end of the record region, with 0–3 alignment bytes at the tail. This is what fails on a wrong stride or a skipped binding.

The two property name hashes are `7935F00C` / `8613CCD3` in all four files (input / action), and every property is type 3 (`stringZ`). Because names are deduplicated, the string pool is smaller than 2×bindings: base 154 strings for 131 bindings, patch 169 strings for 145 bindings, base 130 strings for 94 bindings, patch 147 strings for 104 bindings.

Binding node hashes (decoded by recomputing `rbmhdr.hash_jenkins`, the project's Jenkins lookup3, over candidate names): of 474 bindings the node hash equals `action` 448, `input` 6, `PP+input` 0, `input_lower` 0, `action+input` 0, `input+action` 0, `action_index` 0. So the node hash is the **action id**, and it equals `H(action name)` for 448 bindings; the rest carry ids that none of the candidates reproduces (ids are stable across the base and patch copies for the same action, so they are not per-file).

Root hash `AA7D522A` and list hash `49267ABC` are identical in all four copies, so both devices use one container class. Property types seen: 3×262 (type 3 = `stringZ`, per `rtpcdump.py`), i.e. every property in every binding is a string.

## What an entity or module can change without code

* **Can**: the graphs/objects/states a vehicle carries — entry and exit nodes, trigger volumes, seat points, weapon components, and module blocks such as `arcade.nitro_boost` (decoded in G2-16/18/19/11 and `USAGES.md` §6).
* **Cannot**: the button → action binding. The only button → action tables are the two `settings/keymap_*.bin` files, and no entity names them (0/232 entity files contain `keymap`).
* **Not decoded**: whether replacing `settings/keymap_gamepad.bin` from a dropzone is honoured — that needs a runtime test (no game runs in this card).

## UNKNOWN

- **which action fires nitro / the afterburner** — no action name in either keymap matches NITRO or (vehicle) BOOST; the only boost name is WINGSUIT_BOOST. The data side exists (`arcade.nitro_boost` on the land vehicles, USAGES §6), so the trigger is native or in a graph the files do not name.
- **whether NEXT_WEAPON / PREV_WEAPON reach a vehicle** — both names exist (keyboard) but no file says which mode consumes them, and G2-11 found 2 driver weapon slots with no switch action.
- **how the class-specific action sets are selected at runtime** — the class is the root object of the .epe (CCar / CBoat / CHelicopter / CAirPlane / CTrain / CMotorBike, FORCEPULSE §owners); nothing in the keymap files or the entities names a class to pick a scheme. The selection is native.
- **what a turret aims with** — no TURRET action exists; PRECISION_AIM and the LOOK_* axes are the only candidates, and the hinge wiring is native (TURRET.md).
- **whether a replaced keymap file is honoured from a dropzone** — the files are `settings/*.bin` archive entries; G2-27 showed path overrides work for `.ee`, but no test has been run for a `settings/*.bin` entry (no game runs here).
- **why 26 binding ids are not `H(action name)`** — the id equals the Jenkins hash of the action name for 448 of 474 bindings and none of the other candidates for the remainder (counts printed above). The remaining ids are stable across the base and patch copies of the same action, so they were fixed before the current name or by another rule; which one is not in any decoded file.
- **the `PP` prefix on the stored input string** — the bytes are `PP`+input and the property's offset points 2 bytes past it, so `PP` is a fixed prefix on every input string in both files; what it encodes is not in any decoded file.
- **which keymap layer the game loads (base vs patch)** — both copies are in the install and differ; MOUNT_RANK says patch wins for path lookups, but no runtime observation was made.
