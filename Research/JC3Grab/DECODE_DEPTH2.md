## 1. `.ddsc`: the AVTX container and its mip chain

Header, decoded by offset (all 116 files agree on the layout):

| offset | size | field | evidence |
|---|---:|---|---|
| 0x00 | 4 | magic `AVTX` | 116/116 |
| 0x04 | 2 | version = 1 | 116/116 |
| 0x06 | 1 | unknown (5 or 9) | value constant within a format, meaning UNKNOWN |
| 0x07 | 1 | resource dimension, stored - 1 (2 = TEXTURE2D) | 116/116 = 2 |
| 0x08 | 4 | texel format id (77, 71, 87, 83) | 4 values, see the block map below |
| 0x0C | 2 | width (texels) | mip chain closes from it on 116/116 |
| 0x0E | 2 | height (texels) | same |
| 0x10 | 2 | depth = 1 | 116/116 |
| 0x12 | 2 | flags (0, 1 or 8) | 8 on the `_dif` files, 1 on one, 0 on three |
| 0x14 | 1 | mip count of the full chain | chain start = this - the next field |
| 0x15 | 1 | mip count stored in this file | the chain closes only with this count |
| 0x16 | 2 | unknown1 = 0 | 116/116 |
| 0x18 | 4 | unknown2 = 0 | 116/116 |
| 0x1C | 4 | unknown3 = 0 | 116/116 |
| 0x20 | 4 | header size = 128 | 116/116, and 128 + size_body == file length |
| 0x24 | 4 | payload size | the mip chain sums to it exactly |
| 0x28 | 4 | constant **16** | 116/116; meaning UNKNOWN |
| 0x2C..0x80 | 84 | tail table | zero on the FULL files, non-zero on the PARTIAL ones (UNKNOWN) |

Per-format block size, **derived** rather than assumed: for each file every candidate
(8, 16, 32, 64 bytes per 4x4 block) was tried and only the one whose chain sum equals
`size_body` was kept. The survivors form a function from format id to block size, which
is the fleet invariant that makes the map evidence and not a lookup:

| format id | files | bytes | block bytes | stored mips | FULL | PARTIAL |
|---|---:|---:|---:|---:|---:|---:|
| 77 | 66 | 68988624 | [16] | 594 | 44 | 22 |
| 71 | 46 | 4088832 | [8] | 408 | 24 | 22 |
| 87 | 3 | 541056 | [64] | 3 | 3 | 0 |
| 83 | 1 | 22000 | [16] | 8 | 0 | 1 |

Mip sizes, **derived**: level `L` is `max(1, w>>L) x max(1, h>>L)` texels, priced in 4x4
blocks with each dimension at least one block, so the 2x2 and 1x1 levels cost one block
each. The stored levels are the last `mip_count_in_file` of the full chain, i.e. levels
`mip_count_full - mip_count_in_file .. mip_count_full - 1`; the ranges are laid down
from `size_header` (128) in that order and the last one ends at EOF. That tiling, not
the sum alone, is the oracle: a wrong block size or a wrong start level leaves a gap or
an overrun, and neither happens on any of the 116 files (1013 mips).

## 2. `.pfxc`: the PFX wrapper and the Havok packfile

Every one of the 4 files has the same shape:

- `PFX\0` at 0, then three u32 that are the same on 4/4: [1, 1, 3, 0]; the wrapper is zero from
  0x14 to the packfile, and the packfile starts at 0x44 (located by its own
  `0x57E0E057` magic, not assumed).
- the packfile parses with `jc3hkx.Packfile`: version `hk_2014.1.0-r1`, sections
  `__classnames__`, `__types__`, `__data__`, and its objects are typed from the
  packfile's own virtual fixup table.
- the data section ends at offset 1988 in each file, leaving a 512-byte trailing blob
  that nothing in the project reads. **That is why no `.pfxc` is graded FULL.**

## 4. UNKNOWNs and why

- the `.ddsc` header tail 0x2C..0x80 on the 45 non-zero files (71 zero): a fixed-size
  table whose u32 pattern repeats (`0x10`, `0x10000`, `0x1000010`, `0x20000`...) but no
  field mapping fits the mip sizes yet; tried: u32/u16 reads at every byte offset in the
  tail against the computed mip sizes and offsets, no match. The mip ranges do not need
  it (they close by accounting), so it stays a named UNKNOWN range.
- the u32 at 0x28 (= 16 on 116/116): value decoded, meaning UNKNOWN. It is not the block
  size (format 71's blocks are 8) and not a floor on mip size (1x1 mips are 8 bytes
  there), so neither of the two meanings a reader would expect is supported.
- the byte at 0x06 (5 or 9): constant within a format, mapped to no meaning.
- the `.pfxc` 512-byte trailing blob: not decoded. It is the same length in all 4
  files but not the same bytes (4 distinct md5s), so it is per-file data, not padding:
  it starts with `0x3f800000` and ends with a table of 16-bit pairs. Whether it is
  shape data, a second allocation or a reference list is UNKNOWN.
- whether a `.pfxc` is honoured for debris collision at all: this task decodes the files,
  it does not test them in game (the reset forbids that).
