## 3. The oracle - do the extents contain every decoded hull vertex?

Two independent records are compared: a **stored** AABB (bytes at a fixed offset) and a set of
**decoded** hull vertices (16-byte `hkVector4` triples, `w` = 0.5 + rank). The child's instance
record supplies a 3x3 basis and a translation; the placement rule `p' = M^T p + t` is the one
`jc3hkx.transform_aabb` pins from the data (the other reading leaves rotated children outside
their parent). Tolerance is the child's own convex radius + 1e-3, because a hull is rounded by
exactly that radius.

## 6. UNKNOWNs

1. **The unit of an extent.** The values are game units; a car spans about 3.0 along z and a
   truck 6.1, which is consistent with metres, but no byte in the file states the unit, so
   `metres` is **not** claimed. Tried: the packfile header (version/tag only), the section names,
   the shape headers; none carries a scale.
2. **The mesh vertex frame.** `hknpExternMeshShapeData.packed_vertices` is located exactly
   (`count x 6` bytes, stride proven by the gap to the next allocation), but the 3 x u16 triples
   are quantized against a frame that is still unpinned - the de-quantization reproduces the
   minimum corner but not the extent (DECODE_DEPTH G3-12b/c). So the mesh *AABB* is decoded and
   the mesh *vertices* are not, and the O1 oracle deliberately uses hull vertices only.
3. **`hknpShapeMassProperties` (mass / inertia / centre of mass)** is still named-only: its
   objects are typed by the virtual fixup table and their bytes are in the residue above. That is
   the same gap G3-10c recorded from the BmAK side; nothing here closes it.
4. **The unnamed bytes inside mesh and compound headers.** Named spans at +0x10..0x1C, +0x20..0x28,
   +0x60..0x70, +0xC0..0xC8 leave 80-ish bytes per mesh shape and 100-ish per compound unnamed;
   the AABB fields sit inside the named part, so the extents are unaffected. Tried: reading them
   as flags/pointers by pattern - no invariant pinned them, so nothing is claimed.
5. **Why a hull may poke out of the render-geometry AABB** (section 3, up to ~0.04 units). It is
   expected for a collision hull that approximates a bumper, but the files do not state it;
   reported as measured.
