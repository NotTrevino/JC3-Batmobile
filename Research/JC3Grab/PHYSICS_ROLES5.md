## 1. The two questions, answered

**No second id space.** A part's `ray` value is an index into the physics system's
body-entry array (`hknpPhysicsSystemData+0x40`, 96-byte entries): every non-negative
ray id in the donor (42/42 parts carry one) is inside 0..61, and
fleet-wide **6309/6309** ray ids select a body entry, each with a shape.
The `42..59` window is exactly the body entries whose shape is an
`hknpExternMeshShape` (measured: the set of ray ids at or above the first extern body
equals the set of extern body indices for the donor). It is the body table's order, not a
separate space.

**A static compound is a body's shape, or a child of another compound, and its children
are nested.** Each donor compound is the shape of exactly one body entry and its seven
children are `hknpConvexPolytopeShape` objects that are not in the body table and carry
no part index.

**What is not fleet-wide:** the `CPfxPartIndexProperty` number is not the parts-module
index for every vehicle - 5466/6696 parts agree (121 files).
The property numbering is still a permutation of its range
(50/121 files), so it is a part index in a different
numbering, not noise; the identity of a ray id's part is therefore proved by the
part-index round trip for the donor and where the numbering coincides, and is *not*
proved by it elsewhere. That is the honest limit of this decode.

## 6. UNKNOWNs

* **The parts-module ordering versus the property numbering** for the vehicles whose
  property value differs from the parts index (1230 parts). The property is a permutation,
  so both numberings are well formed; which one the game's raycast query uses is not in
  any decoded file. Where it would be found: the engine's raycast consumer, or a
  geometric oracle per part (hull vs part mesh bounds).
* **Which engine system reads the `ray` id.** The field is decoded from the parts module
  (`_vehicle_parts.vmodc`); its reader is not decoded. Next source: the executable's
  parts-module reader.
* **Whether a compound's child shapes are addressable by any id.** They carry no part
  property; nothing in the file names them except the compound's instance array. Whether
  the engine addresses an instance by index is UNKNOWN.
* **The stored compound AABB** is not the exact union of the children (worst overflow
  above). Why the author's box is looser or tighter is not decoded.
* **Fleet body tables for the entries whose raw `.physicsc` is absent** (112 of 233):
  their `out/` decodes carry `summary` only, so the id mapping cannot run on them; the
  class-count invariants do cover all entries.
