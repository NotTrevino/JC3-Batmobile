**The input half is module data, not code.** `CustomLandGlobal` carries five `arcade.*` blocks
- `heat_boost`, `nitro_boost`, `nitro_boost_upgraded`, `turbo_jump`, `turbo_jump_upgraded` - on **145 of the 232 decoded vehicles**. `nitro_boost`
is the nitro one by name and by what it does to the car: torque x2, grip x2, a 15,000 N push,
0.2 s blend, +40 km/h top speed, with an `_upgraded` twin at 20,000 N and +80 km/h. `heat_boost`
is a separate block (`push_force` 0, +80 km/h) and `turbo_jump*` is the jump, which pairs with the
`EngineTurboJump` usage (11 vehicles). **Which control fires any of them is in no file here** -
the button lives in code / controls data this census does not carry, so that edge is UNKNOWN.

**The effect half has two hash spaces, and only one is named.** The object's `Effect` field is
3518298851 (0xD1B4FAE3), carried by **28 objects on 17 vehicles**
- again all nitrous exhaust: `exhaust_upgrade_nitrous` 12, `exhaust_upgrade_nitrous2` 6, `exhaust_left_upgrade_nitrous` 5, `exhaust_right_upgrade_nitrous` 5.

`dynamic_nitrous`, the object carries a second, unnamed effect hash, and the 9 `*nitrous*.effc`
files are a candidate family matched by **name only** - the object hash -> `.effc` edge is
UNKNOWN (section 7).

**The sound step is data to the sample name.** That GUID is carried by
**202 objects on 172 of the 232 decoded vehicles**, and every carrier is a nitrous exhaust object -

resolves to a real `EVTS` entry, `vehicles` ordinal 249 (195 B) - not a
dangling GUID.

**Which samples? By name.** `vehicles.bank` does not link an event to a sample index (that is
proven in `JC3_AUDIO.md` section 5 - five independent probes, all negative), so the samples are
the ones JC3 named for this event: 56 `jc3_veh_land_premium_nitro_start`, 150 `jc3_veh_land_premium_nitro_loop`, 355 `jc3_veh_land_premium_nitro_stop`.
test-060 swapped exactly those: `_apply_audio.py` replaces 0-based indices
56, 150, 355, and **that is the same set**
as the three indices the names select (checked at build time, not by hand). The bank's other
nitro-named samples are a different set, and only 165 is a fourth nitrous clip (a flame loop
test-060 left alone) - the rest are turbo-jump whooshes and the tank's turbowhistle: 72 `jc3_veh_land_premium_turbo_jump_01`, 90 `jc3_veh_tank_m8_turbowhistle`, 165 `jc3_veh_land_premium_nitro_jet_flame_loop`, 270 `jc3_veh_land_premium_turbo_jump_whoosh_02`, 448 `jc3_veh_land_premium_turbo_jump_whoosh_01`, 584 `jc3_veh_land_premium_turbo_jump_02`, 605 `jc3_veh_land_premium_turbo_jump_03`.

**What a build does with this.** Copy `vehicles.bank`, keep all
649 FSB5 samples and every header, and overwrite the PCM16 payload of
those three indices with the BmAK afterburner start / loop / stop at the same length and rate -
the swap `_apply_audio.py` already performs for test-060, i.e. route (a) of `JC3_AUDIO.md`.
No `.ee`, `.epe` or `.fmod_guids` edit is needed: the usage, the attachment and the event
already exist on the donor, so the mod only changes what the event plays.

- **what drives each usage.** Which variable or event turns a usage on is code; the
  `.epe` declares only the value-driven set in section 4.
- **hash function.** UNKNOWN; hashes are read from the files where the string sits next
  to them, never recomputed, so no identification is needed.
- **which control fires nitro.** `arcade.nitro_boost` says what happens, no decoded file

  picked by name. If a future build hears a wrong clip, a different event on the same bank is
  the likely cause, and only auditioning tells them apart.
- **in-game behaviour.** No game was launched (R6); the nitro flame rendering is a Q
