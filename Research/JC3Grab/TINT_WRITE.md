# The `Palette.tints[i].tint_r` write path (G3-09d)

Generated by `Tools/scripts/jc3_tint_write.py --write`; `--check` re-exports both
carriers, re-runs both round trips from the build bytes and compares this file byte for
byte. Static only: the game is never launched, nothing is installed, and no build file is
modified (every edit is staged in a temp directory, and the source hashes are re-checked).

## 1. Answer

**STATUS: DONE - the write path is decoded and round-trip proven; the current build does
not write a tint value.**

`tint_r` is **not an `.epe` member**, so it cannot be edited "in the `.epe`" as one
value. The paint tint lives in the palette **`.vmodc`** (ADF v4); the `.epe` carries only
a 4-byte module hash that names that file. An edit is therefore one float in the palette
file plus, optionally, a pointer edit in the `.epe` if the palette is renamed:

| carrier | format | repo tool | what it holds for the tint |
|---|---|---|---|
| `..._civilian_01.epe` | RTPC v1 | `ConvertProperty` | one `CCar.palette` int32 at file `0x29a`, the Jenkins hash of the palette module path; no `Palette` node, no `tint_r` |
| `<default|default/batmobile>/v0300_car_kensington_sportsmuscle_palette.vmodc` | ADF v4 | `ConvertAdf` | the `Palette.tints[i]` records, `tint_r` as `ColorRGBA` (four float32 at `Tint+20`) |
| `..._debug.ee` | AAF archive | none in this repo | packs entity files; neither converter reads it (`ConvertAdf`: FormatException, `ConvertProperty`: NotSupported) |

Which build writes what:

* **bm-005 (the build under test)** points `palette` at the vanilla path
  (`-1071400364`) and its palette module is **byte-identical** to bm-001: no tint value is written.
* **bm-RC1 / bm-RC2** move the module to the `batmobile/` namespace and repoint the hash to
  `1322976751`, but ship the **same bytes** (`72d5d04f78c6...`): the pointer is written, the tint is not.
* `Working/Entity/bm_epe_edits.json` has **19** rows, **0** of which name palette/tint:
  the B-05 graph writer never touches either carrier's tint.

So today the Batmobile paints itself with the donor's **White** record
(`tint_r` = 0.0500, 0.0500, 0.0500, 1.0000) exactly as the civilian sportsmuscle did.

## 2. Serialisation, byte level

### 2.1 The palette module (where the float is)

`jc3adf` (independent of Gibbed) decodes the build's palette as one `Palette` instance
named `solar_cars_palette.vmod` (920 B), and `ConvertAdf --e` agrees on every offset below:

| type | size | member | offset |
|---|---:|---|---:|
| `Palette` | 16 | `tints` | 0 |
| `A[Tint]` | 16 | element | stride 80 |
| `Tint` | 80 | `name` (`HashString`) | 0 |
| | | `occurrence` (int32) | 16 |
| | | `tint_r` (`ColorRGBA`) | 20 |
| | | `tint_g` / `tint_b` | 36 / 52 |
| | | `specular_gloss` / `metallic` / `clear_coat` | 68 / 72 / 76 |
| `ColorRGBA` | 16 | `R` / `G` / `B` / `A` (float32) | 0 / 4 / 8 / 12 |

The first record is `White` (occurrence 100); its `tint_r` is
`0.0500000007` at file offset `0x74` - the export's own `offset-in-file` for `tint_r.R`:

```xml
<member name="tint_r" gbltype="Structure" type-hash="1221386478" type="ColorRGBA">
    <member name="R" gbltype="Primitive" offset-in-file="00000074" type="float">0.0500000007</member>
    <member name="G" ... type="float">0.05000000074505806</member>
</member>
```

`tint_r` is therefore **four separate float32 stores**, not one packed colour: an edit
rewrites 4 bytes per channel (16 per colour). The palette holds **10** `Tint` records
(the same count from `ConvertAdf --e` and `jc3adf.walk`), so `tints[i].tint_r.c` lands at
`0x50 + 80*i + 20 + 4*c` (data base `0x50`, array header 16 B).

### 2.2 The `.epe` (where the pointer is)

The exported `.epe` is a `container format="RTPC"` with **8271** lines; it has no `Palette`
object. Its only palette surface is one value on `CCar`:

```xml
<value name="palette" type="int">-1071400364</value>
```

That int is the Jenkins hash of the module **path**, which is why a rename changes it:

```
Jenkins32("editor/entities/jc_vehicles/01_land/v0300_car_kensington_sportsmuscle/modules/default/v0300_car_kensington_sportsmuscle_palette.vmodc") = -1071400364
".../modules/default/batmobile/v0300_car_kensington_sportsmuscle_palette.vmodc" = 1322976751
```

`ConvertProperty -i` writes that int in place at file offset `0x29a` (4 bytes, no size
change, no padding shift).

### 2.3 The edit recipe the bytes imply

1. Export the palette with `ConvertAdf --e`, change the target
   `tint_r.R/G/B/A` text, import with `-i`. One float in, one float out.
2. If the module keeps its path, stop - the `.epe` already hashes that path.
   If it moves (as bm-RC1 did to `batmobile/`), export the `.epe` with
   `ConvertProperty --e`, rewrite the `palette` int to the new path's hash and import.
3. Ship the module at exactly the path the hash names; the `.epe` stores no filename.

## 3. Round trips (ConvertProperty style)

Both were run on the build's own bytes, staged in a temp directory; the build files were
not modified (`--check` re-hashes them afterwards).

| round trip | file | before -> after | bytes that differ | XML diff lines | re-import identical |
|---|---|---|---:|---:|---|
| one tint float | `v0300_car_kensington_sportsmuscle_palette.vmodc` | 1897 -> 1897 B | **4**, all at `0x74` | 2 | yes |
| palette pointer | `v0300_car_kensington_sportsmuscle_civilian_01.epe` | 124488 -> 124488 B | **4**, all at `0x29a` | 2 | yes |

The tint edit changed `0x74..0x77` and nothing else; the binary float at `0x74` went
from `0.0500000007` to `0.238999993` (float32 of 0.239 is `0.238999993`).
Re-exporting the edited file produced exactly one changed *value* line:

```
-                        <member name="R" gbltype="Primitive" offset-in-file="00000074" type="float">0.0500000007</member>
+                        <member name="R" gbltype="Primitive" offset-in-file="00000074" type="float">0.238999993</member>
```

So: **changing one `tint_r` float changes only that float**, and the writer is
layout-stable (same size, same offsets, idempotent re-import). The `.epe` pointer edit
behaves the same way: 4 bytes at `0x29a`, idempotent.

  palette could be inspected there. The loose palette is reached only via the `.epe` hash.
