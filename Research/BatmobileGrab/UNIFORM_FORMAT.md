32 bytes, so the record's length is *derived*:

    span = 40 + n + 32 * count           (n = the name length field, NUL included)

**7278** offsets. **6966** of them are proven end to end (9582 entries, 764817 B); **312**
leave the 32-byte entry shape and are **not** decoded here (section 7).

## 3. The layout, field by field

```
record :=  i32    n          ; 2 .. 300, length of the name INCLUDING its NUL
           u8[n]  name       ; printable ASCII, name[n-1] == 0
           u8[16] guid       ; distinct for every record
           u8[16] zero       ; 0 in every record
           u32    count      ; 1 .. 64
           entry[count]

entry  :=  u32 class        ; FName index, 2040..2055, FMaterialUniformExpression*
```

## 8. Where the format stops: the first field this card cannot explain

The record ends at its entry array, and for the proven records the next u32 is a
plausible count in **6966/6966** cases (oracle O9) - that is the boundary proof.
Beyond it, the record format is not what stops the work; the *entry* format does, for
the 312 headers whose entries are not all vector parameters:

| first non-vector class met | records |
|---|---:|
| `FMaterialUniformExpressionAppendVector` | 206 |
| `FMaterialUniformExpressionFlipBookTextureParameter` | 78 |
| `FMaterialUniformExpressionFoldedMath` | 28 |

Of those, 51 tile only if the FlipBook entry (`FMaterialUniformExpression
FlipBookTextureParameter`) is given the 4-byte width borrowed from the post-record
block model, and only 33 of the 51 then land on a plausible next count - so that width is
not proven either. The remaining 261 never tile at any width tried.

**The first unexplained byte in the file** is at `0x8ac162b`, entry index 3 of `Joker_Young_Shirt_MASTER_MAT`
(record at `0x8ac1586`):

```
    0x8ac162b  000007f9  -> `FMaterialUniformExpressionAppendVector`
    0x8ac1633  000007ff  -> `FMaterialUniformExpressionFoldedMath`
    0x8ac163b  000007ff  -> `FMaterialUniformExpressionFoldedMath`
```

The entry begins with a class FName (`FMaterialUniformExpressionAppendVector`), then
instead of a parameter FName and a value it carries further class FNames - the
operands of the expression. So the entry's width depends on a tree whose encoding
(operand order, per-class payload, termination) is **UNKNOWN** from these bytes; that
is the first field this card cannot explain, and it stops the format work here.

The same thing shows up after the anchor record: its following block declares 26
expressions, 14 parse, and at `0x8bc225d` the u32 is `0x80302` - not a class FName - while `0x8bc225e` begins a
well-formed entry (FMaterialUniformExpressionScalarParameter, Damage_Dirt_Edges, value 1.0). A single byte sits before the nested expression; its
meaning is UNKNOWN (oracle O15). This does not touch the record: its extent is
fixed by its own count (oracle O6).

## 9. UNKNOWNs

1. **The entry payload for every class other than
   `FMaterialUniformExpressionVectorParameter`.**  Section 8: `AppendVector` stores
   operand class FNames where a value would be. Affects 312 of 7278 headers. Would need
   the cooker's serialiser for `FMaterialUniformExpression*`, which the project does
   not have.
2. **The purpose of the 16 zero bytes at `+20+n`.**  Zero in every record, so four
   `u32` zeros, two `u64` zeros and one 16-byte zero field are indistinguishable.
3. **The 514 bytes between the container run and the first record**, and the bytes
   between records. Same filler as the inter-container gaps G3-04d measured (310 …
   2044 B); not decoded there or here.
4. **What the records mean.**  Out of scope by the brief; the slot binding is absent
   from the cache (`SHADER_COMBINE.md`: 0 `RDEF` in 38,201 + 2,098 blobs).
