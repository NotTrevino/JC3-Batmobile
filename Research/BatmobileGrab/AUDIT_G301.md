# AUDIT_G301.md - G3-01's collision card, audited against the packages

Generated by `Tools/scripts/audit_g301.py --write`; `--check` re-parses every export and re-derives every number below. The card (`COLLISION.md` / `COLLISION.json`, generator `grab_collision.py`) is **read-only** here: this file is the audit, not a new version of the card.

The G3-01 tracker row is the claim under test: *the drivable Batmobile has 7 objects (Startup 7530/82147/82148/169640/171103/171104/154788) with 0 unparsed bytes, and a mode-dependent set of collision primitives (two StaticMesh components, three CylinderComponents, RB_StayUprightSetup, SVehicleMesh)*.

**The card's naming and its link rule both break here.** The exports it calls `RB_StayUprightSetup` are named `MyStayUprightSetup` (Startup 154788, BmGame 172112), while the Playable instance 5106 *is* `RB_StayUprightSetup`. The card states that the instance-to-template link is by component name; for this component the names do not match, so the link it used cannot be the name there. The other five components do carry the same name at every layer.

- three CylinderComponents exist as **instances** (276, 277, 278); Startup/BmGame carry templates for only two of them (82147/82148 -> 142597/142598). Export 276's template is absent from both chains - that is the card's own UNKNOWN, and it means the row cannot promise three templated cylinders.
- the mode switch names **only** the two StaticMesh components (`BatmanCollisionMeshPursuitMode` at value 1, `BatmanCollisionMeshBattleMode` at value 2, value 0 attaching neither - G3-01e-fix). No selector argument, detach or attach call mentions a cylinder, `RB_StayUprightSetup` or `SVehicleMesh`, so calling the whole set mode-dependent is not supported by any decoded byte.
- `RB_StayUprightSetup` is 2 bytes in all three layers (only the `0000` terminator): it carries no serialised field at all, so nothing about it can be mode-dependent.

## C3: the two floats at 540 / 544

| object | pkg | 540 | 544 | Translation (400) |
|---|---|---:|---:|---|
| `base_template:FrontCollisionCylinder` | bmgame | [78.0] | [175.0] | [100.0, 0.0, 0.0] |
| `base_template:RearCollisionCylinder` | bmgame | [78.0] | [175.0] | [-200.0, 0.0, 0.0] |

- both values re-derive exactly: **78.0 at 540, 175.0 at 544**, in both BmGame base templates (142597, 142598) and nowhere else in the card's object set.
- the card is right that the **names** are UNKNOWN: `BMSDK_OFFSETS.json` has no CylinderComponent layout, and no decoded file in this tree labels 540 or 544.
- a geometry test separates the two readings, under one stated assumption (a car's collision cylinder lies inside the car's own render bounds): the car's render bounds are Y -174.706..174.824 (half-width 174.765) and Z -0.223..233.962, and the pursuit hull union is Y +/-159.1562. **78 fits as a radius** (78.0 <= 159.1562); **175 does not** (175.0 <= 159.1562 is false) but fits as a height (175.0 <= the 234.185 cm Z span). That is evidence for 540=radius, 544=height - evidence, not a decode, so it stays derived and the names stay UNKNOWN.

So the tracker row's phrasing (`78.0 / 175.0 radius/height at offsets 540/544`) reads the values correctly but states an assignment the card deliberately refuses to make. The card is **not** wrong here; the row over-reads it.
