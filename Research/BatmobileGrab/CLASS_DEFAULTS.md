## 8. UNKNOWNs, with what was tried

1. **Declared properties with no tag in either stream** (§6) - 901 of 1344 across the chain.
   Their effective value is the class's constructed default, which is not in these bytes;
   a runtime read (G3-02d sampler / G3-07) is the only oracle for them.
2. **Array element layouts that are not decoded** - where the class declares an element
   type the reader could not walk (e.g. `ColourLevels`: 5 x 16 B), the bytes are published
   raw and labelled `element layout UNKNOWN`; nothing is inferred from their shape.
3. **Nested struct member names** - `StructProperty` payloads are decoded as nested tag
   lists (offset + type + value per nested tag) but the nested offsets are not resolved
   against the struct's BmSDK layout, so a nested tag has a value and a slot, not a name.
4. **What the referenced sub-objects contain** - e.g. `FrontCylinderComponent` is named and
   its target identified, but the target's own payload (the collision cylinder's radius and
   height) is another object, not decoded here.


## 9. Limitations

* These are the values the cook serialised on the two class default objects. A property
  whose value equals the class's constructed default is not serialised at all, so it has no
  value in these bytes - that is `UNKNOWN`, not zero (see §6).
* The *effective* value of a property inherited from an ancestor is the most-derived stream
  that carries its offset, *if* the streams are delta lists against the parent class's
  default object. That mechanism is not proven here: what is decoded is (a) each stream's
  bytes and (b) which offsets both streams carry and whether the values agree (§5).
* A pointer tag names a target object; it does not say what that object contains. The
  targets' own payloads are separate objects (e.g. `Default__RVehicleBatmobile.SimulationModel`) and are not decoded here.
* Everything here compares files to files. No runtime measurement exists (G3-07).
