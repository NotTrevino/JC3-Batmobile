# MATRIX_ORDER - is the AggGeom `TM` 3x3 stored as rows or columns?

Generated by `Tools/scripts/grab_matrix_order.py` (`--write`); `--check` re-derives every
number from the packages and fails on a one-byte difference. Card: `GRAB_BACKLOG.md`
G3-01b open item U-3. Labels: **decoded** = from bytes (package + export + offset);
**derived** = computed from decoded values with the rule stated; **UNKNOWN** = not
decoded, with why.

## Verdict

- row/column order: **UNSETTLED**
- layout of the 16 floats: **SETTLED: four planes, each (W,X,Y,Z), in the order X, Y, Z, W**
- the tilt: 4.00 deg about the Y axis (magnitude and axis decoded; R and R^T share both). Sign: conditional - +4.00 deg about +Y if the planes are the rows (row-vector), -4.00 deg about +Y if they are the columns.
- why: no transform in this build is stored both as a 64-byte FMatrix and as a quaternion, so there is no known case to compare against; the one the card names (the mesh reference pose of Batmobile_Rig_Weapons_Trans) is the identity rotation

The reference pose is the **identity rotation** for both the weapons bone and the
chassis bone. The tilt the box carries is therefore a shape-local orientation inside
the bone's frame, added by whoever authored the physics asset - it is **not** the
bone's reference pose and no quaternion in the mesh repeats it. The case the card
names is empty.

So: the build stores **matrices only** in aggregate geometry (box/capsule element TMs,

**quaternions only** in skeleton and animation records.
No transform in this build is written both ways, which is exactly what a known case
would need.

This is **evidence, not proof**: it needs the premise that ragdoll capsules are placed
along their bones, the capsule is rotationally symmetric about its long axis so its own
bytes cannot name that axis, and the separation between the two readings is a factor,
not a gap. It is reported because it is the only relation in the build that points
either way, and it points at the **column** reading. It is not used to declare the
order settled.

## 5. What would settle it

1. a native struct dump for this build that fixes `FMatrix`'s row/column semantics
   (G3-06) - the same place a `FKAggregateGeom`/`FKBoxElem` layout would come from;
2. any body in any package whose element `TM` duplicates a bone transform that the
   skeleton also stores as a quaternion (none in these 8 packages: table above);
3. a per-bone vertex set asymmetric enough to bracket a rotated element - the weapons
   bone itself owns **no** skinned points (probe in the DONE report), so its box cannot
   be checked against its own geometry.

## UNKNOWNs

- **U-1 whether the three planes are the transform's rows or its columns** - tried: decoded all three BmGame box TMs; both readings are proper rotations of the same angle about the same axis; enumerated every TM(64) in 8 packages by class; scanned the 20,151,210-byte SkeletalMesh export at every float offset for an orthonormal 3x3; decoded the mesh reference pose of the bone the box belongs to; measured 122 non-identity ragdoll capsules against their bones' own reference-pose directions. Still unknown because the only matrices this build stores are aggregate-geometry element frames (shape-local, no quaternion counterpart); the only rotations it stores as quaternions are skeleton/anim records (no matrix counterpart); the mesh reference pose of the weapons bone is the identity, so it cannot carry the tilt. A native struct dump that fixes FMatrix's row/column semantics for this build (G3-06), or any body whose element TM duplicates a bone transform, would decide it.
- **U-2 which local axis a ragdoll capsule's long axis is** - tried: tested all three local axes against the bone direction under both readings; the capsule is rotationally symmetric about its long axis, so its own bytes cannot name that axis - only the art setup can. Still unknown because no local field names the capsule's axis (BMSDK_OFFSETS.json has no FKSphylElem layout).
