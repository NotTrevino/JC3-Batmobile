## 1. The `.upk` shader cache

One export, class `ShaderCache`, 155333378 B of payload in two regions:

| region | offsets | contents |
|---|---|---|
| shader bytecode | 0x19d .. 0x8ab3e03 | **38201 DXBC containers** |
| material records | 0x8ab3e03 .. end | 6934 per-material uniform lists |

Every container frames from its own header: magic, 16-byte checksum, u32 1, u32 total,
u32 chunk count, a chunk-offset table of that count, then the chunks.  The u32 six
bytes before each magic equals that container's own `total` (0/38201), so the region is
a run of size-prefixed blobs rather than a coincidental byte pattern.

Chunk tags across all 38201 containers:

| tag | count |
|---|---:|
| `ISGN` | 38201 |
| `OSGN` | 38201 |
| `SHEX` | 38201 |

**There is no `RDEF` chunk: 0 of 38201.**  `RDEF` is the chunk that names constants and
their constant-buffer slots; without it the bytecode reads `cb0[..]` by number only.

## 4. Where the chain breaks

| question | answer | evidence |
|---|---|---|
| is the pixel shader bytecode present? | **yes** | 38201 SHEX chunks, 38201 with an OSGN output signature |
| does the bytecode name its constants? | **no** | 0 RDEF in 38201 + 2098 blobs |
| do the parameter names occur near the bytecode? | **no** | 0 hits in the 145440259 B blob region ({'Material0_BaseColour': 0, 'Diffuse_Adjust': 0, 'Material1_Basecolour': 0, 'Material2_BaseColour': 0, 'Batmobile_Worn': 0}) |
| does the material record point at a blob? | **no** | the 14 vector entries are followed by a second list (26 entries), and neither lists a blob start |
| does the material GUID occur beside a blob? | **no** | 5 sites, 0 in the blob region, at ['0x8bc1b46', '0x8bc1f46', '0x8bc1f69', '0x8bc3215', '0x8bc3698'] |

So the cache holds both halves - the compiled PS and this material's uniform list - but
not the map between them.  `Material0_BaseColour` and `Diffuse_Adjust` therefore cannot
be assigned a `cb0` slot from these files: any such assignment would be a guess, and
this card does not make one.

What would close it: a build whose DXBC keeps `RDEF` (then the constant names and
offsets are in the chunk and the PS can be disassembled by name), or the shader-map
hash function the cooker used to key blobs by material, or a runtime capture of the
constant buffer the PS receives.  None of the three is in the project today.

## 6. UNKNOWNs

1. **Which blob is this material's PS.**  No name, no GUID and no offset links the
   record to the blob region (section 4).  Would be found in an uncooked build's
   shader map, or by keying blobs with the cooker's hash.
2. **The constant-buffer slot of each parameter.**  Needs `RDEF`, which is absent from
   all 38201 + 2098 shipped blobs.
3. **The combine operator.**  It is in the PS arithmetic, which is present but unnamed;
   reading it without `RDEF` would mean matching 38,201 blobs to materials by eye.
4. **Lighting, reflection and tonemap.**  Same bytecode, same gap.
