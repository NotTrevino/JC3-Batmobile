# DRIVE_MODES - what decides the Batmobile's behaviour per mode (G3-02l)

Generated by `Tools/scripts/grab_drive_modes.py --write`. `--check` re-derives every number below from `BmGame.upk` and `Startup.upk` and fails on any difference. Static only: the game is never launched or attached to.

**Oracles 8/8 pass.** Two packages read: `BmGame.upk` (214,757,637 bytes, 177,031 exports) and `Startup.upk` (434,869,146 bytes, 174,890 exports).

Labels: **decoded** = bytes read at the export and offset quoted; **derived** = a stated rule over decoded bytes; **UNKNOWN** = no field or body implements it here, with what was tried. Field *names* come from the BmSDK-AK class layout (`BMSDK_OFFSETS.json`); a tag carries only type + offset, so a field is named only where the layout declares one at that offset with a compatible kind.

## 1. The mode the simulation is in - `EBatmobileDriveMode` (decoded)

`RVehicleSimBatmobile.EBatmobileDriveMode` (export 129610) holds 4 values; the payload is a count and (FName, number) pairs, resolved through the package name table.

| value | name |
|---:|---|
| 0 | `BMDM_Drive` |
| 1 | `BMDM_TurnOnSpot` |
| 2 | `BMDM_BattleMode` |
| 3 | `BMDM_MAX` |

`RVehicleSimBatmobile.DriveMode` is a `ByteProperty` at **0x03b0** (class layout). The class default object carries a tag there whose value is the FName `None` - enum value 0, `BMDM_Drive`; the shipped `SimulationModel` object carries no tag of its own at that offset, so it inherits that default. So the car sits in the pursuit drive mode and battle mode is a separate simulation mode that the state sets explicitly, not a flag.

### Stationary turn (decoded carrier, native arithmetic)

The mechanism the station-keeping spin needs is present as fields, not as a script branch: `BMDM_TurnOnSpot` (enum 1), `TurnOnSpotFrontTorqueFactor` and `TurnOnSpotRearTorqueFactor` with **opposite signs** (front 0.6, rear -0.5 in the CDO), `DesiredTurnOnSpotSpeed` 180, `TurnOnSpotModeEngineBrakingFactor` 0.01 in the shipped object, and `TurningModeMaxSpeed` 300. **Derived** (rule stated): a front and a rear torque factor of opposite sign can only produce counter-torque if both axles are driven, i.e. this is a four-wheel torque split rather than a steering-angle spin. The per-wheel `bPoweredWheel` flags are UNKNOWN (see §7), so the *selection* of four-wheel drive is still native; only the symbols it must use are decoded here.

**Who selects mode 1 is UNKNOWN**: the corpus scan finds `SetDriveMode` called from exactly two bodies per vehicle class, with 0 and 2 only. `ForceTurnOnSpotMode` (a `BoolProperty` on the sim) and `DesiredTurnOnSpotSpeed` exist but no decoded body writes them.

## 4. The steering input path

What the script side does (decoded references; the operator chain is an expression tree this walk does not flatten):

1. `CheckBattleStrafe` / `PursuitStrafe` read `PlayerInput.aBaseY` and `PlayerInput.aStrafe` and store them into a local vector (`MoveDir`/`Strafe`), then read `BatmobilePawn.Rotation` and `RVehicleBatmobileBase.BattleModeYawOffset`.
2. `PursuitStrafe` calls `GetMovementAxes(X, Y, Z)`, then `VehicleStrafe(Strafe, BatmobileSideSwipeTarget)` - the side swipe target comes from the controller.
3. `RVehicleBatmobileBase.VehicleStrafe` applies the impulse (`KickStrafe`, `PMDodgeTorque`/`PMDodgeForce`/`PMDodgeDuration`) and spawns left/right exhaust bursts.
4. In pursuit the drive itself stays on the native sim: `PursuitMode.Tick` reads `Core.OutputSteering` and passes it to `SetWantAirBrakes(OutputSteering, ..., OutputSteering)`, and reads `AbsoluteMoveDirection`.

`BattleMode.Tick` has no steering call at all: it only handles audio state, the winch, stuck-flip recovery and the `TryToChangeMode(PursuitMode)` exits. So the battle-mode movement (left stick in the stick's direction, car turning to face the camera) is implemented inside the native simulation, with `AbsoluteMoveDirection`, `BattleModeSteerAngleFactor`, `BattleModeMaxSteering`, `BattleModeTrailingSteerFactorMoving` and `BattleModeYawOffset` as its fields.

## 7. Exact gaps

- **the body of RVehicleSimBatmobile.SetDriveMode** - export 129767 is a native declaration, not bytecode: its whole script is the 0x29 PropRef to its own parameter (5 bytes). The per-mode torque/steer arithmetic therefore lives in the executable, not in the cooked package; only the fields it reads and the mode it is given are decodable here. *Where:* BatmanAK.exe (native), out of scope for a static package read
- **which caller sets BMDM_TurnOnSpot (value 1)** - the corpus scan finds SetDriveMode called only from PursuitMode.BeginState (0) and BattleMode.BeginState (2). No script body passes 1, so either the native simulation switches to it from a speed/throttle test, or the value is set by code the package does not carry. *Where:* the native SetDriveMode body, or an engine-side condition on throttle/speed
- **the operator of the `DriveMode` guard in `BattleMode.BeginState`** - the body reads `DriveMode` and then calls `SetDriveMode(2)`, but the comparison is written through an `EX_Context` (the object expression is `BatmobileSim`), so the operator token sits before a nested expression this one-pass scan does not classify. The reads and the call are decoded; the test is not. *Where:* the same body, with an expression-tree parser
- **the exact arithmetic of the camera-relative move** - CheckBattleStrafe/PursuitStrafe read PlayerInput.aBaseY/aStrafe into a vector, rotate it by the Pawn's rotation and read BattleModeYawOffset in the same expression; the operator chain is an expression tree this one-pass walk does not resolve, so only the inputs and the 16384 constant are decoded. *Where:* the same bodies, with a full expression-tree parser
- **per-wheel powered flags in the shipped sim** - SVehicle.NumPoweredWheels (1908) and SVehicleWheel.bPoweredWheel (116) exist in the layout, but neither the shipped sim object nor the class CDO carries a tag for them, so no shipped value is readable here. *Where:* the wheel objects of the spawned vehicle at run time, or the native sim
