# The material uniform records: 6,943 records, and no parameter-to-slot map (G3-04e)

Generated by `python Tools/scripts/grab_uniform_records.py --write`; re-derived
and compared byte-for-byte by `--check`. Machine half: `UNIFORM_RECORDS.json`.

**The short version.** The 6,943 per-material records in
`CombinedShaderCache-PC-D3D-SM5.upk` are **name-to-value lists**, not
name-to-slot maps. Every one of their
9,553 entries is a 32-byte
`(FMaterialUniformExpressionVectorParameter, parameter, RGBA)` triple, and each
record consumes exactly its declared bytes - there is no field left over that
could hold a `cb0` slot. The blocks between the records are the same materials'
remaining uniform expressions, drawn from the engine's 16
`FMaterialUniformExpression*` classes; they are parameter-level folded
arithmetic, not a shader-parameter map. So the brief's condition - *if* a record
maps a name to a slot - is **not met**, and the paint-colour rule stays
**UNKNOWN**: the SHEX is present, but nothing in these files says which
`cb0[n]` a given parameter arrives in.

## 1. The record layout, decoded from all 6,943

The region runs from the end of the last DXBC container
(`0x8ab3e03`) to EOF:

```
record :=  FString name            ; i32 length (incl. NUL) + bytes
           u8[16] guid
           u8[16] zero pad
           u32 count
           entry[count]
entry  :=  FName class            ; u32 name index, u32 number
           FName parameter        ; u32 name index, u32 number
           f32[4] value           ; RGBA, width fixed by the class
```

| measurement | value |
|---|---:|
| records | **6,943** |
| of which G3-04d's count (6,934) missed | 9 - all with names over 60 chars |
| candidate name-strings rejected by the structure test | 65,555 |
| entries in the primary lists | 9,553 |
| entry size | 32 B |
| bytes between one record's entries and the next record | median 512, p95 3842, range 88 … 668192 (319 gaps over 4096) |
| first record / last record's end / file size | `0x8ab4005` / `0x94232aa` / `0x9423302` |

The entry class census is a single row - that is the finding, not a gap in the
parse:

| class | entries |
|---|---:|
| `FMaterialUniformExpressionVectorParameter` | 9,553 |

Every record is `40 + len(name) + 32 x count` bytes long (oracle
`every_entry_is_32_bytes`). A slot field would have to live somewhere in those
32 bytes, and they are fully spoken for by one FName pair and one RGBA.

The one field that could plausibly have hidden a slot is the second word of each
`FName`, which in this engine is a *name number* - a disambiguator for a repeated
name, not an index into a buffer. Measured over all
9,553 entries: the class FName's number is **0 in all
9,553**, and the parameter's number is 0 in
9,507 and takes only the values
['2', '3', '4', '5'] otherwise
(46 entries) - a range far too small and too
evenly spread to be `cb0` offsets (which reach into the hundreds of bytes).

**Correction to G3-04d.** That pass reported 6,934 records. Its
candidate regex capped the material name at 60 characters, so it dropped
**9** real records - every missed name is longer than 60 (e.g.
`GAMEPLAYONLY_Clocktower_Barbara_Newspaper_Clips_02_Flashback_DO_NOT_USE`).
The count is **6,943** and the entry total **9,553**;
nothing else changes - the extra
records are ordinary one-`SelectionColor` records like their neighbours.

### What the record is not: the chain's overrides

The record holds the *parent* material's default. Where a MIC in the chain
overrides the same parameter, the override lives in the MIC asset (the
`ScalarParameterValues` arrays `COLOUR_PARAMS.md` section 2 decodes), and the
record keeps the default - which is itself a check on both readings:

| parameter | the record's block (`UNIFORM_RECORDS.json`) | the MIC's override (`COLOUR_PARAMS.md`) | same? |
|---|---|---|---|
| `Mud2_Opacity` | 0.65 | 2.0 (Batmobile_V3_Mainbody_NEW_MIC) | no - as expected |
| `Mud_Edges_Opacity` | 0.3 | 100.0 (Batmobile_V3_Mainbody_NEW_MIC) | no - as expected |
| `Mud_Opacity` | 100.0 | 50.0 (Batmobile_V3_Mainbody_NEW_MIC) | no - as expected |
| `Vector_Displacement_Multiplier` | 1.0 | 1.0 (Batmobile_V3_Mainbody_NEW_MIC) | yes |
| `Damage_dirt` | 0.5 | 0.5 (Batmobile_V3_WheelArchs_NEW_MIC) | yes |

So a shader cannot be told `Mud_Opacity` and get 100 on the body: the MIC wins
upstream, in the material instance.  This is exactly why the missing piece has
to be the constant-table naming, not the values.

3. none of them is the *output* combine - they are evaluated into the uniform
   buffer, and which slot each lands in is the shader's business.

## 4. Why that decides the bridge question

| question | answer | evidence |
|---|---|---|
| do the records name their parameters? | **yes** | 14 vector entries for `Batmobile_Worn` |
| do the records carry a `cb0` slot, index, buffer or offset? | **no** | every entry is 32 B of `(class, parameter, RGBA)`; the record consumes exactly its bytes |
| is there a separate parameter map anywhere in the region? | **no** | the class vocabulary is the 16 uniform-expression classes, none of which holds a slot |
| does any parameter name occur in the bytecode region? | **no** | 0 hits over 145,440,259 B |
| does the material GUID sit beside a blob? | **no** | 0 of 5 sites are before the record region |
| can the SHEX arithmetic be attributed to a named parameter? | **no** | the three rows above |

So the last route the brief names is closed by measurement rather than by
assumption: the cache holds the parameter *values* and the *bytecode*, and the
one artefact that would join them - a constant-table chunk, `RDEF` - was stripped
by the cooker from all 38,201 + 2,098 containers.

## 6. UNKNOWNs

- **a mapping from a paint parameter name to a `cb0` slot** - tried: all 6,943 records parsed end to end: each entry is exactly (class FName, parameter FName, RGBA float) and 32 bytes, and every record consumes exactly 40 + name + 32 x count bytes, so no field is left over to hold a slot; the class FName's second word is 0 in all 9,553 entries and the parameter's second word is a name number (2..5, 46 entries) rather than a slot; the inter-record blocks are uniform-expression lists from the engine's 16 classes, not a parameter map; the DXBC containers still carry no RDEF. Still unknown because the binding is not in these two files. In this engine the compiled shader owns the constant layout, and the cooker stripped the chunk that names it (`RDEF`), so a slot would have to come from a build that keeps `RDEF`, from the cooker's shader-map key, or from a live constant-buffer capture. None is in the project.
- **the SHEX arithmetic that turns the paint parameters into the output colour** - tried: the same 38,201 SHEX chunks; they are present and readable, but with no `RDEF` and no slot map there is nothing to attribute a `cb0[n]` read to (`grab_shader_combine.py` and this pass both measure 0 name hits in the 145,440,259-byte bytecode region). Still unknown because attribution, not disassembly. Reading `mul`/`lerp` out of a blob and calling it the paint rule would be a guess about which uniform is which.
- **the entry shape after the 14th scalar expression in the Batmobile block (from 0x8bc225d)** - tried: the first 14 entries of the block parse with the proven widths (class FName + parameter FName + float). Still unknown because the list switches to a shape whose class FName is not one of the 16 at that offset, so the next field is not identified; decoding it would need the cooker's serialiser for that class family, which the project does not have.
