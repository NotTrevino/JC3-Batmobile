**derived** (rule and inputs stated) or **UNKNOWN** (what was tried, where it would be).

## 3. Material slots

Decoded as `int32 count` then `count` × `int32` object references. The oracle is
containment: every non-zero reference resolves to a `MaterialInstanceConstant` or
`Material` export of the same package, and no other run of 8+ such references exists in
the first 32 KiB of the payload, so the location is unique. A slot therefore has no
stored name - its identity is the material object it points at.

## 10. UNKNOWNs

1. **`Showcase_Batmobiles_Standard`: the mesh's collision asset** - the package carries no `PhysicsAsset` export at all (export census by class, this tool); which asset the skin uses in game is not in these bytes - it would be a reference from the archetype or the level actor, which G3-01 covers for the drivable car only
2. **`Showcase_Batmobiles_MK2`: the mesh's collision asset** - the package carries no `PhysicsAsset` export at all (export census by class, this tool); which asset the skin uses in game is not in these bytes - it would be a reference from the archetype or the level actor, which G3-01 covers for the drivable car only
3. **slot names (the `FName` next to each slot's material)** - the cooked slot element is a single 4-byte object reference - there is no name field in the mesh payload, so a slot is identified by its material object; `MATERIALS.md`'s slot numbering is the same object order, not a second field
4. **the mesh geometry behind the 20 MB of bulk data (vertex counts, bones, bounds per LOD)** - this card decodes the mesh's property tags, slots, sockets and collision; the bulk vertex/index blocks are not decoded here - they are named by `MESHES.md` from an umodel export, which is a different read
5. **the 662 bytes that differ after the tag stream between Standard's and Playable's `Batmobile_V2`** - the two meshes differ in 1345 bytes in total; the decoded tag layouts are identical, all 19 decoded object-reference fields resolve to the same names, and 2 of the 363 clusters left over have a 4-byte reading whose two values resolve to the same object name. The rest are in the payload's bulk data, where no field is decoded: telling them apart would need the vertex/index/section layout, which this card does not decode (`MESHES.md`'s geometry comes from an umodel export, a different read)
6. **which skin the drivable car selects, and when** - the packages hold four meshes; the code that swaps `Batmobile_V2` for `Batmobile_MK2_Skin` / `Batmobile_Jokerfied_Skin` is not in them - it would be a class default or a Kismet action (G3-02/G3-06)
7. **the material-parameter effect on screen (whether any decoded difference is visible)** - the parameters are decoded, the shader that consumes them is not; see `COLOUR.md` for what is missing between a parameter and a pixel

## 11. Oracles and checks
