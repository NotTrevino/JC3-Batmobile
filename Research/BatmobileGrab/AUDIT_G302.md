# AUDIT_G302 - the G3-02 / 02b / 02c control chain, audited against the bytes

Generated by `Tools/scripts/audit_g302.py` (`--write`); `--check` re-derives every row from
the ini files, `BmGame.upk` and `BatmanAK.exe` and fails if this text differs by one byte.
Read-only on every input; no game process is touched.

Labels: **decoded** = read from a file at a stated line, or a package/export/offset, or an
exe virtual address with its bytes quoted; **derived** = a stated rule on decoded facts;
**UNKNOWN** = not established, with what blocked it.

## 2. Question 2 - does ToggleBattleMode have a script caller?

### 2.1 The scan

- package: `BmGame.upk` (214757637 B), 29620 Function exports.
- `ToggleBattleMode`: one export, **105028**, path `DrivingMode.ToggleBattleMode`,
  script **200 B**, sha1 `1cb9801219cb` (matches CONTROLS_CONSUMERS.md).
- FName index of `ToggleBattleMode`: **78726**; that 4-byte value occurs
  34 times in the package image, so a raw byte search alone is
  not evidence - each was resolved as a call operand instead.
- encodings tested at every byte offset of every Function script:
  - `0x1B` + name index (virtual call by FName),
  - `0x1C` + export index (final call by object).

| call site | encodings |
|---|---|
| *none* | 0x1B(name 78726) = 0, 0x1C(105028) = 0 over 29620 scripts |

- decoded: **0** call sites. The claim "no script caller" **holds**.
- decoded: `ToggleBattleMode`'s own body calls `TryToChangeMode` (10552) at script offsets
  145, 188 - it is a caller, not a callee.

### 2.2 ... but it is bound in two key maps (the "no binding site" half is wrong)

| file:line | row (decoded) |
|---|---|
| `BmGame.ini:4012` | `DefaultPursuitKeyMap=(Ability="$GFxUI.KeyboardControls.BattleMode",PrimaryKeyName="$PC.Keys.RightMouseButton",SecondaryKeyName="$PC.Keys.UNASSIGNED",Command="HoldToZoom | ToggleBattleMode", Icon="")` |

Both rows are `DefaultPursuitKeyMap` entries for `$GFxUI.KeyboardControls.BattleMode` on
`$PC.Keys.RightMouseButton`, with `Command="HoldToZoom | ToggleBattleMode"`. So the command
is reached as an **exec/console command written in the ini**, not by a script call - which is
consistent with 0 script call sites and contradicts CONTROLS_CONSUMERS.md's "no virtual-call
or binding site". That card only read `DefaultInput.ini`'s `Bindings=` lines (BIND_LINES);
these are `DefaultPursuitKeyMap=` rows in `BmGame.ini` / `PCGame.ini`.

- decoded: the strings and abilities above are quoted from the two lines.
- UNKNOWN: whether the engine routes `DefaultPursuitKeyMap.Command` through the exec chain.
  The name match is decoded; the dispatcher is not in these files.

### 2.3 What the two halves mean together

`ToggleBattleMode` is a leaf: nothing in BmGame.upk calls it, and the only route to it in the
files is the BattleMode key-map command. Any claim that LT *held* means battle mode must
therefore name that ini row, not a script path - and the row is on the **PC right mouse**
button; no `PursuitKeyMap` row in either file names an Xbox button (0 hits).

## 3. Question 3 - the native call claim

### 3.3 The thunk chain - one correction to CONTROLS_NATIVE.md

| hop | site | bytes | target |
|---|---|---|---|
| exec -> parser | `0x140501fa3` | `e9 9e 00 00 00` | `0x140502046` |
| parser -> body | `0x14050207f` | `e9 dc 24 d5 ff` | `0x140254560` |
| exec(TryToChangeMode) -> impl | `0x140547dfa` | `e8 91 c0 b1 ff` | `0x140063e90` |

CONTROLS_NATIVE.md says the DrivingPlayerMove thunk's jump target **is** the body
(0x140254560). It is not: the thunk jumps to **0x140502046**, which jumps to 0x140254560.
The conclusion survives (the body is DrivingPlayerMove's), the stated link does not. The
card's "direct native callers of the body: 1" is therefore true of 0x140502046->0x140254560,
and the thunk itself is two hops away.

- decoded: `0x140063e90` is reached from the TryToChangeMode exec (0x140547ce0) and from
  the body only. **holds, with one correction**: the calls and their arguments hold; the hop count is wrong.

  arguments are decoded; the branch predicates (e.g. `bt ecx,0x10` on `bWeaponsReady`) are
  not resolved to semantics here.

  `eax` after the call (`85 c0` at 0x140254a51), but the return's meaning is not decoded.
