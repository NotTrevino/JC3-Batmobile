# The wheels: grabbed, or shaped by the mesh? (reverify-TYRES)

Generated by `Tools/scripts/bmak_tyres_package.py`. It re-decodes the four cooked
`SVehicleWheel` components out of `Playable_Batmobile_SF.upk`,
names their tags by the `SVehicleWheel` layout in `BMSDK_OFFSETS.json`, scans all **274**
tags of `CLASS_DEFAULTS.json`, and recomputes the mesh numbers with `bmak_tyres.build()`
(same PSKX, same ONE transform). Every number below is re-derived by `--check`.

Verdict vocabulary: **matches-the-package** (the package stores the same value), **mesh-only**
(the package stores no such value), **disagrees** (the package stores a different value).

## 3. The comparison — each wheel number

| wheel number | mesh (this project) | package (the game) | verdict |
|---|---|---|---|
| radius | 0.6827 m (station `radius` 0.6826–0.6829) | 64.0 at offset 568 → 0.640 m | **disagrees** |
| tread diameter | 1.3652–1.3657 m | 1.280 m (2 × 0.640) | **mesh-only** |
| width | 0.7314–0.7325 m | absent (`WheelWidth` @572, all four wheels) | **mesh-only** |
| suspension travel | — (no mesh counterpart) | up 30 / down 40 | **package-only** |

### radius — disagrees

The package's stored wheel radius is **64.0** (0.640 m); the mesh's four station radii are
0.6826–0.6829 m (mean 0.6827). The mesh radius is **0.0427 m (42.7 mm) larger** than the stored value — **6.67%**, far outside the 1.5 mm tolerance — and the tread diameters differ by 0.0852 m. The two
numbers are related but not equal: 2 × 0.640 m = 1.280 m of visual tyre, versus 1.365 m
of tread. This is the same relation `TYRES.md` §4 already prints as the BmAK row — a
contact-radius simplification inside the visual tyre — and the classification is
therefore **disagrees**, not matches-the-package.

### width — mesh-only

The mesh measures 0.7314–0.7325 m across the tyre (`*_Vis` vertices, x = axle). The package
stores **no** `WheelWidth` tag on any of the four wheels: offset 572 is absent from all
four tag lists (`--check` asserts the absence, so a future package change fails here).
There is also no `WheelWidth` entry in `CHAIN.json` (`grep -c WheelWidth` = 0), which is
the independent artifact agreeing. The width is therefore a property of the mesh alone.

### What this means for the reset

The tyre numbers in `TYRES.md` are **measured from the mesh** (vertices owned by the wheel
bones, through the ONE transform), not read out of a package: the game stores a 64.0
(0.640 m) contact radius and no width, while the mesh reads a 0.683 m tread radius and a 0.732 m
width. Where `TYRES.md` calls 1.366 "2 × the physics radius — the same number by design",
the physics it means is **JC3's** `land_global.*_wheels.radius` (T-G2), which this
project set from the mesh; it is not a value the game of origin stores. All three
diameters on that page (1.366 / 1.40 / 1.42) are mesh- or lore-derived; the only
package-sourced wheel number is the 0.640 m radius in its §4 table, already marked
"not imported".

## 4. How to re-measure

```
uv run --with numpy --with pillow python Tools/scripts/bmak_tyres_package.py --check
```

`--check` re-decodes the four wheel exports, re-scans the 274 class-default tags, recomputes
the mesh numbers through `bmak_tyres.build()`, re-derives every verdict and fails if this
page or the JSON differs from the render, or if an invariant breaks (four wheels found; each
tag list closing on its terminator; one `WheelRadius` value across the four; no `WheelWidth`
tag; 274 class-default tags with zero wheel-size values; `CHAIN.json` agreeing with the
bytes).
