## Verdict

**STRUCTURE HOLDS; BODY LENGTH IS ONE BYTE SHORT**

- Head offsets 0/2/6/10/14/18: **confirmed**, each by an oracle over all 29620 `Function` exports (`u16@0` zero 29620/29620, `Children` an own property 22737/29620, trailing FName = own name 29620/29620).
- Body length: **one byte wrong**.  `ScriptSize` is the number of body bytes, not `len + 1`; the note's `len(export) - 38` cuts the last byte in 29475 of 29620 exports (and keeps one trailer byte in 145). - Trailer: 15 bytes, 17 on 145 exports, always ending in the own FName + a zero number; the note's `flags word @size-16` is not a field and `pre-name word == 0x0002xxxx` is not exact.
- Anchors: 5 of the note's 7 hold as stated (A_super, A_children, D_name, E_native_parm_refs — 3407/3407 refs over 1825 stubs — and F_call_token at 54022/54211); 2 do not (B_script_size_is_len_plus_one, C_thinnest_script_is_return).
- Constants: every literal the note quotes for the three audited functions re-decodes to the quoted value, and no plausible float in those bodies is unaccounted for; the note quotes no offsets, this audit adds them.
- Rules: §3.1's armour-mode reduction and §3.4's unconditional `return true` both trace to exact bytecode; §3.4 is also the case where the one-byte error bites, because the cut byte is what completes `return ReturnValue`.

## 5. Two rules traced to bytecode

### `R1_armour_mode_reduction`

Rule as the note states it: DAMAGE_RULES.md 3.1: `ArmouredMode` gates `ArmourModeDamageReduction`, whose shipped value 0 makes armoured mode reduce nothing

- Gate: `0x07 JumpIfNot` at body 108 (`07 cf 00`), jump offset 207, condition at 111 = `2d 01 ff 26 00 00` — the `RVehicleBatmobileBase.ArmouredMode` instance variable.  Offset base assumed = end of the jump instruction; resulting target 318 holds `0xff` (statement start: false).
  The target does not land on a statement start, so `0x07`'s offset base is **not** established here; the gate's sense rests on the token being `JumpIfNot` with that condition, not on the target.  It does not matter for this rule: the two plausible bases put the target at 207 or 318, both past the statement's last byte 142, so `not ArmouredMode` skips the reduction under either convention.
- Statement at 117..143: `0f 00 c3 28 00 00 91 90 00 c3 28 00 00 93 2c 64 01 06 26 00 00 16 16 2c 64 16`

Decoded (each operator is a parm list closed by `0x16`; the nesting balances exactly and the statement ends on the next `0x0f` Let: true):

```
`RVehicleBatmobileBase.TakeDamage.DamageAmount` = 0x91(0x90(`RVehicleBatmobileBase.TakeDamage.DamageAmount`, 0x93(`100`, `RVehicleBatmobileBase.ArmourModeDamageReduction`)), `100`)
```

`ArmourModeDamageReduction` at 134; `100` occurs 2 times in the statement; shipped values `Playable_BatmobileFunhouse_SF.BatmobileFunhouse` = 0, `Playable_BatmobileMK2_SF.Batmobile_MK2` = 0, `Playable_Batmobile_SF.Batmobile` = 0; read by `RVehicleBatmobileBase.TakeDamage`.

The tree is what the bytes say; its *semantics* above `0x7f` are not established (§7).  Read as a percentage cut — `(DamageAmount * (100 - ArmourModeDamageReduction)) / 100` — the two `100`s and the subtract-shaped subexpression fit, and with the shipped value 0 the factor is exactly 1, so the note's conclusion (shipped armoured mode reduces nothing) survives the weaker reading under either assignment of `0x90`/`0x91`.  What is verified: the field is the reduction, it is read here, the assignment is gated on `ArmouredMode`, and every archetype ships 0.

### `R2_ram_is_unconditional`

Rule as the note states it: DAMAGE_RULES.md 3.4: `TakesDamageFromRam` opens with `return true`; its trailing bytes are called an incomplete descriptor of UNKNOWN meaning

- Body, 8 bytes: `04 27 04 3a 60 29 00 00`
- Decoded: 04 Return → 27 True → 04 Return → 3a <ref ReturnValue> 0x2960

The fourth construct's reference completes to export 10592 = `RVehicleBatmobileBase.TakesDamageFromRam.ReturnValue` (BoolProperty).  The note's 7-byte body hashes `1aa78f331a90f55e8fb9f173dcc80128458f4030`: it is this body minus its last byte, and that is exactly why the note had to call the tail UNKNOWN.

## 7. UNKNOWNs

- Opcode semantics above `0x7F` (`0x90`, `0x91`, `0x93`, `0xb1`, …): the bodies use operators the note's token table does not list, and this audit does not name them.  They are decoded only as parm-list operators, and only where the nesting balances exactly; which of `0x90`/`0x91` is multiply and which is divide is not established here.  A runnable oracle (the game's VM) is outside the read-only inputs.
- The trailer's own fields (the bytes before the FName): neither the note nor this audit identifies them.  Only the length, the constant tail (FName index + 0) and the effect on the body boundary are decoded.
- The 145 exports with a 17-byte trailer are counted, not explained.
- `Next`/`SuperField` are checked for resolution and class, not by walking the UField chain in order.
