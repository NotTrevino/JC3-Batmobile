## What this settles

The binary exposes the classes' *behaviour* (the native API) and not their *layout*: there is
no class-qualified property string in the image, so no name can be bound to an offset without
disassembling the registration code. That is the same wall `OFFSETS.md` records from the
package side, now measured from the other side too.

**The registration was then disassembled - see [REGISTRATION.md](REGISTRATION.md).** It is three
16-byte `{name, code}` arrays (`0x309E760` 5 entries for the sim, `0x30A46B0` 75 for the base,
`0x30A4E20` 1 for the predictor) terminated by a zero pair, every name an `exec` function. No
property table exists in the image, so this route ends in a measured negative, not in names.
What it *did* yield is the other half of G1-1: an offset-usage map (111 offsets, 43 functions),
which confirms `0x3B0 = DriveMode` (written by `SetDriveMode`) and `0x3B1 = SkidToStopDir`
(written by `SkidToStop`) - both anchors that the class dump now also lands on exactly.

One correction to the older text here: `0x4A8` is **`AirControlYawTorqueFactorMax`**, not
`AirControlTimeInAir`. The class walk that named it was short by `ArrayDim` on static arrays and by
the transmission struct's `GearRatios[6]`; with those fixed the class ends at `0x4C4` and
`AirControlTimeInAir` is at `0x4BC`. See `REGISTRATION.md`, "The 8,000 at `0x4A8`".

Two class names appear here that no shipped package lists - `RVehicleBatmobileBase` and
`RVehicleBatmobilePredictor` - which fixes the parent/subclass relation the offsets belong to.
