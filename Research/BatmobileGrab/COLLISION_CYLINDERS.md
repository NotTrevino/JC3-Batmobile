   *(An earlier revision of this file walked this object from byte 8 instead of byte 0.
   That walk drops the 540 tag, which is why 540 stayed unnamed; the walk above starts
   at 0 and consumes all 114 bytes, so all three floats are seen.)*

   The three floats sit at **540, 544, 548** (values 22.0, 22.0, 1.0 in the class's own
   default), the class's only `StructProperty` (`CylinderColor`) at **552**, and one
   `BoolProperty` word (its four bools) at **556**. The inherited `PrimitiveComponent`
   members are below all of them (316, 364, 476, 480, 484).

4. **Which float is which** - three facts, all decoded:

   a. *No ancestor owns 540.* Each ancestor's own default object tops out below the
      class's block: PrimitiveComponent max 528, ActorComponent max 120. So the three floats above that boundary are this class's own.
   b. *The class has exactly three float members*, and exactly three float slots lie
      above that boundary: 540, 544, 548. A fourth slot does not exist, and a float below the
      boundary would be an ancestor's.
   c. *Slot order = chain order.* In the chain the three floats come before the struct
      and the bools (`... CollisionHeight -> CollisionRadius -> AABBScale ->
      CylinderColor -> bDrawBoundingBox ...`), and by type the struct is at 552 and the
      bool word at 556 - both **above** all three floats. The chain therefore ascends
      with the offset, and pairing in chain order gives:

      `CollisionHeight`, `CollisionRadius`, `AABBScale` -> **540**, **544**, **548**.

   **The opposite reading is refuted by the same bytes**: with the chain descending, the
   struct member `CylinderColor` - the class's only StructProperty - would have to sit
   *below* all three floats, but its tag is at 552, above 548. Ascending is the only
   reading the types allow.

5. **Containment** (derived): the class's own block is 540..559 inclusive, 20 bytes = 3 x 4 (floats)
   + 4 (struct) + 4 (bool word) - no gap, so the five property members occupy exactly
   the five slots 540, 544, 548, 552, 556 and nothing else fits between them.

## The default values are a second, weaker signal (not proof)

The class default has 22.0 at 540, 22.0 at 544 and 1.0 at 548, so the two lengths
default to the same value and the third defaults to 1.0. That is consistent with the
pairing (a scale of 1.0 at the `AABBScale` slot) but it cannot separate radius from
height - the two are equal there. Only the chain/type argument above does that.

## The executable (static only): no evidence

`BatmanAK.exe` carries **no** `CollisionRadius` / `CollisionHeight` string (0 hits ASCII
and 0 UTF-16), so the names are not recoverable from its registration code. Its
instructions cannot name the fields either: the displacements 0x21C and 0x220 appear in
336 movss sites across .text (166 / 170), 95 windows touch both within 160 bytes and 88 of
those use the same base register - but those displacements are ordinary struct offsets in
this binary, and no site has a class anchor tying it to `CylinderComponent`. The radial
test (one object's two fields into three consecutive vector slots, X and Y from 0x220 and
Z from 0x21C) found 0 qualifying site(s).

So the executable contributes **nothing** to this naming; the derivation above rests
entirely on the packages. (An earlier revision of this file reported a radial/axial
result here and then said no site met the test; that paragraph was removed - it asserted
a conclusion the probe had not produced.)
