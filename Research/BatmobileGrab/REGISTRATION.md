# The native class registration, disassembled (G1-1)

Generated by `Tools/scripts/bmak_reg.py` (`--write`, `--listing CLASS`, `--check`) from
`E:\Games\Batman - Arkham Knight\Binaries\Win64\BatmanAK.exe` (55,101,440 bytes, image base
`0x140000000`).

`NATIVE.md` counted the `<Class>exec<Function>` strings. This is the other half: the arrays those
strings belong to, read out of the image by locating the 8-byte pointers to each string body in
`.rdata`/`.data`, walking the run of entries, decoding `{ const ANSICHAR* Name; void* Code; }`
pairs, and disassembling the code they point at with capstone (x86-64).

## The three registration arrays

| array | VA | entries | class | terminator |
|---|---|---|---|---|
| native functions | `0x309E760` | **5** | `RVehicleSimBatmobile` | `0x309E7B0`, name 0 / code 0 |
| native functions | `0x30A46B0` | **75** | `RVehicleBatmobileBase` | `0x30A4F60`, name 0 / code 0 |
| native functions | `0x30A4E20` | **1** | `RVehicleBatmobilePredictor` | `0x30A4E30`, name 0 / code 0 |

Every entry is 16 bytes: a pointer to the `...exec<Function>` ASCII string, then a pointer into
`.text`. The arrays end on a zero pair. Entry order is not the alphabetical order `NATIVE.md` lists
(UE3 prepends to the class's function chain; the sim's five happen to come out in exact reverse),
and the sim's array reads, in on-disk order:

| offset | name | code |
|---|---|---|
| `0x309E760` | `SkidToStop` | `0x14051B390` |
| `0x309E770` | `ForceUpdateTyreFriction` | `0x140BA2660` |
| `0x309E780` | `SetSuspensionForDriveMode` | `0x14051B260` |
| `0x309E790` | `SetDriveMode` | `0x1404AB050` |
| `0x309E7A0` | `Boost` | `0x1404AB000` |

**There is no property table.** All 81 entries in all three arrays name an `exec` function
(`summary.non_exec_names == 0`) and none of them carries a second value pair, so the registration
the disassembly reaches is a function lookup table and nothing else. Combined with the string scan
in `NATIVE.md` (0 class-qualified property names in 55 MB of image, ASCII), the answer to "read the
names out of the exe" is a measured negative: **the executable does not contain them**. The class
definition it used was a `UClass` loaded from `BmScript`, whose property names exist only in that
(unshipped) package — and, as it turns out, in the copy `BmGame.upk` ships.

## What the disassembly *does* give: field offsets per native

`exec` thunks receive `this` in RCX and forward to the implementation, so the dump walks each thunk
and up to two call targets (300 instructions each) and records every `[reg + disp]` with `disp` in
the reflected-field window `0x100..0xA00`. The register is not resolved — that needs data flow — so
a hit is evidence that some native touches that offset, at that width. **111 distinct offsets** are
touched across **43 functions**; the full map is `REGISTRATION.json` → `field_usage`.

Two hits validate the method against the archetype anchors of `OFFSETS.md`:

| offset | natives | anchor from the cooked data | verdict |
|---|---|---|---|
| `0x3B0` | `SetDriveMode` (byte, read + write) | `DriveMode`, ByteProperty at `0x3B0` | **agrees** |
| `0x3B1` | `SkidToStop`, `SetSuspensionForDriveMode` (byte, write) | the byte right after `DriveMode`: `SkidToStopDir` | **agrees** |

The suspension set is next: `SetSuspensionForDriveMode` and `SkidToStop` write the nine consecutive
dwords `0x3CC … 0x3EC`, and `ForceUpdateTyreFriction` touches `0x350` and `0x338`, all inside the
`PMWheelSuspension*` / `MaxPMSuspensionSpeed` region the class declares. These are measurements, not
names yet: the native tells you *what code thinks the field is*, the class definition tells you what
it is called, and both are needed to bind one to the other.

## The 8,000 at `0x4A8`

`0x4A8` is untouched by every one of the 81 natives, so behaviour cannot name it. The class
definition does, and the value agrees: **`0x4A8 = AirControlYawTorqueFactorMax`** (FloatProperty,
8000 on all four playable archetypes - a torque factor, not a duration).

An earlier pass read it as `AirControlTimeInAir`. That reading came from a walk that under-sized
two slot families and hid it under a compensating base:

- static arrays were laid out as **one** element instead of `UProperty::ArrayDim` elements
  (`BoostCooldown[3]`, `GearRatios[6]`, `VehicleWeapons[10]`, ...), and
- `VehicleTransmission` was counted as 92 bytes instead of its real 112, because its `float
  GearRatios[6]` was counted once.

Both shrink the class, and moving the base up makes the anchors agree again - but the whole
`AirControl*` run then sits one slot early, so `AirControlTimeInAir` took `0x4A8`'s place. With
`ArrayDim`, 4-byte property alignment and 20-byte `FInterpCurve` slots the walk reproduces the
linked class exactly: `AirControlTimeInAir` is at `0x4BC`, `BattleModeSlopeFactor` at `0x4C0`,
class end `0x4C4` (= 1220, the size the running game reports).

What settles it now:

1. The BmSDK-AK dump (below) puts `AirControlYawTorqueFactorMax` at `0x4A8`, `AirControlTimeInAir`
   at `0x4BC`, and the class size at 1220.
2. The shipped declaration, walked with this build's slot rules, lands its extent on 1220 too.
3. 8000 reads as a torque factor; as a duration it would mean "air control for 8,000 seconds".

## Recovering the names: the class definitions, walked against the tags

With the exe ruled out, the names can only come from the class definitions, and `BmGame.upk` ships
them. `bmak_bind.py` walks every archetype stream against the class it belongs to:

- an inline tag name (struct, object, enum byte) pins the object's base exactly;
- the base carries forward through the run and backward from the far anchor of the same run;
- a tag binds only if it lands on a slot whose `UProperty` kind agrees *and* the alignment stays
  monotone in declaration order, so one property is never named twice;
- forward and backward placements that disagree are dropped rather than voted on.

The archetypes whose class is `BmScript.RVehicleBatmobile` are hosted by `RVehicleBatmobileBase`,
which `BmGame.upk` does ship and which anchors 137 of those tags - the parent class supplies the
layout and only the subclass's own tail stays open.

That pass alone named 145 fields. The class-dump pass below took it to **380 named from
the dump**; the structural passes added **40** struct elements and **3** `VehicleLights` layout names.
The ledger now reads **423 fields / 423 named / 0 identified only by referent / 0 undecidable** - the
last eight, nested screen-shake bools and the curve/shake float slots, were closed by resolving each
offset against the **innermost** struct on the tag path and keeping the raw bool bitfield word.

## Two more structural passes

**Struct elements.** A field whose context is a struct-typed property is a *member of that struct*,
and its offset is the member's offset inside the struct, not in the class. The struct's own
declaration names it, and that is independent of where the class layout puts the struct - so this
pass cannot slip. **40** fields are named this way: the four `FInterpCurvePointFloat` lanes
(`InVal`/`OutVal`/`ArriveTangent`/`LeaveTangent`, 116 points across the sim's six curves) and the
`BMScreenShakeStruct` members (`Progress`, `TimeDuration`, `LocAmplitude`, `LocFrequency`,
`RotAmplitude`, `RotFrequency`, `FOVFrequency`, ...) behind every weapon's shake property. Kind
agreement is enforced, so a `BoolProperty` tag never takes a float member's name, and a struct typed
`Vector` takes `VectorProperty` tags. A packed `BoolProperty` is named by its set bits: `0x3` at
`BMScreenShakeStruct 0x0090` is `bSmoothLoc + bSmoothRot`, and `0x7` in `AdvancedOptions` is all
three `bAmplitude*ShowsInitialDirection` flags. Because the key carries the innermost struct,
`RBatmobileCannon 0x0004` is correctly two fields - `TimeDuration` in the shake struct and `OutVal`
in a curve point - which is why the total is 423, not 422.

**Native offsets as corroboration.** The disassembly's field map names nothing on its own, but it
checks the layout where it crosses it: `SetDriveMode` reads and writes `0x3B0`, the `DriveMode`
anchor; `SkidToStop` and `SetSuspensionForDriveMode` write `0x3B1` (the `SkidToStopDir` byte) and the
nine-slot suspension run `0x3CC..0x3EC`; `ForceUpdateTyreFriction` touches `0x338`/`0x350`; `Boost`
compares `0x328` and updates `0x294`. Every one of those lands inside the block the class declares.

## What the earlier walk could not reach

The "two insertion windows" this page used to describe were not insertions. They were the two
slot-size bugs above - static arrays counted once, and the transmission struct's array counted
once - and an offsetting base that made the anchors agree at the ends while the middle of a run
slipped by a slot. With `ArrayDim` and the real struct size the base is one constant (the parent
chain's size, `0x104` for the sim) and there is no window.

The residue at that stage was, by category, and how the class dump closed it:

- **classes no shipped package defines**: `SVehicleWheel` (native) and
  `RBatmobileMissileLauncherJoker` (BmScript) - the dump has both classes, 22 and 18 fields;
- **the subclass tail** of `RVehicleBatmobile` (26): the dump has the subclass's own 41 properties
  at `0x20A0` and up;
- **classes whose shipped copy is larger than the declaration** (`RBatmobileCannon`,
  `RBatmobileMissile`, `RBatmobileHeavyCannon`, `RBatmobileSim`): the dump's offsets are absolute,
  so the name resolves whether or not the copy can reproduce the layout;
- **array-element offsets with mixed parents**: formerly the 8-field residue - fields inside nested
  structs at flattened offsets `0x0000`, `0x0004` and `0x0090`. Now resolved structurally: the key
  carries the innermost struct, and the raw `BoolProperty` word names every bit it sets.

Closing those needed one of: the `BmScript` package from the shipping build, or data-flow on each
native that touches a candidate offset (the map in `REGISTRATION.json` is the input, and the
`0x3B0`/`0x3B1` hits show it works). The first one arrived from outside the install - see below. The
last eight needed neither source: the missing information was the container, not a name.

## The class dump: BmSDK-AK

While the exe route was being closed, another source existed: **BmSDK-AK**
(`github.com/Team-BmSDK/BmSDK-AK`, MIT), a scripting platform for Arkham Knight whose build step
generates C# bindings from the **running game**. Each `UProperty` is emitted with the absolute
object offset the engine linked it to:

    /// FloatProperty: AirControlYawTorqueFactorMax
    public unsafe float AirControlYawTorqueFactorMax
    {
        get { return MarshalUtil.ToManaged<float>(Ptr + 1192); }
        ...
    }

and each `ScriptStruct` with `[StructLayout(LayoutKind.Explicit, Size = 112)]` plus every member's
offset. `Ptr + 1192` is `0x4A8` - the same number space as `FPropertyTagBat2.Offset`, which is why a
cooked field resolves by **class + absolute offset + slot kind**. A copy of the generated classes
for the Batmobile's chain (34 classes, 2,351 properties, 42 structs) is vendored under
`Working/vendor/BmSDK/` with the MIT notice; nothing from the game's own files is copied.

`Tools/scripts/bmsdk_offsets.py` parses that dump into `BMSDK_OFFSETS.json`, and `grab_offsets.py`
resolves each cooked field against it, walking superclasses. `bmsdk_offsets.py --report` prints a
class-by-class cross-check: it lays the shipped declaration out again and asks whether a single base
offset reproduces the dump's names and size.

**Why it is the same build (measured):**

- `RVehicleSimBatmobile`: dump size 1220; the upk walk lands on 0x104 + 0x3C0 = 0x4C4 = 1220, and
  *all 165* declared rows land on the same offset in the dump. 147 match by name directly; the
  other 18 are bools that share one bitfield word with several siblings, so the lookup reports the
  word's first bool (same offset, different bit).
- `RVehicleSimCar` 456 bytes, 37/37 names; `RBatmobileMissileLauncher` 0x0A58, 30/30;
  `RBatmobileEMPMissile` 0x0A70, 36/36; `RBatmobileAllegianceSwitcher` 0x0A20, 21/21;
  `RBatmobileBooster` 0x0960, 2/2; `RBatmobileMissile` 0x0440, 23/23; `RProjectile` and
  `RBasicProjectile` exact too.
- The native anchors agree: `SetDriveMode` writes the byte at `0x3B0` = `DriveMode`, `SkidToStop`
  `0x3B1` = `SkidToStopDir`.
- For the 195 object fields that carry a referent, the dump's declared type agrees with the class
  the reference actually points at (the 13 apparent mismatches are subclasses: `StaticMeshComponent`
  vs `PrimitiveComponent`, `AkDialogueLineSingle` vs `AkDialogueLine`, ...).

**What the dump corrected, beyond the last names:** `0x4A8` (above); `XrayMaskMaterial` at `0x318`
was really `RInventoryGadget.Mesh`, because the layout walker had no `ComponentProperty` slot and
dropped 8 bytes; the weapon array at `0x1334` was `TransmissionAnimNode` but is
`VehicleWeapons[0..9]` - the referents (`RBatmobileCannon`, `RBatmobileWinch`, ...) prove it; and
the field previously named `BoostCooldown` at `0x2AC` is `DriftingBoostCooldown` - the three-slot
`BoostCooldown[3]` array sits before it and had been counted as one float.

**The layout rules it pinned down** (now in `bmak_layout.py`, all measured, no longer fitted):

- `UProperty::ArrayDim` sits at byte 6 of the property export; a static array is one property with
  N slots, not N properties. `GearRatios[6]` and `BoostCooldown[3]` are the two in this package.
- Every property type aligns to **4** in this build, pointer slots included.
- `FInterpCurve<T>` is a **20-byte** slot (16-byte `TArray` + 4-byte-rounded `EInterpCurveMode`),
  whatever the point type.
- `ComponentProperty`, `InterfaceProperty` and `DelegateProperty` are real property classes and must
  be laid out; dropping them shifts everything after by 8/16 bytes.

**Residue.** Seven classes still cannot be reproduced from the shipped declaration
(`RBatmobileCannon`, `RBatmobileHeavyCannon`, `RBatmobileSonar`, `RBatmobileWinch`, `RVehicle`,
`RVehicleBatmobileBase`, `RInventoryGadget`): the copy in `BmGame.upk` is a smaller build than the
linked class, which is exactly why the dump was needed. That does not affect the names, which come
from the dump's absolute offsets; it only means a walk of the copy cannot regenerate them.
