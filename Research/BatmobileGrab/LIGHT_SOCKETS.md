# Light sockets vs the cooked skeletal mesh

Generated by `Tools/scripts/bmak_light_sockets.py` (`--write`); `--check` re-derives every
distance.  Reviewed card: `Research/BatmobileGrab/LIGHTS.md`.

Sources: `LIGHTS.json` (101 entries, 21 sockets, 4 packages), `SKINS.json` (cooked `Sockets`
arrays: `BoneName` + `location_uu`), `BONES.json` (180 bones with bind transforms).

## How the world position is computed

`world = bone.world_position_cm + R(bone.world_rotation_quat) * socket.location_uu`

LIGHTS' `socket_location` could in principle be the raw offset or the world point, so both
are measured and the data chooses:

| interpretation | median error |
|---|---:|
| raw offset vs recorded | 0.000 cm |
| world point vs recorded | 312.400 cm |

**Chosen: `raw`** (smaller median).

## The same socket name, different parents in different cooked meshes

A socket's relative location is only meaningful with the bone it hangs from, so this is the
check that the name -> bone step cannot survive on one table's word alone.

| socket | `playable` | `standard` | `mk2` | `jokerfied` | LIGHTS bones |
|---|---|---|---|---|---|
| `HeadLight1` | - | - | - | - | `Batmobile_Chassis`, `Winch_DOOR_Mesh` |
| `HeadLight1a` | - | - | - | - | `Batmobile_Chassis`, `Winch_DOOR_Mesh` |
| `HeadLight1b` | - | - | - | - | `Batmobile_Chassis`, `Winch_DOOR_Mesh` |
| `HeadLight2` | - | - | - | - | `Batmobile_Chassis`, `Winch_DOOR_Mesh` |
| `HeadLight2a` | - | - | - | - | `Batmobile_Chassis`, `Winch_DOOR_Mesh` |
| `HeadLight2b` | - | - | - | - | `Batmobile_Chassis`, `Winch_DOOR_Mesh` |

The locations differ too, and neither location appears under any other socket name in
any table (`locations` in the JSON), so this is **not** a name/offset shift inside one
array: the two mesh families genuinely record different socket data for the same name.

## Lights whose position differs by more than 1 cm (`raw` mode)

none - every resolved light is within 1 cm.

This is a **consistency** result, not independent confirmation: LIGHTS.md was built from the
same `SKINS.json` socket arrays, so a 0.000 cm median says the card copied its source
faithfully and that the offsets are raw socket-relative vectors (the world interpretation
misses by the bone's bind displacement).  The check that is *not* circular is the
cross-mesh table comparison above.

## UNKNOWNs

1. **Socket tables for the MK2 / Joker / Funhouse packages.**  No cooked socket table was
   decoded for them, so their 73 light rows are unverified.  The `Showcase_Batmobiles_MK2`
   and `_Jokerfied` tables are a different package and are not substituted.
2. **Which family the headlight bones are right for.**  `playable`/`standard` parent the six
   headlight sockets to `Winch_DOOR_Mesh`; `mk2`/`jokerfied` parent them to
   `Batmobile_Chassis`.  This card does not decide which mesh is correct - it reports that
   the tables disagree and that LIGHTS.md inherits the split.
3. **Why a socket is absent.**  `HeadLight1c` and `HeadLight2c` appear in none of the four
   cooked tables, so no mesh in `SKINS.json` carries them; whether another mesh in the
   package holds that name is not claimed.
